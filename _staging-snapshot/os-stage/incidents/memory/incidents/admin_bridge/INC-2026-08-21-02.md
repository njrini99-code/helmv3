- **resolved:** #1559 landed same investigation (initial fix); a residual gap in #1559's own fix was found by a later audit pass and closed by #1579 (item 6) on 2026-08-21 12:27:46 -0400; #1585 (a related but structurally separate surface) landed 2026-08-21 16:53:56 -0400

## Summary

This is a **class** of bug, not one bug: at least three separate admin
Bridge surfaces each independently implement their own notion of "is this
thing stale, stuck, or abandoned," with no shared calculator, and each
shipped with its own recency-window defect:

1. **The Overview "Rounds" card** (`OverviewBriefing.tsx`) — triggered a
   real owner morning scare over rounds that were not actually stuck.
2. **Tracer's stuck/abandoned tiering** (`tracer-round-activity.ts`,
   fixed by #1559) — its own fix had a residual bug, found by a later audit
   pass and fixed separately by #1579.
3. **The "Needs your eyes" briefing** (`src/lib/admin/data/briefing.ts`,
   #1585) — four independent recency-window gaps across four different
   rules in the same file, discovered and fixed together.

The unifying theme, in the fix commit's own words for surface 3: *"surfaces
news, not archaeology."* Each of these surfaces had a lower bound (how
recently must something have started being stale to count) without a
matching **upper** bound (how long is too long for this to still be
"news"), which meant old, already-known, or already-explained state kept
resurfacing as if it were freshly urgent.

## Root cause (verified) — three instances

**Instance 1 — Overview Rounds card:** `total_score==null && created_at>2h`
conflates "has this round been idle" with "was this round created a while
ago," and applies to every status, not just genuinely stuck ones. A round
created 3 hours ago and actively being played would trip this exact same
condition as a round abandoned for a week.

**Instance 2 — Tracer's stuck/abandoned tiering, residual:**
`classifyInProgressActivity` (post-#1559) tiered a round as loudly "stuck"
based on `created_at` falling within a 7-day window, when the actual
determinant of urgency is idle duration (`hoursInactive`, already computed
by the same function for other purposes). A round created recently but
already idle 88–133 hours is not urgent; it's abandoned — but the
`created_at`-based gate tiered it as if it were freshly stuck.

**Instance 3 — Needs-Your-Eyes briefing, four independent gaps, one per
rule, all missing either an upper recency bound or a demo/sport scope:**
1. `checkStuckRounds` had a lower idle bound (1h+) but no upper one — every
   `in_progress` round counted regardless of how many thousands of hours
   idle, including months-old abandoned drafts nobody will ever resume.
   Fixed by importing the *same* two thresholds
   (`STUCK_HOURS_THRESHOLD`, `STUCK_TIER_MAX_IDLE_HOURS`) Tracer's own
   two-tier classifier already used, rather than maintaining a second,
   driftable pair of numbers.
2. `checkNewlyDormantTeams`'s 14–21 day recency window was already
   correct — but it never excluded the two seed/demo teams, so a demo team
   with a leftover seeded round could appear as "just went dormant"
   alongside real programs.
3. `checkInactiveCoaches` filtered `users.role='coach'` directly, but
   `users` carries no sport column, so it also matched BaseballHelm-only
   coaches. Rescoped through `golf_coaches`, with demo-team coaches
   excluded via `golf_team_coach_staff`. Same commit also fixed a "coachs"
   (should be "coaches") typo — not a literal string anywhere, but the
   shared `plural()` helper's naive `+s` suffixing rule, which breaks on
   `-ch`/`-sh`/`-s`/`-x`/`-z` word endings; every other word this helper
   was called with elsewhere was coincidentally unaffected by that same
   defect.
4. `checkStuckOnboarding` had a lower bound only — production had two rows
   from **February and March** pinned permanently at the top of the panel.
   Added a 30-day upper bound: 7–30 days stuck is news; older is
   "archaeology already visible elsewhere" (the Users table).

  the `plural()` pluralization bug fixed at the shared-helper level (not

## Recurrence risk

- **The structural pattern is not fixed, only its three known instances
  are.** There is still no single shared "is this stale" utility that
  every admin surface is required to route through — #1559 consolidated
  Overview and Tracer behind one calculator, and #1585's fix explicitly
  reused Tracer's thresholds rather than inventing new ones, which is
  good practice, but nothing structurally prevents a fourth surface from
  being written tomorrow with its own fifth reimplementation and its own
  missing upper bound.
- Any future Bridge panel that computes "is X stale/stuck/dormant" without
  importing the existing thresholds (`STUCK_HOURS_THRESHOLD`,
  `STUCK_TIER_MAX_IDLE_HOURS`, the 14–21/30-day windows) risks
  reintroducing this exact class, just in a new file.

## Invariant candidate

Yes, though this one is better framed as a **consistency check between
surfaces** than a single-table predicate, since the actual defect is
disagreement rather than any one surface being straightforwardly wrong:

```sql
-- INV-BRIDGE-002: Overview and Tracer must agree on which in_progress
-- rounds are "stuck" vs "abandoned." Any round classified stuck by one
-- calculation but not the other indicates the shared classifier has been
-- bypassed again. Requires both classifications to be queryable directly
-- (e.g. via a view) rather than only computed in application code — worth
-- scoping as a functional/golden-path check if a SQL view isn't practical.
```

A second, simpler invariant is worth adding directly against the
Needs-Your-Eyes briefing's four rules: assert each of the four checks'
underlying queries carry both a lower AND an upper bound in their WHERE
clause (a static/lint-style check against the query text, or a fixture-based
functional check with data on both sides of each window) — this is closer
to what #1585's own regression tests already do, and formalizing it as a
standing check would catch a fifth rule shipping the same way.

## Replay candidate

Partial yes, moderate value. The clearest replay is instance 3
(Needs-Your-Eyes): a synthetic dataset with rows on both sides of each of
the four windows (a round idle 1h, a round idle 25h, a round idle 1000h; a
demo team dormant 19 days, a real team dormant 19 days; a golf coach
inactive 20 days, a baseball-only coach inactive 20 days; a signup stuck 10
days, a signup stuck 60 days) run through `briefing.ts`'s four checks.
Pre-fix: all edge cases on the "should be excluded" side incorrectly
appear. Post-fix: only genuinely newsworthy rows appear. This fixture would
also serve as the natural home for a future fifth-rule regression check.
Lower priority than the round-tracking / calendar-events replays under
extension §10-11's stated priorities, since this entire class carries no
data-loss, tenancy, or concurrency risk — it is display-only.

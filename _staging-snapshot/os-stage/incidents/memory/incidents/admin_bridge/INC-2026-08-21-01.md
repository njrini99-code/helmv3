# INC-2026-08-21-01 — The resolved-blind counting class: every team/player error metric, and the Feature Health RPC, counted incidents that were already resolved

- **id:** INC-2026-08-21-01
- **feature_id:** admin_bridge (registry key: `admin_platform`; code: `src/lib/admin/data/{team-scope,team-detail,pulse-grid,users}.ts`, `get_feature_health()` SQL function)
- **first_seen:** pre-existing (unknown onset — this is a filter that was simply never added when these surfaces were built); found during the 2026-08-21 Bridge accuracy audit (6 auditors, owner-ordered)
- **resolved:** TypeScript surfaces fixed 2026-08-21 12:32:07 -0400 (`8d8f7242d`, #1576); a **known, deliberately-accepted residual gap remains** in the Feature Health RPC's 7-day tier — see Recurrence risk
- **severity:** HIGH — this affected every team/player error count across the admin dashboard simultaneously and was directly misleading an operator (the owner) about live team health
- **classification:** TELEMETRY_DEFECT (primary — the admin dashboard itself, not the product, misreported state) / BEHAVIORAL_REGRESSION (secondary — the misreport could plausibly drive a wrong operational decision, e.g. escalating a team that had zero open issues)
- **status:** resolved (primary surfaces); known partial gap accepted, not fixed

## Summary

Six independent Bridge audit passes converged on the same underlying bug,
found **three separate times** by different auditors working different
surfaces, before anyone connected them: every team/player "errors" count on
the admin console — `TeamHealthTable`, the Teams pulse EKG, a team detail
page's error cluster/grade/insight badge, and `PlayerWatchlist` danger
badges — filtered `admin_events` by `event_type` and `severity`, but
**never by `resolved`**. `/admin/errors` (the actual incident feed) already
excluded resolved incidents; these four downstream surfaces simply never
picked up that same convention. Live check at audit time: **456 of 456**
error/warning/critical `admin_events` rows in the trailing 7 days were
**already resolved** — Guilford's team page read *"67 errors this
week"* (grade C) when the true open count was **zero**. This is not a
rounding error or a display nuance; it is the difference between "this team
has a real problem right now" and "this team is fine."

The same gap existed **one level deeper**, in the `get_feature_health()`
SQL RPC: the Calendar feature was computing an AMBER status off two error
fingerprints that were both already resolved, with the reason text
presenting them as currently open.

## Root cause (verified)

Four TypeScript query builders (`team-scope.ts`, `team-detail.ts`,
`pulse-grid.ts`, `users.ts`) each independently constructed their own
`admin_events` filter for "this team/player's errors," and every one of
them filtered on `event_type` and `severity` but omitted
`.eq('resolved', false)`. There is no single shared query builder these
four went through — each was written (or drifted) separately, which is why
the same gap could exist in four places at once and be found three times
by three auditors before anyone noticed they were the same bug.

The RPC-level instance goes one level deeper: `get_feature_health()`
computes `events_24h.errors` / `.fingerprints` / `.rls_denials` and
`errors_prev_24h` / `fingerprints_prev_24h` directly in SQL, with the same
missing filter. This is architecturally more dangerous than the TS
instances because a fix here needed care about hysteresis: filtering
`errors`/`fingerprints` (an "is this currently a problem" signal) is
correct, but filtering `fingerprints_7d`/`total` too would flip a
freshly-cleared feature from GREEN straight to NEUTRAL — a *worse*
inaccuracy than the one being fixed, since it would read as "we don't know"
instead of either "healthy" or "was a problem." The fix (below) deliberately
did **not** filter those two fields for this reason.

- Feature Health's Calendar tile showed AMBER — "this feature has a live

  an internal-tooling accuracy defect. Its real cost is operator trust and
  attention misallocation, not product breakage.

## Repair

**`8d8f7242d`** ("fix(admin): team grades and feature health stop counting
resolved incidents," #1576):

- Added `.eq('resolved', false)` to the four underlying `admin_events`
  queries in `team-scope.ts`, `team-detail.ts`, `pulse-grid.ts`, and
  `users.ts`. `golf.ts`, `team-page-extras.ts`, and `TeamCommandCard` all
  read through a shared `resolveTeamErrorCounts` helper, so they inherited
  the fix transitively without their own direct edit.
- New migration for `get_feature_health()`: filters `events_24h.errors` /
  `.fingerprints` / `.rls_denials*` and `errors_prev_24h` /
  `fingerprints_prev_24h` by **`resolved IS NOT TRUE`**, deliberately
  **not** `NOT resolved` — `resolved` is nullable, and the naive idiom
  would silently drop any null-resolved row from the "open" count, which is
  the wrong direction to fail in an incident-detection RPC. This distinction
  was checked, not assumed: production's actual `rls_denial` rows were
  live-verified to all be `resolved=true` already (not "never resolved" as
  the original brief had assumed), making the practical effect a no-op
  today but the correct idiom going forward regardless.
- **Deliberately did not filter** `fingerprints_7d` or `total` — filtering
  those would flip a freshly-cleared feature GREEN→NEUTRAL instead of
  GREEN→GREEN, a worse bug than the one being fixed. Recorded as a named,
  accepted gap rather than silently left inconsistent — see Recurrence
  risk.
- Guard-block migration hygiene: carried forward all 8 pre-existing
  `RAISE EXCEPTION` assertions from the prior migration
  (`20260807020000`) verbatim — the fix brief had said "6," a recount of
  the actual prior DO block found 8 including a function-existence check,
  and all 8 were preserved rather than trusting the brief's count. Added
  two new guards: a COUNT-based check for exactly 7 occurrences of
  `resolved IS NOT TRUE` (an existence-only check would pass vacuously,
  since `critical_unresolved`'s pre-existing `NOT resolved` clause already
  contains a matching substring that could false-positive a naive check),
  and a check that `fingerprints_7d`'s own subquery text contains no
  `resolved` reference at all — a structural guarantee the deliberate
  non-filter can't silently regress.
- SQL-lint follow-up (`8d8f7242d`'s second commit in the same PR):
  reformatted the migration to be `sqlfluff`-clean rather than
  byte-copying the prior migration's own already-nonstandard formatting,
  which would have added *new* debt rather than reusing grandfathered debt
  the ratchet is specifically designed to tolerate.

## Recurrence risk

- **Named, accepted, NOT fixed:** Feature Health's low tier uses
  `fingerprints_7d` as its **entire** signal (by the classifier's own
  design, per `feature-health.ts`), and `fingerprints_7d` is deliberately
  left unfiltered by resolved status. A low-tier feature can therefore
  still read AMBER off a since-resolved error for up to 7 days. The
  documented correct fix is an RPC field split — a resolved-aware 7-day
  count kept separate from the `hasNoFeatureData` signal — explicitly
  scoped out of #1576 as future work, not forgotten but not done.
- **No shared query builder was introduced** for the four TS surfaces —
  each was fixed at its own call site rather than consolidated behind one
  function that enforces the resolved filter structurally (aside from the
  three that already transitively use `resolveTeamErrorCounts`). Any
  *new* team/player error surface written without going through that
  existing helper can reintroduce this exact gap a fourth time.
- This is the second incident in the same 24-hour window (see calendar_events
  INC-2026-08-20-01) where an accuracy/authorization assumption shipped
  without being checked against live data, and was only caught because an
  operator (or an audit specifically looking for it) happened to compare
  the number against ground truth.

## Invariant candidate

**Yes — this is explicitly named as the extension's own worked example for
what invariants are for (§9's "resolved-blind counting" example is this
exact class of bug).**

```sql
-- INV-BRIDGE-001: no admin-facing error/incident count should include
-- resolved rows. Bounded, read-only, checks the RPC output directly rather
-- than re-deriving the logic in a second place.
select feature_id, errors, fingerprints
from get_feature_health()
where exists (
  select 1 from admin_events ae
  where ae.feature = feature_id
    and ae.resolved = true
    and ae.created_at > now() - interval '24 hours'
    and errors > 0  -- flags if resolved rows could plausibly be inflating the count
);
```

Severity: MEDIUM-HIGH. A more thorough version would directly assert
`fingerprints_7d`'s known-accepted gap doesn't silently expand (e.g., alert
if a GREEN→NEUTRAL flip rate spikes, which would indicate someone "fixed"
the 7-day filter without doing the field split, reintroducing the worse
bug). Worth two invariants: one for the fixed surfaces staying fixed, one
guarding the deliberately-unfixed gap doesn't get "fixed" the naive way.

## Replay candidate

Yes, moderate value. Minimal sanitized fixture: a synthetic team with a
handful of `admin_events` rows, all marked `resolved=true`, run through
`get_feature_health()` and each of the four TS query builders. Pre-fix:
all five surfaces report non-zero error counts / non-GREEN status. Post-fix:
all five report zero / GREEN. Given this bug was found independently three
times by different people before being connected, this replay's real value
is less about reproducing the mechanism (which is simple) and more about
being the canonical shared fixture that would let a future auditor check
"has this resolved-blind class come back anywhere" in one run instead of
needing six separate audit passes to rediscover it again.

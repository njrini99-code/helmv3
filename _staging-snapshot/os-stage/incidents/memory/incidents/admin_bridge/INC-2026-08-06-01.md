# INC-2026-08-06-01 — Bridge incident queue ranked stale over live and replayed closed incidents as current

- **id:** INC-2026-08-06-01
- **feature_id:** admin_bridge
- **first_seen:** unknown exact introduction date for each of the three defects; found and fixed 2026-08-06
- **resolved:** 2026-08-06 01:33 UTC (PR #1291)
- **severity:** HIGH (meta-incident — this degraded the reliability of the observability system every other incident in this repo relies on)
- **classification:** TELEMETRY_DEFECT (primary)
- **status:** resolved

## Summary

Three independent defects in Helm's own incident-monitoring tool ("the Bridge") made it read as stale and misleading, found against live production data rather than via a report:

1. **False "Regressed" badges** — `queryPriorResolutions` treated *any* prior resolution as evidence a human fix had failed, but the auto-resolve cron deliberately leaves `resolved_by` NULL. All seven badged rows sampled were cron sweeps, a 100% false-positive rate for that badge.
2. **Closed incidents replayed as live** — `fetchError()` had no `resolved` filter at all, so 281 already-resolved rows streamed into the activity feed as if happening now — "most of why the feed read as stale," per the fix.
3. **Wrong ranking signal leading the queue** — the triage queue ranked by `affectedUsers DESC, lastSeen DESC`, but in production `affectedUsers` is nearly binary (7 groups at 1 user, 10 at 0), so it decided almost nothing and recency — the signal that should have mattered — never got to arbitrate first. Concretely: the top-ranked item had been silent for 8.1 hours while two incidents from the last 18 minutes sat at queue positions #8 and #9.

## Root cause (verified)

Each defect is independently verifiable against the code cited in the fix: `incident-feed.ts`'s `queryPriorResolutions` had no filter distinguishing human resolutions from cron auto-resolutions; `activity.ts`'s `fetchError()` had no `resolved` filter at all; `triage.ts`'s ranking used a near-constant field as the primary sort key with the actually-informative field (recency) demoted to a tiebreaker. A fourth, subtler bug is named in the fix but not separately numbered: `livenessBand` originally called `Date.now()` inside a sort comparator, which is a non-transitive sort (the same two items can compare differently on different calls within the same sort) — fixed by taking `nowMs` as a parameter instead.

## User impact

Not user-facing in the product sense — this affects the tool the team (or Claude sessions doing daily observability work) uses to decide what to fix next. The impact is indirect but real: for however long these defects were live, whoever worked the Bridge queue was systematically shown a stale, false, and mis-prioritized picture of production health, which plausibly delayed response to genuinely live incidents that were being outranked by 8-hour-stale ones.

## Repair

`queryPriorResolutions` now filters `.not('resolved_by', 'is', null)` so only human resolutions count toward a "regressed" badge. `fetchError()` gained a `resolved` filter so closed incidents stop appearing in the live activity feed. `triage.ts`'s ranking now leads with liveness bands (recency-derived), with headcount still breaking ties *within* a band — preserving the original intent that raw volume shouldn't be ignored, just not allowed to dominate when it's nearly constant. `livenessBand` now takes `nowMs` as an explicit parameter rather than calling `Date.now()` inside the comparator.

## Verification evidence

Dedicated test file `src/lib/admin/__tests__/triage-liveness-rank.test.ts`, 11 cases built directly on the real production data shape described in the fix. PR states: typecheck 0, eslint 0, 8,965/8,965 unit tests passing, `next build` green.

## Signals

Ironically, none of the standard signal sources (Bridge, Sentry) could have caught this — it *is* the Bridge, and a defect in the observability layer itself is definitionally invisible to that same layer. Found by someone directly inspecting live production Bridge data and noticing the ranking didn't match reality (an 8-hour-silent item outranking 18-minute-old ones).

## Recurrence risk

**Structural**: any future change to Bridge's own ranking/filtering logic needs verification against real production data shape, not just unit fixtures with synthetic distributions — the `affectedUsers`-nearly-binary discovery only surfaced by looking at actual production numbers. The dedicated test file built on real production shapes is a good defense; worth confirming it stays current as the Bridge's own usage patterns evolve (e.g., if `affectedUsers` distribution changes as the user base grows, the tie-breaking logic's assumptions may need revisiting).

## Invariant candidate

Best expressed as an ops/functional check on the Bridge's own output rather than a SQL invariant on product data:

```
# INV-BRIDGE-001: no incident with resolved=true (and resolved_by IS NOT
# NULL, i.e. a genuine human resolution) should appear in the live
# activity feed. No incident whose lastSeen is within the trailing 30
# minutes should rank below an incident whose lastSeen is more than
# 6 hours stale, all else equal.
```
Severity: HIGH given this is the tool other incidents' detection depends on — a regression here has a multiplying effect on every other feature's incident response time.

## Replay candidate

Yes — and the 11-case test file already built for this fix is effectively the replay fixture. The extension-worthy addition: pin the specific production data shape that exposed bug #3 (7 groups at `affectedUsers=1`, 10 at `affectedUsers=0`, an 8.1-hour-stale top item vs. 18-minute-old items at #8/#9) as a named regression fixture, so a future ranking-logic change can't silently reintroduce the near-constant-field-as-primary-sort-key mistake without an explicit test failure naming this exact incident.

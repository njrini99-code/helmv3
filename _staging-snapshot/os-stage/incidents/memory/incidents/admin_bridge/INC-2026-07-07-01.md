# INC-2026-07-07-01 — Two isolated production Postgres errors: a CoachHelm-refresh deadlock and a crm_coaches permission gap

- **id:** INC-2026-07-07-01
- **feature_id:** admin_bridge (spans coachhelm_ai's refresh cron and an admin CRM read path)
- **first_seen:** 2026-07-07 ~16:32 UTC (permission-denied, issue #791); 2026-07-08 ~03:45 UTC (deadlock, issue #790)
- **resolved:** both filed as low-severity, self-healing, single-occurrence; no dedicated fix PR identified in this pass for either specific issue
- **severity:** LOW (both explicitly self-described as single-occurrence, self-healing, not user-facing)
- **classification:** FUNCTIONAL_FAILURE (deadlock) / SECURITY-adjacent CONFIG_DRIFT (permission gap) — grouped for record-keeping efficiency, not because they share a root cause
- **status:** UNKNOWN (no confirmed dedicated fix; may have been resolved incidentally by later, broader security/RLS remediation work in the same window)

## Summary

Two unrelated single-occurrence Postgres errors surfaced by the same Mission Control sweep (2026-07-08 ~04:32 UTC) on consecutive days:

1. **`crm_coaches` permission denied** (#791) — twice, ~17s apart, 2026-07-07 ~16:32 UTC. Likely cause per the filing: a role reading/writing `crm_coaches` without a matching `GRANT`/RLS policy (SQLSTATE 42501), noted as "same class as earlier `permission denied for table golf_rounds` errors... but on a distinct table not previously tracked."
2. **CoachHelm refresh-cron deadlock** (#790) — single occurrence, 2026-07-08 ~03:45 UTC, coinciding with concurrent PATCH/UPSERT operations against `golf_goals`, `golf_causal_relationships`, `golf_coach_insights`, `golf_patterns_v2` during the standing/insight refresh cron. Two transactions acquired `ShareLock`s in opposite order; Postgres aborted one to break the cycle.

## Root cause (verified for the deadlock's mechanism; hypothesized-not-confirmed for the permission gap)

The deadlock's mechanism is directly evidenced: concurrent batched UPSERT operations from the same cron acquiring `ShareLock`s on the same rows in non-deterministic order, a textbook Postgres deadlock shape. The permission gap's cause is filed as a hypothesis by the reporting tool itself ("likely cause... worth checking whether a recent CRM migration dropped or omitted the grant/policy") and not independently confirmed in this pass.

## User impact

Deadlock: "one aborted transaction in the refresh path → a likely partial/failed standing or insight refresh for a single player on that cron tick... self-heals on the next refresh," per the filing's own assessment — not user-facing. Permission gap: "CRM coach reads/writes on that path fail with 42501 for affected requests" for the two occurrences — narrow, admin-surface-only impact.

## Recurrence risk

**Deadlock**: the suggested mitigation (serialize concurrent refresh writes via consistent row-ordering or a per-player advisory lock) was not confirmed as implemented in this pass — if not, the same class of deadlock could recur on any cron tick with sufficient concurrent player-refresh volume. Cross-reference: a *different* advisory-lock defect in a related refresh function (`refresh_crm_coach_engagement`) was found and fixed nearly a month later (2026-08-01, PR #1167) — worth checking whether that fix's pattern (transaction-scoped `pg_advisory_xact_lock` instead of manual lock/unlock) generalizes to harden this cron path too. **Permission gap**: recurrence risk depends entirely on whether the underlying grant/policy gap was ever actually closed, which is unconfirmed.

## Invariant candidate

```sql
-- INV-DB-002: no table should return permission-denied errors for the
-- application's own service/authenticated role in production logs.
-- A recurring or new permission-denied signature in error_logs for any
-- first-party table is itself the invariant violation — it should never
-- reach production undetected via a "sweep found it after the fact" path.
select context->>'action', count(*)
from error_logs
where severity in ('error','critical')
  and context->>'sample' ilike '%permission denied for table%'
  and created_at > now() - interval '7 days'
group by 1;
```

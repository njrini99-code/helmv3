# INC-2026-08-02-01 — deepsec security sweep: unauthenticated push-notification endpoint and an onboarding auth bypass, already live on main

- **id:** INC-2026-08-02-01
- **feature_id:** platform_observability (spans notifications + auth_onboarding_join)
- **first_seen:** the onboarding bypass was introduced 5 weeks before discovery (commit `638a14c64`); the push-notification gap's introduction date is not independently dated in this pass
- **resolved:** 2026-08-02 (PR #1221, wave 2; wave 1 was PR #1220, date not independently confirmed in this pass but precedes #1221)
- **severity:** CRITICAL (two of the findings are unauthenticated write/auth-bypass endpoints already shipped to production, not merely pre-merge catches)
- **classification:** SECURITY (primary)
- **status:** resolved

## Summary

A two-wave `deepsec` automated security scan covered `createAdminClient()` usage across the codebase — wave 1 (#1220) the golf action files, wave 2 (#1221) the remaining 129 files (cron routes, webhooks, admin data layer, CoachHelm v2/v3 mining, baseball actions, notification/email libs). Wave 2 alone found 52 candidate findings, 39 confirmed by adversarial verification, 10 refuted (code was already correct), 1 uncertain. Two findings stand out as already-live, not merely theoretical:

1. **`src/lib/notifications/push.ts`** — `sendPushNotification` and `sendBulkPushNotification` were exported as `'use server'` actions with **zero auth checks anywhere in the file** — a public POST endpoint letting anyone push notifications to arbitrary users and burn the paid notification-provider quota.
2. **`completeCoachOnboarding`** — accepted a client-supplied `_preVerifiedUser` parameter and skipped authentication entirely when present, passing the attacker-controlled object into service-role writes. Introduced 5 weeks earlier in commit `638a14c64` — explicitly noted as "already live on main," a fix to shipped code, not a pre-merge catch.

Additional findings: a stored blind SSRF in `api/push-subscriptions` via an unvalidated Web Push endpoint (validated at neither the route nor a downstream sink that a code comment falsely claimed was kept in sync); `CRON_SECRET` compared with non-constant-time `!==` in two cron routes; rate-limit keys derived from a client-controlled `X-Forwarded-For` header (truncated in the material captured for this record).

## Root cause (verified)

Both headline findings share a pattern: a `'use server'` export trusting either the absence of an auth check (push.ts) or a client-supplied parameter as a substitute for one (`completeCoachOnboarding`'s `_preVerifiedUser`) — the PR's own framing is direct: "every parameter of a `'use server'` action is client-controlled." This is a systemic risk class (server actions with implicit trust in caller-supplied state) rather than two unrelated bugs.

## User impact

Push-notification endpoint: any external caller could trigger push notifications to arbitrary users and consume paid quota, for the duration the file was live with zero auth (introduction date not determined — could be a long window). Onboarding bypass: any external caller could complete coach onboarding with `_preVerifiedUser` set, bypassing authentication and reaching service-role writes, live for ~5 weeks before discovery.

## Repair

39 of 52 findings remediated in PR #1221 (56 files). Highest-impact fixes: auth checks added to `push.ts`; the `_preVerifiedUser` bypass closed in `completeCoachOnboarding`; SSRF validation added at both the route and the previously-unguarded downstream sink in `v3/foundation/push.ts`; `CRON_SECRET` comparisons moved to constant-time; rate-limit key derivation hardened against client-controlled header spoofing (partial detail — full description was truncated in material available for this record).

## Verification evidence

39 of 52 findings independently confirmed true-positive via adversarial verification (a second-pass review distinct from the scanner itself); 10 refuted as already-correct code (explicitly noted as important: "changing it would have been the regression"); 1 uncertain. This confirm/refute discipline is a stronger verification posture than several other incidents in this set, which rely on the fix author's own assertion alone.

## Signals

No Bridge/Sentry telemetry — found entirely by a deliberate automated security-scanning tool (`deepsec`) plus manual adversarial verification, not by any production monitoring signal or exploitation report.

## Recurrence risk

**High, structurally** — the root pattern (a `'use server'` export trusting client-supplied state instead of an explicit auth check) is a class of defect that can recur anywhere a new server action is authored without following the established guard convention. This repo's own CI now has a hard gate for "server action without `supabase.auth.getUser()` before any DB call" (per AGENTS.md's Review Gate description), which is the correct structural defense — worth confirming this specific gate would catch both the push.ts and onboarding shapes (the onboarding one is subtler, since it's not a *missing* auth check but a client-parameter *substituting* for one, which a simple "has an auth call" static check might not catch).

## Invariant candidate

```
# INV-SEC-002: every 'use server' export must either call
# supabase.auth.getUser() (or an equivalent verified-session check) before
# any DB write, OR be on an explicit allowlist of genuinely public actions.
# The subtler version, specific to this incident's onboarding bypass: no
# 'use server' export may accept a client-supplied parameter whose name or
# shape implies pre-verified identity (e.g. *_preVerifiedUser*,
# *_trustedUser*, *_skipAuth*) — these are a code smell independent of
# whether an auth check exists elsewhere in the function, since they
# invite exactly the bypass found here.
```
Already partially enforced by the Review Gate's server-action-auth-check rule; the parameter-naming smell is a candidate addition to the existing `.coderabbit/semgrep/helmv3.yml` pack.

## Replay candidate

Yes for the onboarding bypass specifically — a unit test calling `completeCoachOnboarding` with a crafted `_preVerifiedUser` object and no real session, asserting rejection post-fix (and, as a historical regression marker, that it would have succeeded pre-fix). Priority: HIGH under extension §10-11 (auth/tenancy class), and directly reusable as the canonical "client-supplied trust parameter" regression pattern for any future finding of the same shape.

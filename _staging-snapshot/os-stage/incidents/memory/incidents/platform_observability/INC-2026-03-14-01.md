- **id:** INC-2026-03-14-01
- **feature_id:** platform_observability
- **first_seen:** 2026-03-14 (earliest of the three: the untagged "GolfRoot" flood)
- **resolved:** each storm independently went silent weeks-to-months before the 2026-08-20 Bridge triage that surfaced them; none has a confirmed fix commit
- **severity:** LOW (all three confirmed dead/inert at triage time; grouped here because each represents a real historical production error condition, not because they share a root cause)
- **classification:** TELEMETRY_DEFECT (primary) — in the sense that none produced confirmed user-facing impact and all were left to self-resolve rather than root-caused and fixed
- **status:** resolved (by attrition — dead for weeks-to-months, no recurrence), mechanism UNKNOWN for all three

## Summary

The 2026-08-20 Helm Bridge `error_logs` triage identified four long-dead storms that together accounted for ~78,000 of the ~81,800 total rows across all 152 error signatures ever recorded. The v3 generator storm (~4,877 rows) has its own dedicated record (INC-2026-05-26-01, coachhelm) with a code-verified mechanism. The remaining three, grouped here, have no confirmed root cause in any record reviewed for this pass:

1. **`null` (untagged, "GolfRoot" flood)** — error severity, **72,036 rows**, first_seen 3/14, last_seen 6/25. By far the largest single signature in the repo's entire error history — 88% of the four-storm total, 66% of *all* Bridge error rows ever recorded across every signature.
2. **`cron.eventReminders`** — error severity, 876 rows, first_seen 4/28, last_seen 5/8.
3. **`crmSendEmailApi.send`** — critical severity, 140 rows, single-day burst 4/17.

## Root cause

**Unconfirmed for all three.** The triage that surfaced these explicitly frames its own confidence as "confirmed dead by team-lead context" — meaning the *liveness* status (dead, not currently firing) is verified, but no root-cause investigation was performed or is documented for any of the three. `RootErrorBoundary`/`src/app/golf/error.tsx` exist as the plausible catch point for the untagged GolfRoot flood, but "the component that would have caught it exists" is not the same as "the underlying error condition is understood." Given the sheer scale of the GolfRoot flood (72,036 rows — nearly two-thirds of this repo's entire error history), the honest assessment is this was very likely a single systemic issue with an old build (the triage's own phrasing) rather than 72,036 independent user-facing errors, but the specific mechanism (what threw, and why untagged) was not reconstructed in this pass.

## User impact

**Unknown, and probably not reconstructable from available records.** An untagged error boundary catch at this volume (72,036 rows over 3 months) is consistent with either a low-severity issue affecting a very large fraction of page loads, or a build-time/tooling artifact generating synthetic noise (e.g., a broken source map or dev-mode leak) rather than real user-facing failures — the data available in this pass cannot distinguish between these. `cron.eventReminders` and `crmSendEmailApi` are backend/cron paths with no direct end-user page-load exposure; their impact, if real, would have been missed/duplicate reminder emails or CRM send failures respectively, neither confirmed.

## Repair

None identified. All three signatures simply stopped firing (GolfRoot: after "an old build" was presumably superseded; the cron/CRM signatures: no fix commit found in a targeted PR-title search for `event-reminders`, `crm.*send`, or similar during their respective active windows). This is the honest gap the master spec explicitly anticipates: "many old incidents will be resolved, mechanism partially unknown."

## Verification evidence

The 2026-08-20 Bridge triage confirms current code existence for `src/app/api/cron/event-reminders/route.ts` and `src/app/api/admin/crm/send-email/route.ts` (both still exist and are presumably still live), combined with `error_logs` last_seen timestamps 3.5+ months stale at triage time, as the basis for "confirmed dead."

## Signals

Helm Bridge `error_logs`, grouped by `context->>'action'` × `severity`. No Sentry/GitHub-issue cross-reference found for any of the three in records reviewed for this pass — these appear to have been Bridge-only, never escalated to a filed issue.

## Recurrence risk

**Cannot be assessed without a root cause.** If the GolfRoot flood was tied to a specific old build (as the triage's phrasing suggests) and that build is long superseded, recurrence risk is low by construction. If it was tied to a still-live code path that simply stopped being exercised (e.g., a deprecated route with declining traffic), recurrence risk is unknown and could reopen if that path is exercised again.

## Invariant candidate

The most valuable invariant here is a **telemetry-quality** one, not a product one: no error signature should reach production `error_logs` with a `null`/untagged `context->>'action'`. The GolfRoot flood being unattributed for 3 months and 72,036 rows before anyone could even name what threw is itself the finding — every `logServerError`/error-boundary call site should require a non-null action/feature tag as a lint-level or runtime-assertion requirement, so a future storm of this shape at minimum arrives pre-labeled.

## Replay candidate

No. With no root cause identified for any of the three, there is nothing concrete to construct a fixture against. If the GolfRoot flood's cause is ever reconstructed (e.g., by bisecting the "old build" the triage references against deploy history from that window), a replay candidate could be revisited then — flagging as a future investigation, not closing the door on it.

## Status

Resolved by attrition (all three dead, no recurrence in the multi-month window preceding the 2026-08-20 triage). Root cause UNKNOWN for all three — this is an honest gap, not a claimed resolution.

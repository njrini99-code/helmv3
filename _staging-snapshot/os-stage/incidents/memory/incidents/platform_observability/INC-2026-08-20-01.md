# INC-2026-08-20-01 — Planner COST mis-estimate on an RLS helper function turned every shot-detail read into a sequential scan

- **id:** INC-2026-08-20-01
- **feature_id:** platform_observability (unmapped in `memory/registry.yml` as its own feature — this is a cross-cutting Postgres planner/RLS defect; the affected function, `can_read_golf_shot_detail`, is a `SECURITY DEFINER` RLS helper on `golf_shots`, whose owning product feature is `shot_tracking`)
- **first_seen:** unknown onset (a planner default, not a regression from a specific deploy) — investigated and confirmed 2026-08-20 as part of the 17:07–17:30 UTC statement-timeout cluster investigation (round_tracking INC-2026-08-20-02)
- **resolved:** 2026-08-20 (applied directly to production the same night, migration `20260821035329_can_read_golf_shot_detail_planner_cost.sql`)
- **severity:** MEDIUM (a real, measured 8.3x latency contributor to a shared-instance contention incident; not itself the primary cause of any user-facing outage, but a genuine, previously-invisible performance defect on a hot path)
- **classification:** PERFORMANCE_REGRESSION (primary) — note this was investigated as a suspected contributor to round_tracking INC-2026-08-20-02 and, on measurement, found to be a real, independent defect rather than an artifact of that incident's contention
- **status:** resolved

## Summary

While investigating the 17:07–17:30 UTC statement-timeout cluster (see
round_tracking INC-2026-08-20-02), a specific hypothesis was tested and
confirmed: `can_read_golf_shot_detail` — a `SECURITY DEFINER`, 6-table-join
RLS helper function gating access to shot-level detail — carries Postgres's
**default function COST of 100**. Because the planner has no real signal
that this function is actually expensive (a 6-table join evaluated
per-row), it chose to sequential-scan the detail tables and evaluate the
RLS check row-by-row rather than pushing the filter down efficiently.
Raising the function's declared COST to 10,000 (closer to its real
execution cost) let the planner choose a materially better plan: **877ms →
105ms, an 8.3x improvement**, verified live with a rolled-back test change
before committing to the real fix.

This is a "the map doesn't match the territory" class of bug: nothing about
the RLS policy, its semantics, or the indexes involved was wrong — the
planner was simply working from a cost estimate that was two orders of
magnitude too low for what the function actually does.

## Root cause (verified)

Postgres's default `COST` for a function (used by the query planner to
decide whether pushing a filter down early is worthwhile, or whether it's
cheaper to scan broadly and filter late) is 100 — appropriate for a cheap,
simple function. `can_read_golf_shot_detail` is neither cheap nor simple:
it's a `SECURITY DEFINER` function doing a 6-table join to determine
row-level access. At COST 100, the planner treated it as cheap enough to
evaluate eagerly and often, driving sequential scans on the detail tables
it gates instead of a plan that evaluates the (actually expensive) function
lazily or pushes other filters ahead of it.

Explicitly ruled out during investigation, not assumed:
- **Missing indexes** — checked; indexes on the relevant tables already
  existed.
- **Policy or semantic change** — none; this is a cost hint change only,
  zero behavioral difference to what is/isn't allowed.
- **`getTopInsightForPlayer`'s ~30 timeouts in the same window** — initially
  suspected as related, but corrected on inspection: that function reads
  only `golf_coach_insights` (a clean, 23.7ms query, unrelated table), so
  its timeouts were attributed to the shared-instance contention from
  round_tracking INC-2026-08-20-02, not this COST defect.
- **Sibling RLS helpers with the same shape** (`owns_golf_shot`,
  `is_golf_team_coach`, `is_golf_team_player`) — checked and found to have
  the same default-COST gap, but **measured fine** at current load; fixing
  them was deliberately deferred rather than bundled in, since they weren't
  contributing to an active problem.

## User impact

- Contributed measurably (8.3x on this specific query shape) to the
  latency/contention conditions during the 17:07–17:30 UTC window, though
  it was not itself the trigger of that incident (the trigger was the
  round-autosave lock pile-up — see round_tracking INC-2026-08-20-02). This
  function's cost defect made every shot-detail read on the affected
  instance slower than necessary, compounding pressure during any
  high-load window, not just this one.
- No user-facing behavior changed as a result of the fix — access control
  outcomes are identical before and after; only query planning improved.
- Given this is a planner default rather than a regression, it had likely
  been silently taxing every shot-detail read (not just during incidents)
  since the function was written — a standing, general-purpose latency
  cost that happened to only become visible when a separate incident made
  someone go looking at query plans directly.

## Repair

- `ALTER FUNCTION can_read_golf_shot_detail(...) COST 10000` plus a grant
  re-assertion (to guard against a `CREATE OR REPLACE` on this function in
  the future silently resetting COST back to the default of 100 — the exact
  failure mode a migration accident could reintroduce). Applied with
  `lock_timeout 3s` given this is a production write on a hot function.
- Applied **directly to production** the same night via the standard MCP
  path, migration `can_read_golf_shot_detail_planner_cost`. A mirror
  migration file was subsequently added to `supabase/migrations/` as
  `20260821035329_can_read_golf_shot_detail_planner_cost.sql`, since
  production application via MCP and the committed migration history are
  tracked separately in this repo (per the repo's own "recorded != applied"
  caution) — reconciling the two was an explicit follow-up step, not
  assumed to happen automatically.
- Reviewed by db-migration-reviewer with a verdict of
  **APPROVE-WITH-CHANGES**, remaining items scoped as their own follow-up:
  (a) confirm the mirror migration file landed in
  `supabase/migrations/` (partially done — see above), (b) add a
  schema-budget test asserting `procost=10000` for this function,
  modeled on the existing `golf-shots-select-policy-count.test.ts` replay
  pattern — this guards specifically against a future `CREATE OR REPLACE`
  silently reverting the COST back to 100, which would reintroduce this
  exact defect invisibly.
- **Deliberately deferred, not fixed:** the same default-COST gap on
  `owns_golf_shot`, `is_golf_team_coach`, and `is_golf_team_player` — all
  three measured fine under current production load, so raising their COST
  too was judged unnecessary risk for the night's scope. Worth revisiting
  if any of the three shows up in a future slow-query investigation.

## Verification evidence

- Live, rolled-back test: `ALTER FUNCTION ... COST 10000` applied inside a
  transaction, the target query timed both before and after (877ms →
  105ms), then rolled back before the real, committed change — this is
  what makes the 8.3x figure a measured fact rather than an estimate.
- Post-apply verification against production, checked directly: `procost`
  confirmed at 10000; `anon` EXECUTE confirmed `false`; `authenticated`
  EXECUTE confirmed `true` — i.e., the access-control grants were
  unchanged by the cost-only migration, confirming zero behavioral drift.
- A pre-flight sweep confirmed only the 2 expected RLS policies actually
  call this function — the blast radius of the COST change was scoped and
  checked before applying, not assumed to be limited to the two known
  callers.

## Recurrence risk

- The schema-budget test guarding `procost=10000` (item (b) above) was
  **scoped as a follow-up, not confirmed landed** in the sources reviewed
  for this backfill. Until it exists, a future `CREATE OR REPLACE FUNCTION
  can_read_golf_shot_detail` (for an unrelated logic change) would silently
  reset COST to the Postgres default of 100 and reintroduce this exact
  8.3x regression with no warning.
- The three sibling functions with the identical default-COST gap
  (`owns_golf_shot`, `is_golf_team_coach`, `is_golf_team_player`) remain
  unfixed. They are "measured fine today" under current load, not
  structurally safe — a future increase in call volume or table size on
  any of them could reproduce this same failure shape.

## Invariant candidate

Yes, directly targeted at the exact regression this incident's own review
flagged as the most likely recurrence path:

```sql
-- INV-PERF-001: RLS-gating SECURITY DEFINER functions with a non-trivial
-- join should not carry the Postgres default COST of 100. Catches both
-- this specific function silently reverting via a future CREATE OR
-- REPLACE, and any of the three known-similar sibling functions if their
-- load characteristics change enough to need the same fix.
select p.proname, p.procost
from pg_proc p
join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public'
  and p.proname in (
    'can_read_golf_shot_detail', 'owns_golf_shot',
    'is_golf_team_coach', 'is_golf_team_player'
  )
  and p.procost <= 100;  -- default value = regression signal for the fixed one,
                          -- baseline awareness for the three still-deferred ones
```

Severity: MEDIUM. Cheap, read-only, catalog-only query — no table scan risk
at all, safe to run frequently.

## Replay candidate

No, or low priority. This is a planner-cost/performance defect with a
straightforward, already-executed verification methodology (the live
rolled-back `ALTER FUNCTION` + timing comparison, which is itself
effectively a replay already performed manually). A formal replay fixture
would mostly duplicate the schema-budget test recommended above (assert
`procost=10000` directly) rather than needing a full sanitized-data
reproduction — per extension §10-11's stated priorities (data-loss,
auth/tenancy, silent statistical corruption, concurrency, offline
reliability, critical workflows, CoachHelm reasoning), a planner-cost
performance tune ranks low. The schema-budget test is the right-sized
guard, not a replay fixture.

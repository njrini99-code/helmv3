## Summary

A Supabase dev database password (`EHl4yASa9zM1sb1k`) was committed in plaintext to `docs/setup/RUN_ON_YOUR_MACHINE.md` on 2026-01-14. It was scrubbed from the *current* file on 2026-05-17 (commit `9f44e3ef`, part of a broader P0 security sweep — see cross-reference below) but remained fully readable in git history. Anyone with read access to the repository could recover it from any clone.

## Root cause (verified)

A setup doc for local development included a real dev-project password inline rather than a placeholder. No secret-scanning gate existed on the repo at commit time (gitleaks/Review Gate hardening came later, in the May security wave), so it was never flagged until a manual P0 audit found it four months later.

## User impact

None confirmed. The credential was bound to a Supabase project that no longer exists by the time of discovery, so exploitation was structurally impossible from the moment of discovery onward, and the access-log audit found no anomalies in the window before that.

## Repair

- `9f44e3ef` — scrubbed the password from `docs/setup/RUN_ON_YOUR_MACHINE.md`.
- No rotation needed (project deleted).
- **Deliberately not done:** git history rewrite (`git filter-repo`) to remove the commit. Documented decision in `docs/operations/2026-05-17-p0-runbook.md` §1: once the bound project is confirmed dead, the coordination cost of a history rewrite (force-push, every collaborator re-clones) outweighs the now-zero exploitability. This same precedent was later cited and reused for INC-2026-02-14-01 (the service-role key).

## Verification evidence

Supabase dashboard confirmed project `dgvlnelygibgrrjehbyc` deleted. Access-log query across four production log tables for the full exposure-to-discovery window returned zero anomalies. Both steps are checked off in `docs/operations/2026-05-17-p0-runbook.md` §1.

## Signals

No Bridge/Sentry signal — this was found by manual security audit, not monitoring. No GitHub issue was filed for this specific item; it is documented only in the P0 runbook.

## Recurrence risk

**Low but the mechanism recurred exactly once already** — see INC-2026-02-14-01, a structurally identical failure (a real production credential committed in plaintext to tracked source) that was *not* caught by the same May audit and lived for 5 more months. A per-commit historical secret scan (not just new-commit scanning) is the gap that let both happen; see Invariant candidate.

## Invariant candidate

Not a SQL invariant (this is a git-history property, not a database property). The concrete process gap: gitleaks (`review-gate.yml`) scans only the current push/PR by default, never the full existing tree. A one-time full-history gitleaks scan (`gitleaks detect --source . --log-opts="--all"`) against every branch would have caught this at the point the scanning tooling was first installed, rather than relying on a manual audit to stumble onto it four months later. Worth running once and adding to the repo's one-time security-debt checklist rather than as a recurring CI job (full-history scans are expensive to run on every push).

## Replay candidate

No. This is a documentation/process failure with no application code path — there is nothing to replay against a fixture. The generalizable lesson (scan full history once, not just new commits) is captured as a one-time action, not a regression test.

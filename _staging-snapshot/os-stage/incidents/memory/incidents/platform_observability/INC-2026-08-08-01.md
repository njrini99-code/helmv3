# INC-2026-08-08-01 — Stripe billing webhook fail-open: a discarded read error let a stale event downgrade a paid invoice back to open

- **id:** INC-2026-08-08-01
- **feature_id:** platform_observability (billing/Stripe integration has no dedicated registry feature)
- **first_seen:** unknown exact date the discarded-error pattern was introduced; found and fixed 2026-08-08 via a deliberate scan, not a live-triggered report
- **resolved:** 2026-08-08 11:14 UTC (PR #1352)
- **severity:** HIGH (the only "fail-open" defect in this batch that touches money — a paid invoice could be walked back to "open" by a late-arriving stale Stripe event)
- **classification:** DATA_INTEGRITY (primary)
- **status:** resolved (this specific site); 44 related candidate sites queued, not yet triaged

## Summary

The Stripe invoice webhook handler read the existing invoice row as a no-regression guard before upserting a new terminal status — the comment above the code reasoned this was safe under concurrent-delivery races because "both writers converge on the same terminal row." That reasoning only holds if the read succeeds. The read's error was discarded, so a failed read silently produced `existing = null`, which meant the terminal-status check could never fire, and a late-arriving *earlier* Stripe event could walk an already-paid invoice back to "open" — corrupting billing state, not just displaying something misleading.

## Root cause (verified)

A `try`/`catch`-style discarded error on the invoice-existence read, combined with code reasoning ("both writers converge on the same terminal row") that was true only in the success case and silently false in the failure case. This is explicitly framed by its own fix PR as the third instance of this exact pattern found in the same scan — after a one-team join guard and a baseball schedule-import dedupe — and the first of the three that "corrupts data" rather than merely "misleads someone," since it touches actual billing state.

## User impact

No specific customer/invoice named in available records as having been actually affected — this was caught by proactive code scanning, not a customer billing complaint or a Stripe dashboard anomaly report. The exposure is structural: any customer whose invoice received Stripe webhook events out of order, combined with a transient read failure at exactly the wrong moment, could have had a paid invoice silently reverted to open. Given Stripe's own retry behavior and the narrow failure-timing window required, the honest assessment is this was a real but likely low-frequency risk, not a confirmed-triggered incident.

## Repair

The pre-read now throws on failure. The webhook handler's existing catch-all returns HTTP 500 on that throw, causing Stripe to retry the delivery — at which point the guard gets a real chance to run against a (hopefully) successful read. Acknowledging the webhook despite the failed read (the prior behavior) would have silently dropped the event instead — explicitly called out in the fix as "the one outcome a billing webhook must never choose."

## Invariant candidate

Best expressed as a static/lint-level check rather than a runtime SQL invariant, since the defect class is "discarded error from a read that gates a write," a code-shape property:

```
# INV-CODE-001: any catch block (or discarded promise rejection) on a read
# whose result is used as a guard/precondition for a subsequent write must
# either re-throw, return an explicit failure sentinel the caller checks,
# or have an inline comment justifying why silent-continue is safe in this
# specific case. A bare discard is the failure shape found three times in
# this one scan.
```
Severity: HIGH given the confirmed recurrence rate (3 of the same shape in one scan, 44 more queued). Worth an ast-grep/semgrep rule addition to the existing Review Gate custom pack, since this is exactly the kind of deterministic, code-shape-only check that pack already covers for other patterns (service-role-key-in-client-bundle, DELETE-then-INSERT).

## Replay candidate

Yes, and cheap — a unit test mocking the invoice-existence read to reject/throw, then delivering a stale "invoice.updated → open" Stripe event after a "paid" state is already established; assert the handler now returns 500 (triggering Stripe retry) rather than silently downgrading the invoice. Fast, deterministic, no external Stripe dependency needed. High priority under extension §10-11's "silent statistical/data corruption" class, and doubles as the regression guard for this exact fix.

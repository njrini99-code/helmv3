# INC-2026-02-14-01 — Live production service_role key hardcoded in tracked scripts for ~5 months, closed twice before it was actually fixed

- **id:** INC-2026-02-14-01
- **feature_id:** platform_observability (cross-cutting infra/security; no single registry feature owns `scripts/`)
- **first_seen:** 2026-02-14 (commit `2fa0998c` last touched the scripts; JWT `iat` claim decodes to 2026-01-13, so the key itself was likely issued a month earlier and immediately re-embedded)
- **resolved:** 2026-07-03 (PR #774 / commit `307cbbe2` — actual rotation + full script remediation, after two earlier partial closures)
- **severity:** CRITICAL (a `service_role` key bypasses RLS entirely; live and exploitable by anyone with read access to the repo for ~5 months)
- **classification:** SECURITY (primary) / TELEMETRY_DEFECT (secondary — the regression guard meant to catch this never actually ran, twice)
- **status:** resolved

## Summary

A live production `service_role` JWT (full DB read/write, bypasses RLS) sat hardcoded in plaintext across at least 10 tracked scripts (`scripts/check-policies.ts`, `check-rls.ts`, `db-health-check.ts`, `debug-player-insert.mjs`, `diagnose-rls.ts`, `fix-auth.mjs`, `import-via-api.mjs`, `list-orphan-players.ts`, `run-sql.mjs`, `run-migration.mjs`; two of these also carried the `anon` JWT and a real plaintext account password) for approximately five months. It was reported fixed twice — issue #380 (2026-06-30) and issue #516 (2026-06-30, closed same day) — and both closures were incomplete: the key was removed from the specific scripts each fix targeted but never rotated, and a regression guard meant to prevent recurrence was added with a glob pattern narrow enough to miss every one of the actually-offending files, and was never wired into any test runner regardless.

## Root cause (verified)

Two independent failures stacked:

1. **Product cause:** developer scripts for direct DB access/debugging were written against a hardcoded key instead of env-var loading, likely for local convenience, and the pattern spread to 10 files over time.
2. **Process cause:** the regression guard built specifically to prevent recurrence (`scripts-no-committed-secrets.test.mjs`) had a glob narrow enough to miss the actual offending files, and separately was never executed by any test runner — so it gave "false confidence" (the report's own words) rather than actual protection, for both closure attempts.

## User impact

No confirmed exploitation (no anomalous access-log evidence surfaced in this repo's records). But the honest framing from the runbook stands: "a `service_role` key... must be treated as an active, exploitable credential" for the entire window it was live and public. This was Helm's single longest-duration live credential exposure — roughly 5 months from re-embed to actual rotation, and the key's exposure window traces back further still if the 2026-01-13 issuance date is when it first became a real production key.

## Repair

- PR #417 (2026-06-30) — partial: removed hardcoding from `seed-baseball-stats.mjs` only, added env-var loading + write-block guard.
- PR #380 (2026-06-30) — added gitleaks patterns (new-commit detection only) + a regression test with a glob too narrow to catch the actual files, never wired into any runner.
- PR #774 / `307cbbe2` (2026-07-03) — full remediation: all 10 scripts converted to env-var loading, plaintext password replaced with env vars, regression guard fixed to scan all of `scripts/` and wired into `npm test`.
- Manual key/JWT rotation in the Supabase dashboard — required per the 2026-07-03 runbook checklist; not independently verifiable from repo state alone.
- **Deliberately not done:** git history scrub. Per the same precedent as INC-2026-01-14-01, once the live credential is rotated the historical copies become inert, so the plaintext values remaining visible in git history (`ef1dc926` and forward) were accepted as a lower-urgency residual risk rather than a coordinated force-push rewrite.

## Verification evidence

The 2026-07-03 runbook documents the re-verification methodology (grep for the literal JWT pattern across all of `scripts/` on `main`) that caught the false closure. `scripts/__tests__/scripts-no-committed-secrets.test.mjs` (post-fix) is now wired into `npm test` and scans every file under `scripts/`, not a narrow glob.

## Signals

No Bridge/Sentry telemetry — entirely discovered by manual/agent-driven security review, twice. No production runtime signal would ever have caught this class of exposure; it required either the file-content scan itself or actual credential misuse.

## Recurrence risk

**Confirmed already recurred once at the meta level**: the *first* fix (#380/#516) was itself a false closure, caught only because a second independent pass re-verified from scratch instead of trusting the "closed" issue state. The general failure mode — a regression guard added in response to an incident is scoped too narrowly to the specific file(s) that prompted it, rather than the general pattern — is the same shape as INC-2026-01-14-01's "scan new commits only, not full history" gap. Any future regression-guard PR written in response to an incident should be reviewed for "does this generalize past the reported instance," not just "does this fix the reported instance."

## Invariant candidate

Yes — this is exactly the kind of check that should run once and then continuously:

```
# Not a SQL invariant (no DB state to query) — a static repo-scan invariant.
# INV-SEC-001: no tracked file outside .env* / secrets/ may contain a string
# matching Supabase JWT shape (eyJ... three base64url segments) or a raw
# service_role/anon key assignment pattern.
# Already implemented as scripts/__tests__/scripts-no-committed-secrets.test.mjs
# post-2026-07-03 fix — the invariant candidate here is confirming it stays
# wired into `npm test` (not just existing on disk) on every future CI run,
# since that exact "exists but never executes" failure is what let this
# recur once already.
```

Severity: CRITICAL if it ever fires. The concrete lesson to encode as a repo-doctor check: any `*.test.*` file using `node:test` imports must be reachable by an actual test runner in CI, or the check itself is a false-confidence artifact — this generalizes past secrets scanning to every regression guard in the repo.

## Replay candidate

No conventional replay fixture (no application data flow to reproduce). The more valuable "replay" here is a repo-doctor check that runs `scripts-no-committed-secrets.test.mjs` against a synthetic fixture directory containing a deliberately-planted fake-shaped secret, confirming the guard still fires and is still wired into `npm test` — a regression test for the regression-test-wiring failure itself.

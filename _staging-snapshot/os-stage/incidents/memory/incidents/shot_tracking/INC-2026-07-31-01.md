## Summary

`fetchShotDriversByCategory` requested
`.limit(SHOT_DRIVERS_FETCH_CAP)` = **25,000** rows, but PostgREST silently
caps any single response at **1,000** rows regardless of the requested
limit. The query additionally carried **no `ORDER BY`**, so for any player
with more than 1,000 shots on record, the shot-driver analysis was built
from whichever 1,000 rows Postgres happened to return first — an arbitrary,
non-deterministic subset, not a meaningful sample.

Measured against production on 2026-07-31: max shots for one player was
1,189; **6 of 33 players (18%) were already past the 1,000-row cliff**, and
every player crosses that line at roughly 14 rounds of play — so the
fraction affected was only going to grow as the season progressed, not stay
static.

This is the second instance of the same underlying PostgREST-cap defect
class that #1158's ast-grep rule was written to catch; this one evaded that
rule specifically because the limit value was expressed as a named constant
rather than a literal, and the rule matched literals.

## Root cause (verified)

Two independent defects compounding:

1. **PostgREST's hard 1,000-row response cap** applies regardless of the
   `.limit()` value requested by the client — a platform ceiling the code
   was not written to respect.
2. **No `ORDER BY`** on the query meant that even the 1,000 rows returned
   were not a meaningful or reproducible sample — a different 1,000 could
   return on a different call.

The prior detection tooling (#1158's ast-grep rule) specifically could not
catch this instance because it matched literal `.limit(N)` values; here the
limit was `SHOT_DRIVERS_FETCH_CAP`, a named constant, which the rule's
pattern did not resolve.

## User impact

- 18% of players (6 of 33, measured 2026-07-31) had shot-driver analysis —
  and anything downstream of it, including CoachHelm insight delivery —
  computed from an arbitrary subset of their actual shot history, with no
  indication to the player or coach that the analysis was incomplete.
- Every player was on a trajectory to eventually cross the 1,000-shot
  threshold (~14 rounds), so this was a growing-severity defect, not a
  fixed-size one.

## Repair

**Commit `94dbca778`, PR #1161, merged 2026-08-01T04:44:46Z** (`gh pr view
1161 --json mergedAt`; commit author date `2026-08-01T00:44:45-04:00`).

- Query now paginated via `fetchAllRowsResult`, with the ceiling enforced by
  stopping page accumulation rather than relying on a single `.limit()`
  call PostgREST would silently truncate anyway.
- The existing 5-second best-effort abort budget is preserved end-to-end —
  the abort signal is now carried across every page of the paginated walk,
  so the fix does not remove the existing timeout protection.
- `.order(...)` added so the underlying read is now deterministic rather
  than an arbitrary Postgres-decided subset.
- The nominal cap itself was corrected to be honest about what it actually
  enforces, since the prior 25,000 number was never reachable in one call
  (always silently truncated to 1,000) — full incremental pagination beyond
  the practical ceiling was evaluated and explicitly not done, judged not
  worth the refactor for the current 7.7x headroom margin.
- Two candidate matches inside **code comments** (not live query sites) were
  investigated and confirmed as false positives, not additional instances of
  the bug — recorded in the PR rather than silently dropped.

## Recurrence risk

- The underlying PostgREST 1,000-row cap is a platform behavior, not a bug
  that gets "fixed" — any future query against a high-row-count table that
  omits pagination or relies on a `.limit()` value above 1,000 is
  susceptible to the identical failure shape. #1158's ast-grep rule catches
  literal-value instances; constant-hidden instances (this incident's shape)
  are the demonstrated blind spot and were not, on available evidence,
  closed by a rule improvement — only by fixing this one call site.
- No evidence in available records of a repo-wide sweep for other
  constant-hidden `.limit()` values beyond the two false positives checked
  in this PR.

## Invariant candidate

Yes — this is a good target for a static/CI-time check rather than a
runtime SQL predicate, since the defect class is "a query that can silently
return fewer rows than a player's real data without signaling it," which a
production data query cannot easily self-detect:

```
INV-SHOT-002 (static analysis, CI-time): flag any Supabase/PostgREST query
against a table where row counts can exceed 1,000 per entity (golf_shots,
golf_holes-adjacent) that either (a) has no explicit pagination via
fetchAllRowsResult or equivalent, or (b) has a .limit() value — literal OR
resolved from a named constant — without a matching ORDER BY.
```

Severity: MEDIUM. This generalizes #1158's rule to close the specific blind
spot (constant resolution) this incident exploited.

## Replay candidate

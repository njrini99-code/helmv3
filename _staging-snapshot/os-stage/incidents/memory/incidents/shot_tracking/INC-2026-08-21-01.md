# INC-2026-08-21-01 — Offline sync: an IndexedDB transaction-lifecycle race and a hard device-level open failure, in BOTH offline databases

- **id:** INC-2026-08-21-01
- **feature_id:** offline_sync — registry feature: **`shot_tracking`** (registry key `shot_tracking` owns `src/lib/offline/**`; there is no separate `offline_sync` entry in `memory/registry.yml`). Code: `src/lib/offline/indexed-db.ts` (v1, `golfhelm_offline`), `src/lib/offline/shot-storage.ts` (v2), `src/lib/offline/use-offline-sync.ts`, `src/lib/offline/sync-engine.ts`
- **first_seen:** Sentry-first-seen for this cluster not independently re-derived in this backfill (a single Capacitor-iOS user's device); investigated 2026-08-20/21 overnight
- **resolved:** 2026-08-21 17:18:50 -0400 (`2c27b266f`, #1586)
- **severity:** MEDIUM (single user affected in the observed window; the failure mode is data-loss-adjacent by nature — offline shot/round data that fails to sync silently — even though no confirmed data loss was measured for this specific user)
- **classification:** FUNCTIONAL_FAILURE (primary) / DATA_INTEGRITY (secondary — an offline sync race is structurally a data-loss risk even where this specific occurrence didn't confirm one)
- **status:** resolved

## Summary

Three Sentry issues (internally tagged `P0`/`NZ`/`NY` during triage), all
from a single Capacitor-iOS user, all implicating
`use-offline-sync.ts`'s transaction teardown, were confirmed to be **one
incident with two distinct bug classes**, and — critically — both bug
classes existed **independently in both of the app's offline databases**
(v1 `indexed-db.ts` / `golfhelm_offline`, and v2 `shot-storage.ts`), not
just one. The two classes:

1. **A transaction-lifecycle race.** Several read functions
   (`getSyncMetadata`, `getPendingShots`, `getPendingRoundCount`) placed
   their first IndexedDB request in the *same tick* the transaction was
   created, rather than accounting for browsers — Safari specifically —
   that auto-commit a transaction more aggressively than other engines. On
   Safari, the transaction could auto-commit before any of these functions'
   first request executed, throwing `InvalidStateError` from `objectStore()`.
2. **A device-level IndexedDB open failure with no fail-fast path.** When
   `indexedDB.open()` fails at the device level, the pre-fix code retried
   the same failing open on every call site that needed it — matching the
   reported incident's "5 events" shape (5 repeated failed opens from the
   same session) — instead of caching the failure and degrading gracefully
   after the first one.

## Root cause (verified)

**Bug 1 (transaction race):** IndexedDB transactions auto-commit once the
current microtask/task boundary passes with no pending requests against
them, and browser engines differ in how strictly they enforce this. Code
that creates a transaction and does *not* place its first `objectStore()`
call and request in the same synchronous tick (or ties the first request
tightly enough to survive Safari's stricter timing) risks the transaction
having already auto-committed by the time the first real operation runs,
which throws rather than silently retrying.

**Bug 2 (open failure, no fail-fast):** neither offline database module
cached a failed `indexedDB.open()` result. A device-level failure (this
particular investigation ties it to `isIdbUnavailableThisSession()`-style
device state, not a code regression) meant every subsequent call site that
needed IndexedDB re-attempted the same doomed `open()` call, generating
repeated Sentry events and repeated failed attempts rather than degrading
once and consistently.

**Verified to exist in both databases**, not assumed by symmetry: the fix
commit explicitly mirrors the v2 (`shot-storage.ts`) fix onto v1
(`indexed-db.ts`) as its own separate commit in the sequence, confirming
both bug classes were independently present in the sibling module rather
than one being inferred from the other's presence.

**Ruled out during investigation:** a stale-bundle explanation (the user's
client running old JS across a deploy boundary) — the failure timestamp
(17:54 ET) sits **between** two deploys, not adjacent to either, which is
inconsistent with a stale-bundle theory and consistent with a genuine,
ongoing regression instead.

## User impact

- Confirmed: **one** Capacitor-iOS user, repeated offline-sync failures
  (matching Sentry's "5 events" pattern for the open-failure class).
- Not confirmed either way in the sources reviewed: whether this specific
  user actually lost any pending offline shot/round data as a result, or
  whether the sync eventually recovered once conditions changed (e.g., app
  restart, network return). The fix's design (fail-fast + cached
  unavailability state) is explicitly about *degrading predictably* rather
  than *silently retrying forever*, which suggests the pre-fix behavior
  was at minimum a poor user experience (repeated silent failures) even if
  the ultimate data outcome for this user is unknown.
- Both bug classes are structurally a data-loss risk for **any** offline
  golf round/shot recorded on Safari/Capacitor-iOS under either failure
  condition, not just the one observed user — this is why it's classified
  with DATA_INTEGRITY as a secondary tag despite no confirmed loss in the
  one instance investigated.

## Repair

`2c27b266f` ("fix(golf): offline sync survives a broken IndexedDB," #1586),
landed as four commits:

1. **`shot-storage.ts` (v2) fix** — transaction race + fail-fast open
   failure.
2. **`sync-engine.ts` fix** — gated a duplicate `console.error` on a shared
   flag (noise reduction, same investigation).
3. **`indexed-db.ts` (v1) fix** — mirrors the v2 fix for the *same two bug
   classes* in the sibling database.
4. **Test commit** — 10 new tests in
   `src/lib/offline/__tests__/idb-resilience.test.ts`, covering both bug
   classes across both databases.

The transaction-race fix restructures the affected read functions so their
first request against the transaction happens in the same tick the
transaction is created, closing the window Safari's stricter auto-commit
timing was exploiting. The open-failure fix adds a session-level cached
"IDB unavailable" flag (`isIdbUnavailableThisSession()`) so a second call
site doesn't re-attempt a doomed `open()`, and both
`isOfflineStorageAvailable()`/`isIndexedDBAvailable()` degrade to `false`
cleanly rather than throwing.

## Verification evidence

- 10 new tests in `idb-resilience.test.ts`, covering both bug classes ×
  both databases (v1 and v2):
  - **Transaction-lifecycle race**: a fake `IDBTransaction` that
    "auto-commits" (throws `InvalidStateError` from `objectStore()`) after
    one microtask tick past creation — deliberately modeling Safari's
    stricter auto-commit timing without needing a real Safari browser in
    CI. Asserts `getSyncMetadata`/`getPendingShots`/`getPendingRoundCount`
    all place their first request in the same tick the transaction is
    created, so none of them observe the simulated auto-commit.
  - **Device-level open failure**: a stub `indexedDB.open` that always
    errors. Asserts the *second* call fails fast (no second real
    `indexedDB.open()` attempt is made), `logError` fires **exactly once**
    across 5 repeated calls (directly matching the reported incident's "5
    events" shape), `isIdbUnavailableThisSession()` flips `true`, and both
    availability-check functions degrade to `false` without throwing.
- **Reverse-verified against the pre-fix source**: 8 of the 10 assertions
  confirmed to fail without the fix. The other 2 are graceful-degradation
  checks that pass either way by design (the old code also eventually
  returned `false`, just more noisily/slowly) — recorded explicitly rather
  than silently claiming all 10 as regression-proof.

## Recurrence risk

- The fix addresses the two specific bug classes found in this
  investigation. Both databases (v1 and v2) are now covered symmetrically,
  which closes the "fixed in one, forgot the sibling" risk that this
  incident itself demonstrated is real in this codebase (two independent
  IndexedDB implementations coexisting is itself a standing maintenance
  risk — a future third bug class found in one may again need an explicit
  check against the other rather than an assumed mirror).
- Only one user's failure was directly observed. The true prevalence of
  this failure shape across the broader Capacitor-iOS user base is
  unmeasured — Sentry-based detection depends on the error actually
  firing and reaching Sentry, which offline-by-definition failures may not
  always do promptly.

## Invariant candidate

Partial. This is fundamentally a client-side (browser/device) concurrency
bug, not something a production Postgres invariant can observe directly.
The regression-test coverage added (the 10 tests, especially the two
device-level-open-failure assertions) is the right-shaped guard for this
class and is already in place. A server-side proxy signal is worth
considering: if `sync-engine.ts` reports pending-shot counts or sync
failures to any server-side telemetry, an invariant on **sustained
non-zero pending-sync counts per device** over an unusually long window
could serve as an early warning for a recurrence of this class without
needing Sentry's client-side reporting to fire correctly — flagged as a
candidate for whoever owns the sync-engine's server-side telemetry surface,
not fully specified here since that telemetry path wasn't independently
verified to exist in the sources reviewed.

# INC-2026-08-18-04 — Exposure ledger counted renders, not views: 349 rows for one insight/coach/day, feeding the de-ranking signal

- **id:** INC-2026-08-18-04
- **feature_id:** coachhelm (registry key: `coachhelm_ai`)
- **first_seen:** 2026-08-18 (issue #1506 created)
- **resolved_at:** 2026-08-21 (fixed by PR #1546, merged 2026-08-21)
- **severity:** MEDIUM
- **classification:** DATA_INTEGRITY (primary — the ledger's counts were the input to a de-ranking algorithm, so corrupted counts directly corrupted downstream ranking) / TELEMETRY_DEFECT (secondary)
- **status:** resolved

## Summary

The insight exposure ledger, which records how many times a coach has seen a given insight (used as an input signal for de-ranking repeatedly-shown insights), recorded a new row on every **render** rather than once per genuine **view**. One insight, for one coach, on one day, accumulated **349 exposure rows** — several orders of magnitude beyond a plausible view count, since a coach does not reload the same insight surface 349 times in a day. Because this ledger directly feeds a de-ranking signal, the corrupted counts would have caused affected insights to be de-ranked far more aggressively than their actual view history justified.

## Root cause (verified)

Not independently re-derived beyond the fix's own description: `recordExposureForReturned` recorded an exposure on every call rather than checking for an existing `(insight_id, coach_id, surface)` key for the current day first — any component re-render, refetch, or navigation event that re-triggered the recording path added a new row, regardless of whether the coach had actually seen anything new.

## User impact

- Any insight subject to this bug would be de-ranked far more than its actual exposure justified, potentially suppressing genuinely useful, under-viewed insights from a coach's feed based on a corrupted "coach has seen this many times" signal.
- Scale: at least one confirmed case of 349 rows for a single insight/coach/day; the sources reviewed for this backfill do not establish how many insight/coach pairs were affected platform-wide or for how long.

## Repair

Fixed by PR #1546 (merged 2026-08-21): `recordExposureForReturned` now checks the batch's existing `(insight_id, coach_id, surface)` keys for the current day before writing, and skips already-recorded rows — implemented per the issue's own "Option 1 (racy-but-adequate)" proposal, i.e., a deliberately accepted best-effort dedup rather than a fully race-proof one, on the judgment that occasional double-counting under concurrent access is an acceptable residual risk for this signal.

## Recurrence risk

The accepted "racy-but-adequate" dedup means concurrent recording calls for the same insight/coach/surface/day can still occasionally double-count — a deliberate, bounded residual risk, not a full fix. If de-ranking behavior is ever found to still be over-aggressive for a specific insight, this residual race is the first place to check before assuming a new defect.

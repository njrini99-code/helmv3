- **status:** resolved (round_review path); open (coach_chat sibling, #1540)

## Summary

`generateLLMRecap` built a `facts` block (score, putts, fairway %, GIR %,
front/back nine, season scoring average), instructed the model verbatim —
*"Reference at least one specific stat by number"* — and then called
`compose()` with `evidence: []`. Those two things cannot both be satisfied.
`verifyCitations` rejects every numeric token that isn't present in the
evidence set (except the universally-safe 0/1/2/3/100), so a recap that
*obeyed* the instruction and cited a real figure from the facts block failed
verification, and `compose()` discarded the whole thing for the
deterministic template fallback. **The model was being punished for using
exactly what it was handed.**

## Root cause (verified)

Proof was established two ways before any change was made:

1. **Direct reproduction.** The real verifier, the evidence set exactly as
   shipped (empty), and a recap citing figures drawn from the prompt's own
   facts block, run together, produced
   `AssertionError: unmatched=71,78.6%: expected false to be true` — a
   synthetic failure matching production exactly.
2. **Production correlation.** `golf_coachhelm_llm_calls` for 2026-08-17
   02:37 UTC logged `unmatched_tokens: ["71"]` for a round whose actual
   score was 71 — the exact number the model had correctly cited from its
   own prompt, rejected because the evidence set that should have covered it
   was empty.

**Measured in production (2026-08-17):** every discarded call that recorded
its evidence set recorded it **empty** — 4 of 4, 0 with a non-empty set.
Unmatched tokens across the recent window were plainly the facts themselves:
71 · 26,78,73.5 · 27,78.6 · 14,50 · 50,72.2 · 44.4,83. Across the whole
`round_review` task: **75 calls fell back to template, 28 verified** — the
majority of round-recap generations were silently degraded to templates at
the time of measurement.

This also corrected the fix's own author's earlier diagnosis in #1474,
which had guessed the cause was derived percentages the citation registry
didn't cover — that work was already done and sound in `round-review.ts`.
The recap composer is a **separate** `compose()` caller that registered
nothing at all, a distinct bug from what #1474 had originally assumed.

## User impact

- Real players and coaches received deterministic template-fallback round
  recaps instead of grounded, AI-generated ones for the majority of round
  reviews during the affected window (75 of 103 calls in the measured
  sample fell back).
- No incorrect or hallucinated content reached users — the verifier was
  doing its job correctly by rejecting unverifiable claims; the failure
  mode was silent over-rejection (quality degradation), not
  under-rejection (hallucination reaching a user). This is a meaningfully
  better failure direction than the alternative, worth stating plainly
  rather than dramatizing.
- The degradation was invisible through ordinary error monitoring — a
  template fallback is a successful response from the caller's
  perspective, not an error — which is exactly why it took a direct
  measurement of `golf_coachhelm_llm_calls`'s evidence-set field to find.

## Repair

`7feaeb545` (2026-08-17T04:20:20Z, "fix(coachhelm): the round recap told
the model to cite a number, then supplied none"):

- New `buildRecapEvidence` (in `src/lib/coachhelm/v3/llm/recap-evidence.ts`,
  not inline in the action — `round-recap.ts` is a `'use server'` module
  where every export must be an async function) registers exactly the
  figures the prompt literally showed the model, using the verifier's own
  `extractNumericTokens` so the registered set and the judged set cannot
  drift apart structurally.
- **The verifier is not loosened.** A number the model was never handed is
  still rejected — covered by a test asserting an invented `61` still
  fails post-fix. Percentages register both renderings the model actually
  produces (`"78.6%"` and `"79%"` are the same true fact), following the
  same reasoning `pushDerivedPct` already documents for round reviews.
- Confirmed **not** affected: `practice-rx/composer.ts`, the other
  `round_review` task caller, which always registers at least three claims
  and was never in the empty-evidence state.

## Recurrence risk — the `coach_chat` sibling (#1540, OPEN, not fixed)

**Pre-history:** this is not the first instance of this defect class in
`compose()`. The day before this fix, a three-PR chain (#1455/#1457/#1458,
2026-08-16) fixed the same shape — a citation verifier discarding
legitimate figures the evidence-registration step hadn't been taught to
expect — in the *round_review* composer's own citation coverage (a
coverage gap, not a total absence as here). See `INC-2026-08-16-09` for the
full chain; that incident's own recurrence-risk section points forward to
this one. Two occurrences in two days across two different `compose()`
callers is why the invariant below is written to be caller-agnostic rather
than specific to either.

**This is the load-bearing follow-up finding from the same overnight audit
that verified #1474's closure.** `coach_chat` — a *different* `compose()`
caller than either `round_review` caller checked above — shows an
estimated **~46% ungrounded discard rate**, filed as issue #1540 (opened
2026-08-21T03:19:23Z, open as of 2026-08-21) during the 2026-08-20/2026-08-21
audit. Critically: **this instance is invisible to
the `error_logs`-based detection method** that surfaced the original
`round_review` bug, meaning the standard incident-detection path used
throughout this campaign would not have found it on its own — it required
someone to specifically go measure `coach_chat`'s evidence/discard rate
directly, the same way the original bug required measuring
`golf_coachhelm_llm_calls` directly rather than trusting error monitoring.

**#1540 is open, unfixed, and not investigated in depth in the sources

## Invariant candidate

Yes, and it directly generalizes past this one caller — exactly the kind of
bug class the extension's invariant framing is meant to prevent from
recurring through a sibling code path, which is precisely what happened
here with `coach_chat`:

```sql
-- INV-COACHHELM-002: no compose() caller should have a sustained non-trivial
-- ungrounded-discard rate. Bounded, recent-window, read-only.
select task, count(*) filter (where evidence = '[]'::jsonb or evidence is null) as empty_evidence_calls,
       count(*) as total_calls,
       round(100.0 * count(*) filter (where evidence = '[]'::jsonb or evidence is null) / nullif(count(*), 0), 1) as pct_empty
from golf_coachhelm_llm_calls
where created_at > now() - interval '24 hours'
group by task
having count(*) filter (where evidence = '[]'::jsonb or evidence is null) > 0
   and count(*) > 5;  -- avoid noise on low-volume tasks
```

Severity: MEDIUM. This single invariant, run daily, would have caught both
the original `round_review` bug AND the still-open `coach_chat` bug through
the same mechanism — it is task-agnostic by construction, which is exactly
the generalization this specific incident's recurrence demonstrates is
needed. This is a strong candidate for "a bug should upgrade the control
plane" per extension §8-9: writing this one check retroactively covers the
gap that let #1540 go undetected by the standard method.

## Replay candidate

Yes, for the fixed `round_review` path — cheap and already half-built by
the fix's own verification. Minimal sanitized fixture: a synthetic `facts`
block (fabricated stat values, no real player/round identity) fed to
`generateLLMRecap`'s prompt-building step, asserting the evidence set
`buildRecapEvidence` produces contains every numeric token the prompt
actually shows the model, and that `verifyCitations` then accepts a recap
citing those exact figures. Extending this fixture to also exercise the
`coach_chat` compose() call site (once #1540 is root-caused) would let one
replay harness cover both the fixed and the still-open instance of this bug
class, and would double as the regression guard for #1540's eventual fix.

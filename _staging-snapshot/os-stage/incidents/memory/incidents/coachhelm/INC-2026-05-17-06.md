# INC-2026-05-17-06 — Fire-and-forget round analysis silently dropped 206 of 290 completed rounds; the safety-net cron reported success 332 times while catching none of them

- **id:** INC-2026-05-17-06
- **feature_id:** coachhelm (registry key: `coachhelm_ai`; code: `src/lib/coachhelm/v2/post-round-trigger.ts`, the safety-net cron that re-scans unanalysed rounds, `golf_coach_insights` effectiveness ledger, calibration bucket read path)
- **first_seen:** 2026-05-17T23:38:24Z (commit `20e41cf4a`, "postRoundTrigger wrapper writes terminal state" — the `after()`-based fire-and-forget dispatch is the root mechanism, present from this commit)
- **resolved:** 2026-07-25T15:05:49Z (commit `a48003ef2`, PR #1050 — opened 2026-07-25T11:03:13Z, merged 2026-07-25T15:05:49Z, same-day)
- **severity:** HIGH (96% of visible insights were 31-60 days stale at diagnosis; not a crash, but a silent, months-long accumulation of unprocessed product data)
- **classification:** FUNCTIONAL_FAILURE (primary) / DATA_INTEGRITY (secondary — the effectiveness ledger and a calibration bucket read path were also found broken in the same audit and repaired in the same PR)
- **status:** resolved

## Summary

`postRoundTrigger` dispatches round analysis via Next's `after()`, which
runs fire-and-forget and is **not durable** — if the serverless instance
recycles before the callback completes, the round is silently left
unanalysed with no error, no retry, no log. The safety-net cron that exists
specifically to catch exactly that case only scanned rounds **created in
the last 30 days**, so any round that missed its `after()` window and then
aged past 30 days was permanently unreachable by either path. Measured
against production: **206 of 290 completed rounds — 71% — were never
analysed at all.** The cron itself reported `completed` **332 times over
30 days while doing zero effective work** on the backlog, the same
"green but did nothing" shape later found independently in the genome cron
(`INC-2026-07-07-01`) and the round-recap evidence bug
(`INC-2026-08-17-02`) — this is the earliest instance of that failure
pattern in the reviewed CoachHelm history.

## Recurrence risk

**This is now a recurring failure shape in this codebase, not a one-off.**
Three separate CoachHelm crons/pipelines have independently shown "reports
success while doing no effective work on its actual backlog": this one
(2026-05-17 → 2026-07-25), the genome nightly cron
(`INC-2026-07-07-01`, 2026-07-07 → 2026-08-17), and — by a related but
distinct mechanism (empty evidence sets, not a stale backlog) — the
round-recap composer (`INC-2026-08-17-02`). A platform-wide sweep for this
shape, not per-job fixes, is the generalization worth pursuing; see the
invariant candidate below.

## Invariant candidate

Yes, directly generalizable from the pattern already identified in
`INC-2026-07-07-01`:

```sql
-- INV-COACHHELM-003: a completed round should have a corresponding
-- analysis/insight record within a bounded window (e.g. 72h). Read-only,
-- bounded to a recent rolling window.
select r.id, r.completed_at
from golf_rounds r
left join golf_coach_insights i on i.metadata->>'round_id' = r.id::text
where r.completed_at < now() - interval '72 hours'
  and r.completed_at > now() - interval '30 days'
  and i.id is null;
```

Severity: HIGH. Bounding the window to 30 days keeps the check cheap; the
30-day-window blind spot that caused this incident is exactly why the
check itself must not be limited to "recently created" rows only when
computing the backlog size for alerting purposes (unlike the cron it
would be monitoring).

## Replay candidate

Yes. Minimal sanitized fixture: a synthetic round whose completion
timestamp is set to simulate "created 31+ days ago, never analysed,"
fed through the safety-net cron's own selection query. Pre-fix: the
30-day-window selection excludes it. Post-fix (the drain's corrected
selection logic, if it changed the window rather than being a one-time
script): the round is included. If the fix was a one-time drain script
rather than a durable window-widening change, that is itself worth
flagging — a one-time drain does not prevent recurrence, only clears the
existing backlog once.

## Eval candidate

Not applicable directly — this is a pipeline-completeness/data-freshness
defect, not an LLM generation-quality defect. It matters to CoachHelm AI
eval work only indirectly: any eval case measuring recommendation
freshness or recency should assume the underlying analysis pipeline is
complete, which this incident shows cannot be taken for granted without a
freshness invariant like the one above.

## Status

**Resolved** as of 2026-07-25T15:05:49Z (one-time drain plus targeted
repairs). **Not independently confirmed as of 2026-08-21** (this
backfill's review date) whether the safety-net cron's 30-day window itself
was widened or made durable — if it was not, the same 30-day blind spot
can silently reaccumulate a new backlog starting from whatever `after()`
reliability turns out to be in production. Worth checking the current
cron's window bound directly before assuming this class is permanently
closed.

## Summary

The Genome's `scrambling_rate` dimension measured **short-game shots from
rough/sand that finished within 10 ft of the hole** — proximity, not
outcome. Its own docstring called this "a rough proxy for 'saved par from
trouble,'" which undersold how wrong the proxy was: stiff a chip to three
feet and then three-putt, and the proximity measure still scores it a
save. Meanwhile the Stats tab, via `golf-stats-calculator-shots.ts:951-952`,
had always used the canonical, unambiguous definition:

```ts
scrambleAttempt: !greenInRegulation && score !== null,
scrambleMade:    !greenInRegulation && score !== null && score <= hole.par,
```

One product, one word ("scrambling"), two numbers, shown to the same coach
on two different tabs — and the Genome's number could invert the verdict:
the issue title states the measured result directly — **14 players it
called "Wizard" were actually leaky** by the canonical definition.

## Root cause (verified)

`gir` (green-in-regulation) was never loaded into the query the genome
dimension ran, which is *why* the dimension had to approximate from shot
proximity in the first place — it had no way to know whether a green was
missed at all, only where the ball finished on approach/short-game shots.
Without GIR, "did this scramble attempt succeed" was unanswerable from the
data the query fetched, so proximity-within-10ft stood in for it.

## User impact

Coaches viewing the Genome radar saw a persona label ("Wizard" / "Leaky")
that could be the **opposite** of what the Stats tab, using the correct
formula, would report for the same player. A coach trusting the Genome
label over the Stats number would coach the wrong skill.

## Repair

Commit `b387973a3`, 2026-08-17T18:07:58Z:

- `gir` added to the existing hole select — one column, not a new query.
- A null `gir` is skipped rather than read as "missed" (would invent
  attempts); a missed green with no recorded score is skipped for the same
  reason the stats calculator already documents: outcome unknown.
- **Thresholds re-derived from the squad, not from intuition.** Over the
  genome's own 90-day window, 20 players with ≥15 attempts: p25 27.6%,
  median 34.1%, p75 40.6%. Wizard is now top-quartile (≥0.406), Leaky
  bottom-quartile (≤0.276). The old fixed cutoffs (0.55/0.35) would have
  inverted the error in the other direction — nobody in production clears
  0.55 on the real (harder) definition, so keeping those cutoffs against a
  now-correct formula would have read almost the entire squad as Leaky.

## Recurrence risk — same shape confirmed present in a sibling dimension the same day

The issue that fixed this one explicitly flagged five more Genome
dimensions (`driver-usage`, `par3-proficiency`, `pressure-delta`,
`back-nine-delta`, `scoring-trend`) as needing the same "does the other
surface agree?" pass, because nothing structurally prevents the same value
drift. One of those siblings, `miss-side-bias`, was checked the same day
and found broken by a different mechanism — see
`INC-2026-05-25-04`. All Genome dimensions shipped in the same 2026-05-25
wave (`cf95ee595`) and none had a cross-surface agreement check until this
incident's fix.

## Invariant candidate

Yes — a periodic cross-surface consistency check between Genome dimension
verdicts and the equivalent Stats-tab calculation, for every dimension that
has a Stats-tab counterpart, flagging any player where the two disagree
about which side of a threshold they're on. This generalizes past
scrambling specifically and would have caught the miss-side sibling bug
(`INC-2026-05-25-04`) through the same mechanism.

## Replay candidate

Yes — moderate cost. Fixture: a synthetic round with shots that scramble
successfully by proximity (chip to 3 ft) but fail by the canonical
definition (three-putt from there), fed through both the old
proximity-based dimension logic and `golf-stats-calculator-shots.ts`'s
`scrambleAttempt`/`scrambleMade`. Pre-fix: the two disagree on this
fixture by construction. Post-fix: the Genome dimension's `gir`-based
computation agrees with the Stats calculator on the same input.

## Eval candidate

Not directly — this is a computed-statistic bug, not a prompt/LLM
generation defect, so it does not map to a Promptfoo eval case. The
invariant candidate above is the correct control-plane mechanism for this
class.

## Status

**Resolved.** Cutoffs are now cohort-derived rather than fixed, which means
they should be periodically re-checked against the population as the
season's data shifts, per the fix's own reasoning for why the old fixed
0.55/0.35 cutoffs were wrong.

# INC-2026-05-26-01 — v3 CoachHelm generator storm: 4,877 error rows the day after the partial v2→v3 orchestrator cutover

- **id:** INC-2026-05-26-01
- **feature_id:** coachhelm (registry key: `coachhelm_ai`)
- **first_seen:** 2026-05-26 (all 6 storming signatures first_seen and last_seen same day, except one 5/28 straggler)
- **resolved:** never recurred after the initial storm day(s) — no explicit fix commit identified in this pass; classified as self-resolved/inert, not actively fixed
- **severity:** MEDIUM (large error volume, but confirmed dead for ~3 months at triage time with no recurrence, and no confirmed downstream product impact beyond missing insights for the affected generators on the affected day)
- **classification:** FUNCTIONAL_FAILURE (primary) / TELEMETRY_DEFECT (secondary — a one-time storm inflated the all-time error_logs volume by ~4,877 rows, dominating the signature roster long after it stopped mattering)
- **status:** resolved (mechanism identified with code-level confidence; not independently confirmed fixed by any specific commit)

## Summary

Helm Bridge `error_logs` records six `v3.generator.*` / `v3.composite.synthesis.*` signatures — `ParTypeGenerator` (1,626), `PuttDistanceGenerator` (1,625), `ScramblingGenerator` (542), `PressureGapGenerator` (542), `WarmupHoleGenerator` (542), and a related `v3.composite.synthesis.load` (1,642) — all firing exclusively on 2026-05-26/27, then never again (`TeeStrategyGenerator` fired a smaller, separate 23-row burst on 5/28). Direct inspection of PR #61 ("wave25: orchestrator cutover to v3 generators (partial 7-of-9)", merged 2026-05-25 16:46 UTC) confirms this is not a coincidence: that PR cut the orchestrator over from v2 to v3 `BaseGenerator` implementations for exactly five of these six generators (`ParTypeGenerator`, `PuttDistanceGenerator`, `ScramblingGenerator`, `PressureGapGenerator`, `WarmupHoleGenerator`) the day before the storm, and its own description explicitly documents an unresolved data-model gap: *"v3 covers 3 buckets / 2 directions until cache alignment"* — i.e., the new v3 code paths were deployed still reading against cache columns not yet fully aligned to the new bucket/direction scheme.

## Root cause (verified for 5 of 6 signatures; plausible-but-unconfirmed for the composite-synthesis signature and the 5/28 straggler)

PR #61's own diff and description confirm the mechanism directly: the orchestrator began invoking new `v3.*` generator code paths against a data model with a documented, accepted coverage gap ("until cache alignment"). The generators most likely threw when encountering player/round data that fell into a bucket/direction the v3 cache columns didn't yet support — the exact shape of the documented gap. This is a code-verified mechanism, not an inference from timing alone.

## User impact

For the storm window (2026-05-26, bleeding into 5/27), affected players/coaches would have been missing the insights normally produced by these five generators (putt distance, par-type scoring, scrambling, pressure-gap, warmup-hole) rather than receiving corrupted output — a generator throwing means no insight is written, not a wrong one. No confirmed player-facing complaint or support ticket tied to this window in records reviewed for this pass.

## Repair

**No explicit fix commit was identified in this pass.** Three plausible explanations, none confirmed: (a) a same-week cache-alignment follow-up wave (there are several "wave"-numbered PRs immediately after #61/#62 in the 5/26 sequence) closed the gap incidentally; (b) the storm was a one-time backfill/batch-run hitting existing historical player data against the new buckets, and normal go-forward traffic simply doesn't hit the same gap; (c) the generators remain capable of throwing under the same condition today but the condition (specific bucket/direction combinations in player data) has not recurred. Given the ~3-month dead window at time of triage with zero recurrence, (b) is the most likely explanation, but this is not verified against a specific commit or dataset in this pass.

## Verification evidence

PR #61's file diff (`src/lib/coachhelm/v2/orchestrator.ts`) directly confirmed via `pull_request_read` — the five storming generator names appear verbatim as new orchestrator entries, and the PR's own prose independently names the exact gap ("until cache alignment") that would produce exactly this failure shape. This is a materially stronger evidence base than "timing correlation" — it is the responsible PR's own author documenting the known-incomplete state at merge time.

## Signals

Bridge `error_logs`, `context->>'action'` grouping — six signatures, ~4,877 total rows, all `first_seen`/`last_seen` within a 2-3 day window in 2026-05.

## Recurrence risk

Low, given ~3 months of confirmed silence at last triage — but **unconfirmed as actually fixed** rather than merely dormant. If cache-alignment work never actually landed and the storm was purely a one-time backfill artifact, the same class of error could recur if a future data-migration or backfill re-triggers the same gap against historical data.

## Invariant candidate

```sql
-- INV-COACHHELM-001: no v3 generator signature should produce more than
-- N error rows in a rolling 24h window without a corresponding recent
-- deploy note. Cheap, bounded, catches a repeat of exactly this shape
-- (a cutover deploy followed by a same-day-adjacent error spike) before
-- it needs an audit 3 months later to notice.
select context->>'action' as generator, count(*) as n
from error_logs
where severity in ('error','critical')
  and context->>'action' like 'v3.generator.%'
  and created_at > now() - interval '24 hours'
group by 1
having count(*) > 50;
```

Worth revisiting once/if a specific remediation commit is located.

# INC-2026-07-07-01 — Genome cron ran green 47 times and wrote nothing: a permanent-skip chunk selector jammed on 25 uncomputable players

- **id:** INC-2026-07-07-01
- **feature_id:** coachhelm (registry key: `coachhelm_ai`; code: `src/app/api/cron/v3/genome-nightly/route.ts`, `src/lib/coachhelm/v3/genome/select-refresh-chunk.ts`)
- **first_seen:** data frozen from 2026-07-07 (last successful compute before the jam; time-of-day unknown — `computed_at` date only); diagnosed 2026-08-17 (exact time-of-day of diagnosis itself unknown; the fix that resulted landed the same day, see below)
- **resolved:** 2026-08-17T08:40:54-04:00 / 2026-08-17T12:40:54Z (commit `2e0632326`, prior HEAD `2270e43cb` at 2026-08-17T08:19:47-04:00); **production recomputation not independently re-verified as of 2026-08-21** (this backfill's review date) — see Verification evidence
- **severity:** MEDIUM (silent feature staleness, not user-blocking or data-destructive, but six weeks of a core CoachHelm surface silently frozen)
- **classification:** FUNCTIONAL_FAILURE (primary) / TELEMETRY_DEFECT (secondary — the job logged `completed` on every run with no way to report it had done no work)
- **status:** resolved (fix verified by construction and by pre/post assertion tests; live post-deploy recomputation not confirmed)

## Summary

The Genome surface "looked out of sync" because it was showing analysis
computed on **2026-07-07** — forty-one days stale at diagnosis time.
`background_job_logs` showed `v3-genome-nightly` running **47 times**,
**every single run marked `completed`**, latest run 2026-08-17 02:40, each
taking ~1,039ms — a runtime that could not possibly have rebuilt 25 player
genomes. Nothing anywhere said so: `metadata` on the job rows was `null`, so
the log could not even report that it had done no work. Six weeks of green
dashboards were a lie the job's own logging made unfalsifiable.

## Root cause (verified)

The nightly chunk selector ordered candidates **never-computed first, then
oldest `computed_at`**. A player with no completed round inside the 90-day
scoring window produces zero valid genome dimensions, and
`computeGenomeForPlayer` correctly, deliberately refuses to upsert in that
case — an all-null vector is exactly the trust-eroding state a prior
product decision (`P2-21`) forbids — so it returns
`skipped_reason: 'no_valid_dimensions'` and writes nothing.

Writing nothing means no `computed_at` is ever set. No `computed_at` means
that same player sorts to the front of "never-computed" again the very next
night. And the night after. Production made the collision exact:

```
80  active members
32  never computed
25  of those 32 have NO completed round in the window (permanently uncomputable)
25  PLAYERS_PER_INVOCATION  (the chunk size)
```

Twenty-five permanently-uncomputable players filled the entire 25-slot
chunk, every single night. The 7 never-computed players who *do* have
rounds and could actually be computed never got a turn. The 48 real,
computable genomes were never reached at all.

**Why this survived six weeks of green dashboards**, stated plainly in the
fix commit: the route's own header comment claimed *"Self-balancing — next
run naturally grabs the now-stalest cohort."* That claim was false — the
skip path guarantees some players never advance past never-computed — but
the comment described behavior its own code made impossible, and nobody
had reason to doubt a comment describing a system that was, by every
observable metric (job status, duration, log count), working.

## User impact

- CoachHelm's Genome surface showed stale, six-week-old analysis to
  coaches and players for the entire jam period, with no indication
  anywhere in the UI or the job logs that anything was wrong — every signal
  available to an operator said the system was healthy.
- 48 real, computable player genomes were never refreshed during this
  window purely because 25 uncomputable players occupied the entire nightly
  chunk ahead of them, not because of any load or cost constraint.
- No data was corrupted or lost — this is a staleness/availability failure,
  not a data-integrity one. The stored genome values themselves remained
  correct as of their (stale) `computed_at`.

## Repair

`2e0632326` ("fix(coachhelm): the genome cron ran green for six weeks and
wrote nothing"):

- Chunk selection now **pre-filters to only players who can actually
  produce a vector** — i.e., have at least one completed round inside the
  scoring window — before applying the never-computed-first,
  oldest-`computed_at`-next ordering. A dormant player isn't being starved
  of attention; there is nothing to compute for them, and they re-enter the
  eligible queue the moment they log a round. Priority within the eligible
  set is otherwise unchanged.
- The skip path itself (`skipped_reason: 'no_valid_dimensions'`) was
  correct and left untouched — the fix stops *feeding* it inputs that were
  guaranteed to skip, rather than changing what it does when a genuine edge
  case reaches it.
- `WINDOW_DAYS` is now **exported** from the orchestrator and imported by
  the cron's own pre-filter query, so the cron and the orchestrator can no
  longer disagree about which window counts — "two constants that must
  agree" is called out explicitly in the fix as the shape this whole bug
  class starts from.
- A run that finds nobody eligible now returns an honest, empty chunk in
  one round trip, instead of 25 orchestrator invocations that were always
  going to skip — and the eligibility query itself fails loudly rather than
  treating "unknown" as "nobody," specifically to avoid reproducing the
  exact no-op-but-green failure this incident is about.
- The false "self-balancing" claim in the route's header comment was
  corrected in place to describe what the code actually does.

## Recurrence risk

**A crowd-out sequel was found 2026-08-21** (commits `eeaaadcfec`,
2026-08-21T04:05:26Z, and `4d1f33286`, 2026-08-21T05:40:24Z), in a
*separate* investigation (#1503/#1549): even with the uncomputable-player
pre-filter in place, the eligible pool itself has grown past the chunk
size — **33 eligible players vs. 25 slots, with 7 stuck**. The real
ceiling was identified as `min_rounds: 8` on genome dimensions (a stricter
data-sufficiency bar than "any completed round"), not the original
chunk-selector bug. Fix #1549 added a refusal-marker (no schema change)
rather than resolving the eligibility ceiling itself — worth treating as a
distinct, still-partially-open follow-on rather than assuming
`2e0632326` closed genome staleness permanently. Anyone relying on "genome
is fixed" as of 2026-08-17 should re-check current eligible-vs-slot counts
against production directly (not independently re-run as of 2026-08-21,
this backfill's review date) before trusting that claim today.

## Invariant candidate

Yes, and it directly targets the "green but did nothing" failure mode that
made this take six weeks to notice:

```sql
-- INV-COACHHELM-001: v3-genome-nightly should not report `completed` on
-- runs where zero golf_player_genome rows were actually written/updated.
-- Requires the job to record its own write count in `metadata` (which this
-- incident's root cause shows was previously null) — this invariant is
-- also a forcing function for that logging gap to be closed structurally,
-- not just for this one job.
select id, run_at, status, metadata
from background_job_logs
where job_name = 'v3-genome-nightly'
  and status = 'completed'
  and (metadata is null or (metadata->>'rows_written')::int = 0)
  and run_at > now() - interval '48 hours';
```

Severity: MEDIUM-HIGH. This generalizes past genome specifically: any cron
whose `metadata` is null on `completed` runs is unfalsifiable in exactly
the way this incident was, and is worth a platform-wide sweep, not just a
genome-specific fix.

**Update, 2026-08-21: this platform-wide sweep already happened, independent
of this record.** Issue #1492 ("Cron log discarded the outcome numbers: 11 of
19 job types logged metadata=null on every run, which is why a dead job
looked healthy for six weeks") — note its own title cites this exact incident
as the motivating example — was filed 2026-08-17 and fixed via `9f85cdf92`
(`extractOutcomeMetadata` now takes every bounded top-level scalar instead of
a 7-key whitelist), confirmed live in production with "today's batch promote"
per the issue's closing comment dated 2026-08-21. This is the data-side half
of `INV-COACHHELM-001` above — cron runs across 11 of 19 job types now
actually populate `metadata` with real outcome numbers instead of null. **Not
confirmed:** whether a standing scheduled check (the query above, or
equivalent) was ever wired up to run automatically and alert on a violation,
versus the fix only having closed the data-availability gap that makes such a
check possible. Treat the underlying data as fixed; treat the invariant
itself as still a manual query until a scheduled check is confirmed to exist.

## Replay candidate

Yes — this is a good candidate precisely because the fix commit already
built most of it. Minimal sanitized fixture: a synthetic player population
matching the production ratio that jammed the selector (some fraction
permanently uncomputable — no rounds in window — some fraction genuinely
eligible, sized to exceed the chunk limit), fed through
`selectGenomeRefreshChunk`. Pre-fix: selected chunk is entirely
uncomputable players. Post-fix: selected chunk contains only eligible
players, prioritized never-computed-first among them. The fix commit's own
"proven before fixed" step is materially this replay already — promoting it
into `replay/fixtures/coachhelm/` with a manifest would capture it formally
and also gives a natural home for pinning the #1503/#1549 crowd-out
follow-on as a second, related fixture (eligible-pool-exceeds-chunk-size)
once that fix is more fully resolved.

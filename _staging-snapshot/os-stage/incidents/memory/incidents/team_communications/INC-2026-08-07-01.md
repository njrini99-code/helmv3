# INC-2026-08-07-01 — Dual-squad DM leak: a private 1:1 message could be joined by anyone on the other squad sharing the same coach

- **id:** INC-2026-08-07-01
- **feature_id:** team_communications
- **first_seen:** introduced same-day by an earlier tenant-binding fix (see Root cause) — discovered and fixed 2026-08-07
- **resolved:** 2026-08-07 17:34 UTC (PR #1317)
- **severity:** HIGH (private DM read/join access crossing squad boundaries on multi-squad programs; the specific instance reproduced had no message content because the DM was empty, but the access-control mechanism was real)
- **classification:** SECURITY (primary) / FUNCTIONAL_FAILURE (secondary — a same-day regression from an earlier fix)
- **status:** resolved

## Summary

`createConversation` stamps a new conversation's `team_id` from the *creator's currently-active resolved team*, not from the actual participants. On a program running two squads under one organization with one shared coach (reproduced on Shenandoah's Men's/Women's setup), a 1:1 DM between two Women's players can end up carrying the Men's `team_id` if that was the creator's active team context at creation time. A same-day tenant-binding fix (closing a cross-**org** hole) had made the conversation's `team_id` the trust boundary for self-join — which is correct for team-chat bootstrap, but wrong for private DMs, where `team_id` can be misfiled exactly as described. The result: a Men's player could insert himself as a participant in a Women's private DM and read it.

## Root cause (verified)

The same-day tenant-binding fix conflated two different self-join scenarios that need different trust boundaries: team-chat bootstrap (where "is this your squad's team chat" is the correct and sufficient check) and private DM creation (where only the creator should ever be able to add participants). Trusting `conversation.team_id` for both was correct for the org-boundary case it was built to close and incorrect for the squad-boundary case it inadvertently opened, because `team_id` on a DM reflects the creator's active-team context, which is not guaranteed to match either participant's "home" squad on a multi-squad program.

## User impact

Reproduced directly on production data: a real cross-squad self-join succeeded. The specific DM tested was empty, so no message content was actually exposed in the reproduction — but the finding is that the access-control gate itself was broken, meaning any non-empty misfiled DM during the exposure window (same-day, hours at most, between the tenant-binding fix and this fix) was readable by the wrong squad's player.

## Repair

Self-add to a conversation now requires either: (a) the requester created the conversation — checked via a `SECURITY DEFINER` function, since a conversation's own SELECT policy denies visibility of a row the creator hasn't been added to as a participant yet, which the DM-creation bootstrap depends on — or (b) the conversation is a team chat and the requester belongs to that team. Verified directly on production with an attack + three controls (see Verification evidence). Deliberately left unchanged: the misfiled `team_id` value on the reproduced DM itself — re-stamping historical rows would require guessing which squad a two-squad conversation "belongs" to, and the new policy makes the misfiled value cosmetic (it no longer grants access either way).

## Verification evidence

Verified directly on production:
```
ATTACK   men's player self-joins women's DM ..... BLOCKED 42501
CONTROL  coach creates DM, self+other, posts .... PASSES
CONTROL  player creates DM to their coach ....... PASSES
CONTROL  coach still sees women's roster (6) .... PASSES
```
The broader dual-squad access matrix (teams, rosters, calendar events, classes, announcements) was independently confirmed already correct — this was an isolated gap in one policy, not a systemic dual-squad failure.

## Signals

No Bridge/Sentry telemetry — found by deliberate adversarial testing of a specific access pattern (dual-squad programs), prompted by awareness that the same-day tenant-binding fix might have side effects worth checking.

## Recurrence risk

**Directly caused by an earlier same-day fix for a different incident** — closing one tenant-isolation hole (cross-org) opened an adjacent one (cross-squad) because both were guarded by the same field (`team_id`) with different correct trust semantics depending on conversation *kind* (team-chat vs. DM). Any future access-control fix that introduces a new trust boundary should be checked against every *other* conversation kind/mode that shares the same guarded field, not just the scenario the fix was written for.

## Invariant candidate

Yes, narrow and cheap:

```sql
-- INV-COMMS-001: no non-participant should ever hold membership in a
-- conversation row whose participant count is exactly 2 (a DM) unless
-- they were present at creation. Detects a self-join into a DM after
-- the fact by comparing participant added_at to conversation created_at
-- with a generous tolerance window.
SELECT c.id, c.team_id, cp.user_id, cp.added_at, c.created_at
FROM golf_conversations c
JOIN golf_conversation_participants cp ON cp.conversation_id = c.id
WHERE c.kind = 'dm'
  AND cp.added_at > c.created_at + interval '5 minutes'
  AND c.created_at > now() - interval '24 hours';  -- bounded window
```
Severity: HIGH. A non-empty result within a day of any future access-control change to conversations is a strong signal the same class of gap has reopened.

## Replay candidate

Yes. A minimal synthetic fixture: one organization, two synthetic teams (squads), one shared coach, synthetic players on each squad, one DM created by a squad-A player with `team_id` deliberately set to squad-B (simulating the misfiled-context bug). Assert a squad-B player's self-join attempt is rejected post-fix, and — for regression coverage of the fix that *caused* this — assert a legitimate same-squad team-chat self-join still succeeds. Fast, deterministic, directly reuses the incident's own verification method as the fixture shape. Medium priority under extension §10-11 (auth/tenancy class).

## Status

Resolved. Worth a light follow-up: confirm no other conversations were misfiled with a cross-squad `team_id` during the gap window and non-empty at the time (the reproduction case happened to be empty; a systematic check was not documented as run).

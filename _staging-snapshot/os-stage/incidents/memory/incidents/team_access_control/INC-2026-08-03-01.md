# INC-2026-08-03-01 — Overnight audit: golf_coaches and golf_teams RLS policies with USING(true) exposed every coach's PII and every team's join code

- **id:** INC-2026-08-03-01
- **feature_id:** team_access_control
- **first_seen:** unknown exact date the vulnerable policies shipped; found and fixed 2026-08-03 via an unattended overnight audit
- **resolved:** 2026-08-03 23:22 UTC (PR #1272)
- **severity:** CRITICAL (same defect shape and severity class as INC-2026-05-27-01, this time on the golf side rather than baseball)
- **classification:** SECURITY (primary) / DATA_INTEGRITY (primary, dual-classed)
- **status:** resolved

## Summary

An overnight audit found 22 issues; PR #1272 closed 20 of them same-night, five with production-applied migrations verified by a paired control for each. The two headline findings are structurally identical to the earlier baseball tenant-isolation leak (INC-2026-05-27-01), on the golf side:

- **`golf_coaches`** — `USING (true)` on SELECT exposed 15 coaches' rows (10 emails, 3 phones) to any signed-in user. Notably, this was **invisible to the standard `rls_policy_always_true` Supabase advisor**, because that advisor only inspects INSERT/WITH CHECK clauses, not SELECT — a detection-tooling gap, not just a policy-authoring one.
- **`golf_teams`** — readable via `USING (join_code IS NOT NULL)`. Because RLS policies OR together, this exposed **every** team row and **every** join code to any signed-in user, since the policy was effectively "always true" in practice (nearly every team has a join code). Fixed by moving the lookup into a `SECURITY DEFINER` function that never returns `join_code`, with the join flow re-resolving the team server-side from the code rather than trusting a client-supplied team id.

Three further RLS findings (#1267/#1268: definer RPCs filtering on caller-supplied identity rather than `auth.uid()`), a missing INSERT policy dead-ending Lift Lab coach onboarding (#1253), and two already-merged migrations that had never actually been run (#1262) were also closed. A judgment call: `REVOKE EXECUTE` was deliberately **not** applied to `user_conversation_ids` because five RLS policies evaluate it as the querying user and revoking would have broken golf messaging outright — verified 18 messages / 3 conversations still visible after the other fixes landed.

Separately in the same batch: "Create qualifier" silently did nothing (#1270) — traced to a Base UI library quirk where an ungrouped `Checkbox.Root` registers as a form field with a `null` validity state, and `!null === true` marked all 7 roster checkboxes as permanently invalid, silently blocking form submission with no error shown (no `Field.Root` means no `Field.Error` either).

## Root cause (verified)

`golf_coaches`: an unconditional SELECT policy authored with no scoping predicate. `golf_teams`: a predicate (`join_code IS NOT NULL`) that was structurally almost-always-true given the data shape, combined with RLS's OR-together semantics across multiple policies on the same table — a narrower-looking predicate on one policy doesn't help if another policy on the same table is effectively unconditional. The detection gap (invisible to the standard advisor) is a distinct contributing cause: the tooling meant to catch exactly this class of defect only checks INSERT/WITH CHECK, not SELECT.

## User impact

Confirmed exposure by construction (any signed-in golf user could read all coach PII and all team join codes) for however long the policies were live before this audit — duration not determined in this pass, unlike INC-2026-05-27-01 where the baseline-migration date was known. Given the structural similarity and that this was caught by a similarly deliberate audit rather than a live report, the honest assessment is this class of RLS defect (unconditional SELECT policies on PII-bearing/access-control tables) went undetected by both automated advisors and testing for an unknown but likely multi-week-or-longer window on the golf side, mirroring the baseball side's ~2-month window.

## Repair

Five migrations applied to production, each verified against a paired control: `golf_coaches` SELECT scoped; `golf_teams` join-code lookup moved to a `SECURITY DEFINER` function that never returns the code, with the join flow re-resolving server-side; the two identity-filtering RPCs corrected; the missing Lift Lab INSERT policy added; the two never-run migrations actually run. `user_conversation_ids` deliberately left un-revoked, verified as still functioning correctly for the actual dependent RLS policies. Separately, the "Create qualifier" silent-failure bug (unrelated root cause, same batch) was fixed by working around the Base UI library's `null`-validity-on-ungrouped-checkbox behavior.

## Verification evidence

Each of the five security migrations paired with a control that could fail — the strongest verification discipline in this incident set alongside INC-2026-05-27-01's role-impersonation transactions. Messaging functionality explicitly re-verified (18 messages / 3 conversations visible) after the deliberate no-revoke decision on `user_conversation_ids`, to confirm that judgment call didn't silently break anything.

## Recurrence risk

**Directly confirmed as the same defect class recurring across both sports** (golf here, baseball in INC-2026-05-27-01) — same `USING (true)`-shaped mistake, same detection gap (standard advisors miss SELECT-side always-true policies), different tables. Any future RLS policy authored on a new table should be checked against the invariant below **for both sports**, not just the one being actively worked on.

## Invariant candidate

Directly reuses and extends INV-RLS-001 from INC-2026-05-27-01 — this incident is independent confirmation the same check generalizes across both products:

```sql
-- INV-RLS-001 (extended): no SELECT policy on any PII- or access-control-
-- bearing table should be unconditionally true OR true-in-practice given
-- the data shape (e.g. a predicate on a column that's populated for
-- nearly every row). The second half can't be fully automated as pure
-- SQL — a companion check should sample: for a policy's stated predicate,
-- what fraction of real rows satisfy it? A predicate satisfied by >95%
-- of rows on a sensitive table is a near-miss worth flagging even if not
-- literally `true`.
SELECT schemaname, tablename, policyname, qual
FROM pg_policies
WHERE roles @> ARRAY['authenticated']::name[]
  AND cmd = 'SELECT'
  AND qual = 'true'
  AND tablename IN ('golf_coaches','golf_teams','baseball_coaches',
                     'baseball_teams','golf_players','baseball_players');
```
Also worth fixing the detection tooling gap directly: file feedback or a workaround for the Supabase `rls_policy_always_true` advisor's blind spot on SELECT policies, since relying on manual/overnight audits to catch what a named advisor tool should catch is the recurring failure mode across both this incident and INC-2026-05-27-01.

# INC-2026-05-27-01 — Baseball cross-tenant leak: any authenticated user could read every program's full roster, join codes, and private coach↔player messages

- **id:** INC-2026-05-27-01
- **feature_id:** baseball_core (registry-adjacent: `team_access_control`)
- **first_seen:** 2026-05-27 (production baseline migration `20260527000000_prod_public_baseline.sql` shipped the vulnerable policies)
- **resolved:** 2026-07-30 (last of the six related P0s closed and confirmed applied — `baseball_coaches` org-scoping)
- **severity:** CRITICAL (five distinct RLS policy defects, all live in production for up to ~2 months, exposing PII — email, phone, GPA, SAT/ACT — team join codes, and private messages across organizational boundaries)
- **classification:** DATA_INTEGRITY (primary) / SECURITY (primary, dual-classed — this is a tenant-isolation failure)
- **status:** resolved

## Summary

The 2026-05-27 production baseline migration shipped `baseball_players_select` and `baseball_teams_select` RLS policies with `USING (true)` for the `authenticated` role — meaning any signed-in user, regardless of team membership, could read every other program's full player roster (email, phone, GPA, SAT/ACT scores) and every team's secret `join_code`. A related defect let three additional policies compare a column to itself, exposing every private coach↔player message in the database (SELECT, INSERT, and UPDATE) across team boundaries. A sixth, lower-severity gap (`baseball_coaches` email/phone readable cross-org) was found and closed last, after an audit showed zero of 74 call sites actually needed the cross-org read.

## Root cause (verified)

`USING (true)` on two SELECT policies in the initial production baseline — the simplest possible RLS mistake, shipped at initial baseline time and un-caught for two months because no test exercised RLS as a non-admin authenticated user; tests and manual QA evidently used service-role or same-org sessions that never surfaced the gap. The self-referential-column policies (enabling the message leak) are a related but distinct authoring error in the same baseline migration.

## User impact

**Confirmed live exposure, not just a theoretical hole**, for roughly two months (2026-05-27 → 2026-07-29): every authenticated BaseballHelm user — any coach or player on any team — could enumerate every other program's roster PII and join codes, and (via the message-policy defect) read/write every other team's private coach↔player messages. No evidence in this repo's records of confirmed exploitation by an actual attacker (no anomaly report), but the exposure was real and broad by construction — this was not a narrow edge case.

## Repair

- PR #1092 — migration pair authored (additive functions first, then a policy swap, explicitly sequenced so step 3 without step 2 first would cause an outage rather than a leak).
- PR #1102 — migrations applied to production; verified via role-impersonation queries inside a rolled-back transaction, not by inspection.
- PR #1105 — `baseball_coaches` org-scoping authored after a 74-call-site audit found zero call sites needed the cross-org read; used a `SECURITY DEFINER` helper specifically to avoid the infinite-recursion trap the earlier pair had already hit twice.
- PR #1124/#1129 — final application + reporting.
- Deliberately deferred: building a curated cross-org directory view for a hypothetical future recruiting-contact feature — no such feature exists today, so the fix scopes to self-or-same-org rather than speculatively re-opening a narrower hole.

## Verification evidence

The most rigorous verification in this incident set: PR #1102 measured visibility counts for three real user roles (non-member player, 8-player-roster coach, 14-player-roster owner) before and after, inside a transaction rolled back so the check was free and safe to run directly against production. All three converged to correctly-scoped counts (teams 13→1, players scoped to actual roster size, own-roster access unaffected, message counts unaffected — meaning the message policy fix didn't over-restrict legitimate access).

## Signals

No Bridge/Sentry telemetry — entirely found by manual/agent-driven security audit (`DATABASE_STATUS.md`, referenced but not itself audited in this pass), not production monitoring. This is the same pattern as INC-2026-06-30-01 and INC-2026-02-14-01: BaseballHelm's most severe incidents in this window were caught by deliberate audit, not by any production signal.

## Recurrence risk

**The infinite-recursion trap recurred within this same incident** — "that exact bug shipped twice in the tenant-isolation pair and was caught only by executing the SQL" (PR #1105's own words), referring to an inline self-referential subquery pattern in RLS policy authorship. Any future policy referencing the same table it guards must use a `SECURITY DEFINER` helper function, not an inline subquery — this is now a house convention worth codifying as a lint/review-gate rule rather than relying on each author rediscovering it by testing.

## Invariant candidate

Yes — a bounded, read-only, production-safe check that would have caught the `USING (true)` class of defect immediately after any migration:

```sql
-- INV-RLS-001: no SELECT policy on a table containing PII/tenant-scoped data
-- should evaluate to an unconditional true for the `authenticated` role.
-- Read-only: inspects policy definitions, not data.
SELECT schemaname, tablename, policyname, qual
FROM pg_policies
WHERE roles @> ARRAY['authenticated']::name[]
  AND cmd = 'SELECT'
  AND qual = 'true'
  AND tablename IN ('baseball_players','baseball_teams','baseball_coaches',
                     'golf_players','golf_teams','golf_coaches'); -- extend as needed
```

Severity: CRITICAL. A single non-empty result on a PII-bearing table should page immediately, not queue. This is a direct, general-purpose implementation of the incident's own root cause and would also have caught the `golf_coaches`/`golf_teams` `USING (true)` leaks found later (see INC-2026-08-03-01) — the same predicate, same class of mistake, different sport.

## Replay candidate

Yes, and the incident's own verification method is already most of the fixture: a synthetic multi-org fixture (2+ synthetic teams, synthetic players/coaches, no real identity) driven through the exact role-impersonation transaction pattern PR #1102 used (`SET LOCAL ROLE authenticated` + `SET LOCAL request.jwt.claims`), asserting visibility counts match the caller's own org only. Pre-fix build should show cross-org leakage; post-fix build should show correct scoping. High priority under extension §10-11 (auth/tenancy is explicitly named as a top replay class), and directly reusable for the `golf_coaches`/`golf_teams` sibling incident.

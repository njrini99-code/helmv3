# INC-2026-08-08-01 — Baseball stats import rollback: a failed snapshot meant "undo" would delete a coach's data instead of restoring it

- **id:** INC-2026-08-08-01
- **feature_id:** baseball_core
- **first_seen:** unknown exact date the discarded-error pattern was introduced; found and fixed 2026-08-08 via the same fail-open scan as INC-2026-08-08-01 (platform_observability)
- **resolved:** 2026-08-08 13:59 UTC (PR #1357)
- **severity:** MEDIUM-HIGH (data-loss on an explicit user-initiated "undo" action — the exact scenario a rollback exists to make safe)
- **classification:** DATA_INTEGRITY (primary)
- **status:** resolved

## Summary

`upsertSeasonTotalsImport`'s pre-existing-rows read doubles as the rollback snapshot that `rollbackImport` uses to restore (or correctly delete, if a row genuinely didn't exist before) each affected season stat line. The read's error was discarded, so a failed read produced an empty snapshot — indistinguishable from "no prior rows existed." A later rollback would then treat every row touched by the import as newly created by that run, and **delete** it rather than restore the totals that were actually there before. A coach undoing a bad import would lose their baseline data entirely rather than getting it back.

## Root cause (verified)

Same defect shape as INC-2026-08-08-01 (Stripe): a discarded error on a read whose empty/failure result is indistinguishable from a legitimate "nothing existed" result, which then drives destructive behavior downstream. Here the function is explicitly documented "best-effort: never throws," and that contract is preserved by the fix — a failed snapshot must not fail the whole import — but the fix makes a failed snapshot recognizably different from a genuinely-empty one, rather than silently conflating the two.

## User impact

No specific coach/import instance confirmed as having actually triggered this in available records — found via proactive scanning, not a support report. The exposure is structural and specifically activates on the "undo" path: any coach who imported season stats, encountered a transient read failure during the snapshot step (silent, no error surfaced to them), and later chose to roll back that import would have their pre-import baseline permanently deleted instead of restored. This is the same failure shape (destructive fallback masquerading as a safe undo) as the round-destruction incident already on record in `round_tracking` — see Recurrence risk.

## Repair

The snapshot read's error is no longer discarded; a failed read is now distinguishable from a genuinely-empty prior state, so `rollbackImport` cannot conflate the two and default to destructive behavior. The function's "best-effort, never throws" contract for the import path itself is preserved.

## Recurrence risk

**This is the same failure shape as this repo's most severe round-tracking incident** (a "restore on failure" contract that was false in production, destroying an already-committed round — see the round_tracking incident directory for the full record) — a fallback/rollback path that is *supposed* to be the safety net silently becoming the destructive path instead, because its own precondition-read failure was treated as "nothing to restore" rather than "restoration state unknown." Any code path with a documented "restore/rollback on failure" contract anywhere in this codebase is worth auditing for the same trap: does a failed read of the pre-state get treated as "empty" (dangerous) or as "unknown, abort the destructive branch" (safe)?

## Invariant candidate

Same general shape as INC-2026-08-08-01's INV-CODE-001 (discarded read gating a write), specialized to the rollback case:

```
# INV-CODE-002: any function whose documented contract includes "restore on
# failure" or "rollback" must never treat a failed pre-state read the same
# as a confirmed-empty pre-state — the two must be structurally
# distinguishable in the code (e.g. a tri-state result: found / confirmed-
# empty / unknown), and "unknown" must short-circuit the destructive branch.
```
Severity: HIGH — a violation of this shape is precisely what produced both this incident and the round-tracking data-destruction incident already on record.

## Replay candidate

Yes. A minimal fixture: seed `baseball_player_stats` with known prior season totals for a synthetic player, mock the snapshot read to fail during a re-import, then trigger `rollbackImport`. Pre-fix: the prior totals are deleted. Post-fix: the rollback recognizes the unknown-state snapshot and refuses to delete (or otherwise fails safe rather than destructively). This directly parallels the round_tracking incident's own replay fixture shape (destructive-fallback-on-timeout) and is worth building alongside it as a shared "destructive-fallback" test pattern rather than two unrelated fixtures. Priority: HIGH under extension §10-11 (data-loss is the top-named replay class).

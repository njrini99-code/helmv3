# INC-2026-08-17-01 — Both qualifier save paths reported "saved" on a write that matched zero rows

- **id:** INC-2026-08-17-01
- **feature_id:** qualifiers
- **first_seen:** 2026-08-17 (issue #1498 created)
- **resolved_at:** 2026-08-18 (verified fixed on `main`, issue closed COMPLETED)
- **severity:** MEDIUM
- **classification:** FUNCTIONAL_FAILURE (primary) / DATA_INTEGRITY (secondary — a silent no-op write that reports success is a data-integrity risk even without any row-level corruption)
- **status:** resolved

## Summary

Both qualifier-editing write paths (`updateGolfQualifierDetails` and `setQualifierRoundCourses`) checked only the PostgREST `error` field after an `UPDATE ... WHERE id = ...`. A PostgREST update that matches zero rows resolves `{ data: null, error: null }` — byte-identical to a successful update of an existing row. Neither function distinguished the two. `FairwayEditQualifier` then navigated the coach to the detail page as though the edit had landed; the coach only discovered otherwise on reload. The single-round edit path was the one that actually bit in practice: when `isMultiRound` is false, an empty `roundCourses` array is sent, making the `num_rounds` update the *only* write the function performs — so a silent no-op there meant the entire edit silently did nothing, with no downstream write to fail loudly instead.

## Root cause (verified)

Classic PostgREST footgun: absence of an error is not evidence of a matched row. The fix's own issue body notes this exact class of bug had already been fixed twice elsewhere in the repo (`development.ts`'s `recordFocusAreaOutcome...`, referenced but not fully quoted in the sources reviewed), meaning this was a recurring pattern, not a one-off oversight — the qualifier save paths were simply not yet covered by that established fix.

## User impact

- A coach editing a single-round qualifier (the common case, since `isMultiRound` false triggers the pure no-op path) who hit any condition causing a zero-row match (stale id, permission edge case, or similar) would be told the edit succeeded, navigate away believing it, and only discover the change never happened on their next visit to the page.
- No production frequency/count was given in the sources reviewed for this backfill — the defect was diagnosed and fixed from code inspection plus the PostgREST semantics, not from a measured count of affected saves.

## Repair

- `updateGolfQualifierDetailsImpl` now selects `id` back on the update and treats an empty result as a failure, with the reasoning recorded inline in the fix.
- The fix's own closing comment states a **follow-on was picked up in the same pass**: a sweep of "the remaining untested mutating actions... for this same 0-row-reports-success class" — meaning this fix was treated as an instance of a class, not an isolated patch, and other call sites were checked while the investigator was already in that code.

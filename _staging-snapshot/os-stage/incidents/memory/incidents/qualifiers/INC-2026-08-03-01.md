## Summary

Filed 2026-08-03 after driving the coach qualifier-creation flow against the
production build: with every required field populated (name, start date, end
date) and one player invited, clicking "Create qualifier" produced **zero
observable effect** — no POST, no row created, no error shown, button never
disabled or busy.

The filer's own investigation (documented in the issue thread, individual
comment timestamps not captured by this mining pass) was unusually rigorous
and self-correcting:

1. Ruled out the click/button itself (event fires, `submit` fires,
   `defaultPrevented` flips to `true` — the page's own handler runs).
2. Re-verified the "no POST" measurement with a control, registering the
   network listener at page load and proving it captured 6 real POSTs
   during load before trusting that it captured zero on submit.
3. Proposed, then explicitly disproved with a control, a hypothesis that
   native `required` attributes on the Base UI `<Form>` were the trigger —
   the sibling edit-qualifier form has the identical pattern and submits
   normally.

**The actual root cause, found and fixed the same day (2026-08-03) as part
of a larger 20-issue overnight-audit fix train (PR #1272), was neither of
those:** every `Checkbox.Root` in Base UI calls `useField({ enabled:
!groupContext })`, so an **ungrouped** checkbox (i.e., one not wrapped in a
`Field.Root`/`CheckboxGroup`) registers itself as a field of the enclosing
`<Form>` anyway, inheriting a default field context whose validity is
`valid: null`. The form's submit handler filters
`invalidFields = values.filter(f => !f.validityData.state.valid)`, and
`!null` evaluates to `true` — so all 7 roster checkboxes on the
qualifier-creation form counted as permanently invalid, `Form` called
`preventDefault()`, and the page's own `onSubmit` handler was never
invoked. Because there is no `Field.Root`, there is also no
`<Field.Error>`, so the failure was completely silent — exactly matching
the "the button does nothing" symptom the filer reported.

## Root cause (verified)

Base UI's `Checkbox.Root` always calls `useField({ enabled: !groupContext
})`. Wrapped in a `Field.Root`/`CheckboxGroup`, `groupContext` is set and
the checkbox does not register as an independent form field. **Unwrapped**
— as the qualifier-creation form's 7 roster-invite checkboxes were — each
one still calls `useField`, registering itself against the enclosing
`<Form>`'s field-validity tracking with no group context to suppress it.
Outside a `Field.Root`, the inherited default field validity is `valid:
null`. `Form`'s submit handler computes
`invalidFields = values.filter(f => !f.validityData.state.valid)`; since
`!null === true`, every one of the 7 checkboxes was counted as invalid on
every submit attempt, regardless of whether it was checked. `Form` called
`preventDefault()` and the component's own `onSubmit` was never reached —
which is exactly why every DOM-level signal the filer checked (button
state, native validity, `aria-invalid`) looked clean: the failure happened
entirely inside Base UI's internal field-tracking, invisible to standard
DOM inspection.

The same fix commit notes this was **not an isolated occurrence**: the
identical ungrouped-checkbox pattern was found and fixed in two task
modals in the same PR (`FairwayCreateTaskModal`, where a `type="button"`
primary action happened to dodge the failure path except via Enter-key
submission; and `FairwayCreateFromTemplateModal`, which was additionally
found to be dead code — exported from a barrel file but never rendered
anywhere).

## Repair

Commit `18e6a7cf3` (PR #1272, merged 2026-08-03T23:22:23Z), sub-commit
`fix(qualifiers): un-break "Create qualifier" — ungrouped checkboxes were
killing the form`:

- Wrapped the qualifier-creation roster checkboxes in `CheckboxGroup`,
  which sets `groupContext` and flips each checkbox's internal `enabled` to
  `false` — so they no longer register as independent `Form` fields at all,
  removing the false-invalid classification at its source.
- Same pattern fixed in `FairwayCreateTaskModal` (Enter-key submission
  path) and confirmed as unreachable dead code in
  `FairwayCreateFromTemplateModal`.
- Added a regression test asserting the outcome (the submit action is
  actually invoked) rather than internal state, specifically so it
  "re-fails for any bare Base UI control added to this form" going
  forward — confirmed red against the pre-fix component, green after.
- Verified live against the demo team, per the commit message: POST 200,
  redirect to `/qualifiers`, a row created with exactly the 2 selected
  roster entries (test row deleted afterward).

## Recurrence risk

- The fix addresses this specific form (qualifier creation) and the two
  task modals found in the same audit pass. The underlying Base UI
  footgun — any future ungrouped `Checkbox.Root` (or, by the same
  mechanism, potentially other Base UI field-primitive components) added
  to a `<Form>` anywhere else in the codebase — is not structurally
  prevented, only guarded by the new regression test on this one form and
  the two modals fixed alongside it. A new ungrouped-checkbox form
  elsewhere in the codebase would not be caught by this fix or its test.
- Not independently checked by this miner (as of 2026-08-21) whether a
  repo-wide sweep for the same pattern (`Checkbox.Root` outside
  `Field.Root`/`CheckboxGroup`, inside a Base UI `<Form>`) was performed
  beyond the three sites this PR fixed.

## Invariant candidate

Best expressed as a static/lint-time check rather than a SQL predicate,
since the defect class is a component-composition footgun, not a data
condition:

```
INV-QUAL-001 (static analysis, not SQL): flag any Checkbox.Root (or other
Base UI field-primitive) rendered inside a <Form> that is not wrapped in a
Field.Root or CheckboxGroup ancestor. This is exactly the shape that made
"Create qualifier" fail silently, and the fix commit found the identical
shape in two other components in the same audit pass — evidence this is a
recurring authoring mistake, not a one-off.
```

Severity: MEDIUM — the specific instances found so far are fixed and
tested; this predicate targets prevention of the next occurrence.

## Replay candidate

Yes, and now buildable with a known root cause and a real fix commit to
verify against: a fixture rendering a Base UI `<Form>` with an ungrouped
`Checkbox.Root`, submitted with the checkbox checked, should show pre-fix
`onSubmit` never firing (matching the original "0 POSTs" observation) and
post-fix `onSubmit` firing normally once wrapped in `CheckboxGroup`. Lower
urgency than data-loss/concurrency-class incidents per extension §10-11,
since this defect is already fixed, tested, and does not touch stored
data — but cheap to build given the mechanism is fully understood, and
valuable as a regression guard broader than the one component-level test
already added.

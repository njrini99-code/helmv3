## Summary

Six authorization gates across `tasks.ts` asked only whether the target
team belonged to the coach's **organization** — not whether the coach was
actually staffed on that specific team. Shenandoah (the same org named in
the class-schedule-leak incidents this same week) runs a men's team and a
women's team in one organization, so "does this team belong to your org"
answers yes for both. A coach staffed only on the men's team could
`createTask`, `createRecurringTask`, `createTaskTemplate`,
`updateTaskTemplate`, `deleteTaskTemplate`, and use the shared
delete/reminder resolver against the **women's** team — creating, editing,
and deleting their tasks and templates, and seeding their template
library, despite having no legitimate role on that team at all. The audit
that surfaced this had reported it specifically for templates; the actual
scope, once investigated, was all six call sites.

## Root cause (verified)

The authorization checks tested organization membership
(`golf_coaches`/org-level relationship) as a proxy for team access, which
is only correct in a single-team organization. Any org running more than
one team under one umbrella (explicitly the case here: a men's and a
women's program in one org) breaks that proxy — org membership and
per-team staffing are genuinely different questions, and five of the six
call sites conflated them.

## User impact

A coach staffed on only one team in a multi-team organization could
create, edit, and delete the sibling team's tasks and templates, with no
authorization boundary preventing it. This is a real cross-tenant write
capability on production, not a theoretical one — the audit that surfaced
it was reacting to the organization structure that actually exists in
production (Shenandoah).

## Repair

**2026-08-08 17:43:32 -0400, commit `1297b2a9f0cb6f4e584ec6feb3b974f1ea9771a7`
(#1380).** All six call sites now use the canonical **staff-strict** rule
(`golf_team_coach_staff`) — the same gate the active-team cookie already
goes through, including its documented legacy escape hatch for a coach who
predates the staff table. Five of the six call sites route through the
existing `validateCoachTeamAccess` helper. The shared delete/reminder
resolver deliberately does **not** use that helper and instead reads the
staff row inline: `validateCoachTeamAccess` returns a bare boolean, which
would silently re-collapse "the check failed to run" and "the coach is
genuinely not staffed here" into the same signal — exactly the distinction
`authorizeCoachForTask` (from `#1365`, see `INC-2026-08-08-01` in this
directory) was built to preserve. Every genuine positive/negative case
from before the fix is unchanged and pinned by the existing tests: a
properly staffed coach is still granted access, a coach on the sibling
team is still refused, a task that's genuinely gone still reports as gone.
This is tightening, not widening, an authorization boundary.

**Two mistakes the fix's own tests caught before merge**, worth recording
because they're instructive about this exact class of change:
- Swapping in `validateCoachTeamAccess` initially, silently lost the
  failed-read/genuine-refusal split added by `#1365` — the regression test
  written specifically to pin that distinction failed, catching the
  regression before it shipped.
- The retargeted test fixture initially used `noRow()` (`PGRST116`) for a
  `.maybeSingle()` read, where a genuine miss on that call actually
  resolves as `{ data: null, error: null }` — so the test was asserting
  the wrong code path (the error path) while believing it was asserting
  the refusal path. Caught and corrected before merge.

## Recurrence risk

**High as a class, given how many other multi-team-org boundary gaps this
same investigation week surfaced.** This is not an isolated defect: the
class-schedule privacy leak (`calendar_events`' `INC-2026-08-08-01`) and
the availability-overlay/roster-leakage findings (`INC-2026-08-05-01`,
`INC-2026-08-08-01`, `INC-2026-08-08-03`) were **all** found on the same
production organization (Shenandoah, men's + women's teams) in the same
roughly one-week window. The specific mechanism here (org-membership
checked instead of team-staffing) is a distinct root cause from the
RLS/query-filtering gaps in the other incidents, but the *trigger
condition* — an organization running more than one team — is the common
thread across essentially every incident discovered this week. Any new
authorization check written against `golf_coaches`'s org relationship
rather than `golf_team_coach_staff` risks reintroducing this exact gap.
Worth a repo-wide grep for org-membership-only authorization checks
outside the six sites fixed here; not performed in this investigation.

## Invariant candidate

Not directly expressible as a single SQL invariant (this is an
authorization-logic-per-call-site class, not a data-shape one). The
closest available structural guard is a code-review/lint convention: any
new coach-authorization check against team-scoped data should be required
to route through `validateCoachTeamAccess` or `authorizeCoachForTask`
(their staff-strict, error-distinguishing canonical forms) rather than a
fresh org-membership check. Not found to be enforced by any lint rule as
of this investigation — currently a documentation/convention-only
guarantee, the same category of gap that let this defect exist in five
call sites beyond the one the original audit named.

## Replay candidate

Yes, and this is one of the more directly testable incidents in this set:
stand up two teams (A, B) in one organization, staff a coach only on team
A, call each of the six fixed functions against team B, and assert every
one is refused. The fix commit's own test suite already covers exactly
this (see the two self-caught mistakes above, which were caught by tests
of this shape); confirm the full six-call-site matrix is exercised rather
than assuming coverage from the two documented near-misses alone.

# INC-2026-08-08-03 — After switching teams, task assignment and the command palette kept serving the previous squad

- **id:** INC-2026-08-08-03
- **feature_id:** team_operations (tasks roster picker; CommandPalette) — cross-references `calendar_events`' `INC-2026-08-08-03` (event map + availability overlay), same root-cause family, same investigation day
- **first_seen:** discovered 2026-08-08, same day as the calendar-side members of this family
- **resolved:** 2026-08-08 16:07:31 -0400, commit `3214527133` (#1376)
- **severity:** HIGH (a task could be written to the wrong team's players with no visible sign anything was wrong — "right task, right team header, wrong people")
- **classification:** FUNCTIONAL_FAILURE (stale client state surviving a component-prop change without remount)
- **status:** resolved for the two surfaces fixed here (see calendar_events for the other two members of the same family)
- **investigated:** 2026-08-21 (this incident-mining pass; "as of this investigation" elsewhere in this file refers to this date)

## Summary

Two independent client caches on the team-operations surface survived a
team toggle and each presented the previous squad as the current one —
the same root shape as the calendar's `#1374`/`#1378` (filed as
`calendar_events`' `INC-2026-08-08-03`), all four discovered and fixed the
same day:

1. **Task roster.** The roster-loading effect ran once, with an empty
   dependency array and an eslint-disable suppressing the warning that
   would have caught it. A program-head coach toggling between the men's
   and women's squads kept the **first** team's roster in `players` for
   the rest of the session. "Assign to all players" then wrote the new
   team's task to the **old** team's players — a compliance task landing
   on ten men who were never asked, while the six women it was actually
   for never saw it. Nothing on the page looked wrong: correct task title,
   correct team header, silently wrong recipients.
2. **Command palette.** Palette data (roster, rounds, insights) was
   fetched once on first open and cached for the whole session. A coach
   who opened the palette on the men's team, then toggled to the women's
   team, kept searching the men's roster — with the women's team name
   displayed in the header directly above the results. Jumping to a
   player from search results navigated to someone who was not on the
   currently-viewed team.

A third defect in the same commit, orthogonal to the toggle-staleness
family: the palette swallowed a failed fetch into a silently-empty result,
rendering as "a team with nobody on it" with no distinction from a
genuinely empty roster. Kept as a degrade-to-empty behavior by design
("the palette is not worth failing a page over") but now logs the failure
instead of rendering identically to a real empty state.

## Root cause (verified)

Same as the calendar-side member of this family: `teamId` is passed as a
prop to components that are not remounted on a team toggle, so any
`useState`/effect-cached value initialized once (here, via an
empty-dependency-array effect with an eslint-disable suppressing the
warning that would have flagged the missing dependency) survives the prop
change and continues to reflect the previous team. This is explicitly
**not** a data-visibility hole — RLS was never involved, and the
underlying data fetched for the new team was correct; only the client-side
cached/selected state was stale. The commit's own framing: "the worse kind
of wrong: a confident, correct-looking screen about the other team."

## User impact

A program-head coach (the specific role affected, since they're the one
who manages more than one team) could send a task to entirely the wrong
roster with zero warning signs on the page, or search and navigate to a
player who isn't even on the team currently displayed in the header.

## Repair

**2026-08-08 16:07:31 -0400, commit `3214527133f7402b79ddc4e18ccc5b377702f11e`
(#1376).**

**Tasks:** the roster is now cleared **before** the refetch, so the picker
cannot even briefly flash the previous squad's names during the reload —
"the same wrong answer in miniature," per the commit, which is why a
clear-before-refetch was chosen over a clear-after. Removing the
eslint-disable directive turned out to be safe: with it gone, eslint
correctly reports the dependency array as complete, confirming the
mount-only behavior was in fact the entire defect (no other undeclared
dependency was hiding behind the suppression). **Command palette:** the
cache is now keyed on the active team, so a team switch invalidates it;
every *other* kind of staleness the cache trades for speed (e.g., data
going stale between navigations within the same team) is left as-is —
only the cross-team case was judged unacceptable.

## Recurrence risk

Same assessment as the calendar-side member of this family: four
independent surfaces hit the identical "mount-once client state outlives
the team it was scoped to" shape in a single day, which points to this
being structural to how team-scoped client components are built across
this codebase rather than incidental to any one component. No shared
"reset-on-team-change" hook or lint rule was introduced as a result of
this incident to prevent a fifth instance.

## Invariant candidate

Not a SQL invariant (client-state class). See `calendar_events`'
`INC-2026-08-08-03` for the same recommendation: a shared
`useResetOnTeamChange` convention, enforced by lint or code review, is the
right structural fix and was not found to exist as of this investigation.

## Replay candidate

Yes: render the task-assignment picker and the command palette with
`teamId=A`, populate their respective caches, change the prop to
`teamId=B` without remounting, and assert both reset (empty roster
picker, re-fetched palette results) rather than continuing to serve team
A's data. Coverage confirmed by the passing suite referenced above, though
the specific test names for this scenario were not independently
extracted in this investigation.

## Status

Resolved for the two surfaces fixed here. See `calendar_events`'
`INC-2026-08-08-03` and its Recurrence risk for why the underlying pattern
itself should be treated as still open across the codebase.

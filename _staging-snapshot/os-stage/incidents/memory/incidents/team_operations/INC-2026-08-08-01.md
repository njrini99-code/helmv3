# INC-2026-08-08-01 — Task delete and reminder actions told genuine coaches they were not coaches, on any transient read failure

- **id:** INC-2026-08-08-01
- **feature_id:** team_operations (`deleteTask`, `setTaskReminder`, `clearTaskReminder` in `src/app/golf/actions/tasks.ts`)
- **first_seen:** discovered 2026-08-08, same investigation sweep as the other 2026-08-07/08 team_operations incidents
- **resolved:** 2026-08-08 12:13:30 -0400, commit `790316b0d` (#1365)
- **severity:** MEDIUM-HIGH (false-negative authorization: a genuinely authorized coach was refused with a confusing, plausible-sounding denial, and had no reason to retry)
- **classification:** FUNCTIONAL_FAILURE (fail-closed on read error, but with the wrong error message)
- **status:** resolved
- **investigated:** 2026-08-21 (this incident-mining pass; "as of this investigation" elsewhere in this file refers to this date)

## Summary

`deleteTask`, `setTaskReminder`, and `clearTaskReminder` each carried their
own independently-written copy of the same three-read authorization block
(coach lookup, task lookup, team-authorization lookup), and all three
copies discarded every read error. Since Supabase resolves a failed read
as `{ data: null, error }`, a dropped connection was structurally
indistinguishable from a genuine negative finding — and each read had its
own specific, plausible-sounding wrong answer ready to hand back: "Only
coaches can delete tasks" to an actual coach, "Task not found" for a task
the coach was looking directly at, "Not authorized for this team" for
their own team. None of those three messages suggests trying again, so the
coach's natural response is to stop — leaving, for example, a compliance
task they meant to remove sitting on every player's list.

## Root cause (verified)

Same mechanical root cause as `INC-2026-08-07-01` and
`INC-2026-08-08-02`/calendar's `INC-2026-08-08-02`: a discarded Supabase
`.error` resolves a failed read to the same shape as a genuine negative
result. The specific twist here is that the *direction* of the failure is
fail-**closed** (denying a genuine coach) rather than fail-open (as in the
calendar conflict-checker family) — refusing when a check cannot run is
the correct default, and the fix keeps that default. The actual defect was
that the three call sites each had their own copy of the authorization
logic, so the *wording* of the refusal drifted independently at each site
and never told the coach "we couldn't verify this" versus "you genuinely
aren't authorized."

## User impact

A coach attempting to delete a task, or set/clear a reminder on one, could
be told — with a specific, confident, wrong reason — that they were not a
coach, that the task didn't exist, or that they weren't authorized for
their own team, whenever any one of three underlying reads merely failed
transiently. The task or reminder in question then remained unchanged,
with the coach given no signal that retrying might work.

## Repair

**2026-08-08 12:13:30 -0400, commit `790316b0d28dde86c3428b86b2ca8152786ed9d1`
(#1365).** Refusing when a check cannot run is correct and preserved — only the
message changes. The three duplicated authorization blocks are replaced
with one shared resolver, `authorizeCoachForTask`, mirroring the existing
`authorizeCoachForEvent` pattern already used in `attendance.ts`, so the
honest distinction between "the check failed to run" and "you are
genuinely not authorized" is written once instead of drifting between
call sites. `.single()`'s `PGRST116` (no-row) is explicitly kept on the
genuine-refusal side of the split — "really not a coach," "task really is
gone," "task really belongs to another team," and "coach without an
organization" all retain their own exact, correct messages.

## Recurrence risk

Low for this exact surface, now that the three call sites share one
resolver instead of three independently-drifting copies. Worth noting
this is the *fail-closed* twin of the fail-open pattern documented
repeatedly elsewhere this same week (see `INC-2026-08-07-01`'s Recurrence
risk and the calendar `INC-2026-08-08-02`) — the same root mechanical
cause (discarded Supabase error) can manifest as either a false "yes" or a
false "no" depending on which branch of the calling code the empty result
feeds into. A systematic sweep for discarded `.error` values across
`src/app/golf/actions/**`, checking each site's failure *direction*
(open or closed) rather than assuming all instances are equally severe,
was not performed in this investigation.

## Invariant candidate

Not a SQL invariant. `authorizeCoachForTask` and `authorizeCoachForEvent`
are themselves the closest available structural invariant — any future
task/event authorization check should route through one of these shared
resolvers rather than reimplementing the three-read pattern independently
a third time.

## Replay candidate

Yes: mock a Supabase read failure at each of the three checks (coach
lookup, task lookup, team-authorization lookup) and assert the caller
receives an explicit "couldn't verify" response distinguishable from a
genuine `PGRST116` no-row refusal. The fix commit's own 8-assertion test
delta is this exact shape (see Verification evidence).

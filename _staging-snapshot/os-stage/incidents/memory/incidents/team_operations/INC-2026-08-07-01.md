# INC-2026-08-07-01 — Task template applied to the whole team could reach nobody; three more silent-failure-as-empty task/course reads fixed the same day

- **id:** INC-2026-08-07-01
- **feature_id:** team_operations (`src/app/golf/actions/tasks.ts` — `createTaskFromTemplate`, `completeTask`; `course-library.ts`; `task-reminders.ts`)
- **first_seen:** discovered same-day, 2026-08-07, in the same "failed-read-as-empty" sweep that also touched calendar_events (see cross-references)
- **resolved:** 2026-08-07, two commits: `eec2f647f` (20:32:59, #1330) and `b36b4747b` (14:34:12)
- **severity:** HIGH (a coach applying a compliance task template to the whole team could be told it succeeded while the task was assigned to nobody; a player's own task completion could be silently discarded and reported back to them as "you are not assigned to this task")
- **classification:** FUNCTIONAL_FAILURE (fail-open on read error, resolving to false success or false denial)
- **status:** resolved
- **investigated:** 2026-08-21 (this incident-mining pass; "as of this investigation" elsewhere in this file refers to this date)

## Summary

Two commits, same day, same defect *shape* ("failed-read-as-empty" — a
discarded Supabase read error resolves to an empty result, which the
caller then treats as a genuine, complete answer) applied across four call
sites in the tasks/course-library surface:

1. **`createTaskFromTemplate`** (`#1330`) resolved "all players" **after**
   creating the task, and discarded the roster read's error. An empty
   `playerIds` then skipped the `playerIds.length > 0` assignment guard,
   and the action still returned success — a coach applying a compliance
   template to the whole team saw it succeed while the task sat assigned
   to nobody. The commit calls this "identical defect, identical shape" to
   the announcement-tasks bug fixed the same day (`#1372`, see
   `INC-2026-08-08-02`).
2. **`completeTask`**'s membership check (`#1330`, same commit) needed
   more care than a simple error-check: `.single()` reports "no such row"
   as `PGRST116`, which must be told apart from a genuine read failure.
   Discarding the error meant any transient failure told a player who
   *was* actually assigned that they were not, and their completion was
   silently thrown away.
3. **`course-library.ts`**'s strict loader (`b36b4747b`) had its own
   docstring stating it exists so a failure "can't masquerade as 'this
   team has saved nothing yet'" — but that guarantee covered only its
   *first* read. Its second read (resolving each saved row's course) had
   the error discarded; the mapper dropped any row whose course
   resolution failed, so a failed courses read emptied the map and
   rendered exactly the false-empty state the strict variant existed to
   prevent.
4. **`task-reminders.ts`**'s coach and player identity lookups
   (`b36b4747b`, same commit) discarded their errors, and a null id is not
   neutral in the filter that consumes it — it fails every clause. One
   failed identity lookup silently dropped every reminder the user had,
   returning an empty list with no error, while the reminders read itself
   (which *was* error-checked) made the query look healthy throughout.

## Root cause (verified)

Supabase-js resolves a failed read as `{ data: null, error }` rather than
throwing; every one of these four call sites destructured only `.data` (or
treated an empty result as unconditionally genuine), so a real read
failure was indistinguishable from "the query legitimately found nothing"
at the point each result was consumed. This is the same mechanical root
cause documented for the calendar's conflict-checker family
(`INC-2026-08-08-02` in the `calendar_events` directory) — the pattern
recurred across at least two features (calendar, tasks) in the same
one-week window, discovered independently in each.

## User impact

- A coach applying a task template to the whole team could see a success
  confirmation while the task reached zero players.
- A player who genuinely completed an assigned task could have that
  completion silently rejected with a message implying they were never
  assigned to it, on a transient read failure.
- A coach's saved-course library could render as empty ("you haven't saved
  any courses") on a transient failure, indistinguishable from a
  genuinely empty library — with nothing logged anywhere to tell the two
  apart.
- A user's task reminders could silently vanish (empty list, no error) on
  a failed identity lookup, while the actually-checked reminders read made
  the request look entirely healthy.

## Repair

Two commits, both 2026-08-07: `b36b4747bdb94173e2ec86d966278456be3abdc6`
at 14:34:12 -0400 (course-library + task-reminders reads), and
`eec2f647fed13f2d370eef9fd12176dcae6249d3` (#1330) at 20:32:59 -0400
(task-template + completeTask).

`createTaskFromTemplate` now resolves the player roster **before**
creating the task, so a failure costs nothing (nothing is created, and the
returned message says so) instead of creating an orphaned, unassigned
task. `completeTask` explicitly distinguishes `PGRST116` (genuine no-row)
from a real read failure. `course-library.ts`'s second (course-resolution)
read now throws on failure like the first; its sibling lenient reader
(feeding the course picker's Saved tab) keeps its leniency by design — "a
degraded tab beats a broken picker" — but now logs every failure path
instead of rendering silent emptiness with nothing written down anywhere.
`task-reminders.ts`'s identity lookups now surface their errors rather
than feeding a null id into a filter that would silently exclude
everything.

## Recurrence risk

This is one of at least three independent instances of the same
"discarded Supabase error resolves to a false empty/success result"
pattern found across two features in the same week — see
`INC-2026-08-08-02` (calendar conflict checker, calendar_events) and this
directory's `INC-2026-08-08-02` (announcement-attached tasks) for the
other members. No shared lint rule, code-review checklist item, or
`supabase-js` wrapper enforcing "always destructure and check `.error`"
was found to have been introduced as a structural fix across all
instances — each was fixed at its own call site. A systematic grep for
`.data` destructuring without an adjacent `.error` check across
`src/app/golf/actions/**` was not performed in this investigation and
would likely surface more instances of the same shape.

## Invariant candidate

Not a SQL invariant (error-handling code pattern). The most direct
structural fix would be a lint rule (ast-grep, given the repo already uses
ast-grep-based custom rule packs per `.claude/rules/code-review-tooling.md`)
flagging `const { data } = await supabase...` destructuring patterns that
never reference the corresponding `error` binding in the same scope. Not
found to exist as of this investigation.

## Replay candidate

Yes, for all four call sites: mock a Supabase read failure at each of the
four points and assert the caller surfaces an explicit failure/error
rather than a false empty or false success. Both commits' own test deltas
are exactly this shape (see Verification evidence) — treat those as the
replay fixtures.

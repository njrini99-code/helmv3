# INC-2026-08-08-02 — Tasks attached to an announcement were never created: wrong column name, silently swallowed, reported as success

- **id:** INC-2026-08-08-02
- **feature_id:** team_operations (`golf_announcement_tasks` insert path in the announcements action, `createTask`-adjacent code)
- **first_seen:** date unknown; production `golf_announcement_tasks` had 0 rows at investigation time, "equally consistent with 'the insert always failed' and 'nobody has used the feature yet'"
- **resolved:** 2026-08-08 14:27:19 -0400, commit `ed246c64a` (#1372)
- **severity:** HIGH (a coach was told a compound "announcement + tasks" action fully succeeded while the task half silently did nothing; explicitly acknowledged unknown blast radius, not claimed as zero)
- **classification:** FUNCTIONAL_FAILURE (schema-drift insert failure, silently swallowed)
- **status:** resolved
- **investigated:** 2026-08-21 (this incident-mining pass; "as of this investigation" elsewhere in this file refers to this date)

## Summary

The insert for tasks attached to an announcement named a column
`created_by`. `golf_tasks` has no such column — it has `assigned_by`,
which is what the plain `createTask` path (`tasks.ts:312`) correctly
writes. Postgres answered `42703 undefined_column`; supabase-js resolves
that as `{ data: null, error }` rather than throwing, and the error was
discarded. `insertedTaskIds` therefore came back empty, which skipped
*both* the announcement-link insert and the player-assignment insert via
a `.length > 0` guard — and the action still returned success. A coach
composing "read this, then do these three things" was told it all went
out; not one task actually existed, and nothing was logged anywhere,
so there was nothing to find the failure by after the fact.

A second, compounding defect in the same insert: `status` was hardcoded to
`'active'`. The column is free text defaulting to `'pending'`, and every
other writer and reader in the codebase uses `'pending'` — had the
column-name bug not masked it, an `'active'`-status row would have
inserted successfully and then been **invisible to the tasks list**, the
same failure one layer later, just with different symptoms.

## Root cause (verified)

A hardcoded column name in the insert payload (`created_by`) did not match
the live schema (`assigned_by`), verified against the live table directly
rather than against the generated TypeScript types (the commit explicitly
notes this distinction — the generated types could plausibly have been
equally wrong). The resulting Postgres error was silently discarded by the
standard supabase-js `{ data, error }` pattern, and the empty-result guard
downstream treated "the insert returned nothing" as "there was nothing to
insert" rather than "the insert failed."

## User impact

A coach using the "announcement with attached tasks" compound action saw a
single success confirmation covering both halves, while only the
announcement itself was ever created. The player-facing result: no task
was ever visible, and the coach had every reason to believe one had been
sent — "a player who never saw a task and a coach who assumed they had
ignored it." The commit explicitly declines to claim a specific blast
radius: `golf_announcement_tasks` had 0 rows at investigation time, which
is equally consistent with "this insert always failed" and "nobody has
used this feature yet" — the code defect is certain; the number of
affected coaches is not, and is not claimed.

## Repair

**2026-08-08 14:27:19 -0400, commit `ed246c64a9a2ea0540c5d3d68814f0105e338eab`
(#1372).** Corrected column name (`assigned_by`, matching `createTask`'s existing
pattern) and `status` default (`'pending'`, matching every other
writer/reader). All three inserts in this compound action (task creation,
announcement-link, player-assignment) now report their own failure
explicitly, because the commit identifies three distinct confusing ways
this can still go wrong even with the schema fixed: no tasks created at
all; tasks created but orphaned from the announcement that explained them;
or — judged the worst of the three — tasks created and linked, so the
coach sees them in the list, but never actually reaching any player,
leaving a completion count that reads "0/0" and looks finished rather than
broken. None of the three failure paths aborts the announcement itself,
since by the point any of them could be detected the announcement's own
row is already committed — throwing at that point would leave the
announcement sent with no path to retry just the tasks.

## Recurrence risk

Same mechanical family as `INC-2026-08-07-01` (this directory) and the
calendar-side `INC-2026-08-08-02` — a discarded Supabase `.error` resolves
a failed write/read into a false-success or false-empty result. This
specific instance is a **write-path** version of the pattern (most of the
others found this week were read-path); worth noting that a schema-drift
write failure is strictly more dangerous than a schema-drift read failure,
since the write path had no compensating signal at all (not even a wrong
answer to notice — just silence and a green checkmark). The commit's
explicit refusal to guess a blast radius, rather than claiming zero
impact, is worth preserving as the honest framing rather than being
rounded up to "confirmed no impact" in any future summary of this
incident.

## Invariant candidate

```sql
-- INV-TASK-001: golf_announcement_tasks should never have fewer linked
-- task rows than the announcement's stated task count implies, and no
-- golf_tasks row created via the announcement-attachment path should
-- carry status != 'pending' at creation. Both are structural regressions
-- of this exact defect if either check fails after a schema or insert-
-- path change.
```

A more general invariant, applicable repo-wide given how many incidents
this week trace to the same mechanism: any insert into a table with a
known, enumerable column set should fail loudly (not resolve to an empty,
silently-swallowed result) when the payload names a column that doesn't
exist — this is a class of defect a stricter Supabase client wrapper or a
CI schema-conformance check against literal insert payloads could catch
before merge, not just at runtime.

## Replay candidate

Yes: call the announcement-with-tasks compound action with a valid payload
against the real (or a schema-matching test) `golf_tasks` table and assert
all three inserts (task, link, assignment) actually produce rows, not just
a `success: true` response. The fix commit's own 6-assertion test delta is
this exact shape.

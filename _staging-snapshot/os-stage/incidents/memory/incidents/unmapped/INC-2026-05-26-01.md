## Summary

Three compounding defects, all discovered and fixed together on 2026-08-19,
but with roots dating back to the generator's original 2026-05-26 commit:

1. **The enum generator silently dropped 12 of 18 enums for ~3 months.** A
   regex bug in `extractEnums()` failed on multi-line enums using a
   leading-pipe format, and a `lastIndex` bug swallowed the indentation of
   whatever enum followed a match — so the block shipped **6 enums**,
   stamped `DO NOT EDIT — regenerated`, indistinguishable from a correct
   output. Nothing checked the extracted count against a sanity bound.
2. **59 documented database identifiers did not exist in production** —
   `memory/glossary.md` and multiple `memory/features/*.md` files named
   tables, views, and functions verified absent via direct `pg_class`/
   `pg_proc`/`pg_type` queries, but rendered with full columns, foreign
   keys, and RLS policy names — formatted identically to real entries, so a
   reader (human or agent) had no signal to distinguish fiction from fact.
   Worst offenders: 10 non-existent calendar tables, and 33 lifting tables
   documented under the wrong family name (a migration had completed
   renaming them, but the doc still called the new names "unsynced twins"
   of a legacy name that no longer existed).
3. **No gate could catch either problem.** `docs:check` re-runs the same
   (buggy) generator and diffs its output against itself — structurally
   incapable of catching a bug in the generator, since the generator is
   both the thing being checked and the thing doing the checking.

## Why "6 months" in some framings vs. this incident's ~3-month first_seen

The task brief that prompted this mining pass described this as "~6
months." The verified git history shows the generator itself was born
2026-05-26 (local) / 2026-05-27 (UTC), making the enum-dropping bug's
actual lifespan **exactly 85 days (2.8 months / 12.1 weeks, computed by
calendar-day subtraction — holds under either the local or UTC date pair,
since both commits cross the UTC boundary the same direction and the
85-day gap is unaffected)** — the "~6 months" figure does not match the
`regen-docs.mjs` commit history found in this repo and is not repeated in
this incident's `first_seen`/`resolved_at` fields. Flagging the discrepancy
rather than silently adopting either number, per this repo's own
documentation-hygiene rule ("never document a table, column, or path you
have not just verified" — `.claude/rules/shipping.md` §1).

## Fix (2026-08-19 local / 2026-08-20 UTC, `d24524e42`; test-locked 2026-08-20, `801b5ea29`)

- `extractEnums()` fixed to handle multi-line/leading-pipe enums; an
  assertion now emits the extracted count so future drift is loud, not
  silent. Verified: 18 enums extracted (was 6).
- New `scripts/check-doc-schema-drift.mjs`: queries `database.ts` (the real
  source of truth) against every sport-prefixed identifier named in the
  docs, fails CI on any NEW phantom, and ratchets the known-59 baseline
  toward zero (`.doc-schema-baseline.json`) — this is the gate that makes
  defect #3 above structurally impossible to repeat, unlike defects #1/#2
  which were one-off corrections.
- Wired into `.github/workflows/ci.yml` as "Check knowledge base against
  the schema," ordered after typecheck.
- `memory/glossary.md`, `memory/features/calendar-events.md`,
  `memory/context/baseballhelm-database.md`, and `CLAUDE.md` all corrected
  with the verified counts/facts and a trust-tier framing (AUTOGEN blocks
  authoritative, hand-written narrative a "hint only").

## Why this is a `TELEMETRY_DEFECT`, not just a docs bug

The extension spec's `TELEMETRY_DEFECT` classification exists for exactly
this shape: a signal (the AUTOGEN enum block) that LOOKS authoritative
("DO NOT EDIT — regenerated") but was silently wrong, and the reader (an
AI agent operating from these docs, per this repo's entire `CLAUDE.md`/
`AGENTS.md` routing model) had no way to distinguish it from ground truth.
CLAUDE.md's own header, written in response to this incident, states the
lesson directly: "A 'DO NOT EDIT — regenerated' stamp is not evidence of
correctness. That exact stamp sat on an enum block that reported 6 of 18
enums for ~6 months because the generator's regex silently dropped the
rest." (Note: CLAUDE.md's own header uses the "~6 months" figure this
incident's evidence section above could not independently verify against
`regen-docs.mjs`'s actual 2026-05-26 birth commit — recorded as a
discrepancy, not corrected here, since this incident doc is not the place
to edit CLAUDE.md.)

## Invariant candidate

**INV-DOCS-001** — already effectively implemented by
`check-doc-schema-drift.mjs` and the extraction-count assertion added in
the same fix. Recorded here for completeness rather than as a new
recommendation: any future AUTOGEN-block generator should assert its
extracted-item count against an independent ground-truth count (e.g.,
`grep -c "CREATE TYPE"` against the schema) at generation time, not merely
diff itself against its own prior output.

## Replay candidate

Not built in this pass. A natural fixture: a small multi-line/leading-pipe
enum definition (synthetic, not real schema) run through both the
pre-fix and post-fix `extractEnums()` implementations, asserting the
pre-fix version under-counts and the post-fix version matches ground
truth. `801b5ea29` ("lock the enum extractor shapes") may already
constitute this as a regular test rather than a `replay/` fixture — not
independently verified against the `replay/` directory shape in this pass
since that directory did not exist at mining time.

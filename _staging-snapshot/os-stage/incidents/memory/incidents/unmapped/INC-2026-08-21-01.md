## Summary

Owner screenshots of production on an actual iPhone Safari surfaced text
that was "nearly invisible" — stuck at its scroll-reveal hidden state. That
single report led to a systematic sweep across all landing/marketing motion
code, which found **three independent root causes**, two of them
timing/race-dependent on mobile scroll behavior and one **fully
deterministic** (would reproduce on every single mobile page load, no race
involved):

1. **#1582** — reverted an August 19 marketing copy rewrite (jargon back to
   coach-speak) and fixed two separate root causes behind a qualifier-card
   animation defect.
2. **#1583** — the `Reveal`/`useSequence` and `[data-reveal]`/`[data-fx]`
   custom (non-GSAP) scroll-reveal systems could permanently strand an
   element in its hidden state if the one scroll frame where it crossed the
   reveal threshold was never sampled — a real risk on iOS Safari, which
   coalesces `scroll` events heavily during a fast fling.
3. **#1584** — a sweep of all 11 landing GSAP scene files (prompted by
   #1582/#1583) found **two more**, structurally different, defects: a
   masked-word reveal scheduled directly on a scrubbed timeline (freezes
   mid-scrub on any resting scroll position), and a mobile dock-scene
   readout animated on `opacity` alone while hidden via `autoAlpha`
   (`visibility: hidden` + `opacity: 0`) — a tween that only touches
   `opacity` can never clear `visibility`, so the element was **guaranteed
   invisible on every single mobile load**, not intermittently.

## Root cause (verified) — three distinct mechanisms

**#1583 — sampled-frame scroll reveal.** The GSAP scrub-based scenes
(`coachHelmDeepScene`, `derivationScene`, `dockScene`, etc.) already
followed the codebase's own established rule (never bare `opacity` on a
scrubbed timeline; always the `arrive()` helper's `autoAlpha` snap) and
were immune to this specific bug — `scrub: 1` runs a continuous
RAF-driven interpolation, so it structurally cannot miss a threshold
crossing. The two **custom, non-GSAP** reveal systems were not immune:
`Reveal`/`useSequence` (`components/landing/motion.tsx`, used on `/`,
`/about`, `/pricing`) hides via `clip-path` and reveals only on a scroll
frame where a rect-based `visibleFraction()` sample crosses a threshold;
`[data-reveal]`/`[data-fx]` (`useProductsEffects.ts`, used on `/products`)
hides via `opacity` and reveals via IntersectionObserver / scroll-sampled
rect checks. Both decide "reveal now" only on a scroll frame where the
element happens to be *sampled* crossing the threshold. iOS Safari
coalesces `scroll` events sparsely enough during a fast fling — and
IntersectionObserver has a documented history of not re-firing against the
dynamic toolbar's viewport resize — that the one frame where an element
crosses the reveal point can go entirely unsampled: the element jumps
straight from "below the fold" to "already scrolled past" with no callback
firing in between, and stays hidden for the rest of the session.
`useProductsEffects`'s `runFx` had the identical bug from the opposite
direction: its early-return explicitly *skipped* `[data-fx]` elements
already scrolled past on the first sampled frame, so they never got marked
done and never revealed at all.

**#1584, defect 1 — masked-word reveal on a scrubbed timeline.**
`coachHelmDeepScene.ts`'s "3.2 three-putts per round" symptom sentence used
masked-word text (legible only at `yPercent 0` or `110`, per the
codebase's existing `primitives.ts` convention for this pattern) but
scheduled it directly on the card's **scrubbed** cascade timeline
(`tl.to(symptomWords, ..., 0)`). Any scroll position landing mid-tween
freezes the sentence sliced through its own line boxes, illegible.
Mobile Safari's momentum scrolling settles on arbitrary intermediate
positions far more often than a desktop wheel does, making this
substantially more likely to be hit on mobile.

**#1584, defect 2 — `autoAlpha` set, `opacity`-only reveal.** On mobile
(`compact: true`, no wiring lines), `dockScene.ts` hid each program
surface's readout with `gsap.set(l.readout, { autoAlpha: 0, y: 10 })` but
revealed it with a tween touching only `opacity`. `autoAlpha` sets
`visibility: hidden` alongside `opacity: 0`; a tween that only animates
`opacity` never clears `visibility`, so the readout reached `opacity: 1`
while remaining `visibility: hidden` — **permanently invisible on every
mobile load, deterministically, not a timing race at all.**

## User impact

- Real headline and CTA copy on the public-facing marketing site
  (AboutView's "The Problem" heading, a CoachHelm feature-explanation card,
  and dock-scene program readouts) was rendering invisible to real mobile
  visitors — this is top-of-funnel marketing content, so the impact is
  direct: visitors who never see the pitch don't convert.
- The `dockScene` defect (#1584) affected **every** mobile page load
  deterministically, not intermittently — the most severe of the three in
  terms of guaranteed reach, even though it was found third.
- The scroll-sampling defect (#1583) is probabilistic (depends on scroll
  speed/pattern actually skipping the reveal frame), so exact affected-user
  count is not knowable from the sources reviewed — but iOS Safari's fast
  fling behavior makes it a real, recurring condition, not a rare edge
  case, per the fix's own reasoning about why this reproduces.
- Caught only because the owner happened to personally screenshot
  production on a real device — none of these three defects triggered any
  automated signal (error, Sentry event, or otherwise), consistent with
  this being a purely visual/behavioral regression with no exception thrown
  anywhere in the stack.

## Repair

- **#1582**: Aug-19 copy reverted, byte-verified against the pre-rewrite
  text (not a re-write from memory); jargon replaced with coach-speak;
  qualifier-card animation's two separate root causes fixed in the same PR.
- **#1583**: both custom reveal systems now also settle an element the
  moment it has scrolled fully above the viewport (`rect.bottom <= 0`)
  without ever having revealed — by definition the reader is already past
  it, so nothing is lost by showing it immediately rather than leaving it
  hidden indefinitely. Scroll animation still adds polish (wipe, rise) but
  can no longer *gate* legibility. `prefers-reduced-motion` was confirmed
  already unaffected on both paths (neither system hides anything under
  it) — verified by test, not assumed. This is a **shared-primitive fix**,
  so it closes the gap everywhere both systems are used, not just the two
  originally reported spots: `Reveal`/`useSequence` covers AboutView ("The
  Problem" + Our Principles), FeatureSections, FinalCTASection, TeamSection,
  PricingView, StatsShowcase; `[data-reveal]`/`[data-fx]` covers
  ProductsLanding intro, the CoachHelm card, FinalCta, LiveRound,
  ProductsIntro, StatsTicker, TeamManagement.
- **#1584**: `coachHelmDeepScene.ts`'s masked-word reveal moved onto its
  own paused, clock-based timeline played by a plain
  `ScrollTrigger.create({ onEnter, onRefresh })` — matching the pattern
  already shipped for `coachHelmScene`/`thesisScene`/`openingScene`'s own
  masked reveals, rather than inventing a new pattern.
  `dockScene.ts`'s mobile readout tween changed from animating `opacity`
  to animating `autoAlpha` directly, so the property that hides the
  element is the same property that reveals it.
- **Full sweep performed, not assumed sufficient after 3 fixes**: all 11
  landing scene files checked (6 under `components/landing/scenes`, 5 under
  `components/products/landing/scenes`). The other 9 confirmed clean:
  `heroScene`/`thesisScene`/`openingScene`/`coachHelmScene`'s masked
  reveals already used the correct clock+`ScrollTrigger.create` pattern;
  `statsScene`/`derivationScene`/`coachHelmScene`'s panel arrivals go
  through `arrive()`, which snaps `autoAlpha` consistently; `captureScene`/
  `captureLoopScene`/`pinScene` each use one property (`opacity` XOR
  `autoAlpha`) consistently between their initial `.set()` and their
  reveal tween.

## Recurrence risk

- The class of bug (a reveal-hide pair using mismatched or
  scroll-frame-dependent mechanics) is now guarded by shared primitives
  for the two custom systems (#1583) and by explicit pattern-matching to
  the established `arrive()`/masked-word conventions (#1584) — a future
  scene author following the same conventions should not reproduce these
  specific defects. There is no automated lint/check confirmed in the
  sources reviewed that would catch a *new* scene file mixing `opacity`
  and `autoAlpha` inconsistently, or scheduling a masked-word reveal
  directly on a scrubbed timeline again — the sweep was manual, and a
  twelfth scene file added later would need the same manual check repeated
  unless a lint rule captures it (see Invariant candidate).
- The `unmapped` feature-registry gap is itself a standing recurrence risk
  in a different sense: without a registry entry, this surface has no
  `required_docs`/`required_checks` gate, so a future change here would not
  automatically trigger the feature-awareness review this backfill's own
  campaign relies on for other features.

## Invariant candidate

Not a SQL invariant — this entire incident is client-side rendering logic
with no database component. The better-suited control is a **static/lint
check** rather than a runtime one:

- A lint or `ast-grep` rule (consistent with this repo's existing custom
  rule packs under `.coderabbit/ast-grep/`) asserting that any GSAP
  `gsap.set(...)` call using `autoAlpha` on an element is matched by a
  subsequent tween on that same element also touching `autoAlpha` (not
  `opacity` alone) — this directly targets #1584 defect 2's exact shape
  and is cheap to check statically without running the animation at all.
- A second rule flagging any `tl.to(...)` call inside a function whose
  timeline is constructed with `scrub:` where the target is one of the
  masked-word helper's known elements — targets #1584 defect 1's shape.

Recommend filing this as a follow-up for whoever owns the ast-grep/semgrep
rule packs, since it's a better fit than the invariant registry (which per
extension §8-9 is specifically for read-only *production data* checks).

## Replay candidate

Marginal. These are visual/CSS-timing bugs best caught by the component
tests already added (#1583, #1584), which are effectively replay fixtures
already — synthetic scroll-frame sequences and property-mismatch assertions
with no real user data involved. Per extension §10-11's stated priorities
(data-loss, auth/tenancy, silent statistical corruption, concurrency,
offline reliability, critical workflows, major CoachHelm reasoning
failures), a marketing-site visibility bug ranks low — no data or
correctness risk, purely presentational. Not recommending a dedicated
`replay/` fixture beyond the test coverage already landed.

## Summary

The CRM engagement-scoring matview refresh was scheduled at a 5-minute
cadence from the moment CRM Phase 1 shipped (`ab11f3c21`, 2026-04-28,
"foundations, engagement scoring, timeline, segments") through
2026-08-20 — **288 full matview rebuilds per day**, for a sales/CRM dashboard
the fix commit describes as having "one viewer." The cadence survived a
2026-05-26 cron-load reduction pass (`b29dda6d6`, "ops: reduce cron load to
test Vercel deploy block") and a 2026-07-09 defect-sweep wave
(`11180c543`) that both touched `vercel.json` without catching this one.

Fixed 2026-08-20 (`e75be41d5`) after the owner, on seeing the schedule,
called it "crazy": first changed to hourly (offset :10 from the :00
reminder crons), then to every 4 hours (6 rebuilds/day) per explicit owner
follow-up in the same commit — a 48× reduction from the original cadence.
The commit notes the change only takes effect at the *next* production
deploy, since `vercel.json` crons are read at deploy time.

## Lineage — the fix uncovered a second, distinct defect

The 2026-08-21 Bridge audit (`w-audit-6`, per `/tmp/claude/night/ledger.md`)
found that `cron-registry.ts`'s contract still stated the OLD 5-minute
cadence after the schedule itself had already moved to 4 hours. Because
nothing checks the registry's stated cadence against `vercel.json`'s actual
schedule, the Bridge computed "overdue" by comparing the real ~164-minute
last-refresh age against the wrong 5-minute expectation — a perpetual false
"overdue" flag on a job that was in fact running exactly on schedule. This
is a distinct root cause from the cost regression above (a stale
cross-file contract, not a scheduling mistake) but was only discovered
*because* of this incident's fix — recorded here as the second sighting in
the same lineage. **This second defect's fix (F26, extending the cron
cadence contract test) was still in flight as of the 2026-08-21 audit** —
per the sibling window's ownership, its resolution is not confirmed in this
pass.

## Why this belongs in the TELEMETRY_DEFECT family

The false-"overdue" artifact is exactly the shape the extension spec's
canonical `TELEMETRY_DEFECT` example describes: a monitoring/contract layer
reporting a problem that does not exist because two independent sources of
truth (the actual cron schedule vs. the registry's stated expectation) were
allowed to drift apart with nothing checking they agree. It is a different
mechanism from the `resolved`-column drift documented in the flagship
incident (`INC-2026-07-01-01.md`), but the same failure *class*:
"the dashboard's belief about a system's state and the system's actual state
have no enforced agreement."

## Invariant candidate

**INV-CRON-001** (candidate): a contract test asserting that every cron
schedule declared in `vercel.json` matches its stated cadence in whatever
registry/config declares "how often should this run" for Bridge-freshness
purposes (`cron-registry.ts` per the audit finding). Per the 2026-08-21
ledger this is exactly what F26 was scoped to add — recorded here as
confirmation the invariant is warranted, not as evidence it shipped.

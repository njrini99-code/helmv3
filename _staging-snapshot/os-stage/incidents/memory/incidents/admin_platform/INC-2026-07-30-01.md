## Summary

For roughly three weeks, Inngest — the durable job/retry layer behind round
analysis and other background work — was credential-broken against
production, and round analysis ran inline with no retry instead. The failure
was correctly classified by the code as a configuration/credential problem
(not a bug) essentially the whole time, which is precisely why it sat
unfixed for three weeks: every triage pass that touched it explicitly
decided NOT to fix it and move on to something else, because "it's an env
var, not a code defect" reads as lower-urgency than it actually was — this
was a real outage of a durability guarantee (retries on transient failures),
not merely noisy telemetry.

## Root cause

`INNGEST_SIGNING_KEY` (and/or the event key) was mismatched between Vercel's
production environment and the Inngest app's configuration. This is a
credential/config problem, not a code defect — confirmed by every commit
that touched it treating it as such. **What is not established in this
pass:** exactly what caused the mismatch to begin on 2026-07-30
specifically (a key rotation on one side without the other? a new Inngest
app/environment created without carrying the key forward?) — no commit in
the window explains the triggering event, only its discovery and eventual
fix.

## Why this is a process incident, not just a config incident

The interesting failure here is not "a credential was wrong" — that happens.
It's that the platform correctly and repeatedly classified this as
low-urgency ("just an env var") precisely because the observability layer
was working as designed (sighting #2 shows real engineering effort going
into making sure the *symptom* wasn't scary), while the actual business
impact — a durability/retry guarantee silently absent from round analysis
for three weeks — never got its own tracked severity commensurate with what
it meant. "Correctly classified as non-actionable-by-code" and "not urgent"
are different judgments that got conflated here.

## Invariant candidate

**INV-CRON-003** (candidate): background_job_logs (wired into all 14 cron
routes per `d86b6b0a3`, 2026-07-02) or an equivalent durable-job health
check should distinguish "a job ran and failed" from "a job's execution
layer itself is unavailable" (i.e., Inngest rejecting every event), and the
latter should have its own severity tier independent of how noisy or quiet
the resulting telemetry looks — so "the durability guarantee is currently
absent" cannot be deprioritized simply because the credential-failure
messages themselves were successfully made non-scary.

## Registry gap

Inngest has no entry under `memory/registry.yml`'s `integrations:` block
(which lists `github_actions`, `vercel`, `sentry`, `datadog` — not
`inngest`), despite being load-bearing for durable background work across
multiple features. Recommend adding an `inngest` integration entry pointing
at `src/app/api/inngest/**` and the cron routes that dispatch through it.

## Summary

The event-reminders cron (`src/app/api/cron/event-reminders/route.ts`) shipped
on **2026-04-28** as part of a same-day feature wave: `8a5dad192`
("feat(calendar): cron reminders fan out to push + email"), alongside
`1707906cf` ("align attendance schema, enforce RSVP deadline, ship reminders
+ roster tools") and `aafef456b` ("coach-of-team auth gate, drop orphan rsvps
table, dedupe types"). The cron then produced 876 error-severity rows over
the following 11 days (through 2026-05-08) before going completely quiet —
confirmed dead in production, zero recurrence in the **104 days (2026-05-08
→ 2026-08-20, computed)** to the 2026-08-20 audit.

**Root cause not established in this pass.** No commit between 2026-04-28 and
2026-05-08 specifically touches `event-reminders/route.ts` — the next commit
that references it after the launch wave is `47787751a` (2026-05-06,
"fix(build): pin ai dep + add ambient shim; sweep remaining drift"), which is
a general build-dependency fix, not an event-reminders-specific change. That
means either:

- the failure was config/data-shaped (e.g., malformed attendance/RSVP rows
  from the same-day schema work in `1707906cf` that gradually cleared as
  clean data replaced bad rows), or
- an infrastructure-level fix (a build/dependency issue, matching the
  timing of `47787751a`) incidentally resolved it, or
- it self-resolved as a race/timing issue in the newly-shipped fan-out logic
  stopped triggering once initial backlog drained.

This is a genuine gap, not a confirmed diagnosis — flagged for anyone who
wants to pull actual `error_logs` sample rows for this window (not done in
this read-only mining pass; the 2026-08-20 audit that surfaced this fingerprint
only pulled the aggregate count, not samples, since it was already
long-dead).

## Why this is worth a durable record despite being fully dead

The event-reminders cron has a documented history of **shipping broken and
being fixed in slow motion** — three separate correctness bugs were found and
fixed in it much later (2026-08-15 ×2, 2026-08-17), all outside this
incident's window but worth noting for pattern-recognition:

- `48b69f62f` (2026-08-15): "offseason digests kept sending, and a same-day
  event said 'Tomorrow'"
- `b6f2cfa55` (2026-08-15): "event reminders told players the wrong day AND
  the wrong time"
- `3132e64e7` (2026-08-17): "the reminder cron could email a player's class
  timetable to the team" (a real data-leak-shaped bug — wrong recipient
  scope)

None of these three are the same root cause as the 876-row 2026-04-28→05-08
burst (those are correctness/content bugs discovered via other means, not
`error_logs` error-severity failures), but the pattern — this cron shipping
with a defect, running for weeks to months before the defect surfaces, then
getting fixed — recurred at least 4 times total (this incident + the 3
August fixes) on the same route. That's a strong candidate for "this cron
route needs pre-ship review depth it hasn't been getting," independent of
any single fix.

## Invariant candidate

**INV-CRON-002** (candidate): `cron.eventReminders` (and cron routes
generally) should have a synthetic/canary check — a known test event with a
known expected reminder recipient list and content, verified after each cron
run — rather than relying on real production sends to surface correctness
bugs. `d86b6b0a3` (2026-07-02, "wire background_job_logs outcomes into all 14
cron routes") added run-outcome logging after this incident's window, which
would catch execution *failures* but not the wrong-content/wrong-recipient
class of bug that recurred 3× in August.

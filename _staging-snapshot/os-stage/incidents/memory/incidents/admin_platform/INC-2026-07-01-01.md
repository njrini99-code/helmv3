- **feature_id:** `admin_platform` (Helm Bridge observability stack:
  `src/lib/admin/observed-action.ts`, `incident-classification.ts`,
  `auto-resolve.ts`, `incident-resolver.ts`, `observe-action-result.ts`,
  `severity.ts`, and every `src/lib/admin/data/*.ts` reader)
- **status:** **partially resolved, recurring class — treat as ongoing until
  an invariant enforces it structurally** (see Open Question at the end)
- **resolved_at:** NOT resolved — unresolved as of **2026-08-21** (the date
  of the most recent confirmed sighting, #9). Sightings #1-#8 each have their
  own resolved_at, listed in the sighting table below; the class as a whole
  (the recurring architectural failure mode) has no resolved_at because
  INV-ADMIN-001, the fix that would close it structurally, does not exist yet
  as of this mining pass.
- **classification:** `TELEMETRY_DEFECT` — this is the canonical example the
  engineering-OS extension spec (§36-43) names directly: "resolved telemetry
  counted as active errors." This incident documents its full history because
  the extension spec explicitly requires that for the canonical example in
  whichever domain owns it, and this is that domain.
- **severity:** varies per sighting (see table)
- **first_seen (earliest sighting, foundational infrastructure):** 2026-07-01
  (commit-author local date, America/New_York; the commit's UTC timestamp is
  2026-07-02T03:49:07Z — see Date convention below)
- **most recent sighting in evidence:** 2026-08-21 (outside this incident's
  nominal 08-17 window, included because it is the same recurring class and
  a meta-incident's job is to show the whole arc)
- **fingerprint:** not a single fingerprint — this is a **root-cause class**
  spanning multiple distinct code locations that all share the same shape:
  *a query or classifier counts/displays an incident/error/health signal
  without checking whether it has already been resolved, or without agreeing
  with the system that already knows the correct verdict.*

## Date convention

Every commit date in this document is pulled directly from `git show -s
--format="%aI"` (the commit's author timestamp with its recorded UTC
offset, not guessed or estimated). All commits in this lineage carry a
`-04:00` (America/New_York, EDT) offset. Dates given as a bare
`YYYY-MM-DD` below are that **local** calendar date, matching how this
repo's own `git log --date=short` and every other incident doc in this
folder report dates. Where a commit's timestamp is late enough in the day
that its UTC calendar date differs from its local calendar date (a ~20:00
–23:59 local commit lands after midnight UTC), **both dates are given
explicitly** rather than silently picking one. Full ISO-8601 timestamps
(local, with offset) are in the sighting table's Timestamp column;
UTC-crossing cases are called out in prose inline.

## Why this is one incident, not nine

The dedupe rule in `memory/incidents/README.md` says: "Several fingerprints
tracing to one proven root cause become one incident, not many." The nine
sightings below (numbered 0-9; #0 is foundational infrastructure with no
defect of its own, so nine are actual sightings, numbered 1-9) are NOT
literally one root cause each time — they are independent code locations
that each reinvented the same category of mistake ("count/display a signal
without checking `resolved`" or "without matching the read-time classifier's
verdict"). That is itself the pattern worth recording as one incident: this
is a **recurring architectural failure mode**, not a single bug that got
refixed by accident nine times. The invariant candidate at the end exists
specifically because nine independent occurrences of the same shape over
115 days is strong evidence that documentation and one-off fixes are not
sufficient — the class needs to be structurally impossible, not repeatedly
caught.

## Full lineage (chronological)

### 0. Foundational infrastructure — 2026-07-01 local / 2026-07-02 UTC, `2bcdde74b` ("W6")
Commit timestamp `2026-07-01T23:49:07-04:00` (= `2026-07-02T03:49:07Z`) —
one of the day-crossing cases flagged in Date convention above.
`withAdminObserved` wrapper is born: a generic action-observability wrapper
that logs outcomes to `admin_events`/`error_logs`. This is the instrumentation
layer every later classification fix builds on top of. Not itself a defect —
recorded as the starting point of the timeline, not itself an incident with
a resolved_at.

### 1. 2026-04-28, `7e8fc9ad9` — earliest noise-reduction, pre-classifier era
`src/lib/admin/incident-resolver.ts`'s `archiveIncidentsByCriteria()` is
added as a one-shot manual tool to archive two specific known-fixed error
patterns (a migration ON CONFLICT fix and a demo_request CHECK constraint
fix) by hand. This predates any general classifier — it is evidence that
"stuff that's actually fixed keeps showing as unresolved" was already a
recognized problem 3 months before the first systematic fix, and the fix
available at the time was manual, per-incident archiving.

### 2. 2026-07-14, `5958e375e` — expected-empty-state registry
UI-audit item SH-002: empty-state codes (`EXPECTED_EMPTY_STATE_CODES`) had
existed in the soft-failure observer since #804/#807 but UI surfaces
rendered hardcoded copy with no knowledge of *why* data was absent — "user-
facing copy and observability classification could silently drift." A new
`src/lib/view-state/expected-empty-states.ts` becomes the single owner of
both the classification codes AND the user-facing copy, with a registry
test locking the invariant that "observer classification and registry codes
can never disagree." This is the first instance of the general pattern
("two things that describe the same state must be forced to agree, not
independently maintained") being fixed with an actual enforced invariant
rather than a one-off correction.

### 3. 2026-07-17, `eb406b0b7` — auto-resolve is born
`auto-resolve.ts`'s first version ships: release-aware auto-resolution
Rules A/B, which infer "fixed" from a fingerprint going quiet for 14 days
(Rule B) or surviving 24h past the newest deploy with zero new occurrences
(Rule A). This is the mechanism whose structural blind spot — it can only
ever detect *bugs going quiet*, never *telemetry that was never a bug* —
becomes the root cause of sighting #8 below (Rule D, fixed 2026-08-21),
**35 days later** (2026-07-17 → 2026-08-21, computed).

### 4. 2026-07-29, `6b6dda539` — `classifyIncident` / the KIND axis is born
Measured against production: **85% of July's 2,728 error rows were not
bugs.** The top "unresolved incident" was `gateMetrics` at 575 rows —
routine threshold telemetry — and 129 rows were `Integrity PASS` checks
that *passed*, sitting in the same unresolved bucket as real defects. This
commit adds a read-time `KIND` axis (`classifyIncident`) computed with no
migration/backfill, applying retroactively to ~93k historical rows. This is
the classifier that every later fix in this lineage either extends or
finally gets *trusted* by (sighting #6).

### 5. 2026-07-31, `527dfba71` — auto-resolve's OWN resolution mechanism was broken
Independent of classification correctness: Rule C (the legacy-row
auto-resolver born alongside Rules A/B) had never resolved a single row
since it shipped. It selected up to 2,000 ids and spent them in one
`.in('id', ids)` UPDATE — PostgREST puts filters in the query string, and
~1,000 uuids is a ~39KB URI that Supabase's edge rejects with `400 Bad
Request` before Postgres even sees it (measured ceiling on this project:
584 ids / ~22.8KB works, 585 does not). Compounded by `LEGACY_BATCH = 2000`
being above PostgREST's own 1,000-row response cap, so a full page always
looked "short" against the drain-loop's completion threshold and the loop
believed the backlog was empty every single night. **87,619 legacy rows
were unresolved when this was caught** — the auto-resolve system had been
silently failing to do its one job since it shipped 2 weeks earlier. Fixed
by chunking the UPDATE at 200 and lowering `LEGACY_BATCH` to 1000. This is
a different micro-root-cause (PostgREST payload-size limits, not
classification logic) but the same macro-symptom as every other sighting
here: rows that should read as resolved don't.

### 6. 2026-08-05, `ea6ad417f` — "stop filing correct behaviour as defects"
A real 24h incident export (2026-08-05, 23 "actionable" incidents) showed
several were the platform doing exactly the right thing, logged as
error-severity defects. Headline case: a player already on the women's
roster who opened the men's invite link was correctly told she's already
placed — the one-team-per-player rule working — filed as a defect anyway.
Adds patterns to `USER_INPUT_REJECTION_PATTERNS` so they classify as info
and never reach Sentry. Also downgrades `SIGNUP_ACCESS_CODE unset` from
critical to a one-shot info event: the shared signup code was deliberately
retired 2026-08-04, so the "unset" alarm had started firing on **every**
signup describing the now-intended configuration — 10 critical incidents
in one day, none actionable.

### 7. 2026-08-06, `af3e7205a` — "the Bridge had two definitions of an error"
A distinct but closely-related drift: severity-filter inconsistency, not
resolved-filter inconsistency. Seven call sites hand-wrote either
`.in('severity', ['error','critical'])` or `.neq('severity', 'info')` —
both individually defensible, never declared once. Over the 30 days to
2026-08-06 the feed showed 667 events while the KPI tiles counted 390 —
**41.5% of what an operator could see did not exist in the headline
number.** Fixed by declaring `INCIDENT_SEVERITIES` / `FAILURE_SEVERITIES`
once in `lib/admin/severity.ts`, with a test that scans the data layer and
fails if a hand-written severity filter reappears. Same commit also fixed
team-detail's seven per-section bare `catch { x = [] }` blocks going
silently "clean" instead of logging failure — a second flavor of "the
dashboard says fine when it isn't."

### 8. Investigated 2026-08-20, committed 2026-08-21, `fbd74c13c` — Rule D: auto-resolve finally trusts the classifier
Two distinct dates, both explicit rather than collapsed to one: the commit
message states the production measurement was taken "tonight
(2026-08-20)"; the commit itself landed `2026-08-21T01:41:18-04:00`
(= `2026-08-21T05:41:18Z`) — after local midnight, so both the
investigation date (08-20) and the commit/resolved_at date (08-21) are
recorded. (An earlier, non-fast-forwarded commit `3746c8489` at
`2026-08-21T00:14:10-04:00` = `2026-08-21T04:14:10Z` carries the same
change — `fbd74c13c` is the version that landed on `main` via PR #1550.)
resolved_at for this sighting: **2026-08-21**. Measured against production
the night of 2026-08-20: 3,661 unresolved
`admin_events` rows with `event_type='error'`, ~2,570 of them already
classified `actionable:false` by `classifyIncident` — routine
`.gateMetrics`/`.starvation` telemetry, `Integrity PASS` rows, "not enough
data yet" empty states, expected access denials. **Nothing in
`auto-resolve.ts` could ever touch them**: Rules A/B/C all infer "fixed"
from a fingerprint's silence, which structurally cannot apply to a row that
was never a defect to begin with — a message *designed* to fire
continuously (e.g., `belowRoundFloor`, firing ~46×/day since 2026-08-06)
can never go quiet for 14 days, so it sits open forever regardless of age.
Adds Rule D: bulk-resolve unresolved `event_type='error'` rows the
classifier already says are not actionable, at read time, from the row's
own content — explicitly preserving the deliberate exception that
provider/billing faults (Inngest credential, AI Gateway credit) must never
resolve on silence, since "no deploy has ever topped up a billing account."
Reduced unresolved `admin_events` from 3,661 to ~274 in one pass.

### 9. 2026-08-21, `8d8f7242d`/`c0d152396` — the THIRD independent instance, per the audit that found it
This is the sighting the extension spec's canonical example most literally
describes. A dedicated Bridge-accuracy audit (`w-audit-5`, per
`/tmp/claude/night/ledger.md`) found that **every team/player error count in
the Bridge UI** — `TeamHealthTable.errors7d`, the pulse-grid's `errors30d`,
team letter grades, `TeamCommandCard`'s watch pill, `PlayerWatchlist` badges
— read `admin_events` **without a `resolved` filter at all**, across four
files (`team-scope.ts`, `team-detail.ts`, `pulse-grid.ts`, `users.ts`).
Concretely: "Guilford '67 errors this week', all resolved, grade C" and "11
Guilford players danger-red off resolved incidents." A second auditor
(`w-audit-6`) independently found `get_feature_health` (the RPC backing
per-feature health badges) counting RESOLVED rows in its fingerprint/error
counts too, calling it explicitly "the 3rd instance of the resolved-blind
class" — i.e., the auditors themselves recognized this as the same
recurring pattern documented here. **Discovered and resolved_at both
2026-08-21** (same day) — fix commits `c0d152396`
(`2026-08-21T11:30:53-04:00` / `15:30:53Z`) and `8d8f7242d`
(`2026-08-21T12:32:07-04:00` / `16:32:07Z`, PR #1576) — migration
`20260821050000_feature_health_excludes_resolved_incidents.sql` for the RPC,
`resolved IS NOT TRUE` added to the four data files — per the
`w-fix-8`/`w-db-review-1` review, deliberately as ONE unit with a
count-based guard test (an earlier substring-match guard "passes
vacuously"), and deliberately NOT filtering `fingerprints_7d`/`total`
(filtering those would flip cleared features GREEN→NEUTRAL post-clear,
which the reviewer judged "worse" than the original bug).

This sighting and its fix are dated 2026-08-21 — outside this incident's
nominal pre-08-17 mining window — but the *underlying code* it fixed
(`team-scope.ts`, `team-detail.ts`, `users.ts`) was born **2026-07-02**
(`fe082d4b9`/`40818e06e`, "V2 data layer" / "users & teams data layer"),
and `pulse-grid.ts` was born **2026-07-17** (`d0f6b9073`). Both predate this
incident's window. Exact elapsed time, computed (not estimated): 2026-07-02
→ 2026-08-21 is **50 days (~7.1 weeks)**; 2026-07-17 → 2026-08-21 is **35
days (exactly 5 weeks)**. The bug existed silently in production for
**5 to 7.1 weeks depending on which file**, not a single round number —
included here per the task brief's explicit instruction to document this
class's full lineage regardless of discovery date, since the discovery date
is not the same as the introduction date.

## Invariant candidates

**INV-ADMIN-001** (highest priority): every query in `src/lib/admin/data/*.ts`
(and any RPC backing a Bridge health/error/grade display) that reads
`admin_events` or `error_logs` for a "how many errors does this
team/player/feature have" purpose MUST include an explicit `resolved`
filter (or be checked against `classifyIncident`'s verdict). A static
check — ast-grep or semgrep rule under `.coderabbit/ast-grep/` or
`.coderabbit/semgrep/helmv3.yml` per `.claude/rules/code-review-tooling.md`
— flagging a `.from('admin_events')`/`.from('error_logs')` call with no
`.eq('resolved', ...)` / `.is('resolved', ...)` / `resolved IS NOT TRUE`
nearby would have caught sighting #9 (and prevented a 4th) at review time
instead of via a dedicated audit weeks later. This is the single highest-
leverage fix candidate in this entire incident: it converts a recurring
manual-discovery pattern into a structural impossibility.

**INV-ADMIN-002**: every unresolved-count/display path must agree with
`classifyIncident`'s `actionable` verdict — either by filtering through it
directly, or by an `auto-resolve` rule (Rule D) that keeps `resolved`
reality in sync with it. Sighting #8 is the fix that makes this true for
`admin_events.resolved`; sighting #9 shows the invariant still doesn't hold
for *display-layer* queries that never consult `resolved` at all — meaning
#1 and #2 are the same invariant, enforced at different layers, and #1
alone would have been sufficient to prevent #9.

**INV-ADMIN-003** (narrower, from sighting #5): any bulk `UPDATE ... WHERE
id IN (...)` issued through PostgREST must be chunked below the measured
~584-id / ~22.8KB URI ceiling for this project. A lint/test asserting no
`.in('id', ids)` call site in `src/lib/admin/**` operates on an unbounded
array would have caught this before 87,619 rows piled up.

## Replay candidates

Not built in this pass (the replay lab did not exist at mining time — see
`docs/ai-system/GOLFHELM_ADVANCED_RELIABILITY_EXTENSION.md` §10-11 for the
target shape). Two fixtures are clearly warranted once `replay/` exists:

1. **INV-ADMIN-001 replay**: a fixture `admin_events` table with rows split
   across resolved=true/false × actionable=true/false, and each of the 4
   data files' queries run against it. Pre-#9-fix: resolved rows appear in
   counts. Post-fix: they don't. Fixture data should be synthetic
   (`playerId: 'fixture-player-1'`, generic titles), never copied from real
   production rows.
2. **INV-ADMIN-003 replay**: a mocked PostgREST-shaped endpoint that
   rejects any `.in('id', ids)` request whose serialized URI exceeds the
   measured 22.8KB ceiling. Pre-fix (unchunked): fails. Post-fix (chunked at
   200): passes.

## Open question — is this class actually closed?

**No, not with confidence.** Nine independent sightings of the same shape
over **115 days (2026-04-28 → 2026-08-21, ~3.8 months, computed from the
sighting table's dates, not estimated)**, the most recent just before this
mining pass, is not
evidence the pattern is exhausted — it is evidence the pattern is easy to
reintroduce (any new Bridge data file that queries `admin_events`/
`error_logs` without remembering the convention reintroduces it) and hard to
catch by review alone (three of the nine sightings survived code review and
were caught only by a dedicated post-hoc audit). This incident should stay
open / monitored, not archived, until **INV-ADMIN-001** exists as an
enforced static check — at which point a 10th sighting becomes structurally
impossible rather than merely embarrassing to find twice more.

## Summary

For **103 days (2026-03-14 → 2026-06-25, ~14.7 weeks / ~3.4 months, computed
from the two dates directly, not estimated)**, every client-side error that
bubbled up through `GolfRoot`/`RootErrorBoundary` without an explicit `action`
tag landed in `error_logs` as a single untagged `null`-action signature. It
never got broken down by route, component, or failure mode — it was one
undifferentiated flood, effectively impossible to triage from the aggregate
view alone (no way to tell if it was one recurring bug or a thousand distinct
ones without pulling individual sample rows).

It stopped appearing after 2026-06-25 and has had zero recurrence in the 8
weeks since (confirmed live against production during the 2026-08-20 Bridge
audit). `RootErrorBoundary` / `src/app/golf/error.tsx` still exist and are
still the code path that would emit this signature if it fired again — so this
is not a case of the code being deleted out from under the incident, it
genuinely stopped happening.

## Root cause

**Not independently re-diagnosed in this pass** — the 2026-08-20 audit
confirmed this is dead and attributed it to "an old build" per team-lead
context, but did not identify which specific commit or deploy stopped it
firing. Given the timing (dies 2026-06-25, `withAdminObserved`'s
`requestId`/action-tagging work lands 2026-07-01 per `2bcdde74b`, and the
classifier/KIND-axis work lands 2026-07-29 per `6b6dda539`), the most likely
explanation is that whatever pre-`withAdminObserved` error path was emitting
untagged rows was superseded by the wave of instrumentation work that shipped
across 2026-07-01 (`2bcdde74b`, commit-local timestamp
`2026-07-01T23:49:07-04:00` / `2026-07-02T03:49:07Z` UTC) through 2026-07-29
(`6b6dda539`, `2026-07-29T07:57:37-04:00` / `11:57:37Z` UTC) — see the
flagship lineage in `INC-2026-07-01-01.md` — rather than a single fix
commit. Note this instrumentation wave starts **6 days after** this
signature's own last occurrence (2026-06-25 → 2026-07-01), so it cannot be
the direct cause of the signature going quiet; it is offered only as the
most plausible *adjacent* explanation, not a proven one. **This is a gap,
not a confirmed root cause** — flagged for backfill if anyone wants the
exact commit.

## Why it matters as a `TELEMETRY_DEFECT` example

This is the largest-volume instance in the repo's history of a signal that
was *structurally* untriageable — not because the underlying failures weren't
real, but because the observability layer didn't have enough shape (no action
tag) to let anyone tell one failure mode from another. It sat in the
"DEAD" bucket of the 2026-08-20 triage precisely because nobody could ever
have separated a real bug inside that 72,036-row pile from noise at the time
it was live. Contrast with the classification-drift lineage in
`INC-2026-07-01-01.md`, which is about *correctly-tagged* signals being
miscounted — this incident is about signals with *no tag at all*.

## Invariant candidate

**INV-ADMIN-004** (candidate, not yet registered in
`memory/invariants/registry.yml` — that file did not exist at the time of this
mining pass): every row written to `error_logs`/`admin_events` must carry a
non-null `action`/`context->>'action'` tag. A `sql_read_only` check counting
`(action IS NULL)` rows in a recent window (e.g., last 24h) and alerting above
a near-zero threshold would have caught this class within a day of it
starting, instead of it running for 3.5 months before anyone looked. Deferred
to backfill: no such check exists today; `src/lib/admin/incident-classification.ts`
and `src/lib/admin/observe-action-result.ts` both assume a populated `action`
field and have no explicit handling for `action IS NULL` documented in this
pass.

## Replay candidate

Not built in this pass (read-only mining; replay lab did not exist yet). A
future replay fixture would need: a small `error_logs` table with N rows
where `action IS NULL` inserted in a tight window, an invariant script per
above, and an assertion that the check fires. Fixture should NOT reuse raw
production error text — synthesize a generic "unhandled client exception"
message.

## Registry gap

`memory/registry.yml`'s `admin_platform` entry has no sub-feature for "Bridge
observability instrumentation" specifically — its `code.services` lists only
`src/lib/supabase/admin*` and `src/lib/cron/**`, not
`src/lib/admin/observed-action.ts`, `src/lib/admin/incident-classification.ts`,
`src/lib/admin/auto-resolve.ts`, or `src/lib/error-logging.ts`, all of which
are load-bearing for every incident in this folder. Recommend adding these to
`admin_platform.code.services` (or splitting a `bridge_observability`
sub-feature) so future `knowledge:map` runs actually resolve these files to a
feature.

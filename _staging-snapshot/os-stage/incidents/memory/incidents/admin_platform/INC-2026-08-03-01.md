## Summary

Two separate Bridge integration-health widgets lost their credentials
within days of each other in early August, both degrading gracefully
(no page crash, no data corruption) — which is exactly why they are easy to
miss without a dedicated audit:

1. **Vercel deployments widget** — `integration.vercel`, error, n=2, last
   2026-08-03 04:47. Sample: "vercel rejected the configured credential —
   it is set but no longer valid. (deployments fetch)",
   `errorCode: provider_vercel_invalid_credential`. This is Vercel actively
   **rejecting** the token as invalid, not merely being unreachable — a
   distinct and more concerning failure mode than a transient network blip.
   No recurrence in the **17 days (2026-08-03 → 2026-08-20, ~2.4 weeks,
   computed)** to the 2026-08-20 audit, which the
   auditor could not distinguish from "already rotated" vs. "the widget
   simply hasn't been loaded since" — flagged **OWNER-CALL, still open** as
   of that audit (per the `/tmp/claude/night/REPORT.md` night-triage report,
   whose latest internal timestamp is **2026-08-21 09:17 ET**: "Vercel
   Bridge token — the admin deployments widget's API credential is rejected
   as invalid; rotate in dashboard" was still on the owner action list at
   the end of that pass).
2. **Sentry integration widget** — `integration.sentry`, warning, n=27,
   last 2026-08-06. Message: "sentry could not be reached. The Bridge is
   rendering without its data." Classified as expected external-dependency
   degradation by the 2026-08-20 warning/info triage (the app "already
   degrades gracefully"). A SEPARATE later data point: the same triage's
   DEAD table lists a *different* `integration.sentry` action string
   (warning, n=27... actually the ACTIVE-REAL table's entry is n=27 with
   no recurrence since 8/6) with the note "No call site found anywhere in
   `src/`/`scripts/` for this exact action string — likely an SDK-internal
   or since-removed integration path." That second note suggests this
   specific string may not even be actionable from this codebase — a
   genuine ambiguity, not resolved in this pass.

## Why these are grouped as one incident

Both are the same shape (a Bridge integration widget's credential fails,
degrades gracefully, is easy to overlook specifically *because* it degrades
gracefully) discovered in the same audit pass within days of each other.
Grouping them surfaces a pattern worth a structural fix rather than two
isolated "rotate a token" tickets: **the Bridge has no proactive credential-
health check for its own integrations** — both were discovered by a human
reading `error_logs` after the fact, not by any monitoring that watches
"is this integration's credential still valid" independent of whether
someone happened to load the widget recently.

## Root cause

Not established in this pass for either — no commit references credential
rotation for either integration in the relevant window. Both read as
external credential expiry/rotation events (a token expiring, being
revoked, or an app-side key rotation not mirrored into Vercel env vars),
consistent with the pattern already documented for the separate Inngest
outage (`INC-2026-07-30-01`) — this repo has now shown at least three
instances of "a third-party credential silently went stale and only
surfaced via graceful-degradation telemetry that's easy to not notice."

## Invariant candidate

**INV-ADMIN-007** (candidate): a scheduled, read-only credential-liveness
check for each Bridge-integrated external service (Vercel, Sentry, Inngest,
Resend) — distinct from "did anyone load the widget" — that pages on
`provider_*_invalid_credential`-shaped failures rather than waiting for
someone to notice a "rendering without its data" banner. This is the third
sighting in this mining pass of the same general problem: this repo does
not proactively monitor its own third-party credential health, and has
instead discovered every instance of it (Inngest, Vercel, Sentry) via
after-the-fact `error_logs` archaeology.

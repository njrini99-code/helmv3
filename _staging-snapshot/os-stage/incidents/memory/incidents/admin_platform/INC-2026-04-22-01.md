## Summary

A three-day arc, all in the same week:

1. **2026-04-21, 15:11:15 -04:00** (`19:11:15Z` UTC) — `getAdminDashboardData`
   was refactored from ~93 inline Supabase queries to 3 parallel RPC "rollup"
   fetchers (`5ae643a89`), expected to cut ~93 round-trips to ~10. It shipped
   broken: the RPC guards (`SELECT 1 FROM users WHERE id = auth.uid() AND
   role = 'admin'`) returned `NULL` for `auth.uid()` because the TS fetchers
   called them through a `service_role`-JWT client, so every admin got
   `Forbidden` and `/golf/admin` crashed for everyone. Diagnosed via several
   wrong hypotheses (closure this-binding, explicit `.bind()`,
   layout-provider removal) that didn't fix it, so the whole refactor was
   **reverted same-day at 20:04:27 -04:00** (`435926f2a`,
   `2026-04-22T00:04:27Z` UTC — crosses to the next UTC day) back to the
   93-query original — the 8 new RPCs stayed deployed but unused.
2. **2026-04-21, 20:15:53 -04:00** (`2026-04-22T00:15:53Z` UTC) — just
   **11 minutes after** the revert, the *actual* root cause was found
   (`9f7dc718c`): the fetchers needed the request-scoped `createClient()`
   (carries the invoking admin's JWT) instead of `createAdminClient()`
   (service_role, no `auth.uid()`), for the 5 RPC guards that checked
   `auth.uid()` directly. Slice B already used a different,
   service_role-safe gate and was unaffected.
3. **2026-04-22** — with the RPC path re-enabled and the auth bug fixed,
   a *second*, unrelated failure mode appeared: `get_admin_errors_rollup`
   and `get_admin_analytics_rollup` started hitting Postgres
   `statement_timeout` (code `57014`) and crashing the System tab, because
   nobody had load-tested the new SQL against production data volume before
   shipping it.
4. **2026-04-23** — two same-day fixes: `58cbdf4b8` rewrote the slow SQL
   (see Root Cause below), and `d29d12577` made the *symptom* non-fatal —
   `Promise.allSettled` + typed empty-fallback payloads so one slow RPC
   degrades that one panel instead of crashing the whole page.
5. The fingerprint kept firing at low volume through **2026-05-13** —
   **20 days (2.9 weeks, computed)** after the 2026-04-23 fixes — before
   going fully quiet. No single commit
   in that window specifically targets this fingerprint again; the SQL
   rewrite likely reduced frequency/severity without eliminating every slow
   path, and the graceful-degradation fix meant later occurrences degraded
   silently instead of paging as loudly, which may itself have suppressed
   further investigation. **Not confirmed** — flagged as a gap.

## Root cause (2026-04-23 fix, `58cbdf4b8`)

Three distinct SQL problems in the same rollup functions:

1. `get_error_summary`: a `WITH base AS (SELECT * FROM error_logs WHERE ...)`
   CTE materialized the full row — including large JSONB `context` and text
   `stack` columns — for all ~70k matching rows before aggregating. Projecting
   only the columns the aggregates actually use dropped memory pressure ~90%
   (steady-state ~130ms after).
2. `get_admin_event_summary`: same `SELECT *` problem, compounded by
   re-scanning the (even after projection) 47k-row CTE 4× for different
   counts. Rewritten to a single aggregate with `FILTER` clauses, each
   dimension doing its own index scan (7.3s → ~85ms steady-state).
3. `get_admin_analytics_rollup`: the `admin_error_events` CTE had **no time
   bound** — it scanned all 69k `admin_events` rows across all of history for
   `severity IN ('error','critical')` on every dashboard load. Scoped to the
   already-available `p_ago30d` parameter to match the dashboard's actual
   recent-state semantics.

## Lineage — this failure CLASS recurred later (outside this incident's window)

The general shape — "an admin/analytics read times out under Postgres
`statement_timeout` because of unindexed/unbounded work, and it's discovered
via a symptom (a crashing page or a burst of Bridge errors) rather than a
proactive check" — recurred at least twice more (outside this incident's
2026-04-22→05-13 window, documented by the sibling covering that period,
cross-referenced here for continuity, dates as given in that source
material):

- A **2026-08-20** 17:07–17:30 UTC cluster of 9 independent read-path timeouts
  (`getTeamOverview`, `getInsightsForPlayer`, `getPlayerHubSummaryData`, etc.)
  was root-caused not to a slow query but to lock contention from a
  concurrent-autosave pile-up on `save_partial_round_atomic` — a different
  mechanism (write-side lock queueing starving reads on a small
  `max_connections=60` instance) producing the same `statement timeout`
  symptom.
- Investigating that cluster surfaced a THIRD, genuinely query-shape root
  cause: `can_read_golf_shot_detail` (a `SECURITY DEFINER` RLS helper) was
  mis-costed at Postgres's default `COST 100`, causing the planner to
  seq-scan detail tables evaluating it row-by-row on every shot-detail read;
  re-costing it to `10000` cut execution from 877ms to 105ms (8.3×).

None of these three are the same root cause as each other or as this
incident — they're grouped here only because they all present as
"admin/analytics `statement timeout`" and a future triage should check
which of the three (unbounded/unprojected SQL, write-side lock contention,
planner mis-cost on an RLS helper) it actually is before assuming it's a
repeat of any specific prior fix.

## Invariant candidate

**INV-ADMIN-006** (candidate): any RPC called from `getAdminDashboardData`
or its rollup slices should have a `performance` baseline (expected p95
execution time under a realistic row count) checked against
`pg_stat_statements` on a recurring basis, so a regression like the
unbounded `admin_error_events` CTE is caught by a threshold check before it
reaches production `statement_timeout` failures. No such baseline check
exists today; `58cbdf4b8`'s fix was reactive (post-incident), not caught by
any pre-existing gate.

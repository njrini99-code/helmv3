# INC-2026-07-29-01 — Auth-degraded fallback took the entire site down (every route, including logged-out marketing pages)

- **id:** INC-2026-07-29-01
- **feature_id:** auth_onboarding_join
- **first_seen:** 2026-07-29 ~04:16 UTC
- **resolved:** 2026-07-29 13:51 UTC (PR #1098 merged)
- **severity:** CRITICAL (helmsportslabs.com stopped serving on every route for a 9-hour window, including routes that need no auth at all)
- **classification:** FUNCTIONAL_FAILURE (primary) / DEPENDENCY_OUTAGE (secondary — triggered by upstream Supabase flapping, but the site-wide blast radius was a self-inflicted defect in the safety net)
- **status:** resolved

## Summary

The Supabase project began returning Cloudflare 522 ("connection timed out") in flapping windows — a project-specific degradation, not a platform-wide Supabase incident (their status page showed all-green). Middleware's `getUserResilient` function exists specifically to keep the site usable during exactly this kind of auth-backend degradation, but its final fallback step called `supabase.auth.getSession()`, which — despite being documented as a local cookie read — attempts a network token-refresh call when the stored access token has expired. That network call was unwrapped, so the fallback could throw the exact error class it existed to absorb. Because middleware runs in front of every request, the escaping error became a 500 on every route site-wide, including the login screen and marketing pages that need no auth.

## Root cause (verified)

`getUserResilient`'s fallback path called `supabase.auth.getSession()` unwrapped. `getSession()` is documented as a local-cookie read but silently attempts a token-refresh network call when the cached access token is expired — a call to the very auth server already established as unreachable in this scenario. The safety net therefore shared the exact failure mode of the thing it was built to protect against, and because it runs in middleware (in front of every request), the blast radius was the entire site rather than just authenticated routes.

## User impact

Every visitor to helmsportslabs.com for up to 9 hours (window bounded by the flapping errors, not necessarily continuous downtime) — including unauthenticated visitors trying to reach marketing pages or the login screen — received a 500. This is one of the few incidents in this repo's history with confirmed full-site blast radius rather than a scoped feature/tenant.

## Repair

`getSession()`'s fallback call wrapped; an unreadable session during the outage is now treated as "no session" (fail closed, not fail open) — the PR explicitly notes this is "not a security relaxation... returning null only ever denies access." Public routes now serve normally during an auth-backend outage; only genuinely authenticated routes fail (correctly, since identity can't be confirmed).

Detected via Vercel runtime error counts (292× `AuthRetryableFetchError`, 926× `TimeoutError`), not Bridge/Sentry — this predates or sits outside this repo's Bridge instrumentation for middleware-layer errors specifically.

## Recurrence risk

**Structural risk remains**: the trigger (Supabase project-specific 522 flapping) is an upstream dependency behavior outside this repo's control and could recur at any time. The fix makes recurrence non-catastrophic (scoped to auth routes only) rather than preventing the upstream flapping itself. Any other code path that calls `supabase.auth.getSession()` or `.getUser()` inside a fallback/error-handling branch should be audited for the same unwrapped-refresh-call trap — this was found in one call site; there is no confirmation in this pass that it was the only one.

## Invariant candidate

Best expressed as a functional/synthetic check rather than a SQL invariant, since the failure lives in application code behavior under a simulated backend outage, not in stored data:

```
# INV-AUTH-001: with the Supabase auth backend simulated as unreachable
# (mocked network timeout), getUserResilient must return a "no session"
# result without throwing, for both a request with an expired cached
# token and one with no cached token at all.
```

Severity: CRITICAL — a violation means a repeat of this exact site-wide outage shape. This is directly testable without needing real Supabase downtime.

## Replay candidate

Yes, and cheap. A unit-level fixture mocking `supabase.auth.getSession()` to throw `AuthRetryableFetchError` (simulating the exact upstream 522 condition), asserting `getUserResilient` returns a null/no-session result rather than propagating the throw. Pre-fix behavior: throw propagates through middleware. Post-fix: null returned, request proceeds to public-route handling. Fast, deterministic, no timing dependency — a strong candidate per extension §10-11's "critical workflows" and "offline reliability" priority classes.

## Status

Resolved. Recommend one follow-up: audit other `supabase.auth.getSession()`/`.getUser()` call sites in error-handling/fallback branches for the same unwrapped-refresh trap (see Recurrence risk).

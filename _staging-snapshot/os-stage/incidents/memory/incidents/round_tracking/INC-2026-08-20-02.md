# INC-2026-08-20-02 — 17:07–17:30 UTC statement-timeout cluster: the same lock pile-up, nine unrelated read paths starved

- **id:** INC-2026-08-20-02
- **feature_id:** round_tracking (registry key: `golf_round_lifecycle`) — blast radius crossed into `coachhelm_ai` and `admin_platform` read paths (see User impact)
- **first_seen:** 2026-08-20 17:07:45 UTC
- **resolved:** 2026-08-20 17:21:26 UTC (17 minutes after first symptom, fixed mid-incident)
- **severity:** HIGH (would have been CRITICAL — same destructive mechanism as INC-2026-08-20-01 — had it recurred against a round instead of merely starving reads)
- **classification:** PERFORMANCE_REGRESSION (primary — recurrence of known lock contention) / FUNCTIONAL_FAILURE (secondary — nine unrelated read paths returned errors to users)
- **status:** resolved

## Summary

A second, smaller occurrence of the *exact* mechanism already root-caused
earlier the same day in INC-2026-08-20-01: concurrent auto-saves for the same
`golf_rounds` row queuing on the `SELECT ... FOR UPDATE` lock inside
`save_partial_round_atomic`, which starves every other read against the same
small Postgres instance (`max_connections=60`) while it holds the lock
through a row-by-row delete+insert of holes/shots. The audit doc from the
first incident had explicitly listed the fix ("single-flight the auto-save
per round," `FOR UPDATE NOWAIT`) as **not yet landed** at the time it was
written. It landed by migration at **17:21:26 UTC** — in the middle of this
exact cluster — and the cluster stopped immediately after.

This was investigated fresh, not assumed to be the same bug: the hypothesis
tree included "13:12 ET deploy fallout" (a deploy did land 5 minutes before
the cluster started) before being ruled out in favor of the lock-contention
recurrence, once the team/timing/table evidence lined up with the earlier
incident.

## Root cause (verified)

Not deploy fallout — the same self-amplifying lock pile-up as
INC-2026-08-20-01, on the same team's roster. `save_partial_round_atomic`'s
first row action is `SELECT ... FOR UPDATE` on `golf_rounds`; a second
concurrent save for the same round queues on that lock (up to 10s in the
worst case observed), then still runs its full row-by-row delete+insert of
~70 shots once it acquires it. Clients abandon each request at their own
HTTP abort while the server keeps working, then fire the next auto-save into
the same pile. **Why nine unrelated read paths failed for a write-side lock
issue:** on a small instance (`max_connections=60`, with Auth alone reserving
up to 10 per the `auth_db_connections_absolute` advisory finding), the
CPU/IO/connection pressure from the write-side pile-up is shared with every
other read against the same database. `getTeamOverview`, `playerHub
summary`, `insight-delivery`, `/golf/dashboard`, and `announcements` don't
block on the round row lock directly — they queue for the same limited
connections and CPU while the write-side pile-up runs hot. Indexes were
ruled out (Supabase advisors clean on all nine paths' tables).

## User impact

- Nine independent read paths returned errors or empty states for
  ~17 minutes to at least one team (Guilford): team overview, insight
  delivery (urgent pass + shot drivers), team-hub classes panel, cached
  player dashboard data, `/golf/dashboard` render itself, and player-hub
  announcements.
- No confirmed second data-destruction event in this window — the fix
  landed mid-incident before the same failure sequence could reach the
  destructive-fallback code path again. This is closer to a near-miss than
  a repeat of INC-2026-08-20-01.
- Two `admin_events` rows in this window were initially miscategorized as a
  session-expiry bug (`836ce3b6`, "Auto-save failed: user session expired
  mid-round") — later corrected (`3464e4374`, see coachhelm INC-2026-08-17-02
  cross-reference) to reflect that a killed round trip to GoTrue during DB
  contention is indistinguishable, in the code as written, from a real
  session rejection.

## Repair

- **`save_partial_round_atomic`: `FOR UPDATE` → `FOR UPDATE NOWAIT`.**
  Migration `single_flight_partial_round_save`, applied 2026-08-20 17:21:26
  UTC by njrini99@gmail.com; codified as commit `e196ef6a8`
  ("single-flight the auto-save per round — skip, don't queue," #1517).
  If any writer already holds the round's row — another auto-save, or an
  in-flight `submit_round_atomic` — the new save fails immediately with
  `55P03` and returns `{success:false, error:'busy'}` instead of queuing.
  Dropping a save is safe by construction: every save carries the full round
  state, so the next tick (after each shot, and every 15s) covers anything a
  skipped one held.
- Action-side: `savePartialRound` passes `'busy'` through verbatim and logs
  nothing — a coalescing skip is not an incident, and the prior night's 15
  `admin_events` rows of healthy coalescing were exactly the noise that had
  buried the real signal.
- Client-side: both round trackers treat `'busy'` as a silent no-op (no
  circuit-breaker advance, no warning); the two user-initiated "save for
  later" paths retry once after 1.5s instead.
- **Follow-up gap identified, closed the next day:** `submit_round_atomic`
  was *not* covered by this migration — it took the same row lock without
  NOWAIT on its first write. Investigated (F20): the function is
  transactional with 30s/15s timeouts, so it was not itself a destroy
  vector (deletes roll back on failure), but the check-then-update wasn't
  single-flight, producing a 15s lock-wait and an ugly error under
  contention with autosave. Fixed by replacing the `PERFORM`-existence
  check with `FOR UPDATE NOWAIT` + a `55P03` handler returning a clean
  "save in progress" — migration `20260821043500_single_flight_round_submit.sql`,
  applied 2026-08-21 08:15 UTC, reviewed by db-migration-reviewer.
- **Not yet landed:** batching the row-by-row hole/shot inserts into
  set-based inserts (latency-only follow-up, same as INC-2026-08-20-01).

## Recurrence risk

- The underlying lock-contention *mechanism* is now closed on both RPCs
  (single-flight NOWAIT on `save_partial_round_atomic` and
  `submit_round_atomic`), but the row-by-row insert batching that produces
  the multi-second tail in the first place is still not landed — a large
  enough concurrent team session could still produce elevated latency and
  `'busy'` responses, just not silent data loss or unrelated-path timeouts
  at this scale.
- The small Postgres instance size (`max_connections=60`) is a standing
  constraint that makes any future write-side contention on this table
  cross-contaminate unrelated reads. Not addressed by either fix.

## Invariant candidate

Yes — a companion to INC-2026-08-20-01's invariant, catching the mechanism
*before* it needs a destructive fallback to become visible:

```sql
-- INV-ROUND-002: no round should accumulate 3+ auto-save timeout events
-- inside a 5-minute window. That shape IS the lock pile-up, independent of
-- whether it happens to also destroy data this time.
select round_id, count(*) as timeout_events, min(created_at), max(created_at)
from admin_events
where title ilike '%Auto-save RPC failed%'
  and created_at > now() - interval '1 hour'
group by round_id
having count(*) >= 3;
```

Severity: HIGH. This is a read-only, bounded, recent-window check —
production-safe per the invariant registry's own constraints.

## Replay candidate

Partial yes. The single-flight NOWAIT fix itself is a good target for a
concurrency replay fixture (two simulated concurrent auto-save calls against
one fake round row; pre-fix both queue and the second times out under the
old `FOR UPDATE`, post-fix the second returns `'busy'` immediately). Lower
priority than INC-2026-08-20-01's replay, since this incident's destructive
path never actually re-triggered — it is a near-miss / mechanism-recurrence
replay, not a data-loss reproduction.

# INC-2026-08-20-01 — Round destruction: `attemptDirectSubmitFallback` deleted a round Postgres had already committed

- **id:** INC-2026-08-20-01
- **feature_id:** round_tracking (registry key: `golf_round_lifecycle`; primary code: `src/app/golf/actions/golf.ts`, RPCs `submit_round_atomic` / `save_partial_round_atomic`)
- **first_seen:** 2026-08-20 02:48 UTC (round `8e89c73e` created) — data destroyed 2026-08-20 ~03:19:22 UTC
- **resolved:** Root cause + fixes 1–3 landed 2026-08-20 (day-of); fix 4 (single-flight NOWAIT) landed 2026-08-20 17:21:26 UTC (`save_partial_round_atomic`) and 2026-08-21 08:15 UTC (`submit_round_atomic` mirror, migration `20260821043500_single_flight_round_submit.sql`). The destroyed round itself is **not** resolved — see User impact.
- **severity:** CRITICAL
- **classification:** DATA_INTEGRITY (primary) / FUNCTIONAL_FAILURE (secondary — the "restore on failure" contract in `submitRoundDirectFallback` was false in production)
- **status:** resolved (mechanism), unrecoverable (the specific data)

## Summary

`src/lib/supabase/server.ts:43` aborted every HTTP request at **10s**, while
`submit_round_atomic` and `save_partial_round_atomic` granted themselves
**30s / 20s** of `statement_timeout` via `proconfig`. When the client gave up
before Postgres did, Postgres kept working and **committed successfully** —
but the app, having only seen a client-side `TimeoutError`, believed the
submit had failed and ran a DELETE-then-INSERT "fallback" over a round that
was already saved correctly. The fallback's own restore step then also timed
out (contending with live auto-saves on the same row), and its `catch {}`
swallowed that failure silently. Net result: a fully-entered, `completed`
round left with 0 holes, 0 shots, and no draft to recover from.

The load-bearing line was a comment that lied about its own neighborhood:
`// 10s HTTP abort — DB statement_timeout is 8s, so DB error bubbles up
first`. True for ordinary PostgREST queries. False for exactly the two RPCs
in the round-submit path, which negotiate their own longer timeout.

## Root cause (verified)

Established from the function body, not timestamp inference:
`submit_round_atomic` is the *only* writer that sets `draft_data = NULL`
together with `status = 'completed'`. The fallback's own success path writes
a non-null `draft_data` marker, and that fallback failed — so it never ran.
`persistRoundSubmissionBackup` had already written a backup before the RPC
call. `draft_data IS NULL` today is therefore reachable *only* if
`submit_round_atomic` ran to completion and committed. Mechanism, step by step:

1. `submit_round_atomic` is called; Postgres grants it 30s via `proconfig`.
2. The client `fetch` in `server.ts` aborts at 10s. Aborting an HTTP request
   does **not** cancel the Postgres backend — it keeps running and commits:
   round marked `completed`, 18 holes and 72 shots written, `draft_data`
   cleared.
3. The app sees only a client-side `TimeoutError` and treats the submit as
   failed.
4. `attemptDirectSubmitFallback` (`golf.ts:1682`) runs. It snapshots the
   holes/shots the RPC just wrote, `DELETE FROM golf_shots`,
   `DELETE FROM golf_holes`, re-inserts 18 holes — and the shot re-insert
   itself aborts at 10s, because the freshly-committed transaction is
   contending with still-running auto-saves on the same round row.
5. `restoreSnapshot()` runs to undo the delete. It **deletes holes and
   shots again**, and its own re-inserts also time out. Every failure here
   was swallowed by a bare `catch {}` commented *"Best-effort rollback — the
   caller surfaces the ORIGINAL failure either way."*
6. Final state: 0 holes, 0 shots, `status='completed'`, no draft, no backup
   reference retained. The player was shown *"Round submission hit a server
   error, but your round data was preserved... Do not re-enter it"* — false
   on both claims.

**Underlying contributor — why the tail was slow at all:** row-by-row
`FOR...LOOP` inserts in both RPCs (~100 individual `INSERT`s per round,
each firing three triggers), `recalculate_round_strokes_gained` running
inside the submit transaction, and auto-save pile-up (three saves fired
within 80 seconds, each abandoned client-side at 10s but still holding row
locks server-side for up to 20s, each new attempt contending with the
previous one's still-live transaction). Self-amplifying: the slower it
gets, the more overlap, the slower it gets.

**Onset — this was new, not a long-tail defect.** Across the prior 30 days
of `admin_events`, every `TimeoutError` on a round path falls on 2026-08-19
(9) or 2026-08-20 (13); zero before. Submits had been succeeding at roughly
1/day through late July/early August. The six migrations stamped
`20260819*` are the most likely trigger, not independently confirmed here.

**Not a round-only bug.** In the same window, `getTopInsightForPlayer` and
`fetchShotDriversByCategory` also hit the 10s abort and silently
catch-and-continued — a coach's dashboard quietly missing insights and shot
drivers with *no error surfaced at all*. The fix (below) is a platform-wide
timeout-budget correction, not a round-submit special case.

## User impact (honest blast radius)

- **One round permanently destroyed**: James Peach, 18 holes and 72 shots
  entered by hand over ~30 minutes, unrecoverable (see below).
- **Blast radius checked, not assumed:** a direct query
  (`golf_rounds` where `status='completed'` and no matching `golf_holes`)
  returned exactly one row platform-wide. This was not a systemic
  corruption — one specific interleaving of timeout + concurrent load hit
  one specific player.
- **Latent, unrepaired exposure found in the same investigation:** a
  *separate* bug (`836ce3b6` — "user session expired mid-round", 6
  occurrences / 4 rounds) is `savePartialRound` calling
  `supabase.auth.getUser()` and getting `null` when GoTrue itself was
  contended, not because the session was actually dead. No data was lost to
  it this time (final submit re-sends the whole round), but while it's
  live, auto-save silently stops protecting the player. **Not fixed by this
  incident** — flagged as needing its own diagnosis.
- **Recovery is permanently off the table.** PITR is **not enabled** on the
  production project (verified in the Supabase dashboard, not assumed —
  "Point in Time Recovery is available as an add-on"). Daily snapshots
  bracket the round on both sides (Aug 19 backup at 04:46 UTC predates the
  round; Aug 20 backup at 04:44 UTC postdates the wipe by 85 minutes) — the
  data existed for 31 minutes, entirely between two snapshots. Reconstruction
  from `golf_round_stats_cache` was evaluated and rejected: it pins the
  *multiset* (5 birdies, 8 pars, 5 bogeys, 7 one-putts, etc.) but not which
  hole each belongs to, and fabricating holes/shots to match would poison
  strokes-gained and his trend line permanently. If Peach kept a paper
  scorecard he can re-enter against the multiset; otherwise the round is gone.
- The round was unbricked (`status` flipped `completed → in_progress`,
  2026-08-20 16:09:05 UTC) so Peach isn't blocked from playing his next
  round, but his 2026-08-19 round's real shot data cannot be recovered.

## Repair (PRs / commits / migrations)

Landed same-day, in order:

1. **Never run the destructive fallback on an abort.** An abort means the
   transaction outcome is *unknown*; on an abort the correct response is to
   re-read the round and reconcile, never to delete. Guard sits inside
   `attemptDirectSubmitFallback` (one choke point all four call sites pass
   through). Landed in `src/app/golf/actions/golf.ts`.
2. **`restoreSnapshot` no longer fails silently.** The bare `catch {}` was
   replaced: every restore-stage error is checked, and a failed restore now
   logs at `critical` **with the snapshot attached**, so the round survives
   in the log even when it can't be re-seated.
   - 2b. The "your round data was preserved — do not re-enter it" message is
     now conditional on the backup having actually persisted.
3. **Client abort raised 10s → 35s**, above the 30s ceiling any of these
   RPCs grant themselves, and made storage-aware (mirrors the existing
   `STORAGE_TIMEOUT_MS` idiom). `authenticated` still carries an 8s DB
   `statement_timeout` for ordinary queries, so normal failures are
   unaffected — the new budget only engages calls that legitimately need
   more. Landed in `src/lib/supabase/server.ts`.
4. **Single-flight the auto-save per round** (`FOR UPDATE NOWAIT`) —
   landed as a *separate* incident's fix, see INC-2026-08-20-02 and commit
   `e196ef6a8` (#1517, `save_partial_round_atomic`) plus the
   `submit_round_atomic` mirror the next day (migration
   `20260821043500_single_flight_round_submit.sql`).

**Where fixes 1–3 actually landed is worth recording as its own lesson:**
they are not in a commit of their own. Four sessions were working this
repo's single shared checkout at once, and another session committed while
these files were staged — the fix ended up inside `c38596d82`
("state the join result's type so `main` type-checks again"), alongside an
unrelated `teams.ts` change from a third session. Content was verified
intact (`REQUEST_TIMEOUT_MS = 35_000` and the `isIndeterminateWriteFailure`
guard both present); nothing was lost, but `git log` by subject line will
not find this fix — only a content search will. This is the `git add -A`
hazard `.claude/rules/autonomy.md` warns about, observed live: staging
explicit paths stops *you* sweeping in someone else's work, it does not stop
someone else committing *yours*.

**Discriminator used for "safe to rebuild" vs. "unknown, do not touch":**
SQLSTATE presence. A real Postgres error (e.g. `57014`) always carries one —
Postgres rolled back, so rebuilding is safe. A client-side abort never does —
outcome unknown, refuse to delete. `save_partial_round_atomic` deliberately
gets no such guard: its error path only logs and returns, with no
destructive rebuild behind it, so an abort there costs one auto-save cycle,
never data.

## Recurrence risk

- Fix 4's follow-up (batching the row-by-row hole/shot inserts into
  set-based `INSERT ... SELECT FROM jsonb_to_recordset`, and moving
  `recalculate_round_strokes_gained` out of the submit transaction) is
  **still not landed** — it attacks the latency that produces the tail, not
  just the symptom.
- The `836ce3b6` "session expired mid-round" false-positive is **still not
  diagnosed**. It is a live, unrepaired path where auto-save silently stops
  protecting a player during exactly the kind of DB contention this
  incident describes.
- PITR remains **off** in production — an explicit, still-open owner
  decision. Until enabled, any recurrence of this failure shape is again
  unrecoverable between daily snapshots. Note it protects only from
  enablement forward, nothing retroactive.
- See INC-2026-08-20-02 for the recurrence of the underlying lock-contention
  mechanism seven hours later, and INC-2026-08-21-03 for a related but
  distinct data-integrity issue on the same table (CI writing junk rounds
  into this same production player pool).

## Invariant candidate

**Yes — this is the master spec's own example of what invariants are for.**
Draft predicate (read-only, SQL, production-safe):

```sql
-- INV-ROUND-001: a completed round must have at least one hole.
-- Catches exactly this failure shape: status flips to 'completed' but the
-- destructive-fallback / restore path leaves 0 holes behind.
select r.id, r.player_id, r.status, r.total_score, r.updated_at
from golf_rounds r
where r.status = 'completed'
  and r.updated_at > now() - interval '24 hours'  -- bounded window, not a full scan
  and not exists (select 1 from golf_holes h where h.round_id = r.id);
```

Severity: CRITICAL (data-integrity class). A single non-empty result should
page, not queue. This would have caught the incident within the first
24-hour scheduled run rather than requiring an owner report to surface it.
A companion invariant is worth drafting for the underlying mechanism (any
`golf_rounds` row with 3+ auto-save timeouts inside a 5-minute window is a
lock-pile-up in progress, independent of whether it eventually destroys
data) — that would catch INC-2026-08-20-02's shape *before* it needs a
destructive fallback to become visible at all.

## Replay candidate

**Yes — extension §10-11 names data-loss and concurrency explicitly as top
replay priorities, and this incident is both.**

Minimal sanitized fixture: a `golf_rounds` row in `in_progress` with a
handful of `golf_holes`/`golf_shots` rows (synthetic data, no real
player/team identity), driven through a fake RPC layer that (a) resolves the
`submit_round_atomic` call *after* the caller's abort signal fires but
before the fallback executes, and (b) makes the fallback's restore step also
time out. Expected: pre-fix build ends with 0 holes/0 shots and
`status='completed'` (destroyed); post-fix build refuses the destructive
rebuild on the abort and leaves the round re-readable. This is materially
what `golf-round-submit-abort-no-destructive-fallback.test.ts` already
proves in isolation — the replay's value would be running it against the
*actual* pre-fix commit (not a reconstructed unit test) to get an
independent confirmation, and pinning fix 4 (NOWAIT) as a regression guard
in the same fixture so a future change can't silently reintroduce the
queuing behavior that created the concurrent-write conditions in the first
place.

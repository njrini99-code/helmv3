# INC-2026-08-21-03 — CI's e2e job seeded 37 junk rounds into a real production player's account

- **id:** INC-2026-08-21-03
- **feature_id:** round_tracking (registry key: `golf_round_lifecycle`) — cause is CI infrastructure (`.github/workflows/playwright.yml`, `e2e/golf-round.spec.ts`), not application code
- **first_seen:** unknown exact start (every push to `main` triggered it) — stopped by owner action 2026-08-20 14:25:39 -0400 (commit `65fe08a7b`); discovered and cleaned 2026-08-20 23:00–23:30 (per ledger timestamps)
- **resolved:** 2026-08-20/21 (stopped by `65fe08a7b`; cleaned same night; teardown fix landed as #1557)
- **severity:** MEDIUM (real production account polluted with test data over an extended period; no permanent data loss, fully cleaned with an undo path preserved)
- **classification:** DATA_INTEGRITY (primary — real player account, real roster) / TELEMETRY_DEFECT (secondary — CI test infrastructure writing to production, not a product defect)
- **status:** resolved

## Summary

CI's full end-to-end job ran on **every push to `main`**, against
**production** — real Supabase secrets, real test account
`rinin376@gmail.com` (player `49ffe06d`), on the **real Guilford roster**.
`golf-round.spec.ts`'s save-in-progress test seeded one junk round per CI
run, with **no teardown**. Over an unknown number of pushes this
accumulated 37 rounds under a real player's account, mixed in among their
genuine round history.

## Timeline

- (unknown start) — every push to `main` runs the full e2e job against
  production; `golf-round.spec.ts` seeds a junk `in_progress` round each time
- 2026-08-20 14:25:39 -0400 — owner commit `65fe08a7b`
  ("ci: cut PR check time — chromium E2E manual-only, timezone tests off the
  PR gate," #1524) makes the full e2e job manual-dispatch-only. This was made
  for CI-time reasons, not specifically to stop the prod-writing behavior,
  but it had that effect as a side benefit.
- 2026-08-20/21 (night) — discovered during the overnight Bridge/DB audit
  while investigating an "in_progress rounds pileup" signal; traced to the
  CI job, confirmed empirically clean for 9+ hours by that point (no new
  junk rounds since `65fe08a7b`)
- Cleanup executed via MCP: 37 junk rounds deleted, preserved in
  `backup_ci_junk_rounds_20260821` (37 rows, undo path retained); 666

  genuine round (dated 07-25) was explicitly preserved and verified intact;
  `junk_left=0` confirmed post-cleanup

## Root cause (verified)

`golf-round.spec.ts`'s save-in-progress test authenticated as a real test
account that happens to sit on the real Guilford team roster (not a
seeded/demo team), created a round via the normal app flow to exercise the
auto-save path, and never deleted it afterward. Because the full e2e job ran
on every push — not gated behind manual dispatch, not pointed at a
throwaway stack — each push added exactly one more junk round to that
account's history.

## User impact

- One real player's account (`rinin376@gmail.com` / `49ffe06d`, Guilford
  roster) accumulated 37 junk `in_progress` rounds mixed into their round
  history. Blast radius confirmed as exactly this one player — not spread
  across the roster.
- No stat/analytics corruption identified: the rounds were `in_progress`
  (never submitted), so they would not have contributed to strokes-gained,
  season averages, or CoachHelm genome computation the way a `completed`
  round would.
- Indirect cost: this class of junk data is exactly the shape that fed the
  "in_progress rounds pileup" investigation and, separately, the
  stale-abandonment display bugs in `admin_bridge` (INC-2026-08-21-02) — junk
  test rounds sitting in `in_progress` status make the Bridge's stuck/dormant
  round tiering harder to reason about and harder to distinguish from real
  abandoned rounds during any investigation.

## Repair

- **Immediate stop:** `65fe08a7b` (#1524) took the full e2e job off the
  automatic per-push trigger, making it manual-dispatch-only. This was the
  operative fix for the write-to-production behavior, even though it was
  landed primarily for CI runtime reasons.
- **Cleanup:** 37 junk rounds deleted via MCP with a preserved undo table
  (`backup_ci_junk_rounds_20260821`); 666 cascaded `golf_holes` rows
  removed; the player's one genuine round explicitly verified untouched.
- **Structural fix (#1557):** e2e teardown added via the real UI's discard
  flow (an XPath ancestor-based idiom was needed; a first-pass version
  matching on `text()` was caught and corrected pre-commit) plus a
  prod-seeding header warning so a future manual e2e run against production
  credentials is visibly flagged rather than silent.
- **Owner decision still open, not yet actioned:** the e2e test account
  (`rinin376@gmail.com`) still lives on the real Guilford roster. Recorded
  as a standing item to move it to a demo/seed team so a manual e2e run
  (still possible via workflow dispatch) can no longer write into a real
  team's roster at all, even with teardown in place.

## Verification evidence

- 37 rows counted and matched to `backup_ci_junk_rounds_20260821` (37 rows)
  — count parity confirmed before delete.
- 666 cascaded `golf_holes` rows counted and confirmed cascaded correctly
  (no orphans left behind — explicitly checked, not assumed).
- The player's genuine 07-25 round explicitly queried post-cleanup and
  confirmed present and untouched.
- `junk_left=0` — a follow-up query for any remaining rounds matching the
  junk-seed signature confirmed the cleanup was complete.
- Empirical confirmation that `65fe08a7b` actually stopped new junk rounds:
  9+ hours with zero new junk-shaped rounds appearing before the cleanup was
  executed, ruling out "the job is still running some other way."

## Signals

- CI workflow: `.github/workflows/playwright.yml`, `e2e` job, prior to
  `65fe08a7b` — ran on every push to `main`, no `if:` gate distinguishing PR
  vs. push vs. manual dispatch for the full chromium suite.
- Test file: `e2e/golf-round.spec.ts`, save-in-progress scenario.
- Distinguishing signature used to identify junk rounds vs. real ones during
  cleanup: seeded by the test account, `in_progress` status, no
  corresponding real play session — captured precisely in the cleanup
  queries (not reproduced here to avoid stale-query drift; see the backup
  table for the authoritative row set).

## Recurrence risk

- The manual-dispatch-only gate (`65fe08a7b`) and the #1557 teardown both
  reduce risk, but the test account still sits on a real team's roster. A
  manually-dispatched e2e run (which remains possible) can still write into
  a real production roster if teardown itself fails partway — the same
  failure-swallowing risk pattern seen in INC-2026-08-20-01's fallback.
  Moving the account to a demo team removes this risk structurally rather
  than relying on teardown discipline holding every time.
- No CI gate currently detects a *new* accumulation of this shape
  automatically — the pileup was found via a separate, unrelated
  investigation, not a dedicated check. See Invariant candidate.

## Invariant candidate

Yes. A cheap, bounded, read-only check specific to this exact failure shape:

```sql
-- INV-ROUND-003: the CI/e2e test account should not accumulate more than
-- one in_progress round. A count above 1 means something is writing to
-- production on a repeating trigger without teardown.
select player_id, count(*) as in_progress_count
from golf_rounds
where player_id = '<ci-test-account-player-id>'  -- pin once the account is known/moved
  and status = 'in_progress'
group by player_id
having count(*) > 1;
```

Severity: MEDIUM. This is narrow (one known account) but cheap and would
have caught the pileup on its second or third occurrence rather than
requiring an unrelated audit to stumble onto it 37 rounds in. Broader
version worth considering once the account moves to a demo team: alert on
*any* `in_progress` round accumulation on a demo/seed account past a small
threshold, which generalizes the check beyond this one incident.

## Replay candidate

No. This is a CI/test-infrastructure misconfiguration, not an application
logic defect — there is no code path to reproduce via a fixture; the fix is
already verified structurally (manual-dispatch gate + teardown + the
existing undo table as evidence the cleanup was reversible). Lower priority
under extension §10-11's stated criteria (data-loss, auth/tenancy, silent
corruption, concurrency, offline reliability, critical workflows, CoachHelm
reasoning) — this incident produced no data loss and no corruption of real
data, only pollution that was fully reversible.

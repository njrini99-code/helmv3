# INC-2026-08-15-01 — The schedule importer reported "Synced to your calendar" while writing zero events, plus six more live defects in the same path

- **id:** INC-2026-08-15-01
- **feature_id:** calendar_events (`calendar-sync.ts`, class-schedule text-paste importer; issue #1225)
- **first_seen:** issue #1225 opened 2026-08-02; re-investigated and largely re-scoped 2026-08-15 because two-thirds of the original filing had already been fixed by intervening work
- **resolved:** 2026-08-15 21:38:58 -0400, commit `f59f68cbb`
- **severity:** HIGH (a false-success toast is the worst failure mode for an import feature — the user has no reason to retry or report it, believing the sync worked)
- **classification:** FUNCTIONAL_FAILURE (primary: false-success reporting) / DATA_INTEGRITY (secondary: several sub-defects write wrong data rather than none)
- **status:** resolved for the 7 defects confirmed live at investigation time; one (re-import duplication) is a documented latent risk, deliberately not closed with a migration
- **investigated:** 2026-08-21 (this incident-mining pass; "as of this investigation" elsewhere in this file refers to this date)

## Summary

Issue #1225 was re-verified against `main` before any fix work started,
because two-thirds of the original filing was already stale: the
hardcoded `'Spring 2026'` fallback and the discarded sync-results problem
had been fixed by earlier work, and the parser-format fix from 2026-08-13
(`77b611316`, see `INC-2026-08-13-03`) already held across all seven
export shapes. Only the original "phantom-class" claim survived from the
initial filing. Re-testing against the current code found **seven** live
defects, each reproduced with a concrete input, most unrelated to the one
that had originally been reported:

1. **Success reported for zero events written** — the defect that made
   every other one silent. `calendar-sync` returned `success: true,
   eventsCreated: 0` whenever the desired event set was empty, and the UI
   only recorded a failure on `!success`. A class with no parseable days
   or times (e.g. `"ENGL 200 Composition ONLINE Asynchronous"`) produced
   the toast "Synced to your calendar" and put nothing on the calendar.
   Fixed first, because every defect below degrades loudly once this one
   is honest.
2. **An undated paste on May 15 or August 15 produced an already-ended
   term.** `detectSemester` maps an August day ≤ 15 to Summer; "Summer
   2026" resolves to `{2026-06-01, 2026-08-15}` — a window that has
   already closed by the moment of import on those two specific calendar
   days per year. The `MIN_PLAUSIBLE_TERM_DAYS` override that would have
   caught this only runs when a `customStartDate` is supplied, and a plain
   text paste never has one.
3. **A location line became a phantom class.** `COURSE_CODE_RE` and
   `LOCATION_RE` match the same shape (2–5 letters plus 3–4 digits), so
   "Smith Hall 201" satisfied both and parsed as a fabricated class code
   "HALL 201" with no days and no times, sitting alongside the real class
   it was actually describing the location of. This is issue #1225's
   original "phantom class" report, confirmed still live.
4. **A header row silently stripped the times off the real row below
   it.** The identical paste, without its `Course/Title/Days/Start/
   End/Room` header, parsed `09:00-09:50` correctly; with the header
   present, start and end came back empty. Excel and Banner exports
   always carry a header row.
5. **A custom start date was not bounded by the term's own start.**
   `parseSemesterDates` checked only `>= year-01-01`, so "Fall 2026" paired
   with a `2026-01-20` custom start produced a 329-day term — an MWF class
   generating roughly 140 meetings instead of the expected ~50. Weighted
   as more than cosmetic because `golf_events` is in the realtime
   publication: a bulk insert of that size is one realtime message per row
   fanned out to every open calendar.
6. **Trailing junk became the course name.** `"Advisor: Dr. Jones"`,
   appearing after a blank line, was adopted as the preceding real class's
   `course_name`.
7. **Re-import duplication (latent, not closed).** `golf_player_classes`
   has only `PRIMARY KEY (id)` and the insert path has no dedup, so
   re-pasting the same schedule creates new rows with new ids, hence new
   `[class:<id>]` tags that reconciliation logic cannot see across.
   Production had zero duplicate `(player_id, class_name, semester)`
   groups at investigation time, so nobody had hit this yet. Handled in
   application code; a uniqueness DB constraint was **deliberately not
   added** here, flagged as a separate migration on a shared production
   database requiring its own review.

## Root cause (verified)

No single root cause — seven independently caused defects across the
import pipeline's success-reporting, semester-window inference,
course/location regex disambiguation, header-row handling, term-bounding,
trailing-text handling, and dedup logic. The unifying thread is the same
one named in `INC-2026-08-13-03`'s Recurrence risk: the importer has
historically been tested against a narrower matrix of real-world input
shapes than it needs to handle, and each of these seven was found by
deliberately constructing a concrete adversarial input for each mechanism
rather than by a production report (except #3, which traces to the
original #1225 filing).

## User impact

A player pasting a schedule with any unparseable entry (defect #1) saw a
success toast while nothing was written — no error, no reason to retry.
A player importing near a term boundary on two specific calendar days per
year (defect #2) got a class that had already "ended" the moment it was
created. A player's real class list could include a fabricated "class"
named after a room description (#3). A player using an Excel/Banner
export with its standard header row lost all times on every class (#4) —
plausibly the highest-blast-radius single defect here, since headers are
the *default* shape for the most common export tool. A custom-start MWF
class could generate ~140 meetings instead of ~50 (#5), each one a
realtime broadcast to every open calendar on the team.

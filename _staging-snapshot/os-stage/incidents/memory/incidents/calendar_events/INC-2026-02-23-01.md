## Summary

`PlayerDashboard` and `CoachDashboard` computed a greeting string and
`todayStr` via `new Date()` inside a `useMemo` that ran during SSR. Vercel's
server renders in UTC; the browser renders in the visitor's local timezone.
For any visitor whose local time fell on a different calendar day or
daypart than UTC, the server-rendered HTML and the client's first render
disagreed, producing a React hydration mismatch. Fixed by deferring both
computations to `useEffect`, so the value is only ever computed client-side
after mount.

## Timeline

- **date unknown** — Sentry accumulates 56+ occurrences of JAVASCRIPT-NEXTJS-3
- 2026-02-23 10:31:54 -0400 — `b8d82dd8` fixes both dashboards

## Root cause (verified)

`new Date()` evaluated inside `useMemo` at render time is not
environment-stable: Vercel's server process runs in UTC, the browser runs in
the visitor's local zone. Any component that derives day-boundary or
greeting text from `new Date()` during the render that produces SSR HTML
will hydrate-mismatch for a meaningful fraction of visitors (anyone whose
local offset puts them on a different day, or across a greeting-threshold
hour, than UTC at request time).

## User impact

React hydration errors/console warnings for any visitor outside UTC at the
moment of request; visually this can manifest as a flash of the wrong
greeting or date on first paint. No data was written incorrectly — display
only.

## Repair

**2026-02-23 10:31:54 -0500, commit `b8d82dd81b34b7fce8f58f955a49ca6b77da6078`.**
Move the `new Date()`-dependent computation out of the SSR-shared render
path and into `useEffect`, so server HTML never asserts a specific
wall-clock value that the client must match exactly.

## Recurrence risk

**HIGH as a class, not as this exact mechanism.** This is the earliest
dated member of a recurring "SSR renders in UTC, client renders in local
time / reads client-only state during a shared render path" family that
reappeared repeatedly on calendar-adjacent surfaces:

- 2026-04-02 `dad182fd9` — hydration mismatches on login and calendar pages
- 2026-04-23 `71dd486ee` — two more SSR/CSR drift sources causing React
  #418 (see INC-2026-04-23-01), which explicitly left React #310 on
  `/golf/dashboard` unfixed for lack of a reproducible stack
- 2026-08-20 (post-window, sibling-owned) — `CalendarPage` React #418/#310
  hydration mismatch logged in the Bridge, per the 2026-08-20 error-log
  triage, fixed by commit `8a0b74686` (converting server-shape ISO strings
  to `Date` before formatting in `EventDetailModal.tsx` and
  `FairwayEventEditor.tsx`)

Each fix has closed one specific instance; no structural guard (lint rule,
test, or code-review checklist item) prevents a new `new Date()`-in-render
or client-only-state-in-shared-render-path defect from being introduced
again. Worth an invariant that is a code pattern, not a data query.

## Invariant candidate

Not a SQL invariant (this is a code-pattern class, not a data-shape one).
Candidate as a static/lint check instead: flag `new Date()` calls (or
`window`/`localStorage`/`document` reads) inside `useMemo`/render-body code
in any file under `src/app/golf/(dashboard)/**` or `src/components/golf/**`
that is known to be SSR-rendered. No such lint rule exists today; this is a
gap, not a covered invariant.

## Replay candidate

Yes, cheaply: render the affected component with the server clock and
client clock pinned to different UTC offsets/dates (e.g., server=UTC,
client=UTC-8, request time near a day boundary) and assert no hydration
warning / identical first-paint output. Not implemented as of this
investigation.

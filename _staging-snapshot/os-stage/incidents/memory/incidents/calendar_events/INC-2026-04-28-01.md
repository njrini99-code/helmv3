## Summary

A same-day review pass found and fixed four related defects on the
attendance/RSVP/reminder surface:

1. **Dead-column schema drift.** `attendance.ts` read/wrote columns
   (`responded_at`, `updated_at`, `absence_reason`, `reminder_sent`) that no
   longer existed on the live table; the real columns were `rsvp_at`,
   `checked_in`, `checked_in_at`, `notes`. This produced latent Postgres
   42703 (`undefined_column`) errors on `checkInPlayer`, `bulkCheckIn`, and
   `markNoShow`.
2. **No RSVP-deadline enforcement.** `updateRSVP` did not check whether
   `rsvp_deadline` had passed before accepting a response.
3. **Reminder-spam IDOR.** `sendEventReminderToPlayers` used the
   service-role admin client to write to `golf_calendar_notifications`
   without verifying the caller was on the event team's coaching staff —
   any authenticated user could trigger reminder notifications into any
   team.
4. **Orphan phantom table.** `golf_event_rsvps` was defined in migration
   `030_golf_calendar.sql` but was **never actually created in
   production**; its trigger function lingered in the live database with
   nothing backing it.

## Root cause (verified)

- **Schema drift:** application code and the live schema had diverged —
  columns referenced in `attendance.ts` had been renamed/replaced at some
  point without every call site being updated, producing errors only on
  the specific write paths that still used the dead names.
- **IDOR:** `sendEventReminderToPlayers` used an admin (service-role)
  Supabase client — which bypasses RLS by design — without adding an
  equivalent authorization check in application code. Using the
  service-role client for a write path implicitly requires the code itself
  to enforce what RLS would have enforced.
- **Orphan table:** a migration defined a table that was never actually
  applied/created in the live database (divergence between "recorded in
  the migrations directory" and "applied state" — see the general
  `shipping.md` warning that these two are not the same thing), leaving a
  trigger function referencing a nonexistent table.

## User impact

- Real users hit latent write failures (42703) on check-in, bulk check-in,
  and no-show marking before the schema realignment.
- Any authenticated user (not just a coach) could spam event-reminder
  notifications into any team's calendar via `sendEventReminderToPlayers`,
  until the coach-of-team gate was added — a real cross-tenant abuse
  vector, though no evidence of exploitation was found or claimed in the
  fix commits.
- RSVPs could be submitted after the coach-set deadline, undermining the
  deadline's purpose, until enforcement was added.

## Recurrence risk

Low for the specific defects fixed. Worth noting as a general pattern:
**"recorded in a migration file" is not evidence a table exists in
production** — `golf_event_rsvps` sat as a phantom for an unknown duration.
This is the same category of drift that the 2026-08-19/20 documentation
audit later found at much larger scale (59 non-existent database
identifiers named across `memory/**`). This incident is an earlier,
narrower instance of the same underlying failure mode (docs/migrations
claiming a schema object exists when it doesn't), now generally guarded by
`npm run docs:schema-drift`, though that gate checks documentation
prose against the schema, not migration files against applied state.

## Invariant candidate

Yes, narrow and cheap:

```sql
-- Any golf_calendar_notifications row with notification_type LIKE
-- 'rsvp_response:%' should have a valid player_id suffix resolvable
-- against golf_players — catches a regression to the pre-fix collision
-- shape on the (event_id, user_id, notification_type) UNIQUE constraint.
```

A second, structural invariant worth having going forward: a periodic
check that every table referenced in `supabase/migrations/*.sql` actually
exists in `pg_class` (would have caught `golf_event_rsvps` directly, and
generalizes the drift class this incident exposed).

## Replay candidate

Partial. The schema-drift and deadline-enforcement fixes are directly
testable (call `checkInPlayer`/`bulkCheckIn`/`markNoShow` against the real
column names; call `updateRSVP` past a deadline and assert rejection). The
IDOR is testable as an authz test: call `sendEventReminderToPlayers` as a
coach NOT on the event team's staff and assert rejection. Not confirmed
present in the current test suite as of this investigation.

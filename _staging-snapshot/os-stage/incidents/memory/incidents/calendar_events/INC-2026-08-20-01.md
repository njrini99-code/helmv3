# INC-2026-08-20-01 — Conflict-check gate compared player ids to user ids — denied every coach

- **id:** INC-2026-08-20-01
- **feature_id:** calendar_events (`src/app/golf/actions/golf.ts` — `resolveSharedScheduleScope`, `checkScheduleConflicts` library)
- **first_seen:** 2026-08-20 (same morning as an authz sweep deploy) — first observed failure caught in the Bridge at **19:03:10 UTC**
- **resolved:** 2026-08-20 22:13:03 -0400 (commit `2f800ec47`, PR #1538)
- **severity:** HIGH (100% feature breakage for every coach from the moment of deploy; no data-integrity impact, purely a false-denial availability bug)
- **classification:** FUNCTIONAL_FAILURE (primary) / ROLL_OUT_REGRESSION (secondary — introduced by the same day's authz sweep)
- **status:** resolved

## Summary

A same-day authorization-hardening sweep added `resolveSharedScheduleScope`
with a false premise baked into its own doc comment: *"attendeeIds are auth
user ids."* They never were. The calendar event editor hands the conflict
library `golf_players(id, ...)` records, and the conflict-check library
filters `golf_players.in('id', attendeeIds)` — player-table ids end to end.
The new gate built its allow-set out of auth **user** ids, a set that
structurally cannot contain a player id. Every conflict check with at least
one attendee was denied, for every coach, from the moment the sweep
deployed — a complete, silent breakage of the "find another time" /
conflict-check feature.

Only one coach actually exercised the feature that day, so his single denial
in the Bridge was the only production evidence this had broken for
everyone — a good illustration of why a feature this narrow needs a
deterministic check rather than relying on someone hitting it.

## Root cause (verified)

`resolveSharedScheduleScope`'s allow-set was built from auth **user** ids
(one id space) and checked against `golf_players.in('id', attendeeIds)`
(a structurally different id space — the player table's own primary key).
There is no overlap between the two id spaces by construction, so the
authorization check denied every request that included at least one
attendee, unconditionally, for every coach on every team, from the moment
of deploy. This is not a narrow edge case: it is a 100% breakage of a
feature that fails *closed* (denies availability data rather than leaking
it), which is why it did not show up as a security incident — it showed up
as the feature simply not working.

## User impact

- Every coach who tried to check attendee availability while building a
  calendar event, from the sweep's deploy time through 22:13 ET the same
  day, was denied — told they were "not authorized" to check availability
  for their own roster.
- No data exposure occurred (the bug fails closed, denying legitimate
  access rather than leaking conflict data to unauthorized viewers) — the
  gate's actual security purpose (conflict results leak names, avatars, and
  busy-titles, so foreign ids must stay denied) was never compromised.
- Confirmed single-day, single-symptom blast radius: only one
  `admin_events` row for this exact fingerprint exists in the incident
  window, consistent with low feature usage that day rather than a
  narrowly-scoped bug — the code path was broken for 100% of callers, usage
  was simply low.

## Repair

- `2f800ec47` ("fix(golf): conflict-check gate spoke the wrong id
  language — denied every coach," #1538). The allow-set is now built from
  the **player ids** on the caller's teams (staffed teams for a coach,
  joined teams for a player, both for a dual-role account) — the same id
  kind the client sends and the conflict library consumes. The gate's
  actual purpose (deny foreign ids) is unchanged; only the id kind it
  compares against was wrong.
- The RETRY-vs-DENIED distinction on failed roster reads (a transient read
  failure should say "retry," not "denied") was preserved through the fix.
- Bundled in the same PR (separate root cause, same investigation): a fix
  for `savePartialRound`/round-submit auth checks discarding
  `getUser()`'s error object, which made a killed round trip to a
  contended GoTrue indistinguishable from a real session rejection — see
  round_tracking INC-2026-08-20-01/02 for the DB-contention context that
  made this visible the same day.

## Recurrence risk

Low for this exact shape — the fix is covered by id-kind-level tests that
would catch a regression to comparing the wrong id space again. The general
risk pattern is worth naming: this is the second incident in the same
24-hour window (see admin_bridge INC-2026-08-21-01, "resolved-blind") where
a security/authorization or accuracy hardening change shipped with a false
premise stated confidently in its own doc comment, and the premise wasn't
checked against the actual data shape before shipping. Worth a lightweight
review habit — verify an id-kind or filter-semantics claim against a live
query before merging any authorization-gate change — rather than a code fix
specific to this one gate.

## Invariant candidate

Yes — narrow and cheap, and it would have caught this on the first
production call rather than requiring a coach to report it:

```sql
-- INV-CAL-001: resolveSharedScheduleScope's allow-set should never be
-- empty for a coach who has at least one staffed team with roster players.
-- (Application-level invariant — best expressed as a synthetic-check
-- assertion rather than pure SQL, since the allow-set is computed in code,
-- not stored. Included here as the predicate the check should assert.)
--
-- For a coach account with >=1 staffed team and that team has >=1 roster
-- player: resolveSharedScheduleScope(coachId) must return a non-empty
-- player-id set. An empty set for a coach who structurally has attendees
-- to check is the exact shape of this bug.
```

This is better suited to a synthetic/functional check (call the resolver
function directly against a known-good fixture team on a schedule) than a
pure read-only SQL invariant, since the bug lives in application code
comparing two id spaces, not in stored data. Flagging it as a candidate for
the golden-path / functional-check layer rather than the SQL invariant
registry.

## Replay candidate

Yes, and cheap to build. Minimal sanitized fixture: one synthetic coach
account staffed on one synthetic team with 2–3 synthetic `golf_players` rows
(no real names/emails), calling `resolveSharedScheduleScope` and asserting
the returned allow-set is non-empty and contains the expected player ids.
Pre-fix build returns an empty set (or a set built from user ids that never
matches); post-fix build returns the correct player-id set. This is a small,
fast, deterministic replay with no timing dependency (unlike the
round-destruction incidents), making it one of the cheaper replay fixtures
in this batch to actually build.

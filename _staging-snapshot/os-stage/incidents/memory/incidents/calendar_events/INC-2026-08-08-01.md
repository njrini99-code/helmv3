# INC-2026-08-08-01 — Teammates' class schedules (education-record data) leaked across three defense layers: API route, browser query, and display filter

- **id:** INC-2026-08-08-01
- **feature_id:** calendar_events (`GET /api/calendar/events`, the calendar's browser range-fetch hook, `attributeClassEvents`, `golf_events_select_team` RLS policy)
- **first_seen:** discovered via a "C19" audit report on 2026-08-08; underlying exposure had existed since class-schedule sync was built (unknown duration, real production data confirmed exposed)
- **resolved:** 2026-08-08, three commits closing three layers of the same hole: `0ccad97c7` (13:45:02, #1370), `f82257aae` (14:10:23, #1371), `ba7f5477b` (15:12:49, #1375)
- **severity:** CRITICAL (FERPA-adjacent education-record data — course, building, meeting times, full academic term — plus physical whereabouts, exposed to every teammate on a real production team; measured exposure, not theoretical)
- **classification:** SECURITY (data exposure / privacy) — the RLS-policy layer itself remains open by explicit owner-deferred decision (see Status)
- **status:** partially resolved — application-layer exposure closed at all three layers found; the underlying RLS policy (`golf_events_select_team`) still grants every rostered player SELECT on every class row on the team, deliberately deferred pending a `created_by` backfill
- **investigated:** 2026-08-21 (this incident-mining pass; "as of this investigation" elsewhere in this file refers to this date)

## Summary

A single root defect — no application-level filtering scoped a player's
class-schedule rows to that player — existed simultaneously at three
independent layers, and closing any one alone would have left the data
exposed through the others:

1. **`GET /api/calendar/events`** (`#1370`) did `select('*')` on
   `golf_events` scoped only by `team_id`, with zero class-row filtering.
2. **The browser's calendar range-fetch hook** (`#1371`) fetched
   `golf_events` directly from the client using the anon key; the calendar
   *page* filtered class rows in the DOM after the fact, which is a
   display filter, not a privacy boundary — the rows had already crossed
   the wire and sat in the page's network payload, one DevTools tab away
   from any teammate.
3. **`attributeClassEvents`** itself (`#1375`), the shared in-memory
   filter both surfaces relied on, degraded **open**: when it could not
   resolve a class row's owner (e.g. a transient roster-read failure), it
   left the row visible rather than hiding it — so a single failed lookup
   flipped a player's calendar from "my classes" to the whole squad's,
   fully rendered.

**Measured on production, same day, same team** (Shenandoah women's golf):
**323 class rows** belonging to three named players — Sofia Bogaty (185
rows), Gabriella Frick (110 rows), Carley Westmoreland (28 rows) — course,
building, meeting times, for the full term, readable by their five
teammates via any of the three layers above.

This is filed as one incident because all three commits are one continuous
same-day investigation of one C19 audit finding, explicitly cross-referenced
in each commit message as closing "the same hole" one layer down from the
last ("this is the data layer behind #1370", "third and last layer of the
same hole").

## Root cause (verified)

`golf_events` has no `player_id` and no visibility column; `created_by` is
NULL on every synced class row, so there was and is **no database-level
way to scope class-row ownership**. `golf_events_select_team` grants
`is_golf_team_coach(team_id) OR is_golf_team_player(team_id)` — a positive
RLS grant to every rostered player for every row on the team, class or
not. With no application-level filter, that RLS grant alone was
sufficient for any teammate to read another player's class schedule via
an authenticated fetch. Three call sites independently needed, and lacked,
that application-level filter.

## User impact

Real, measured production exposure: three named players' full-term class
schedules (education-record data plus physical location/whereabouts)
readable by their five teammates through at least three independent
mechanisms, for an unknown duration prior to discovery. No evidence
presented in the fix commits that this was actually exploited by a
teammate (as opposed to being a latent capability), but the exposure
itself is not hypothetical — it is the actual shape of a real request/
response on a real team.

## Repair

Three commits, all 2026-08-08 (see Timeline for full detail): API route
fix at 13:45:02 -0400, commit `0ccad97c7aa902c79b729b9cd73bef7ba4c980b7`
(#1370); browser-query fix at 14:10:23 -0400, commit
`f82257aae1bc4ffe0475519889608130453e05d4` (#1371); display-filter
fail-closed fix at 15:12:49 -0400, commit
`ba7f5477b72e2b30154e19b3c940d9b9042e08c6` (#1375). Net effect: the API
route and the browser query both now narrow to "non-class rows + the
viewer's own class rows" at query time (not display time); a coach's
query is intentionally unchanged (the whole squad's class blocks are the
point of the conflict-checker feature for coaches). The in-memory filter
fails closed for players (briefly missing your own classes on a transient
error is treated as the acceptable failure mode for a privacy filter) and
continues to fail open for coaches by design.

## Recurrence risk

**Confirmed the same root class recurred before this fix** — see
INC-2026-08-05-01 (2026-08-05, #1292), which fixed the *display*-layer
ownership resolution for team-scoped reads three days earlier but
explicitly deferred the RLS-policy fix for the same stated reason
("an owner decision, not a drive-by"). This incident is effectively round
two of the same underlying gap, closing two more layers (API route,
browser query) that #1292 didn't reach — because #1292 fixed the
*display* filter, not the fact that unfiltered rows were already on the
wire.

**The RLS-policy layer itself remains open as of this incident's fix.**
`golf_events_select_team` still grants every rostered player SELECT on
every class row on the team; the fix works because every known
application-layer read path now filters before rendering, but any NEW
read path against `golf_events` that queries by `team_id` alone, without
importing the same class-filtering logic, reopens this exact exposure.
This is a structural risk, not a hypothetical one — it is precisely the
shape of defect that recurred once already (INC-2026-08-05-01 →
this incident) in a three-day window.

## Invariant candidate

Yes, and this is the single highest-value invariant to add given the
confirmed-recurring root cause:

```sql
-- INV-CAL-007: golf_events_select_team should not grant a player SELECT
-- on a class-type row they do not own, once created_by is backfilled.
-- Until that backfill happens, this cannot be enforced at the RLS layer —
-- track it as an open structural gap, not a false-negative invariant.
-- Interim (application-layer) check: any new code path selecting from
-- golf_events by team_id should be audited against the class-filtering
-- helper used by /api/calendar/events and the range-fetch hook.
```

A stronger, permanent fix (backfilling `created_by` on synced class rows
and moving the filter into RLS itself) was explicitly identified and
explicitly deferred in `#1371`'s own commit message as an owner decision.
No evidence found that this was completed before 2026-08-17; flag it as
still open.

## Status

Partially resolved. All three application-layer exposures found by the
C19 audit are closed. The underlying RLS policy grant remains
unchanged and is the structural reason this class of defect can recur at
a fourth layer without warning — see Recurrence risk. Report this as an
open structural risk, not a fully closed incident, until the
`created_by` backfill + RLS-policy fix referenced in `#1371`'s commit
message is actually done.

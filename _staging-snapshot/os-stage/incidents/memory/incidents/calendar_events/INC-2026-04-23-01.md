## Summary

Two independent client/server render-divergence bugs, both producing React
#418 (hydration mismatch):

1. `use-appearance-preferences.ts` read `localStorage` at **module load**
   via a top-level `if (typeof window !== 'undefined')` block, mutating a
   shared `cachedPrefs` object before React hydration ran. Depending on
   `useSyncExternalStore`'s hydration-safeguard timing, this produced
   different date-format text on the client's first render vs. the
   server-rendered HTML for any user with a non-default date format
   preference.
2. `crm/page.tsx` initialized `useState<TabId>` by reading
   `window.location.search` inside a `typeof window !== 'undefined'`
   branch. The server always saw `window === undefined` and rendered
   `'dashboard'`; the client read the real URL and could render a
   different tab (e.g. `?tab=inbound`) — guaranteed hydration mismatch for
   any deep link.

A third case, React #310 on `/golf/dashboard` (1 occurrence, 1 user), was
investigated and explicitly **not fixed**: no anti-pattern was statically
visible in any top-level hook in `PlayerDashboard`/`CoachDashboard`/
`TodayTimeline` (all fire unconditionally, before any early return). Tabled
pending a second occurrence or a reproducible stack.

## Root cause (verified)

Same class as INC-2026-02-23-01: code that reads an environment-dependent
value (`localStorage`, `window.location`) during a code path shared between
SSR and the client's first render, rather than deferring the read to
`useEffect` (post-hydration). Two distinct call sites, same mechanism.

## User impact

Hydration console errors/warnings for affected users; the CRM deep-link
case is user-visible — a user landing on `/golf/admin/crm?tab=inbound`
briefly hydrates with the Dashboard tab tree before the post-hydration
effect promotes the URL param, so the initial paint shows the wrong tab.

## Repair

**2026-04-23 22:33:17 -0400, commit `71dd486eedf3608943aff3224e02697e467902cc`.**

- `use-appearance-preferences.ts`: deferred the `localStorage` read to a
  `useEffect` inside the hook; module load now always leaves `cachedPrefs`
  at defaults, guaranteeing SSR/CSR/hydration all agree. `hydrateCacheOnce()`
  runs once post-mount, reads storage, and notifies subscribers.
- `crm/page.tsx`: removed the `window`-aware branch from the `useState`
  initializer; state always starts at `'dashboard'`. The existing
  `searchParams` sync effect (already present) promotes the URL tab
  post-hydration, so deep links still work end-to-end, just one frame
  later.
- React #310 on `/golf/dashboard`: **not fixed**, deliberately tabled.

## Recurrence risk

**Confirmed to have recurred.** Per the 2026-08-20 Bridge error-log triage
(post-window, sibling-owned for remediation), `CalendarPage` produced React
#418/#310 hydration errors on 2026-08-18–19, root-caused to
`EventDetailModal.tsx`/`FairwayEventEditor.tsx` formatting server-shape ISO
strings without converting to `Date` first, and fixed by commit
`8a0b74686` on 2026-08-20. That is a *different* specific mechanism (ISO
string formatting, not `localStorage`/`window` reads) but the same error
signature and the same general class: something in the calendar/dashboard
render path reads or formats an environment- or shape-dependent value
inconsistently between server and client. This is the second dated
recurrence of the pattern (first: INC-2026-02-23-01) with a third,
independently root-caused instance landing after this fix. Treat "React
#418 on a golf dashboard/calendar surface" as a recurring failure class,
not a one-off, when triaging any future occurrence.

## Invariant candidate

Not a SQL invariant (code-pattern class). See INC-2026-02-23-01's Invariant
candidate section for the same recommendation: a lint/static-analysis rule
flagging `window`/`localStorage`/`document` reads or `new Date()` calls
inside render-body/`useMemo`/`useState`-initializer code in SSR-shared
components would catch this entire recurring family at authoring time
instead of one Sentry-occurrence-driven fix at a time. No such rule exists
as of this investigation — three dated incidents (02-23, 04-23, and the
08-20 recurrence) all hit the same unenforced pattern.

## Replay candidate

Yes for both fixed cases: (1) render `use-appearance-preferences`-consuming
components with a non-default stored preference and assert identical
SSR/first-client-render output; (2) request `crm/page.tsx` with a
`?tab=inbound` query param and assert the server-rendered HTML matches the
client's pre-hydration DOM. Not confirmed present in the test suite as of
this investigation. React #310 has no reproduction and cannot be replayed
until one is found.

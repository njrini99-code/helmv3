# INC-2026-08-07-01 — Class meetings after a DST boundary were an hour early in production: 281 of 879 rows already wrong

- **id:** INC-2026-08-07-01
- **feature_id:** calendar_events (`syncClassToCalendar`, class-sync timezone handling)
- **first_seen:** not independently datable — the defect was live from whenever class-sync first wrote a series crossing a DST boundary; confirmed already-wrong in production at investigation time, spanning events dated 2026-11-02 through 2026-12-15
- **resolved:** 2026-08-07 10:33:16 -0400, commit `1ffd395c8` (#1314)
- **severity:** HIGH (real, already-materialized wrong data affecting real players' calendars — not a hypothetical future bug; 281 of 879 production class-event rows measured wrong at investigation time)
- **classification:** DATA_INTEGRITY
- **status:** resolved (code fix + data repair both applied to production, verified 0 wrong rows remaining)
- **investigated:** 2026-08-21 (this incident-mining pass; "as of this investigation" elsewhere in this file refers to this date)

## Summary

`syncClassToCalendar` stamped every occurrence in a recurring class series
with **one fixed UTC offset**, captured at save time. A semester
consistently crosses at least one US daylight-saving boundary (November),
so a schedule entered in August (EDT, `-04:00`) wrote its November and
December occurrences at `-04:00` too — but November/December are EST
(`-05:00`). Every meeting after the DST change was stored, and displayed,
an hour early. This was not a latent/future-only bug: of 879 class events
in production at investigation time, **281 were already an hour early**,
spanning 2026-11-02 through 2026-12-15, across 17 classes and 2 real
teams. A player checking their December schedule that day saw the wrong
time.

## Root cause (verified)

A fixed numeric UTC offset (`timezoneOffset`) cannot express "the same
wall-clock local time, correctly adjusted, on either side of a DST
transition" — only an IANA timezone identifier (e.g.
`"America/New_York"`) resolved **per occurrence**, at the wall-clock date
of that specific occurrence, can. The prior code resolved the offset once
for the whole series at save time and reused it for every future
occurrence regardless of which side of the DST boundary that occurrence
actually fell on.

## User impact

Any player with a synced class meeting scheduled after the DST change saw
that meeting displayed and (more importantly) treated as busy/conflicting
at the wrong wall-clock hour — a genuine risk of a coach scheduling
practice on top of what looked like a free hour, or a player missing a
class-conflict warning that should have fired. 281 real rows across 2
teams were already wrong at the moment this was found, not merely a
future risk.

## Repair

**2026-08-07 10:33:16 -0400, commit `1ffd395c8104ba157ec3ae86bd82c51a9861a771`
(#1314).** `timezone` (IANA identifier) now travels with the sync payload end to end,
and the UTC offset is resolved **per occurrence** from that zone rather
than once for the series. `timezoneOffset` remains as a fallback only for
any caller not yet updated to pass a zone; an unrecognized zone string
falls back rather than guessing.

**Data repair** (applied to production via two migrations, tracked in the
fix commit): the primary repair does not assume a uniform "+1 hour" shift
— it recomputes each event from the class's own wall-clock time in the
team's timezone, evaluated on that specific event's own local date, so it
is correct on either side of the DST boundary and a no-op for the 598 rows
that were already right. A second, smaller repair caught one row the
first pass missed: it was scoped to rows whose *start* disagreed (the
exact DST-affected population), which skipped one row whose start was
already correct but whose *end* was stale from an earlier edit
(`PSY-222-F2F1`, ending 15:00 while the class's canonical end is 15:30).
Both repair passes are idempotent.

## Verification evidence

As of the fix commit, 2026-08-07: `src/test/lib/class-sync-dst.test.ts` pins that an 08:30 class reads
08:30 in August, November, **and** December — the test includes a
non-vacuity case that reproduces the OLD single-offset behavior and
asserts it drifts to 07:30, so the suite cannot pass against an
implementation that changed nothing. Post-repair production measurement:
879 class events, 0 wrong start times, 0 wrong end times. Typecheck, lint,
1247 tests passing.

## Recurrence risk

Low for this exact mechanism (the fix structurally cannot regress to a
single-offset-for-the-series bug without failing the non-vacuity test
case). Worth flagging as part of a broader pattern: this is one of several
distinct class-sync data-correctness defects found across a roughly
one-week window in August 2026 (per-player leakage 08-05, this DST bug
08-07, the C19 privacy/fail-open family 08-08/09, semester-null-cascade
and parser defects 08-13, importer false-success 08-15) — the
class-schedule-sync subsystem as a whole had an unusually high defect
density in this window. No single shared root cause connects all of them,
but they share a surface (`calendar-sync.ts` / `syncClassToCalendar` and
its immediate callers) that would benefit from a consolidated regression
suite rather than the per-incident testing each fix added individually.

# INC-2026-07-26-01 — Class import wizard's model was unreachable for every screenshot, then a second fix stopped it from inventing meeting days

- **id:** INC-2026-07-26-01
- **feature_id:** calendar_events (class-schedule screenshot import; `schedule-vision.ts`, `SCHEDULE_VISION_MODEL`)
- **first_seen:** date unknown; every schedule-image import was failing at investigation time (#1071)
- **resolved:** 2026-07-26 13:20:38 -0400, commit `d9f33f5ad2` (two-part fix, same commit)
- **severity:** HIGH (100% failure rate on a core import path, followed by a silent-wrong-data risk once reachability was restored)
- **classification:** FUNCTIONAL_FAILURE (reachability) / DATA_INTEGRITY (day-inference guessing)
- **status:** resolved
- **investigated:** 2026-08-21 (this incident-mining pass; "as of this investigation" elsewhere in this file refers to this date)

## Summary

Two sequential defects in the class-schedule screenshot importer, found and
fixed in one investigation:

1. **Total reachability failure.** `SCHEDULE_VISION_MODEL` was set to
   `anthropic/claude-opus-4.8`. Both slug spellings (`opus-4.8` and
   `opus-4-8`) were refused by the account's tier — a
   `GatewayInternalServerError: Free tier users do not have access to this
   model`. Because this file passed a bare `'provider/model'` string, every
   call routed through the Vercel AI Gateway and **never used
   `ANTHROPIC_API_KEY`** the way the chat route does — so having that key
   set in production did not rescue it. The failure was identical for a
   perfectly legible screenshot and a genuinely bad one, so every import
   surfaced as "we couldn't read your schedule" regardless of image
   quality.
2. **Confident wrong-day guessing, once reachability was fixed.** On the
   same test image, the fallback model (Sonnet 5) returned Wed/Fri for a
   class and dropped the Monday meeting — it had inferred meeting days from
   block *duration* (75min ⇒ MWF, 105min ⇒ TR) instead of reading the
   day-pill strip, and said so in its own warning text. A coach relying on
   this would have believed the player was free at 1pm Monday when she was
   actually in class.

## Root cause (verified)

- **Reachability:** a bare `'provider/model'` string always routes through
  the Vercel AI Gateway regardless of `ANTHROPIC_API_KEY` availability, and
  the configured model was outside the account's tier for that gateway
  path — a billing/catalog-tier mismatch, not an image-quality problem, but
  it surfaced identically to one.
- **Day inference:** the vision model, when the day-pill strip was hard to
  read, fell back to inferring days from meeting-block duration heuristics
  rather than reporting uncertainty — a confident-guess failure mode
  specific to LLM-based extraction, not a traditional code bug.

## User impact

100% of schedule-image imports failed before the fix, indistinguishable
from a genuinely unreadable photo. After the reachability fix, a narrower
risk remained: a coach could have believed a player was free during an
actual class period, because the model guessed a wrong meeting day with
high stated confidence.

## Repair

**2026-07-26 13:20:38 -0400, commit `d9f33f5ad2a5232413057dbef013753494194032`.**

- Default model changed to Sonnet 5 (reachable on this account);
  `SCHEDULE_VISION_MODEL` remains an override for accounts with Opus
  access. Added a single retry on the fallback model specifically when the
  primary is UNREACHABLE (a billing/tier error, not a content error) — a
  student is not told their schedule is illegible because of an account
  configuration issue. Schema and content failures still surface as such
  (retrying those would only spend twice for no benefit).
- Prompt now explicitly forbids inferring days from block duration and
  names this exact failure case. A day-only second verification pass reads
  just the day-pill strip; where the two reads disagree, that class's days
  are **cleared** (not intersected, not unioned — both of those are still
  guesses) and the class is flagged in a warning with the existing
  per-class day-toggle UI for the coach/player to fix in one tap. The
  decision logic is pulled into a pure, model-free function
  (`applyDayVerification`) so it is unit-tested without invoking the model,
  including asserting that a majority-style resolution is never taken and
  that a missing second-read row is silence, not disagreement.

## Verification evidence

As of the fix commit, 2026-07-26: verified on the actual screenshot that had failed, through the real
prompt: before = gateway error, zero classes extracted; after = 4/4
classes extracted, 4/4 day sets correct against the pills (MWF / TR / MWF
/ TR), correct times and rooms, confidence 0.70–0.75 with an honest
warning that the pill strip was hard to read. Day-verification logic:
zero wrong day sets shipped across 3 test runs after the fix (vs. multiple
guessing strategies — native-resolution slicing, margin trimming,
position-based reading, best-of-three majority vote — all tried and
rejected during investigation because each still produced wrong answers,
in one case *more* confidently).

## Recurrence risk

Low for this exact defect (model-tier reachability is now decoupled from
per-call configuration risk via the retry-on-UNREACHABLE fallback). Worth
noting the same underlying "single hardcoded model slug, no fallback"
shape recurred conceptually in the 2026-08-13 semester/parser incident
family (see the existing `INC-2026-08-13-02` in this directory), where a
*different* LLM call site had a similar bare-string provider selection
defect discovered in the same investigation session as the semester bug —
model-selection fragility across multiple class-schedule-adjacent call
sites is a recurring theme, not isolated to this one file.

## Invariant candidate

Not a SQL invariant (this is an LLM-call-configuration and prompt-behavior
class). The `applyDayVerification` pure-function extraction is itself the
right invariant-equivalent: any future prompt/model change can be tested
against its documented non-vacuity cases (a lone weekday must not widen; a
missing second read is silence, not disagreement) without needing the
model in the loop.

## Replay candidate

Yes — already implemented as part of the fix: `applyDayVerification` has
direct unit tests independent of the model, and the reachability fix has
a real-screenshot before/after verification captured in the commit
message. Treat those as the replay fixtures.

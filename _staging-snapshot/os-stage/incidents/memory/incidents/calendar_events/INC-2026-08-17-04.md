# INC-2026-08-17-04 — All-day events used inclusive-end-date storage against instant-interval logic, breaking ICS export, month-grid display, and conflict detection on the same defect

- **id:** INC-2026-08-17-04
- **feature_id:** calendar_events
- **first_seen:** 2026-08-17 (three issues filed same day; underlying storage convention predates discovery, exact date not established)
- **resolved_at:** #1494 and #1495 closed 2026-08-17 (same day); #1493 closed 2026-08-17 — all three same-day turnaround
- **severity:** HIGH
- **classification:** FUNCTIONAL_FAILURE (primary — three separate user-facing surfaces broken by one storage/semantics mismatch)
- **status:** resolved (3 of 4 known affected surfaces; 4th latent, see Recurrence risk)

## Summary

`golf_events` stores an all-day event's end date as the coach's literal **inclusive** last day (`golf.ts:2302` writes the End Date field verbatim as `${endDate}T00:00:00+00:00`). Three independent consumers of that same stored value each assumed a different, incompatible semantics, and each broke a different surface:

1. **#1493 — ICS export.** Both calendar-subscription generators fed the inclusive stored end date directly into iCal's `DTEND`, which RFC 5545 defines as **exclusive** (the first day *not* in the event). Every multi-day event exported to a subscribed calendar app would show its final day missing.
2. **#1494 — Month grid / agenda display.** Four separate day-bucketing call sites keyed events only off their start day and ignored the end entirely, so a coach opening the calendar mid-tournament saw "Nothing on the books for this day."
3. **#1495 — Conflict detection.** The conflict checker treated `[start_time, end_time]` as a literal instant interval. Because `end_time` is stored at the *opening* midnight of the inclusive last day, a single-day all-day event read as a **zero-length busy period** (free all day) and a multi-day event's final day read as free — a practice could be booked directly on top of a tournament's last round, the exact failure the conflict checker exists to prevent.

## Root cause (verified)

One storage convention (inclusive end date, written verbatim from a coach-facing date picker) with three independent consumers, none of which agreed with it or with each other on what the value meant. This is the same *class* of defect this codebase has hit before with date/timezone handling (see the `052156d30` "ambient-zone scanner" commit referenced in deploy history around this period, which specifically catalogs "a WALL-CLOCK value crossing into a UTC instant" as a recurring bug shape) — not confirmed here as the same root cause, but the same family of local-date-vs-instant confusion.

## User impact

- **#1493:** measured against production 2026-08-17: 44 all-day events, 14 multi-day (every one a tournament). **Correction made mid-investigation and preserved here as a model of honest scoping:** the first pass claimed a subscriber had already seen a truncated event; re-checked against the actual feed-to-team mapping and found **zero actual exposure to date** — the two active feeds belonged to a demo team with no all-day events, and the two feeds with real teams' events had no matching coach row to ever sync. The defect was real and unconditional in the generator; live user impact was, by measurement, zero at time of fix.
- **#1494:** every coach viewing the calendar mid-tournament, for any of the 14 multi-day events in production, saw a false "nothing on the books" for every day of the event except its first.
- **#1495:** every all-day event in production (30 single-day + 14 multi-day = 44) was invisible to conflict detection for at least part of its span — a coach could double-book practice over any of them with no warning, which is the specific failure mode the feature exists to prevent.

## Repair

- **#1493:** ICS generators fixed to write an exclusive `DTEND` (end date + 1 day) per RFC 5545, rather than the stored inclusive value verbatim.
- **#1494:** all four day-bucketing call sites (`FairwayMonthGrid`, `FairwayAgendaView` day mode, `FairwayAgendaView` range mode, `FairwayCalendar`'s day-view hero count) rebuilt on a shared `eventDaySpan` helper with its own contract tests (inclusive multi-day span, single-day collapse, absent end, inverted end, null start, timed-vs-all-day branch). **Known, accepted UI consequence, not treated as a regression to undo:** multi-day events now correctly claim a chip slot on every day of their span, and `FairwayMonthGrid`'s `MAX_CHIPS = 3` means tournament-heavy months (5 of 14 production multi-day tournaments start in September) will show "+N more" considerably more often. Flagged as a genuine follow-up (a continuation/spanning treatment) rather than fixed in this pass.
- **#1495:** the conflict path (`checkEventConflicts` → `findCommonAvailability` → `generateTimeSlots`) fixed to hand a **24-hour block that fully encloses** the working window, not one that merely overlaps it — verified end-to-end (not just at `getUserBusyPeriods`, which the original tests stopped at) specifically because a slot filter written for partial overlaps could miss a fully-enclosing block and still incorrectly offer a slot.

## Verification evidence

- #1493: production feed-to-team mapping directly queried to correct the initial (wrong) impact claim before closing — a real self-correction preserved in the issue thread, not silently edited away.
- #1494: three of four call sites have direct render tests; the fourth (`FairwayCalendar`'s hero count) is covered indirectly via its now-shared `eventDaySpan` contract tests, with the gap in direct coverage explicitly acknowledged rather than claimed as fully tested.
- #1495: `checkEventConflicts` full-path test confirms the enclosing-block fix actually reaches the coach-visible slot list, not just the lower-level busy-period function.

## Signals

- Issues #1493, #1494, #1495 — all created 2026-08-17, all closed 2026-08-17 (same-day turnaround on all three).

## Recurrence risk

**A fourth affected surface was found and deliberately left unfixed**, on evidence rather than guesswork: `golf_coach_blocked_time` has the identical shape (`all_day` written by `golf.ts:4935`/`:5082` but never selected, and the busy-interval read falls back to time-of-day columns instead of the real `start_date`/`end_date` span). Directly queried against production: **0 total rows, 0 all-day rows** — the table is empty, so there is nothing to verify a fix against and no user currently affected. Recorded as latent: **"If coach blocked-time ever ships for real, this is waiting."** Any future work that populates `golf_coach_blocked_time` must account for this before it becomes a live, user-facing instance of the exact bug this incident fixed everywhere else.

## Invariant candidate

Yes, generalizing across all four surfaces (three fixed, one latent):

```sql
-- INV-CAL-003: any table storing an all_day span (golf_events,
-- golf_coach_blocked_time) should have its end value consumed only through
-- the shared eventDaySpan-family helper, never raw start_time/end_time
-- comparison. Not directly SQL-checkable (it's a code-usage invariant);
-- better suited to an ast-grep rule flagging raw start_time/end_time
-- comparisons against a table with an all_day column. Flagged as a
-- candidate for the custom rule packs under .coderabbit/ast-grep/ rather
-- than the SQL invariant registry.
```

A direct, cheap SQL check is still worth having as a tripwire for the latent surface specifically:

```sql
-- Alert the moment golf_coach_blocked_time stops being empty, so the known
-- latent bug becomes a tracked follow-up instead of a silent recurrence.
select count(*) from golf_coach_blocked_time where all_day = true;
-- expected 0 today; any future non-zero result should re-open this class.
```

## Replay candidate

Yes, moderate value — the underlying `eventDaySpan` contract tests already function as a replay for the display defect (#1494); extending a similar fixture to the ICS-export and conflict-detection paths (synthetic multi-day and single-day all-day events, asserted against expected `DTEND` and busy-interval output) would consolidate the three fixes into one shared regression suite that also guards the latent fourth surface the moment it stops being empty.

## Status

**Resolved** for the three surfaces with real production impact. **Latent, deliberately unfixed** on `golf_coach_blocked_time` — empty table, no current user impact, explicitly flagged for whoever ships coach blocked-time next.

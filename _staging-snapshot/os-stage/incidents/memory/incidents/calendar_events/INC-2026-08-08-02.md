# INC-2026-08-08-02 — C19: the scheduling conflict checker told coaches everyone was free, on two independent failed-read paths

- **id:** INC-2026-08-08-02
- **feature_id:** calendar_events (`checkEventConflicts`, `getUserBusyPeriods` / `getUserBusyPeriodsWithStatus`, availability.ts)
- **first_seen:** discovered via the same "C19" audit report as INC-2026-08-08-01, 2026-08-08
- **resolved:** two commits one day apart — `61260649c` (2026-08-08 12:47:11, #1367) and `f8e64f2ba` (2026-08-09 07:32:41, #1418)
- **severity:** HIGH (advisory surface, not a write-blocking gate, but a coach's next action on a false all-clear is to double-book a real practice on top of a class or existing event)
- **classification:** FUNCTIONAL_FAILURE (fail-open on read error)
- **status:** resolved — both known frames closed; see Recurrence risk for the general pattern's status
- **investigated:** 2026-08-21 (this incident-mining pass; "as of this investigation" elsewhere in this file refers to this date)

## Summary

Two false all-clears on the conflict-check path, discovered a day apart,
both the same "a failed read resolves to empty, and empty reads as
no-conflict" shape:

1. **`checkEventConflicts`** (`#1367`, 2026-08-08) read the attendee list
   first and returned `{ hasConflict: false }` the instant that read came
   back empty — and a *failed* read also comes back empty from the
   caller's point of view. One bad query told a coach every attendee was
   free, without the actual `availability.ts` conflict logic ever being
   entered. One frame down, `getUserBusyPeriods` had five separate reads
   binding only `.data` and discarding `.error`; a failed team read left
   `teamIds = []`, which then skipped the team-events query outright via
   a `teamIds.length > 0` guard — so a player with a failed read appeared
   to have zero events and therefore zero conflicts. Same silent-removal
   shape for the class-read and blocked-time-read branches.
2. **The identity lookup itself** (`#1418`, 2026-08-09) — one frame
   earlier still. The player/coach identity lookups ran in a
   `Promise.all` and only `.data` was taken; on failure, both `player` and
   `coach` came back null, `isCoach` was false, **neither** team branch
   ran, `teamIds` stayed empty, and the team-events query was skipped by
   the same `teamIds.length > 0` gate. The `#1367` fix had already added a
   `partial` flag to signal "this is an incomplete answer, not a genuine
   all-clear" — but this earlier failure point never set it, so the
   caller was told the (empty, wrong) result was complete.

## Root cause (verified)

Supabase-js resolves a failed read as `{ data: null, error }` rather than
throwing. Multiple call sites destructured only `.data`, so a genuine
database/network failure was structurally indistinguishable from "the
query legitimately found nothing" at every point along this chain:
attendee list → team membership → team events / class events / blocked
time → identity lookup. An advisory conflict-checker built on a chain of
silently-optimistic reads degrades toward "no conflict" by construction,
because every failure mode along the chain resolves to an empty
downstream set.

## User impact

Advisory only — this path never blocks a save, so a false all-clear does
not corrupt data, but it removes a warning silently. The described
consequence in both commit messages is the same: "the coach's next move is
to schedule practice over someone's class" (or over an existing event).
This is a real double-booking risk, not merely a cosmetic UI gap.

## Repair

Two commits: `#1367` — 2026-08-08 12:47:11 -0400, commit
`61260649c6717a33c5dda38717ede4d6b00c31ce`; `#1418` — 2026-08-09 07:32:41
-0400, commit `f8e64f2ba4e03de1dce9d0704c5001c9ef40cbdf`.
`ConflictResult` (and the newer `getUserBusyPeriodsWithStatus`, which the
conflict checker now uses instead of the older array-returning
`getUserBusyPeriods`, kept unchanged for its two callers that render
periods directly) carries an optional `partial` field, set only when a
read actually failed — a clean run omits the field entirely, preserving
existing caller behavior. `partial` is not decorative: `insights.ts:4628`
counts it toward `playersFailed`. Explicitly **not** changed: a genuinely
empty RLS result (error === null) stays a clean, real all-clear — flagging
that case too would put a false "couldn't check" warning on every event
with zero attendees, which the fix commit explicitly rejected as
over-correction. `.maybeSingle()` on a user who is genuinely neither
player nor coach correctly returns `{ data: null, error: null }` and stays
a trusted, complete, empty answer — both cases are tested to keep this
distinction from drifting.

## Recurrence risk

**This is one instance of a repo-wide "failed read resolves to empty, and
empty is treated as a genuine result" pattern**, not unique to the
calendar. The same shape was found and fixed the same week in
`team_operations` (task-template roster resolution, `course-library.ts`,
`task-reminders.ts` — see the `team_operations` incidents for 2026-08-07)
and in the class-schedule privacy family (INC-2026-08-08-01, where the
*opposite* failure direction — fail-open exposing data instead of
fail-open hiding a warning — was the defect). Two conflict-checker
call frames were fixed here on consecutive days precisely because the
first fix didn't reach far enough back in the call chain; a third,
undiscovered frame earlier in the chain (e.g., inside `availability.ts`'s
own internals) cannot be ruled out without a systematic sweep, which does
not appear to have been done as a single pass — these were found
incrementally, by testing what the previous fix's own boundary revealed.

## Invariant candidate

Not a SQL invariant (this is an error-handling code pattern, repeated
across many call sites). The `partial` flag itself is the right ongoing
guard, but only for code that checks it — a regression test asserting
"a forced Supabase error on the attendee read / team read / identity read
results in `partial: true`, never a clean empty all-clear" for each of the
frames fixed here (and ideally for `availability.ts`'s own internals,
unverified in this investigation) is the most direct standing check.

## Replay candidate

Yes, cheaply, for both fixed frames: mock a Supabase error on (a) the
attendee-list read and (b) the player/coach identity read, and assert
`checkEventConflicts` returns `partial: true` rather than a clean
`hasConflict: false`. Both fix commits' own test deltas are this exact
shape (see Verification evidence) — treat those as the replay fixtures.

## Status

Resolved for the two frames found. See Recurrence risk for why this
should not be read as "the fail-open pattern is fully closed" across the
whole conflict-check call chain.

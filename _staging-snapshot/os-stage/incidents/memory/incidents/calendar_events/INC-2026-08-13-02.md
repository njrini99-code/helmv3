# INC-2026-08-13-02 — Class semester was never persisted: null columns re-guessed the term on every edit, silently re-dating series

- **id:** INC-2026-08-13-02
- **feature_id:** calendar_events (class-sync write/read paths, `src/lib/golf/timezone.ts`-adjacent code, `parseSemesterDates`)
- **first_seen:** pre-existing at unknown depth (data measured as already corrupted at investigation time); investigated and fixed 2026-08-13; backfill of already-written bad data executed 2026-08-20/21 as #1473; **step 4 (6-row `golf_events` DELETE) remains open, owner decision pending**
- **resolved:** write-path fixed 2026-08-13 (`dbbe593dc`, #1446); backfill steps 1–3 completed 2026-08-20/21; **not fully resolved — step 4 open**
- **severity:** HIGH (silent, ongoing data corruption affecting real class schedules for an unknown duration — "it is moving all the events around" was a live player-facing complaint)
- **classification:** DATA_INTEGRITY (primary) / FUNCTIONAL_FAILURE (secondary — the truncated-series half actively deleted a player's real fall schedule)
- **status:** partially resolved (write path fixed and backfilled; 6-row cleanup + 17 orphans await an explicit owner decision)

## Summary

Two related defects, discovered in the same investigation and fixed in the
same commit:

1. **Never-persisted semester.** Three write paths stored
   `semester: ... || null` while three read paths fell back to
   `detectSemester('')` — a pure function of **today's date** — whenever the
   column was null. A null semester column did not mean "no term," it meant
   "re-guess the term on every edit," and the guess moved as the calendar
   moved: a class added in August resolved to Summer; the identical class
   edited in September resolved to Fall — silently re-dating the whole
   series on every touch. This is the mechanism behind the reported
   complaint: *"it is moving all the events around."*
2. **Truncated series from a boundary misread.** A schedule imported on
   6 August carried a real, screenshot-read start date of 12 August (a Fall
   start), but because 6 August (the import date) falls inside the summer
   window, the label said "Summer 2026." `parseSemesterDates` honored the
   custom start date against the *summer* end date and produced a
   2026-08-12 → 2026-08-15 semester — three days — deleting the player's
   entire fall schedule from their calendar.

Measured in production at investigation time: **26 of 30 synced class
series carried a NULL semester**, and **four series had been generated with
only one or two meetings each** (the truncation bug's victims).

## Root cause (verified)

**Bug 1 (null → re-guess):** three write paths persisted `semester` as
either the resolved value or `null` (`... || null`), and three independent
read paths, on encountering null, called `detectSemester('')` — a function
with no arguments describing the schedule itself, resolving purely off the
current wall-clock date. Two constants (the stored value and "whatever
today implies") were expected to agree and had no mechanism keeping them
in sync. All three writes now persist the *resolved* term at write time, so
it is decided once, not re-derived on every future read.

**Bug 2 (boundary misread):** `parseSemesterDates` trusted a custom start
date (read directly off an imported schedule image — strong evidence) but
paired it with the term-window's *label-derived* end date rather than
re-deriving the term from the start date itself. A start date read off the
actual schedule is stronger evidence of the real term than a guess based on
which calendar day the import happened to run on. Fixed: a term left with
under 21 days by its own start date is now re-derived from that start date.
The accepted tradeoff (a late-Fall start extending into Winter) is pinned
in a test with the reasoning recorded inline, not left to be rediscovered.

## Repair

- Write-path fix: all three semester-persisting call sites now store the
  resolved term, not `null`. `dbbe593dc` (#1446).
- Truncation fix: `parseSemesterDates` re-derives the term from a
  screenshot-read start date when the labeled term would produce under 21
  days. Same commit.
- Backfill (issue #1473), steps 1–3 executed 2026-08-20/21 via MCP:
  1. Snapshot `golf_player_classes` → `backup_class_semester_20260813`
     (67 rows preserved as undo).
  2. Derive each class's real term from its own calendar events.
  3. Write the derived term onto the 22 rows with a healthy series
     (label-only correction — no event row touched, no meeting moved).
     Result: 22 fixed (17 Fall, 5 Summer); nulls 43 → 21.
  4. **Not executed:** relabel the 4 truncated series as Fall 2026 and
     delete their 6 bogus meetings so a re-save regenerates the real series
     through the fixed code path. Deliberately left for the owner to
     eyeball before a destructive `DELETE` runs, per the backfill script's
     own design (it ends in `ROLLBACK` by default).
- Classification detail worth preserving: the backfill classifies each
  series by its **last** meeting rather than its first — described as "not
  cosmetic," caught specifically by the dry run before execution. (Term
  ends are fixed by the window; starts are not, so anchoring on the end is
  the more stable classifier.)

  closes the mechanism that produced the silent re-dating going forward.

## Invariant candidate

Yes, cheap and directly targeted:

```sql
-- INV-CAL-002: a synced class series should never carry a NULL semester.
-- Catches exactly the write-path regression this incident was: any new
-- code path that reintroduces `semester: ... || null` shows up here within
-- one scheduled run instead of silently re-dating series again.
select id, team_id, semester, synced_at
from golf_player_classes
where semester is null
  and synced_at is not null;  -- bounded to actually-synced rows, not drafts
```

Severity: HIGH. Also worth a second invariant for the truncation shape
specifically (a class series with fewer than N meetings relative to its
labeled semester length), since that failure mode is structural, not just a
null check.

## Replay candidate

Yes. Two small, independent fixtures:
1. **Null re-guess:** a synthetic `golf_player_classes` row with
   `semester=null`, read on two different fake "today" dates (one in each
   half of an academic year) — pre-fix, the two reads disagree; post-fix,
   the write path is exercised directly and the stored term never depends
   on read-time date.
2. **Truncation:** a synthetic schedule-import payload with a start date
   inside one labeled term window but structurally a different term (the
   real 6 August → 12 August shape, with synthetic dates) fed to
   `parseSemesterDates` — pre-fix produces a sub-21-day series; post-fix
   re-derives the full term from the start date.

Both are cheap, deterministic, and directly reproduce the two distinct
mechanisms rather than relying on timing.

# INC-2026-03-23-01 — Calendar notification inserts threw duplicate-key errors on repeated event triggers

- **id:** INC-2026-03-23-01
- **feature_id:** calendar_events (`golf_calendar_notifications` insert path, event create/update triggers)
- **first_seen:** date unknown; Bridge fingerprint `createGolfEvent.insertNotifications` shows n=15, first occurrence tracked from 2026-03-23
- **resolved:** 2026-03-23 19:47:48 -0400, commit `bf05ff017`; Bridge confirms zero recurrence after 2026-04-04 (fingerprint status: DEAD)
- **severity:** LOW-MEDIUM (errored inserts, not data corruption; the underlying unique constraint was doing its job, the insert method was wrong)
- **classification:** FUNCTIONAL_FAILURE
- **status:** resolved (confirmed dead in production telemetry, no recurrence in 4+ months as of the 2026-08-20 Bridge triage)
- **investigated:** 2026-08-21 (this incident-mining pass; "as of this investigation" elsewhere in this file refers to this date)

## Summary

`golf_calendar_notifications` carries a UNIQUE constraint on `(event_id,
user_id, notification_type)`. Any code path that could trigger the same
notification twice for the same event/user/type — e.g. a rapid create
followed immediately by an update — hit a plain `INSERT` and threw a
duplicate-key violation instead of silently no-op'ing. Fixed by switching
to `upsert(..., { ignoreDuplicates: true })`.

## Root cause (verified)

Plain `INSERT` against a table with a UNIQUE constraint on
`(event_id, user_id, notification_type)`, called from a path that can
legitimately fire more than once for the same key (rapid create/update of
the same event). Postgres correctly rejected the second insert as a
constraint violation; the code had no handling for that expected case.

## User impact

Event creation/update requests could surface a server error to the caller
or fail a notification-insert step, even though the "duplicate" was
semantically a no-op (the notification already existed). No data was lost;
this is an availability/error-noise defect, not a correctness one.

## Repair

**2026-03-23 19:47:48 -0400, commit `bf05ff0171b47adb5448ee24f1f630300ee5452e`.**
`insertNotifications` now calls `.upsert(rows, { onConflict:
'event_id,user_id,notification_type', ignoreDuplicates: true })` instead of
plain insert, so a repeat trigger for the same key is a silent no-op rather
than a thrown error.

## Recurrence risk

Low. The fix is structural (idempotent upsert on the exact conflict key,
not a retry or a caught-and-swallowed exception), and the Bridge confirms
no recurrence across a multi-month window. Note the related but distinct
`golf_calendar_notifications` CHECK-constraint defect fixed later
(2026-06-10, `3f711ea36`/PR #260): a *different* bug on the same table
where a content-bearing `event_updated:<timing>` notification type
violated the CHECK constraint and every reschedule notification was
silently dropped. Both defects hit the same table via different
mechanisms (UNIQUE vs. CHECK); worth keeping in mind that this table has a
history of constraint/write-shape mismatches, not just this one instance.

## Invariant candidate

Marginal. A regression test asserting that re-triggering the same
notification key is a no-op (not a thrown error) would catch a reversion
back to plain `INSERT` on this exact path. Not written as a standing SQL
invariant since this is a write-path behavior, not a queryable data-shape
property — a bad insert here simply doesn't happen, it doesn't leave a
detectable row.

## Replay candidate

Yes, cheaply: call the notification-insert path twice with an identical
`(event_id, user_id, notification_type)` key and assert the second call
does not throw and does not create a duplicate row. Not confirmed present
in the current test suite as of this investigation.

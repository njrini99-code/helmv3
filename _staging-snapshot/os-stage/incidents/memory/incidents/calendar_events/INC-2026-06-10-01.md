## Summary

A formal adversarial audit (`docs/audits/GOLFHELM_CALENDAR_AUDIT_2026-06-10.md`)
scored the calendar feature **20/100** and found 38 filings deduping to 32
distinct confirmed defects: 2 P0 (destructive), 11 P1 (major), 14 P2
(moderate), 5 P3 (minor). The audit's own verdict: *"the narrow happy path
... works and is genuinely well secured ... everything surrounding that
path is structurally broken."* Nearly all 32 were remediated same-day in
one large PR (#259), followed immediately by a smaller PR (#260) fixing
three issues the *reviewers of #259 itself* found.

**The two P0s, and why they're one interlocking finding, not two:**

1. Deleting the **first occurrence** of a recurring series cascade-wipes
   the entire series plus every attendee's RSVP history (FK `ON DELETE
   CASCADE`). The root row of a series **is** occurrence #1 and rendered
   indistinguishable from a genuine one-off event, so a coach clicking
   plain "Delete" on what looked like a single event had no series warning
   and no undo.
2. A series edit with scope `thisAndFuture`/`all` applied one literal
   start/end timestamp to every matched row — a title-only "edit all
   events" silently collapsed every occurrence onto a single date. This
   P0 was **latent only because of a P1** (#6: the calendar page's data
   fetch omitted `parent_event_id`/`recurrence_rule`, so the scope picker
   never rendered and series editing was unreachable). Fixing #6 alone,
   without also fixing #1 and #2, would have converted a UX gap directly
   into mass schedule destruction — which is why the audit's own top
   priority explicitly required shipping the recurrence-safety bundle
   (#1, #2, #6) as one PR, not incrementally.

**Selected P1s (11 total, ~93% event-visibility/data-loss impact):**
reminders structurally dead for ~93% of events (weekly Sunday-05:00 cron
against 25h/75min lookahead windows — the hourly-designed 1-hour cadence
had fired zero times ever); editing an event wiped every existing
invitee's RSVP/check-in/reminder-eligibility state (attendee list seeded
empty on the edit form); `createGolfEvent` silently dropped
`requires_rsvp`/`rsvp_deadline`/`max_attendees` (prod fingerprint: 0/75
events had a deadline); conflict detection blind to timed team events
(midnight-UTC date collapse); ICS subscription unreachable for every
player and every mobile coach; a fixed ±3-month calendar window with no
refetch on navigation (an October tournament created in June silently
vanished after save).

## Root cause (verified)

No single root cause — this is an audit-driven remediation of 32
independently-caused structural defects accumulated over the feature's
build-out (recurrence built without series-scope safety; RSVP config
fields added to the type but never wired into the insert path; reminder
cron scheduled once and never revisited when the lookahead windows
changed; ICS entry points never added to the mobile/player shell). The
audit doc's own "Strengths" section is notable: security architecture held
under adversarial review (5 major claims refuted against live RLS),
write-integrity and authz discipline were the best-scored parts — the
defects are concentrated in **lifecycle correctness** (recurrence, RSVP,
reminders), not in access control.

## User impact

- Any recurring series was one misclick from irrecoverable full-series
  deletion (P0 #1), for the entire lifetime of the feature before this
  fix.
- ~93% of events never sent a reminder on any channel (P1 #3).
- Editing any event to add one attendee silently deleted every other
  attendee's RSVP/check-in state (P1 #4) — "silent, unrecoverable, both
  live UIs."
- Every one-off event created with RSVP required landed disarmed; a coach
  had to notice and re-edit (P1 #5, confirmed 0/75 events in prod had a
  deadline before the fix).
- Attendance check-in/no-show/reporting had a full working backend and
  zero UI (P2 #21) — invisible feature.
- A fetch failure on the calendar page rendered as a cheerful empty
  calendar with no error surfaced — "indistinguishable from 'my season got
  wiped'" (P2 #20).

## Recurrence risk

**Medium, on the specific mechanisms this remediation touched.** Several
individual mechanisms fixed here later regressed or resurfaced in a
different shape:
- The class-sync ownership fix in PR #260 is a narrower instance of the
  much larger class-schedule privacy-leak family found and fixed
  2026-08-08 (see INC-2026-08-08-01) — ownership/visibility on
  class-derived calendar rows was a recurring soft spot across three
  separate incidents (this one, 2026-08-05's INC via #1292, and
  2026-08-08's three-layer leak).
- The reminder-cron cadence fix (weekly → hourly) is a distinct mechanism
  from, but the same *feature area* as, the notification-duplicate-key
  incident (INC-2026-03-23-01) and the notification-CHECK-constraint
  defect fixed in the immediate PR #260 follow-up — `golf_calendar_notifications`
  has now had three independent defects across three dates on write-shape/
  constraint mismatches.
- The 2 explicitly-deferred items (availability debounce,
  restore-from-cancelled) remain open as of this investigation's window;
  no evidence found that they were later addressed before 2026-08-17.

## Invariant candidate

Yes, several, directly derivable from the P0/P1 findings — the two most
valuable:

```sql
-- INV-CAL-003: no golf_events row should have end_time < start_time
-- (already enforced by a DB CHECK per this remediation — this invariant
-- exists to catch a REGRESSION of that CHECK, e.g. an unreviewed
-- migration that drops or weakens it)
select id, team_id, start_time, end_time
from golf_events
where end_time < start_time;
```

```sql
-- INV-CAL-004: every event with requires_rsvp = true should carry a
-- non-null rsvp_deadline (catches a regression of P1 #5 — createGolfEvent
-- silently dropping RSVP config)
select id, team_id, created_at
from golf_events
where requires_rsvp = true
  and rsvp_deadline is null;
```

A regression test pinning "deleting occurrence #1 of a series prompts a
scope choice and never cascade-deletes without explicit confirmation"
would directly guard the highest-severity finding (P0 #1) going forward.

## Replay candidate

Yes, several are cheap and deterministic: (1) create a recurring series,
delete its root occurrence, assert the rest of the series survives absent
an explicit "delete all" confirmation; (2) edit a series with scope=all
and a title-only change, assert per-occurrence dates are unchanged; (3)
create an event with `requires_rsvp: true` and assert the deadline
persists. Test coverage for these was added as part of the remediation
itself (976 new tests in PR #259) — treat those as the replay fixtures
rather than writing new ones from scratch.

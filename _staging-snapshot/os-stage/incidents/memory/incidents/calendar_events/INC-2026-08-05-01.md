# INC-2026-08-05-01 — A player's class schedule was indistinguishable from the team's schedule: 556 of 578 "team events" were two players' fall semesters

- **id:** INC-2026-08-05-01
- **feature_id:** calendar_events (`syncClassToCalendar`, `getUserBusyPeriods`, `lib/calendar/class-events.ts`, coach/player dashboard schedule counts, both iCal feeds, CoachHelm chat calendar tool + program pulse, `get_coach_today_schedule`)
- **first_seen:** date unknown; reported by a coach who found filtering the calendar to his own avatar showed his whole roster's classes
- **resolved:** 2026-08-05 22:37:38 -0400, commit `9ca57de2b` (#1292)
- **severity:** HIGH (education-record data — course, building, meeting times, full term — exposed to every team surface that queried "team events"; also crowded out real events in LIMIT-capped reads including what CoachHelm told the coach)
- **classification:** DATA_INTEGRITY (missing ownership marker) / FUNCTIONAL_FAILURE (crowding-out of real events)
- **status:** resolved
- **investigated:** 2026-08-21 (this incident-mining pass; "as of this investigation" elsewhere in this file refers to this date)

## Summary

`syncClassToCalendar` wrote one `golf_events` row per class meeting onto
the **team** calendar — deliberately, so classes appear in the calendar's
"All" lens — but nothing on the row identified *whose* class it was.
`event_type` was `'other'` (indistinguishable from a real team event) and
the only owner link was a `[class:<id>]` tag buried in the free-text
description. Every query that swept `golf_events` by `team_id` and called
the result "someone's schedule" was therefore wrong: on the reporting
team, 578 "upcoming team events" were actually 556 rows belonging to two
players' fall semesters.

## Root cause (verified)

`golf_events` had no `player_id` or visibility column for class rows, and
`created_by` was NULL on every synced class row (no database-level way to
scope ownership). The only distinguishing signal was a tag embedded in a
free-text field that no query filtered on — every "team schedule" read
path treated class rows exactly like real team events.

## User impact

- A coach's own-calendar filter that should show only his events showed
  48 blocks; after the fix, only 22 were genuinely his (the rest were
  players' classes he'd been shown as "his own" or as team-wide).
- "Upcoming events" counts on both coach and player dashboards read 578
  before the fix, 22 after — the real number was buried under class noise.
- Both iCal feeds (external calendar subscriptions) exported class rows as
  generic team events.
- The CoachHelm chat calendar tool and "program pulse" surface are both
  LIMIT-capped reads; classes were crowding out real events in what the AI
  told the coach.
- `get_coach_today_schedule`'s `LIMIT 10` was filling with classes and
  pushing actual practice off the card.
- Also fixed in the same commit: `expandRecurringClass` (the fallback for
  a class with no synced occurrences) matched full weekday names against
  the short day-codes the class UI actually stores (`'M'`, `'Th'`), so it
  had never produced anything — a class using this fallback path silently
  never expanded at all.

## Repair

**2026-08-05 22:37:38 -0400, commit `9ca57de2b1eae5677de19de6f44d5348a4a8b810`
(#1292).** Two markers now carry the distinction, in `lib/calendar/class-events.ts`:
`event_type = 'class'` (filterable in SQL, not buried in description) and
the existing `[class:<id>]` tag now resolved for real ownership.
`getUserBusyPeriods` splits the team sweep and resolves each class
occurrence's owner against `golf_player_classes`, keeping only the
caller's own — **fail-closed**: an unresolvable ownership tag blocks
nobody (a coach has no player row, so no class is ever theirs by
construction). All team-scoped reads listed under User impact now say
"team events only." `expandRecurringClass` is bounded by the class's
`semester` (previously collected on create/import but dropped on the
floor) — a weekly class no longer marks a player busy forever, including
over the summer, and refuses to expand when the term is unknown.
Classes still appear on the calendar's "All" lens, now labeled "Class"
instead of an unexplained generic "Event" chip. Migration: backfill of
666 existing rows to `event_type = 'class'`, applied in batches (`golf_events`
is in the realtime publication — a single bulk `UPDATE` would have fanned
out one realtime message per row to every open calendar). Reviewed by
db-migration-reviewer; the backfill's own reversibility precondition was
checked before applying.

## Recurrence risk

**Confirmed to have recurred, at greater severity, three days later.**
This fix corrected the *display/query-filter* layer (application-level
ownership resolution against `golf_player_classes`). It explicitly did
**not** touch the underlying RLS policy, because the policy scoping
required `created_by` to be backfilled on synced class rows first — noted
in this commit as "an owner decision, not a drive-by." That gap is exactly
what the 2026-08-08 privacy-leak incident (see INC-2026-08-08-01)
exploited: the RLS policy still granted every rostered player SELECT on
every class row on the team, and two lower layers (the browser's direct
`golf_events` query and the `/api/calendar/events` API route) had **no**
application-level filter at all — this fix's `attributeClassEvents`
display filter was the *only* thing hiding teammates' classes, and it was
a display filter, not a privacy boundary: the rows had already crossed the
wire. Read this incident and INC-2026-08-08-01 together — they are the
same underlying "class rows lack a real ownership/visibility mechanism"
root cause, discovered in two passes three days apart, with the RLS-policy
gap this incident explicitly deferred being the exact hole the second
incident closed one layer down (query-time) without yet closing the
policy layer itself.

## Invariant candidate

Yes:

```sql
-- INV-CAL-005: every golf_events row with event_type = 'class' should
-- carry a resolvable [class:<id>] owner tag pointing at a live
-- golf_player_classes row. An orphaned class-type event (tag missing or
-- unresolvable) is either a data-integrity bug or a sign the owning
-- class/player was deleted without cascading the calendar rows.
select ge.id, ge.team_id, ge.description
from golf_events ge
where ge.event_type = 'class'
  and ge.description !~ '\[class:[0-9a-f-]+\]';
```

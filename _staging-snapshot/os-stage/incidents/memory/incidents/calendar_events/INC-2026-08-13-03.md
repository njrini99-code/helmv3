# INC-2026-08-13-03 — The class-schedule parser silently dropped end times, collapsed multi-day weeks to one day, and discarded a schedule's own stated term

- **id:** INC-2026-08-13-03
- **feature_id:** calendar_events (`src/lib/utils/schedule-parser.ts` — `inferColumnsFromContent`, `FULL_DAY_RE`, `parseMultiLineFormat`)
- **first_seen:** date unknown; found by testing the parser against the actual formats students paste (space-columnar, tab, CSV, pipe, multi-line block, 24-hour, long weekday names) rather than only the one shape the existing tests covered
- **resolved:** 2026-08-13 22:46:10 -0400, commit `77b611316`
- **severity:** HIGH (each of the three defects put structurally wrong data — a class with no end time, a class missing two of its three weekly meetings, or a class with the wrong term — directly onto a player's calendar with no error surfaced)
- **classification:** DATA_INTEGRITY
- **status:** resolved
- **investigated:** 2026-08-21 (this incident-mining pass; "as of this investigation" elsewhere in this file refers to this date)

## Summary

This is a **distinct commit and defect set** from the class-semester
persistence bug already documented in this directory as
`INC-2026-08-13-02` (`dbbe593dc`, #1446) — same investigation day, same
general subsystem (class-schedule import), but a different file
(`schedule-parser.ts`) and a different mechanism (parsing format coverage,
not semester persistence). Not merged into that file because the two are
independently root-caused, even though the later `f59f68cbb` (2026-08-15,
see `INC-2026-08-15-01`) commit message explicitly ties this fix to issue
`#1446` ("#1446's parser fix genuinely holds across all seven export
shapes"), suggesting both were tracked under the same issue number despite
being separate code changes.

Three defects, all format-specific data loss:

1. **Delimited exports lost the end time.** `inferColumnsFromContent`'s
   single-time-column branch was guarded on `!classData.start_time`.
   Delimited formats (tab, CSV, pipe) put start and end times in
   *separate* columns — the first column set `start_time`, and the second
   column then hit the now-false guard and was silently discarded. Every
   class imported from a delimited export got a start time and **no end
   time** — a calendar event with no duration.
2. **Space-separated weekday lists collapsed to one day.** `FULL_DAY_RE`'s
   separator character class was `[/,&]`, which matches "Monday,
   Wednesday" and "Monday/Wednesday" but not the equally common "Monday
   Wednesday Friday" (space-separated, no punctuation) — that pattern
   matched only the leading "Monday." A genuine MWF class was saved as
   Monday-only, silently losing two-thirds of its weekly meetings.
3. **A schedule that named its own term had that term discarded.**
   `parseMultiLineFormat` accepted a `semester` parameter but never wrote
   it onto the resulting class object — only the separate compact-line
   parsing branch used it. A document headed "Fall 2026 Schedule," parsed
   via the multi-line branch, produced classes with `semester: ''`, and
   the caller then fell back to `detectSemester('')` — a pure function of
   *today's date*, not the document's own stated term. (This is explicitly
   the upstream half of the three-day-semester bug independently fixed the
   same day in `0bf466dcf`, documented in `INC-2026-08-13-02`: that commit
   stopped a bad *guessed* semester from being persisted; this commit
   stops the parser from discarding the *correct*, document-stated
   semester in the first place.)

## Root cause (verified)

Each defect is a narrow, format-specific logic gap that the single-shape
test coverage never exercised: a boolean guard that assumed one time
column implies a missing (not a second, valid) time; a regex character
class that covered punctuation separators but not whitespace; and a
parameter accepted by a function but never actually written to its output
in one of two parsing branches. None are related to each other except by
being found in the same systematic-coverage sweep.

## User impact

A class schedule imported via a delimited export produced calendar events
with no end time (zero-duration blocks, breaking any duration-dependent
display or conflict logic). A schedule listing an MWF class via
space-separated days produced a calendar with only the Monday meeting —
the player's actual Wednesday and Friday obligations were simply absent,
with no error or warning. A schedule that stated its own term in a header
line ("Fall 2026 Schedule") had that term silently replaced by a
today's-date guess whenever parsed via the multi-line branch.

## Repair

**2026-08-13 22:46:10 -0400, commit `77b611316adac795a6058cd8e90aeed399e59231`.**

1. `inferColumnsFromContent` now fills `end_time` from a later lone time
   column when one is found, requiring `end > start` so an unrelated time
   column (a due date, a second meeting slot) isn't mistaken for the
   class's end.
2. `FULL_DAY_RE`'s separator now also matches whitespace; the alternation
   still requires the next token to actually be a day name, so "Monday
   Physics 200" does not over-match into treating "Physics" as a day.
3. `parseMultiLineFormat` now writes the `semester` parameter onto the
   class object in both branches, so `detectSemester('')`'s today's-date
   guess is only ever a fallback for a genuinely termless document, not a
   silent override of a document that named its own term.

Explicitly **not** claimed as fixed, and named as real remaining gaps:
`course_name` is not extracted when a heading line precedes the first
course entry; building/room fields are not populated by any format.
Neither misplaces a meeting (cosmetic relative to the three fixed
defects), but both are acknowledged open gaps.

## Verification evidence

## Recurrence risk

Medium. This is the third distinct class-schedule-import defect class
found in roughly a one-week window (semester persistence 08-13,
this parsing coverage gap 08-13, the false-success importer bug 08-15 —
see `INC-2026-08-15-01`, which itself found and fixed *seven more*
defects in the same importer two days after this fix). The consistent
theme across all of them: **the parser/importer subsystem was tested
against far fewer real-world input shapes than it actually needs to
handle**, and each fix has been discovered by someone deliberately testing
a wider format matrix rather than by a production incident report. This
suggests remaining untested format combinations are more likely than not
to still contain undiscovered defects of the same shape.

## Invariant candidate

Not a SQL invariant (parsing-logic class). The 14 regression tests added
here are themselves the closest available invariant. A useful addition
would be a documented, maintained matrix of "every export format this
parser claims to support × every field it claims to extract," checked off
against actual test coverage — the three defects fixed here all trace to
cells in such a matrix that had never been exercised.

## Replay candidate

Yes — already implemented as the 14 added regression tests in
`schedule-parser-formats.test.ts`, including the specific non-vacuity
cases called out above. Treat that file as the replay fixture; extend it
rather than writing new ad hoc reproductions if a new format-coverage gap
is found.

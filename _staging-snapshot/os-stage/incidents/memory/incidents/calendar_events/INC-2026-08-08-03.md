- **id:** INC-2026-08-08-03
- **feature_id:** calendar_events (`FairwayCalendar.tsx`'s event map / loaded-range bookkeeping; the availability overlay's `selectedPlayerIds`) — cross-references team_operations' `INC-2026-08-08-03` (tasks roster + CommandPalette), same root-cause family, same investigation day
- **first_seen:** discovered during the 2026-08-08 investigation sweep (same day as the C19 audit fixes)
- **resolved:** two commits same day, 2026-08-08 — `a25e250ee9` (15:43:22 -0400, #1374, calendar events + loaded range) and `e834b101c` (17:09:54 -0400, #1378, availability overlay)
- **severity:** MEDIUM-HIGH (not a visibility/data-leak hole — no RLS or cross-tenant read was involved — but a confident, correct-looking screen showing the wrong team's data to a coach actively trying to schedule around real people)
- **classification:** FUNCTIONAL_FAILURE (stale client state surviving a component-prop change without remount)
- **status:** resolved for the calendar-surface members of this family (see team_operations for the tasks/search member)
- **investigated:** 2026-08-21 (this incident-mining pass; "as of this investigation" elsewhere in this file refers to this date)

## Summary

Four independent surfaces shared one defect shape on 2026-08-08 — client
component state that outlived the team it was scoped to, because a
program-head coach toggling between a men's and women's team does not
remount the shared components; `teamId` changes as a prop, not via a fresh
mount:

1. **Calendar's event map and loaded-range bookkeeping** (`#1374`) — two
   pieces of the calendar hook's state were never cleared on a team
   change, failing in two different directions. `eventVersions` (a
   merge map keyed by event id) only ever ADDS on its `initialEvents`
   effect, so toggling from the men's to the women's team kept every
   men's event in the map — the women's calendar rendered both squads at
   once, no error, just a calendar quietly showing a program that does
   not exist. `loadedRef` was initialized once on mount and never
   rebuilt, so after a toggle the hook believed the new team's date
   window was already loaded and skipped the fetch entirely — a month
   the coach had already visited under the old team rendered only the
   old team's events, "the worse [failure], it looks like a complete
   answer." The real person this happened to: Shenandoah's head coach
   (Scott Singhass) is head coach of *both* Shenandoah squads, so he is
   specifically the one who toggles between them.
2. **Availability overlay's `selectedPlayerIds`** (`#1378`, this incident's
   namesake commit) — `FairwayCalendar` is not remounted on a team toggle,
   so a coach who had three men's players pinned to the availability
   overlay kept them pinned after switching to the women's team. Because
   those player ids don't exist in the new team's member list, the rail
   could not even name them: three anonymous "Player" schedules overlaid
   on the wrong squad's week, with no way to tell whose they were or why
   they were there — while the coach was specifically using this surface
   to find a time everyone is free.
3. **Tasks roster + assignment picker** (`#1376`, filed under
   `team_operations`) — same shape, different surface.
4. **Command palette** (`#1376`, same commit as #3) — same shape, search
   surface instead of a picker.

This incident file covers the two calendar-surface members (#1374, #1378);
the tasks/search member (#1376) is filed as its own incident under
`team_operations` since it belongs to that feature, with an explicit
cross-reference in both directions.

## Root cause (verified)

`FairwayCalendar` receives `teamId` as a prop and is not remounted when a
coach toggles between teams; any `useState` initialized once (mount-only,
often via an empty dependency array with an eslint-disable) survives the
prop change and continues to reflect the previous team until something
explicitly resets it. This is a distinct failure mode from a data-access
bug: RLS was never involved, and the underlying data fetched for the new
team was itself correct — only the leftover **client-side selection
state** was wrong.

## User impact

A coach switching from the men's to the women's team could see the
availability overlay confidently showing three unlabeled "Player" busy-time
blocks that belonged to nobody on the currently-viewed team, while looking
for a time when "everyone" was free — the exact use case this surface
exists for. The commit's own framing: "they were confident, correct-looking
screens about the other squad" — this is the failure mode of a data bug
without any of a data bug's warning signs.

## Repair

**#1378 (availability overlay) — 2026-08-08 17:09:54 -0400, commit
`e834b101cb323c148440376d29da995d28188610`:** `selectedPlayerIds` is reset
**during render** (not in an effect) to match the range hook's own
team-reset timing — an effect-based reset would clear the stale overlay
only after the coach had already seen one bad frame painted. **#1374
(calendar event map) — 2026-08-08 15:43:22 -0400, commit
`a25e250ee9fcd828120916cf67f730e336fcfba9`:** both `eventVersions` and
`loadedRef` are now reset when `teamId` changes, along with the fetch
epoch so a response still in flight for the previous team cannot land
after the switch and overwrite the new team's correct data. Reset happens
**during render, not in an effect** — an effect runs after paint, which
would let the other squad's schedule flash up first on the exact surface
a coach uses to decide who travels. The reset is scoped to key on a
genuine team change, not on every render, since this hook merges events
by generation and a spurious reset would drop a live in-flight edit back
to the last server-fetched payload — that distinction is pinned by a test.

## Recurrence risk

Medium as a class. This is the second dated "client state outlives the
team it was scoped to" family found in this repo's history (the first,
broader instance of "toggle-staleness" thinking doesn't appear to predate
this date in the material reviewed) — four independent surfaces hit the
identical shape in one day, which suggests the underlying pattern (mount-
once state keyed by an implicit "current team" assumption, no shared
"reset-on-team-change" convention) is structural to how team-scoped client
components are built in this codebase, not incidental to any one
component. A fifth or sixth surface with the same shape, not yet
discovered, would not be surprising. No shared hook or lint rule enforcing
"state that depends on the active team must reset on team change" was
found to have been introduced as a result of this incident.

## Invariant candidate

Not a SQL invariant (client-state class). The actionable structural fix
would be a shared `useResetOnTeamChange` (or equivalent) convention/hook
that any team-scoped `useState` is expected to use, with a lint rule or
code-review checklist item flagging a bare `useState` inside a
team-scoped component that isn't wired to team-change resets. Not found
to exist as of this investigation.

## Replay candidate

Yes, cheaply, for both fixed surfaces: render the component with
`teamId=A`, set selection state, change the prop to `teamId=B` without
remounting, assert the selection state is empty/reset for team B. Exact
current test coverage for `#1374` not independently confirmed in this
investigation; `#1378`'s fix is covered by the passing suite referenced
above.

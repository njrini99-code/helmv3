## Summary

Coach Ben Potter reported that a player's detailed stats view was showing
blank/placeholder values ("— / 0 of 1") for strokes-gained, driving
distance, miss bias, proximity, putts/GIR, 3-putts, scrambling, and approach
detail, while round-level fields (scoring, GIR, fairways, putts/round)
rendered normally.

Root cause: `queryDetailedStatsWithClient` has a round-level fallback path.
When a **coach** views a **player's** shot-level stats, the query reads
roughly 1,000 `golf_shots` rows through per-row RLS (`is_golf_team_coach()`
evaluated on every row). Under DB load this exceeded the `authenticated`
role's 8-second `statement_timeout` (Postgres error 57014), and the code
treated that timeout identically to "no shot-level data exists" — silently
degrading to round-level-only stats rather than surfacing an error or
retrying. A player viewing their *own* stats is cheap (own-row RLS, no
per-row coach-membership check) and was unaffected, which is why only the
coach-viewing-player path hit it.

Explicitly ruled out during investigation: the concurrent PGA/LPGA
strokes-gained baseline migration. Ben's stored data (rounds, shots, caches,
standings) was fully intact and untouched by that migration — his
`sg_baseline` was already NULL beforehand. This distinction mattered because
the two could easily have been conflated (both would present as "wrong SG
numbers"), and only one was the actual cause.

## Root cause (verified)

`queryDetailedStatsWithClient`'s round-level fallback triggers on **any**
failure of the shot-level query, without distinguishing "no data exists"
from "the query failed." A coach's view of a player's shot-level stats
walks ~1,000 `golf_shots` rows through `is_golf_team_coach()` evaluated
per row; under load this crossed the `authenticated` role's 8-second
`statement_timeout` (57014). The same query run as `service_role` (no RLS,
no `statement_timeout`) completed in ~63ms — confirming the cost was
entirely the per-row RLS evaluation under load, not the data volume itself
or a missing index. Production `error_logs` independently corroborated 57014
timeouts inside Ben's exact session window, so this was not solely inferred
from the code path.

## User impact

- A coach's detailed view of at least one player (Ben Potter's team,
  Guilford Men's Golf) rendered strokes-gained, driving distance, miss bias,
  proximity, putts/GIR, 3-putts, scrambling, and approach detail all blank,
  with round-level fields still rendering — a partially-broken page that
  looked like a data problem rather than a transient timeout.
- Scope beyond the one reported case not independently re-measured by this
  miner; the fix targets the general coach-viewing-player code path, so any
  coach hitting the same load-dependent timeout would have seen the same
  degradation.

## Repair

**PR #339, merged 2026-06-23T01:02:47Z** (`gh pr view 339 --json
mergedAt`), touching `src/app/golf/actions/stats-data.ts` only.

On a 57014 timeout, the query now retries **once** on the service-role admin
client (no RLS, no `statement_timeout`) and returns full stats instead of
falling through to the round-level fallback. Authorization is already
enforced upstream by `getDetailedStats → verifyPlayerAccess`, so the retry
widens no data access — same pattern as the existing `getDetailedStatsAsAdmin`.
Recursion is guarded via an explicit `allowAdminRetry=false` parameter on the
retry call, so the admin-client retry cannot itself trigger another retry.
If the admin retry also fails, Sentry is paged and the code falls through to
the existing round-level fallback — so a genuine double failure still
degrades gracefully rather than erroring the whole page.

## Verification evidence

- Same query re-run as `service_role`: ~63ms (vs. timing out under RLS at
  8s+) — isolates the cost to RLS evaluation specifically.
- Production `error_logs` show 57014 timeouts in Ben's exact session window
  — corroborates the reported symptom against server-side evidence, not
  just the client screenshot.
- Explicitly ruled out the SG-baseline migration as a contributing cause by
  checking Ben's `sg_baseline` was already NULL pre-migration and his stored
  data was untouched — a documented negative check, not an assumption.
- Code-review flagged one residual gap on this PR, not independently
  confirmed fixed by this miner: `getDetailedStatsAsAdmin` (which already
  uses the service-role client) does not explicitly pass
  `allowAdminRetry=false` at its call site, so it inherits the new
  `allowAdminRetry=true` default — meaning if that admin-client call ever
  itself produced a 57014, it would spawn an unnecessary second admin-client
  retry. Low-severity (the admin client shouldn't hit RLS-driven timeouts at
  all) but not confirmed closed as of 2026-08-21 (this record's authoring
  date; not re-checked against current `main`).

## Recurrence risk

- The reviewer-flagged gap (`getDetailedStatsAsAdmin` inheriting
  `allowAdminRetry=true` by default rather than explicitly passing `false`)
  was not confirmed resolved as of 2026-08-21 (this record's authoring
  date) — worth a quick check against current `main` before treating it as
  closed. Low practical risk
  since the admin client itself shouldn't be RLS-timeout-prone, but it is a
  documented, unconfirmed loose end.
- The broader pattern — a query timeout silently substituting a degraded
  "looks like normal data" fallback rather than surfacing as a distinguishable
  failure state — is the same class of problem this codebase's
  `EXPECTED_EMPTY_STATES` / soft-failure-observer work (see
  `src/lib/admin/incident-classification.ts`, and commit `3464e4374`,
  "stop filing two routine states as production defects") was later built to
  address generally. This specific incident predates that infrastructure and
  was fixed ad hoc (retry-then-page) rather than by classifying the failure
  mode explicitly — worth checking whether `queryDetailedStatsWithClient`'s
  fallback path now emits a coded, classifiable signal on failure rather
  than only a Sentry page.

## Invariant candidate

Yes — narrow and load-bearing given this exact shape recurred as a class
elsewhere in the codebase:

```sql
-- INV-STATS-001: a player_stats-adjacent detailed-stats read that falls
-- back to round-level-only data should be distinguishable, in telemetry,
-- from a read that found no shot-level data because none exists. If the
-- fallback path fires at materially higher volume for COACH-viewing-PLAYER
-- requests than for PLAYER-viewing-OWN requests, that skew itself is the
-- signature of an RLS-cost-driven silent degradation, independent of any
-- single query's timing.
```

This is better expressed as an application-level metric (fallback-path hit
rate, segmented by viewer-role) than a single SQL predicate, since the
production-safe read-only form doesn't have direct visibility into which
code path served a given request without additional instrumentation.

Severity: MEDIUM. Silent, not data-destructive, but user-facing and prone to
being misdiagnosed as "the data doesn't exist" rather than "the query timed
out," as this incident's title case demonstrates directly.

## Replay candidate

Partial. A fixture with a synthetic team/player and an artificially slowed
`golf_shots` RLS evaluation (or a query harness that forces a 57014) run
through `queryDetailedStatsWithClient` pre- and post-fix would demonstrate:
pre-fix, a coach-viewing-player request silently returns round-level-only
data on timeout; post-fix, the same request retries via the admin client and
returns full stats. Lower priority than data-loss/concurrency classes per
extension §10-11 — this is silent degradation of a read, not data loss or
corruption.

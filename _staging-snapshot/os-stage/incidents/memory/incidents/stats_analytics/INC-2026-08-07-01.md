## Summary

Issue #1297 reported that GolfHelm's player dashboard and CoachHelm AI's
normalization layer read **different strokes-gained column families** from
the `player_stats` cache and reported **contradictory numbers for the same
player**:

- Player dashboard reads `sg_total_per_round` (a per-round aggregate).
- CoachHelm AI normalization reads `strokes_gained_total` (a season aggregate).
- Live data check (as filed): 26 of 28 cached player rows showed the two
  families diverged — one cited example: a player showing **-6.6 SG** on the
  dashboard and **-85.84** in the CoachHelm narrative for the same player.

Root cause as filed: the two SG column families exist and persist
**independently** in `player_stats`. Stat sources (TrackMan, Arccos, Garmin
adapters) populate one family or the other inconsistently, or recalculation
pipelines touch only one family and leave the other stale.

A companion issue, #1300, was filed the same day noting there was **no
automated check** for this: `npm run check:stats` existed but only validated
cached putts/GIR/fairways against raw holes/rounds, with no SG-family
coherence check and no cross-surface (dashboard vs. CoachHelm) agreement
check. #1300's own text states the drift "was discovered via code
inspection, not automated test" — i.e., this class of bug has no detection
mechanism even after being found once.

## Root cause (as filed, not independently re-verified)

Two SG column families (`strokes_gained_*` season aggregates and
`sg_*_per_round` per-round aggregates) persist independently in
`player_stats`. Different stat-ingestion adapters and different
recalculation code paths write to one family or the other without a shared
reconciliation step, so a player's row can carry two numbers for
"strokes gained" that disagree, and different UI surfaces read different
families without either surface knowing the other exists.

**This miner did not re-run the reproduction query as of 2026-08-21** (this
record's authoring date) (`SELECT player_id,
sg_total_per_round, strokes_gained_total FROM player_stats WHERE
sg_total_per_round IS NOT NULL`) against current production, so whether the
26/28-row divergence measured on 2026-08-07 still holds, has grown, or has
been quietly corrected by an unrelated data pipeline change is not known
from this pass.

## Invariant candidate

Yes — this is exactly what #1300 proposed, restated as a concrete
production-safe check:

```sql
-- INV-STATS-002: for any player_stats row where both SG families are
-- populated, they should be mathematically consistent (or the divergence
-- should be small and explainable — e.g., season-to-date vs. most-recent-
-- round scope difference). A large, unexplained divergence between
-- strokes_gained_total and sg_total_per_round is the exact signature #1297
-- measured (e.g., -6.6 vs -85.84 for one player).
select player_id, sg_total_per_round, strokes_gained_total,
       abs(strokes_gained_total - sg_total_per_round) as raw_divergence
from player_stats
where sg_total_per_round is not null
  and strokes_gained_total is not null
  and abs(strokes_gained_total - sg_total_per_round) > 5  -- threshold needs calibration against a legitimate season-vs-round-scope gap
order by raw_divergence desc
limit 50;
```

Severity: HIGH if it still reproduces at anything close to the originally
measured 26/28-row rate — this predicate should be run once, manually,
before anything else, to establish current ground truth.

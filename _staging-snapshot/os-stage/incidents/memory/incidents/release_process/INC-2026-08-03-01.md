## Summary

For roughly 35+ hours (from **2026-08-01 15:04 UTC** to at least **2026-08-03 08:31 UTC**, per direct evidence, likely longer), production served the exact commit deployed on 2026-08-01 (`a2a6a79`, PR #1190 — a dependency-bump commit, not a fix) while `main` sat **5 commits and 120 non-test source files ahead**. That gap contained **two full "deepsec" security remediation waves**, squashed into commit `2a95fca00` (PR #1220, +11,422/−1,417 across 177 files). Concretely, during this entire window, production was actively serving:

- **#1200** — unauthenticated public POST Server Actions (`sendPushNotification`, `sendBulkPushNotification`) with no auth/authorization check, allowing arbitrary-user push spoofing and paid-API abuse.
- **#1199** — `completeCoachOnboarding`'s `_preVerifiedUser` parameter, callable directly by any attacker with a forged identity object, bypassing auth entirely for service-role writes that create organizations, coach accounts, and can flip a `player` role to `coach`.
- **#1198** — a stored (blind) SSRF via an unvalidated Web Push `endpoint`.

All three vulnerabilities had already been **found, fixed, reviewed, and merged to `main`** before this incident was even discovered — the failure was entirely in the deployment pipeline, not in the fix work. Separately, the same investigation found **seven already-CLOSED issues** (#1239–#1245 among them) whose fixes were also not running in production, meaning the GitHub issue tracker was actively lying about what was shipped for the whole gap.

## Root cause (verified)

`vercel.json` carries `deploymentEnabled: {"*": false}` — no branch auto-deploys on push, and production promotion is a manual, on-demand CLI action (per this repo's own documented policy in `CLAUDE.md`/`.claude/rules/shipping.md`). This is a deliberate design choice (cost control, controlled release cadence — "≤2 routine prod deploys/calendar week"), but it has a structural failure mode this incident demonstrates directly: **nothing in the repo compared the production deployment SHA against `origin/main`.** A merge to `main` — including a security fix — created no signal, no alert, and no gate forcing a timely promote. The gap grew silently until someone happened to go looking, specifically triggered by checking whether an unrelated recently-merged fix was actually live.

**Compounding factor, found in the same investigation:** the GitHub issue tracker's own state was actively misleading. Several issues (including seven cited by number) had already been marked CLOSED because their fix was merged to `main`, with no distinction in the tracker between "fixed in code" and "live in production." An operator or a future audit trusting issue state alone would have concluded these vulnerabilities were resolved, when in production they remained fully exploitable.

**A parallel, independently-discovered instance of the identical failure class exists at the database layer**, found the same day by the same investigator: **issue #1262** ("Every uploaded document is readable+deletable by any authenticated user across both sports — the team-scoping migration was merged but never applied to prod," created 2026-08-03 05:51:47 UTC, closed 2026-08-03 23:22:26 UTC — same day, fast resolution, well before my 2026-08-17-onward slice boundary and not claimed as part of this incident's own repair). The repo's own later documentation calls this general pattern "recorded != applied" — a migration file existing in the repo's history is not evidence it was ever run against production. #1262 is the DB-layer sibling of this exact incident: a fix existing in source control with no verification that it reached the live system. **Not investigated further here** — it belongs to the pre-2026-08-17 history and is flagged only as a cross-reference so the pattern is visible.

## User impact

- For a minimum of ~35 hours (2026-08-01 15:04 to at least 2026-08-03 08:31 UTC — the true end of the exposure window is only bounded, not pinned, to sometime before 2026-08-04 02:34), three genuine, previously-audited vulnerabilities were live and exploitable in production: unauthenticated push notification spoofing/API abuse, an unauthenticated privilege-escalation path into service-role writes, and a stored blind SSRF.
- **No evidence was found in the sources reviewed that any of these three were actually exploited during the exposure window** — the investigation and this backfill are both working from static/API verification (comparing deployed source to `main`), not from exploitation logs or Sentry events showing an actual attack. This should be stated as an honest unknown, not assumed either way.
- Seven additional issues (cited as #1239–#1245 in the investigation, not independently re-verified here) were closed in the tracker while their fixes were also not live — meaning any operator trusting the issue tracker's state during this window had a false picture of the platform's actual security posture, beyond just these three headline vulnerabilities.

## Repair

- **The fix itself required no new code** — `2a95fca00` (PR #1220) already contained the complete remediation for both deepsec waves. The repair was entirely a deployment action: promoting `main` to production.
- Confirmed structurally rather than narratively: by 2026-08-04 02:34:27 UTC, `target:production`/`READY` deployments were carrying commits from PRs well past #1220 (specifically #1276 confirmed directly via the Vercel API), which is only possible if #1220's changes were already live.
- **No explicit "promoted" comment, PR, or commit was found confirming the exact promote action or who performed it.** This backfill's resolution window (08-03 08:31 to 08-04 02:34) is the tightest bound the available evidence supports, not a confirmed single timestamp.

## Recurrence risk

**This is the single clearest, most explicitly-named invariant candidate in the entire backfill — the investigation that found this incident stated the missing control directly, unprompted.** From #1269's own final comment: *"nothing today compares the production deployment SHA to `origin/main` — which is why this went unnoticed."*

- No evidence was found that a drift-detection check was ever built following this incident. If one exists, it was not surfaced in any source reviewed for this backfill (`memory/**`, `.github/workflows/**` were not exhaustively re-audited here specifically for this — worth a direct follow-up check before assuming the gap is still open).
- The GitHub-tracker-state-vs-production-state mismatch (issues closed while their fix isn't live) is a second, related, and equally unaddressed gap: nothing ties an issue's `closed` state to a confirmed production deployment SHA.
- Given `vercel.json`'s `deploymentEnabled: {"*": false}` and the documented "≤2 deploys/week" policy remain the operating model (confirmed current as of `CLAUDE.md`, checked 2026-08-21), the underlying condition that allowed a 35+-hour (or longer) silent gap — manual, un-monitored promotion — is structurally still true today unless a drift check was separately added.

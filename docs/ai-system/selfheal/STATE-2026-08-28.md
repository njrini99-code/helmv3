## 5. Gaps observed (the honest part)

Ordered by how much they undermine the system's purpose.

### 5.1 — Two error surfaces that disagree *(biggest)*

The **Errors tab** reads `admin_events` (what the app logs about itself) + live
Sentry issues. The **Reliability tab** reads the cross-source snapshot
(Sentry + Supabase + Vercel), refreshed every 3h. They overlap only partly, run
on different clocks, and **nothing tells the operator why they differ.** Two
tabs both showing "errors," showing different sets, reads as broken.

This is the root of most of tonight's confusion, and it is the same split that
made the analyses invisible in the first place.

**Recommended fix:** one unified error surface — every error appears once,
deduped across all sources, source(s) tagged, analysis attached; Reliability
becomes a *filter/lens* on that one list, not a separate list. This is a
redesign, not a patch. (An earlier investigation rejected *merging the storage
tables* for good reasons — double-counting; but "one operator-facing list" is a
different question from "one table," and is the right goal.)

### 5.2 — "NEEDS MORE EVIDENCE" is mislabeled, and evidence-gathering is shallow

Three of five NEEDS MORE EVIDENCE analyses tonight **found the complete root
cause and named the exact commit that fixes it**, then filed themselves under
"not enough evidence" — because the contract only allows ALREADY FIXED once the
error is *observed* to stop firing post-deploy. The system solved them and
called itself clueless.

The genuinely-thin two (`fetch failed`, a minified React hooks error) were
analysed from the signal *summary* — the agent never pulled the **full Sentry
issue** (source-mapped stack, breadcrumbs, request context), which is exactly
where the missing evidence lives.

**Recommended fixes (contract-only, no deploy):**

1. Cause found + a deployed commit addresses it → **ALREADY FIXED** (Close
   confirms via silence), never NEEDS MORE EVIDENCE.
2. NEEDS MORE EVIDENCE only allowed *after* pulling the full Sentry issue.
3. *(bigger)* A **reproduction** step — a stage that triggers the failing path.
   This is the real answer to "reproduce the error, then write the analysis."

### 5.3 — Repair stage unproven end-to-end

Root cause of the hangs: the agent's first step queried Supabase over an
OAuth-gated MCP server, which a headless (no-browser) process can never
complete — it blocked on device-flow polling (the observed 15–47 min windows).

Fixed: empty MCP set (`--strict-mcp-config`), reads production via headless
`node --env-file=.env.local`, `bypassPermissions` (deny rules still hold),
`--output-format stream-json` (logs never blank again), and a `perl alarm 1800`
watchdog. **But no real run has completed.** 06:40 ET is the first test.

### 5.4 — Capture-time instrumentation is thin

`errorCode` sits on **2.9%** of error rows and `errorHint` on 2.6%. Client
errors carry no stack. `"Load failed"` fragments across ~12 fingerprints (one
transport cause, many call sites) because the rows carry nothing to group on but
the route. Thin evidence at capture is *why* downstream analysis so often lands
on "needs evidence." **Prevention** — richer capture (stable transport error
codes, client stack capture) — is higher-leverage than any downstream fix.

### 5.5 — Worktree lifecycle leak (operational)

`scripts/new-worktree.sh` creates worktrees; nothing retires them. Eleven
accumulated today, seven on long-merged branches, and their `.next` build
outputs filled the disk to **179 MiB free** — which killed a production build on
ENOSPC mid-session. Cleaned up tonight (now ~15 GiB free). The prune query keyed
on PR state already exists in `.claude/rules/autonomy.md`; it is wired to
nothing. **Recommended:** a companion prune script run on a schedule.

### 5.6 — Deploy budget

Five production deploys this ISO week against a ceiling of two. Each was
owner-directed, but the system has no live counter enforcing (or even
surfacing) the budget. `release:budget` is referenced in the ledger as
not-yet-built.

## 6. Recommended next work (prioritized)

1. **Unify the error surface** (§5.1) — the redesign that ends the two-tab
   confusion. Highest user-visible leverage.
2. **Fix the NEEDS MORE EVIDENCE labeling + require full-Sentry-pull** (§5.2,
   items 1–2) — contract-only, no deploy, picked up by the 5:17 ET run.
3. **Prove Repair end-to-end** (§5.3) — watch the 06:40 ET run; if it hangs
   again, the launcher needs deeper work.
4. **Prevention: richer error capture** (§5.4) — stable transport codes + client
   stacks. Turns "needs evidence" into "here's the cause" upstream.
5. **Reproduction stage** (§5.2 item 3) — the deep capability; biggest build.
6. **Worktree auto-prune** (§5.5) — small script, removes a recurring
   disk-exhaustion failure mode.

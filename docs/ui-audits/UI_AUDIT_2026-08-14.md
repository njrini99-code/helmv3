# Run 3 — 2026-08-15 01:22–01:45, coach persona, MOBILE, live prod

**Method limit, stated up front:** Chrome enforces a ~500px minimum window
width, so `resize_window(390)` silently yields a **500px viewport**. Mobile
breakpoints do engage at 500px (`max-width: 640px` matches; the bottom tab bar
renders), so this tests mobile *layout* — but it does NOT test the narrowest
phones, which is where overflow and clipping usually bite. **No claim below
covers 390px.** Real device emulation is needed before mobile can be called
clean.

**Second method trap, worth writing down:** a DOM probe fired 6–9s after
navigation returned zero interactive elements and the text "Loading
dashboard…" on both routes. Read literally that is "the page never loads on
mobile" — a P0. It is not. Waiting a further 8s showed the calendar fully
rendered and correct. **A probe that runs during the loading phase measures
the skeleton, not the page.** The real signal here is cold-load duration
(>14s to interactive), which is the `(dashboard)/layout.tsx` sequential
auth→team query chain diagnosed in the theme workstream — not a mobile bug,
but mobile makes it look like one.

## P0 — React #418 on `/whats-new` (diagnosed 02:45, NOT yet fixed)

The Playwright pass caught `Minified React error #418 … args[]=text` on
`/golf/dashboard/whats-new`, mobile. #418 with a `text` arg is a hydration
**text-content mismatch**, and the cause is unambiguous.

`src/components/fairway/pages/whats-new/FairwayWhatsNew.tsx` is a client
component (`useState` at :206) — which Next still server-renders — and it
formats every timestamp with the **runtime default locale and timezone**:

- `:132` `new Date(bucketIso).toLocaleDateString(undefined, …)`
- `:136` `new Date(iso).toLocaleTimeString(undefined, …)` ← timezone-dependent
- `:142` `new Date(iso).toLocaleString(undefined, …)`
- `:192-193` `dayBucketKey(new Date())` — "today" computed at render time, so
  the server's today and the client's today can be different days

`undefined` as the locale argument means "whatever the runtime default is":
Node's on the server, the browser's on the client. For a *time*, that is a
guaranteed divergence whenever the server and viewer are in different zones —
which is always, for a Vercel function in `iad1` serving a coach anywhere.

**This file is the outlier, not the pattern.** The rest of the app already
does this correctly: the Ask page formats with
`new Intl.DateTimeFormat('en-US', { …, timeZone: ctx.timezone })` on the
SERVER and passes the finished string down, and `ProgramOpening` documents its
`asOfLabel` prop as *"Preformatted on the server — formatting a time on the
client mismatches."*

**Fix (next cycle):** follow the established convention — format on the server
against the team's timezone and pass preformatted strings as props, rather
than reaching for `suppressHydrationWarning`, which would hide the mismatch
while leaving the text to swap under the reader. Deliberately not attempted in
the cycle that found it: a hydration fix that cannot be verified rendering at
mobile width is not a fix, it is a guess.

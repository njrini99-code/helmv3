# CoachHelm Approved Fixes — Implementation Plan
2026-07-25 · read-only spec, no repo edits made · repo: helmv3-wt/e2e-timeout, branch plan/coachhelm-remediation

Three fixes are owner-approved: (1) drain the 200 stranded rounds, (2) fix the effectiveness ledger, (3) move post-round analysis to Inngest. All three ship in **one deploy**. This document is the spec an implementer executes and the founder can sanity-check without reading source.

Every design below already went through an adversarial critique pass. Two of the four lanes had a **blocker** that changed the design; this doc reflects the corrected design, not the original draft. Where I re-verified a critique's claim directly against the checked-out source (not just trusted the critique's own citation), I say so.

## 1. What ships and in what order

### Fix 1 — Drain the 200 stranded rounds + honest cron self-reporting

**File:** `src/app/api/cron/coachhelm-safety-net/route.ts` only.

The critique found the alarm mechanism partly dead and one snippet non-compiling; both are fixed below. Verified against source I read directly: `route.ts:38` (`LOOKBACK_MS = 30 * 24 * 60 * 60 * 1000`), `:63` (`.gte('created_at', sinceIso)`), `:83` (`const pending: Array<{ id: string; player_id: string }> = ...` — no `created_at` in scope today).

1. **Remove the `.gte('created_at', sinceIso)` filter entirely.** `coachhelm_analyzed_at`/`coachhelm_failed_at IS NULL` is already a fully deterministic terminal-state gate — the moment `postRoundTrigger` writes either column, on every code path, that round drops out of this query for good, regardless of age. The date window added zero correctness value; it only ever narrowed which never-processed rounds were visible, which is the entire bug. Live-verified: the true unwindowed population is exactly 200 rows (not thousands) and the partial index `golf_rounds_pending_coachhelm_idx` (`WHERE coachhelm_analyzed_at IS NULL AND coachhelm_failed_at IS NULL AND status='completed'`) already scopes the scan to exactly that set — removing the window costs nothing extra.
2. **Rename `LOOKBACK_MS` → `STALE_THRESHOLD_MS`, reporting-only**, still defaulting to 30 days, optionally overridable via `COACHHELM_SAFETY_NET_STALE_THRESHOLD_MS` (not required for correctness).
3. **Modify the existing `pending` declaration in place** (route.ts:83) to carry `created_at` — do **not** add a second `const pending`. (The original spec's snippet re-declared `pending` as a second statement; applied literally that's a TS2451 duplicate-`const` compile error. The fix is one edited line, not an inserted block.)
4. **Compute the stale backlog as a numeric comparison, not a string comparison.** `r.created_at` comes back over PostgREST as a Postgres timestamptz string; `new Date().toISOString()` uses a different suffix/precision. Use `new Date(r.created_at).getTime() < Date.now() - STALE_THRESHOLD_MS`, not a raw `<` on the two strings — string comparison isn't guaranteed order-preserving across serializer formats.
5. **Alarm via `logServerError` only, unconditionally, severity `'warning'`.** This reaches Sentry + `admin_events` regardless of anything in `job-log.ts` — a real, already-wired channel.
6. **Drop the "reuse job-log metadata keys for the admin cron board" change entirely.** I re-read `src/lib/admin/data/jobs.ts` myself: `BackgroundJobLogRow` (its interface, ~50-55) has no `metadata` field, and `fetchJobsTab`'s select list (~75-79) is `job_type, status, duration_ms, error_message, started_at` — no `metadata`. The only function powering `/admin/jobs` never reads the column this change would have written to. Writing `count`/`processed` into `background_job_logs.metadata` would persist correctly (confirmed: `extractOutcomeMetadata`'s whitelist in `job-log.ts` does include those two keys) but be invisible everywhere in the UI — exactly the "computes and has no effect" pattern this whole mission exists to kill. If cron-board visibility is wanted later, it needs its own change (extend `fetchJobsTab`'s select + the `JobsTab`/`CronBoardRow` types + the Jobs page) — not part of this deploy.
7. **Rewrite the header docblock** (currently documents the 2026-05-23 24h→30d widening, which becomes actively false once the filter it describes is deleted) to describe the new design.

**Owner will observe:** within 30 minutes of the deploy (next scheduled cron tick), the cron's JSON response shows `pending` dropping from 200 toward 0 across one or a few ticks, `recovered`/`failed` counts moving, and — because every one of the 200 rows is older than the 30-day staleness threshold on the first tick — one Sentry `warning`-level event, `cron.coachhelm.safetyNet.staleBacklog`, firing once (or on however many ticks it takes to fully drain). After the drain completes, the alarm goes silent unless a fresh backlog regrows — which would now mean `after()` is losing rounds *again*, not that the cron's own window expired them.

### Fix 3 — Move post-round analysis onto Inngest

**Files:** `src/lib/inngest/client.ts`, `src/lib/inngest/functions.ts`, `src/app/golf/actions/golf.ts`, `src/lib/admin/data/jobs.ts` (1-line), `src/app/api/cron/coachhelm-safety-net/route.ts` (companion change, layered on top of Fix 1's rewrite).

The critique found an **important** correctness bug in the original design (re-verified below) plus a minor duplication; both are fixed.

**The bug, re-verified directly against source:** `submitGolfRoundComprehensive(roundData, existingRoundId)` is a real, wired resubmission path — called from `new-round-client.tsx:1526`, `continue-round-client.tsx:808`, and `FairwayRecoverRound.tsx:386`. A successful resubmission re-runs `submit_round_atomic` against the *same* `existingRoundId` and falls through to the identical shared `after()` block as a first-time submit — there is no status/analyzed-state gate in between. `postRoundTrigger` itself has no "already analyzed?" guard. **Today, in production, every successful resubmission unconditionally re-triggers a fresh CoachHelm pass** — that's existing, relied-upon behavior (a coach fixes a miskeyed hole, resubmits, gets corrected insights). The original design's `inngest.send({ id: 'coachhelm-round-submitted-${roundId}', ... })` plus `idempotency: 'event.data.roundId'` on the function would silently dedupe a second successful submission of the same round within Inngest's ~24h window: no error, no fallback (`send()` doesn't throw on a dedupe), `coachhelm_analyzed_at` already non-NULL from the first pass so the safety-net cron never picks it up either. That reproduces the exact "stale insight, silent no-op, no cron backstop" defect class this whole mission exists to fix, in a new and subtler place, on the resubmit path specifically.

**Fix:** drop the static per-round `id` on the `inngest.send()` call (let Inngest assign one) and drop the function-level `idempotency: 'event.data.roundId'` config entirely. The `concurrency: [{ scope: 'fn', key: 'event.data.roundId', limit: 1 }, { scope: 'fn', limit: 3 }]` constraint is the actual requirement — "never analyze the same round concurrently" — and it's unaffected by removing idempotency; Inngest's own retry model already prevents duplicate *independent* runs from a single event without an idempotency key layered on top.

**Design, otherwise unchanged from the original spec:**

- `client.ts`: add `isInngestConfigured(): boolean` checking both `INNGEST_EVENT_KEY` and `INNGEST_SIGNING_KEY`. **One addition beyond the original spec:** I found `src/lib/admin/data/jobs.ts:156` already computes the identical boolean inline (`inngestActivated: Boolean(process.env.INNGEST_EVENT_KEY && process.env.INNGEST_SIGNING_KEY)`), confirmed by reading the file — a closer, already-shipped precedent than the `gmail-send.ts`/`resend-client.ts` idiom the original spec cited. Change `jobs.ts:156` to call the new `isInngestConfigured()` instead of re-deriving the boolean, so there's one source of truth instead of two that can silently drift.
- `functions.ts`: add `onCoachHelmRoundSubmitted`, consuming `coachhelm/round.submitted`, wrapped in `withBridgeLogging` per the file's own convention, `retries: 3`, `onFailure` logging via `logServerException`, one `step.run()` around `postRoundTrigger`. Register it in the exported `functions` array.
- `golf.ts`: inside the existing `after()` block (still not blocking the user response — the original P-HIGH-1 rationale, golf.ts:1868-1870, still holds), branch on `isInngestConfigured()`. If true, `inngest.send()` the event and return; a `send()` failure is caught and falls through to today's exact direct `postRoundTrigger` call as self-healing. If false, log once at info/`skipSentry` and fall through to the same direct call — with keys unset, behavior is byte-for-byte identical to today.
- `route.ts` companion change (layered on top of Fix 1's already-rewritten query): add a `MIN_AGE_MS` floor (`.lte('created_at', untilIso)`, 5 minutes) so the cron never re-triggers a round still inside its first Inngest attempt's retry-backoff window. Not required for correctness — `postRoundTrigger`'s terminal write is idempotent at the column level and duplicate insight rows are structurally prevented by `golf_coach_insights`'s unique dedup index — but it closes a narrow, pre-existing race cheaply.

**Coordination flag, not a defect:** `src/app/baseball/actions/coachhelm.ts:13` and `src/lib/baseball/coachhelm/outcome-sweep.ts:15` both reference "the Inngest scheduled sweep (`src/lib/inngest/functions.ts`)" as an existing/planned job that doesn't exist in `functions.ts` today. Both this fix and that baseball track edit the same `export const functions = [...]` line — check with whoever owns the baseball CoachHelm work before landing to avoid a merge collision.

**Owner will observe:** with no keys set, nothing changes — the existing regression test (`golf-round-submit-after-chain.test.ts`) passes unmodified because no `.env.test`/CI file sets either key, so `isInngestConfigured()` returns `false` in that suite. With both keys set in Vercel Production before the deploy, new round submissions show up as function runs in the Inngest dashboard, and — critically, now that the bug above is fixed — resubmitting the same round still triggers fresh analysis rather than being silently deduped.

## 2. Exactly what the owner must do

**One deploy. That's it for Fixes 1 and 2 — no other action.** Fix 1's drain is entirely automatic: it starts on the **first scheduled cron tick after the deploy**, not before (the code doesn't run until it's live, and nothing manual triggers it — no curl, no dashboard click, no cron edit). `vercel.json`'s existing `*/30 * * * *` schedule and existing `CRON_SECRET` auth are unchanged.

**Timing for the 200-round drain:** `BATCH_LIMIT=200`, `CONCURRENCY=5`, cron runs every 30 minutes. No direct timing sample exists for a 200-round backlog (every one of the 334 retained `background_job_logs` rows for this cron had `pending=0`, because the entire retained log history postdates the backlog falling outside the old window). The closest real proxy is the sibling `coachhelm-roster-sweep` cron, which calls the same `postRoundTrigger` bridge at `CONCURRENCY=3` across 51 players nightly: 24976-41531ms per real run. Scaled to `CONCURRENCY=5` across 200 rounds (40 chunks), that's an estimated **80-200 seconds for a full drain** — comfortably inside the 300s function budget. Treat this as an estimate, not a guarantee (see §3).

**Fix 3 needs one owner action:** set `INNGEST_EVENT_KEY` and `INNGEST_SIGNING_KEY` in Vercel's Production environment **before** the deploy fires, if the goal is for the deploy to go live already routing through Inngest. Vercel bakes env vars into a deployment at deploy time — a value set in the dashboard *after* the deploy doesn't take effect until the next deploy. Setting the keys afterward is not broken, just deferred: the system correctly stays on the direct `postRoundTrigger` fallback (today's exact behavior) until whatever the next deploy naturally is.

No DB migration, no GRANT, no cron schedule change, no manual endpoint call is required from the owner for any of the three fixes.

## 3. What could go wrong

**Inngest keys absent at deploy time.** Fix 3 simply doesn't activate — `isInngestConfigured()` returns `false`, every submission takes the direct `postRoundTrigger` path exactly as today. This is the same code path Fix 1's cron backstops, so nothing regresses; Fixes 1 and 2 are fully independent of whether Inngest is configured. Mitigation: none needed, this is the intended degrade path — confirmed by the fact that the existing regression test exercises exactly this branch today with no keys set in CI.

**The drain cron run times out or gets killed mid-batch.** Safe by construction, not a data-loss risk. `postRoundTrigger`'s terminal-state write is a per-round `.update(patch).eq('id', roundId)`, independent of every other row in the batch — rounds whose write already landed keep their state; whichever round(s) were mid-flight when a kill happened stay `NULL`/`NULL` and are picked up automatically by the next scheduled tick 30 minutes later. No duplicate-insight risk either way: `golf_coach_insights` has a live `UNIQUE` index (`golf_coach_insights_dedup_key` on `signature, player_id, coach_id, team_id`) and the v2 insight writer upserts against exactly that key. Worst case: the full drain takes a handful of 30-minute cycles instead of one — never an infinite loop, never lost work.

**Awaiting the ledger write (`recordInsightAction`) adds user-visible latency.** `recordInsightAction` is unconditionally failure-silent (full try/catch, `event-ledger.ts:182-216`) — a slow response or DB error can only add latency to the click, never surface an error or roll back the primary mutation, which has already succeeded by the time this call runs. The marginal cost is one more Supabase REST insert on actions that, via `withAdminObserved`'s own unconditional post-return `resolveObservedUser()` await, already pay a same-class round trip after returning — this isn't new latency of a different order of magnitude. **Residual, unresolved:** neither the original spec nor the critique confirmed whether the admin Supabase client has any request timeout configured. Under a genuine Supabase outage, an unbounded `await` could in theory stall a response past the platform's own request timeout. This needs a quick check of the `supabase-js` admin client's fetch/timeout config before shipping — see §5.

**Fix 1 and Fix 3 both edit `route.ts`.** Apply as one combined diff in the order given in §1 (Fix 1's rewrite first, Fix 3's `MIN_AGE_MS` floor layered on top) — applying them as two independent patches against the original file will conflict.

**`functions.ts` collision with the baseball CoachHelm track.** Both add a function to the same exported array; not a defect in this plan, but coordinate before landing (see §1, Fix 3).

## 4. Round Review and Strengths/Weaknesses audit

Investigation only — no code changed for this section, and none of these findings are part of the three approved fixes. All 284 completed rounds and all figures below are FACT (direct file read or live read-only SQL), not inference, unless marked UNVERIFIED.

### Trustworthy

- **The headline Strokes Gained number.** Across all 284 completed rounds, `corr(golf_rounds.strokes_gained_total, -score_to_par) = 0.975` — SG moves in lockstep with the box score, no sign flips or scale outliers. `RoundSGSummary` and the per-hole "expected vs actual" narrative read exclusively from the DB-cached `strokes_gained_*` columns and the canonical `golf-stats-calculator-shots.ts` engine. A separate, self-flagged-dead duplicate (`src/lib/golf/strokes-gained.ts:95`) has zero call sites in production code — only its own tests, which alias-import the canonical version anyway.
- **The narrative/copy layer.** `generateReviewContent` (`round-review-content.ts`) is null-safe by construction: `calculateComparisonAverages` (`round-review-system.ts:314-354` — not `round-review-content.ts`, correcting a mis-citation the critique caught) returns `null` per-field rather than a fabricated benchmark when fewer than 3 comparison rounds exist. The team already self-caught and removed one internal contradiction: a heuristic "Where strokes went" block (built from a hand-tuned `strokesToGain` estimate) was deleted 2026-07-23 because it disagreed with the authoritative per-shot SG tornado (`FilmstripReview.tsx:340-344`). The `strokesToGain` field is still stored on every review row but is no longer rendered anywhere — a future feature should not resurrect it without re-deriving it from the same per-shot SG data the tornado uses.

### Not trustworthy — specific numbers a user should not currently trust

1. **Round Review coverage.** Only 63 of 284 completed rounds (22%) have ever produced a schema-valid review, purely because generation is 100% lazy/on-visit — every completed round already has shot-level data (avg 74.8 shots/round) and a cached SG total, nothing is blocking generation except nobody having opened the review page. "No review yet" on a round is not a data problem; it's an unvisited page. This is separate from, and not fixed by, Fix 3 (Inngest covers `coachhelm_analyzed_at`, not `golf_round_reviews` generation) — a future backfill of round reviews specifically would need its own line item, not covered by the three approved fixes.
2. **The "Strengths & Weaknesses" grades** (`generateStatisticalStrengthsWeaknesses`, `strokes-gained.ts:259`, live via `stats-data.ts:2493` → `StatsSpineStage.tsx`). Graded against one fixed, non-gender/division-aware `COLLEGE_BENCHMARKS` table, while the Season Standing / leak-map screens on the *same player* use gender- and division-tiered PGA/LPGA benchmarks (`stats-leak-maps.ts:186-219`). A women's-team or D3 player can see her GIR%/fairway%/putting grade **disagree between two CoachHelm screens on the same underlying stat.** Do not trust cross-surface agreement between "Strengths & Weaknesses" and "Season Standing" until these are unified onto one benchmark source.
3. **`TeamCategoryLeakBand`'s "needs attention" flags** (`team-category-insights.ts:872-884`). Fire whenever a player is >1 stddev from the team average with **no minimum sample-size floor**, unlike the sibling leak-map cards which explicitly expose `sample_n` for exactly this reason. Real roster sizes are small: 51 `golf_team_members` rows across 9 teams that have any roster at all (13 teams exist total, several with zero members) — several active rosters sit in the single digits, where ">1 stddev below the mean of 4-8 players" is a weak, noise-prone signal the card gives no way to caveat.
4. **A real team's data has been cloned into demo accounts.** `scripts/seed-demo-team-from-guilford.ts` copies real `golf_rounds`/`golf_holes`/`golf_shots` rows from 5 named Guilford College "Men's Golf" players (coach `bpotter@guilford.edu`, a real .edu account) into 5 "Demo University Golf" identities — 51 of Guilford's 67 completed rounds (76%) are cloned, byte-identical shot sequences, into a demo login. A second demo team appears to hold a further duplicate set via an unidentified process. Not a computation bug — Guilford's own reviews are computed honestly from Guilford's own data — but a data-hygiene/privacy issue: anyone using the demo login is looking at a real athlete's real competitive rounds under a fake name. **RESOLVED 2026-07-25: consented.** The owner confirmed Guilford is aware of and agreed to this use. No action required; this should not be re-raised by future audits.
5. **Round-review generation runs the full CoachHelm V2 pipeline twice per cold generation.** `useRoundReviewV2`'s `generate()` calls `generateAndStoreRoundReview`, which itself calls `coachHelmIntelligence.generateRoundReview`, and then separately calls `generateAIRoundReview`, which independently calls the *same* underlying function a second time. Not a trust issue, but a real compute-cost issue given the LLM budget cap. Adjacent to this: a fully-built, zero-caller orphaned API route (`src/app/api/golf/rounds/generate-review/route.ts`) and a ~1970-line largely-dead legacy file (`src/app/golf/actions/round-reviews.ts`) where 14 of 16 exported functions — including a second `createFocusAreaFromReview` explicitly flagged as superseded in `development.ts:936` — have zero live callers. Three files now define something callable `generateRoundReview`; only two are wired to any live UI. Worth its own cleanup pass, not part of the three approved fixes.

## 5. Still open

- **Supabase admin client timeout, unresolved.** Neither the ledger fix's design nor its critique confirmed what request timeout (if any) applies to the admin client's REST calls. Settles by: inspecting the installed `supabase-js` client's default fetch/timeout config, or checking Supabase project settings directly — needed before shipping the `await`-based ledger fix with full confidence.
- **200-round drain timing is an estimate, not a measurement.** No log history exists where the safety-net cron actually processed a nonzero backlog (every retained run had `pending=0`). The 80-200s estimate is scaled from a different cron's proxy workload (`roster-sweep`, same bridge call, different player mix, some of which take a cheap already-analyzed skip-path none of the 200 backlog rounds can take). Settles by: observing the first real post-deploy invocation's `duration_ms` — retroactive, not something that can be known before the deploy without running code.
- **Alarm severity judgment call.** `'warning'` (recommended) vs `'error'` for the `cron.coachhelm.safetyNet.staleBacklog` Sentry event is a one-line, owner-preference decision, not a technical blocker.
- **Inngest concurrency/idempotency field shapes vs the exact installed package version.** Verified against Inngest's public docs via live fetch, not against `inngest@^4.11.0`'s actual installed TypeScript types. TypeScript strict mode catches any field-name drift at compile time; settles by running `tsc` against the real dependency tree before shipping, not by trusting this doc's syntax blindly.

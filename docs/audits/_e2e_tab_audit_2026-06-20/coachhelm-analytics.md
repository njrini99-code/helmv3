## CoachHelm Analytics [coach]

End-to-end audit of the CoachHelm Analytics ("Effectiveness") tab.

- Route: `src/app/golf/(dashboard)/dashboard/analytics/coachhelm/page.tsx`
- Actions: `src/app/golf/actions/coachhelm-analytics.ts`
- Legacy UI (flag OFF): `src/components/golf/coachhelm/analytics/CoachHelmAnalyticsDashboard.tsx` (+ `AnalyticsSummaryCards`, `InsightEffectivenessPanel`, `PredictionAccuracyPanel`, `PatternImpactPanel`)
- Redesign UI (flag ON, **live in prod**): `src/components/fairway/pages/coachhelm/FairwayEffectiveness.tsx` (mounted in `CoachHelmShell`)
- Writers (populate the rollup tables): `src/lib/coachhelm/v2/analytics/effectiveness-writer.ts`, `prediction-performance-writer.ts`, invoked daily by `src/app/api/cron/coachhelm-insight-lifecycle/route.ts` (cron `0 2 * * *` in `vercel.json:50-52`)

### How it is actually wired (end-to-end)

1. **Auth + role gate (page.tsx:25-35).** `getGolfSessionProfile()` → redirect `/golf/login` if no session; redirect `/golf/dashboard` if `!coach`. `getGolfSessionProfile` (session.ts:142-167) resolves `coach` from `golf_coaches WHERE user_id=auth.uid`, so only a coach reaches the body. Team is resolved deterministically via `resolveCoachTeamIdWithCookie(supabase, coach.organization_id, coach.id)` (page.tsx:35); no-team forks to `FeatureUnavailable` (redesign) / bespoke "No Team Found" card (legacy).
2. **SSR data load (page.tsx:78-83).** `Promise.all` over the four loaders `getCoachHelmOverview`, `getInsightEffectiveness`, `getPredictionPerformance`, `getPatternImpact` — all passed `teamId`.
3. **Each loader re-checks auth itself** — `supabase.auth.getUser()` then `verifyTeamAccess(teamId, user.id)` (coachhelm-analytics.ts:147-155, 290-298, 454-462, 630-638). `verifyTeamAccess` uses the `coach_id_for_team` RPC (verify-player-access.ts:84-108), so a player who guesses a teamId still gets `Forbidden`. No role-leak.
4. **Render fork (page.tsx:91-124).** Flag ON → `FairwayEffectiveness` cockpit inside `CoachHelmShell active="effectiveness" role="coach"`, plus `getAlertCounts(coach.id)` for the Signals badge. Flag OFF → `CoachHelmAnalyticsDashboard`. Both receive the SAME four SSR results and re-fetch via the SAME four actions on range-change / refresh.
5. **Tables touched (all sport-prefixed, columns verified vs golfhelm-database.md):**
   - `golf_insight_effectiveness` (rollup; cols match :558-581) — primary read in `getInsightEffectiveness`.
   - `golf_prediction_model_performance` (rollup; cols match :973-995) — primary read in `getPredictionPerformance`, filtered on `period_end >= start` (a deliberate fix for a temporal-drift bug, documented :304-312).
   - `golf_patterns_v2` (cols match :689-722) — read in `getPatternImpact` / `getCoachHelmOverview`. Correctly uses singular `stroke_impact` (default 0); plural `strokes_impact` is empty per memory and is NOT used.
   - `golf_coach_insights` (cols match :231-262) — read in `getCoachHelmOverview` + the live fallback, **through `applyInsightVisibility`** (the v3 visibility contract: v3-engine-only + visible lifecycle states + not-dismissed) so analytics counts match what the product surfaced.
   - `golf_predictions` (cols match :997-1027), `golf_team_members` (`status` enum, default pending; `.eq('status','active')` correct).
6. **Real analytics, not static.** Every displayed figure traces to a query. There are NO hardcoded "demo" numbers — the old mock generators were neutralized: `generateMockInsightEffectiveness` / `generateMockPredictionPerformance` now return all-zero shells used only as the genuine empty state, and `generateMockPatternImpact` was removed entirely (errors now surface as `{success:false}` per the comments at :155-156, :171-181). Rollup tables are actively populated by the daily cron (route.ts:47-48, 268+) via idempotent **upserts** on natural keys (effectiveness-writer.ts:211-216, prediction-performance-writer.ts:299-303) — no destructive delete-then-insert. The redesign cockpit additionally enforces honesty thresholds (InsufficientData / "awaiting signal" below GAUGE_MIN_RESOLVED=2, BUCKET_MIN_RESOLVED=5, GLOBAL_LOW_CONFIDENCE_RESOLVED=50; FairwayEffectiveness.tsx:104-106).

### Expected vs actual (golfhelm-features.md #17)

The feature doc (#17, status ⚠️ 70%) lists the four loaders + the six tables and one Known Gap: "Effectiveness data sparse — `golf_insight_effectiveness` not actively populated." That gap is now **partly closed**: a daily cron populates both rollup tables, and both readers have a live raw-table fallback when rollups are empty. Behaviorally the tab matches the spec's data flow exactly. Divergences found are correctness/consistency issues below, not missing wiring.

### Findings

| Severity | Category | file:line | Issue | Impact | Fix |
|---|---|---|---|---|---|
| MEDIUM | wrong-data | coachhelm-analytics.ts:626-627,734-741 | `getCoachHelmOverview` hardcodes a 30-day window and does not accept a `dateRange`. In the legacy dashboard `handleDateRangeChange` never re-calls it (CoachHelmAnalyticsDashboard.tsx:119-128), so the summary cards (Total Insights / Action Rate / Improvement Rate / Prediction Accuracy / Strokes Saved) stay frozen at the 30d SSR snapshot while the panels below them update to the selected range. | Coach selects "7 days" / "90 days" and the headline KPIs silently keep showing 30-day numbers — the cards contradict the panels on the same screen. | Accept `dateRange` in `getCoachHelmOverview` and re-call it from both `handleDateRangeChange` paths; or label the summary cards explicitly as "last 30 days". |
| MEDIUM | correctness | AnalyticsSummaryCards.tsx:80 vs FairwayEffectiveness.tsx:386,419 | Two different "Prediction Accuracy" numbers from two sources on the same feature. Overview card uses `overview.predictionAccuracy` = raw `golf_predictions.was_accurate` averaged over the last 30d (coachhelm-analytics.ts:729-741). The redesign cockpit's hero uses `performance.summary.overallAccuracy` = mean of `accuracy_rate` across `golf_prediction_model_performance` rollup snapshots (coachhelm-analytics.ts:425). These two computations can disagree for the same team/window. | "Is CoachHelm helping" headline accuracy can differ between the overview readout and the cockpit gauge, undermining trust in the number. | Pick one source of truth for prediction accuracy (prefer the rollup `overallAccuracy`) and have `getCoachHelmOverview` derive `predictionAccuracy` from the same path, or drop the duplicate. |
| MEDIUM | no-error-state | page.tsx:78-83,99-102,117-120 | SSR loaders that return `{success:false, error}` are unwrapped with `result.data` (undefined). The page never inspects `.success`, so a server-side query failure renders the empty/"no signal" state instead of an error. The redesign component only sets `loadError` on the client re-fetch path (FairwayEffectiveness.tsx:195-201), not on the initial SSR data. | A real DB/RLS failure on first load looks identical to "no data yet" — a coach sees a falsely-empty dashboard and has no signal that something broke or a Refresh would help. | On SSR, capture per-loader `success` and pass an `initialError` into the component so the first paint can show the existing `InlineNotice` (redesign) / error treatment. |
| LOW | pagination-cap | coachhelm-analytics.ts:729-734,974-980,663-668,497-512 | The raw-table reads (`golf_predictions` in `getCoachHelmOverview` and the `calculate*FromPredictions/Insights` fallbacks, plus `golf_patterns_v2`/`golf_coach_insights` reads) are unpaginated `.in('player_id', playerIds)` queries with no `.range()`. PostgREST caps at 1000 rows. For a normal team in a 30-day window this is well under the cap, but a large/active team (or a wide custom range) could silently truncate, undercounting insights/predictions/patterns. | Edge-case undercount of effectiveness metrics for high-volume teams; no user-visible error, just quietly-wrong totals. | Paginate via `fetchAllRowsResult` / `.order('id').range()` for these reads, consistent with the project's 1000-row policy. |
| INFO | pagination-cap | prediction-performance-writer.ts:112-118 | The rollup writer fetches ALL `golf_predictions` across every team in the 30-day window with no pagination before bucketing per team. This is the populate side (out of this tab's render path) but at platform scale it will hit the 1000-row cap and produce incomplete rollups that this tab then reads as truth. | Future-scale risk: the rollups the cockpit trusts could be computed from a truncated prediction set. | Paginate the writer's prediction fetch; same policy. Tracked here because this tab consumes the output. |
| INFO | spec | golfhelm-features.md:760 | Known Gap "golf_insight_effectiveness not actively populated" is now stale — the daily `coachhelm-insight-lifecycle` cron calls `rollupInsightEffectivenessForYesterday` + `rollupPredictionPerformanceRolling30d` (route.ts:47-48). Population still depends on the cron firing in prod (a recurring half-firing-cron gotcha in this repo) and on coaches recording focus-area outcomes for the improvement-rate to be non-zero. | Doc drift; the tab can legitimately read empty until outcomes are recorded, which is handled honestly. | Update feature-doc #17 to reflect the cron + raw-table fallback and the real remaining dependency (outcome capture). |

### Coverage notes / open questions for live verification

- All findings are static-code-grounded. Whether `golf_insight_effectiveness` / `golf_prediction_model_performance` actually contain rows in prod depends on the cron firing — needs live verification (this repo has a documented history of Vercel crons half-firing).
- The MEDIUM "frozen summary cards" and "two accuracy numbers" findings are best confirmed by clicking the date-range control as a coach and comparing the overview card vs the cockpit hero. Both are deterministic from the code, but live confirmation makes the user impact concrete.
- RLS posture not separately re-verified here beyond the action-level `verifyTeamAccess` gate; the readers rely on it + table RLS. No anon/over-broad grant introduced by this tab's code.

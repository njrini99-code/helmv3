## 3. Client-runtime errors (the gap)

`POST /api/log-error` returned **200 for ≥50 distinct requests over a 3-hour window** (01:55, 02:11–02:14, 02:22–02:23, 02:34–02:39, 03:08 UTC). The endpoint accepts any authenticated client error report, sanitizes it, and writes a row to **`error_logs`** + **`admin_events`** (`src/app/api/log-error/route.ts:61-85`). The 200 means **ingestion succeeded** — it does NOT mean nothing's wrong; each 200 represents a distinct client-side exception captured by `src/lib/error-logging.ts`.

**What is needed to triage these:** `SELECT message, severity, url, count(*) FROM error_logs WHERE timestamp >= now() - interval '24 hours' GROUP BY 1,2,3 ORDER BY count(*) DESC LIMIT 10;` against the Supabase project — exactly the query Step 1 instructed via `mcp__supabase__execute_sql`. This run could not authenticate Supabase (`HTTP 403: Host not in allowlist` on OAuth init from this remote container), so the payloads stay opaque.

**Bursty timing (clustered ~5-second-spaced POSTs)** is a fingerprint of either (a) a regression in a frequently-mounted component firing repeatedly, or (b) a single user hitting a flaky path multiple times. Without the payloads, I can't distinguish.

**Recommendation for the human reviewer:** in Supabase SQL Editor, run the query above. If a clear top pattern emerges, file a follow-up issue and re-trigger this nightly run from an environment that has Supabase MCP access wired up (or with `MCP_SUPABASE_TOKEN` plumbed through this container so OAuth isn't needed).

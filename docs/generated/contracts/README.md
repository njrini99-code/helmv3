# docs/generated/contracts/

This README is hand-written, not generated — only the `<feature_id>.json` and
`<feature_id>.md` files in this directory are, each carrying its own
`GENERATED by scripts/contracts/resolve.mjs` stamp.

Output of `npm run contract:resolve -- --feature <id>` (the Active Contract
Compiler — `docs/ai-system/CONTROL_PLANE_IMPLEMENTATION_PLAN_2026-09-03.md`
§7 K.4.3). Each `<feature_id>.json` is the structured artifact a later
invariant/journey validator is meant to consume; the matching `<feature_id>.md`
is the same content rendered for a human reader. Neither is hand-edited —
regenerate with:

```bash
npm run contract:resolve -- --feature <id> --json --out docs/generated/contracts/<feature_id>.json
npm run contract:resolve -- --feature <id> --out docs/generated/contracts/<feature_id>.md
```

`<id>` may be a `memory/registry.yml` feature id directly, or a
`src/lib/admin/feature-registry.ts` runtime FeatureKey (e.g.
`round_tracking`) — the tool resolves it to its owning feature id and names
that resolution at the top of the output; the FILE is always named after the
resolved **feature id**, never the requested alias, so a later validator
never sees two files for one feature.

Regenerating is safe at any time — the tool is read-only over `memory/**`,
`src/lib/admin/feature-registry.ts`, `src/lib/types/database.ts`,
`supabase/migrations/**` and `git ls-files`; it writes nothing anywhere else,
and nothing outside this directory depends on these files existing or being
current. Staleness here means "run the command again before trusting it",
not "something broke" — there is no CI gate on these files being up to date.

Each contract's own `superseded_claims` section is a finding, not a defect in
this compiler: it means the compiler is doing its job. A non-empty
`superseded_claims` array never indicates the tool failed — see
`scripts/contracts/resolve.mjs`'s own header for the exit-code contract
(exit non-zero only on an unresolvable `--feature` id).

# CoachHelm Insight Delivery — Root-Cause Dossier

**Date:** 2026-07-25
**Scope:** Every live insight-delivery surface a coach or player can reach (Triage Desk / coach Brief, player Hub signal card, player CoachHelm feed, coach per-player Scouting Report, round-review takeaway, roster top-insight card, morning-digest email), plus the generation, persistence, and read-path layers that feed them.
**Method:** Original top-down source read + live read-only SQL against production `golf_coach_insights` / `golf_learned_behavior` / `golf_insight_action` / `golf_coach_behavior_log` / `pg_policies`. No prior trace document existed at the expected paths (`insight-trace-A-routes.md`, `insight-trace-C-dead.md`) — both were checked and are absent; this report is not a verification pass over someone else's draft.
**Conventions:** FACT = read directly in source or queried directly from the live DB. CONCLUSION = inferred from facts. UNVERIFIED / UNVERIFIABLE = flagged explicitly, with what would settle it. No file was modified to produce this dossier.

## 1. The question, and the one-paragraph answer

**Question:** Do accurate CoachHelm insights reach the UI?

**Answer:** Partially, and unevenly across the two engines that write the same table. The v3 engine's output (447 of 548 rows) mostly does reach the UI, through one consistently-applied filter (`applyInsightVisibility`) used correctly at roughly 20 call sites across every traced surface. But an entire vocabulary of v2-generated alerts — roster-risk flags, cross-metric pattern detections, streaks, plateaus, tournament-pressure, team trends (11 insight types, 101 rows, actively written today by a live cron) — is **100% invisible on every surface, indefinitely**, because its writer never stamps the one field (`engine_version`/`signature`) the shared filter checks, not because the underlying detection logic is wrong. Layered on top of that is the exact disease the product owner named: several fully-computed, correct values are wired to a component or a table that nothing downstream reads — a dead prop (`data.insights`), a dead trust-signal component (`InsightTrustChips`), a discarded `BehaviorLearner` call, three composite rules that fabricate a literal `sample_n` instead of computing the one they already have the formula for. None of these are logic bugs in the sense of "the math is wrong" — the detection and scoring logic downstream of a successful write is generally sound. The failure mode is structural: **producer and consumer independently assume a contract (a version stamp, a type key, a prop name, a component wire-up) that nothing enforces between them**, so correct work silently stops being seen the moment one side changes and the other doesn't.

## 2. THE ROOT CAUSE PATTERN

**Name it precisely: one-sided contract enforcement.** Every gate, filter, ranking function, or component boundary in this pipeline is written *as if* its upstream producer satisfies an assumption — a version tag is stamped, a type key is present in a metadata blob, a prop is read by the component it's passed to, a formula that exists elsewhere in the same file tree is reused instead of re-typed as a literal. Nothing enforces that assumption on the producer side. Both sides typecheck. Both sides run without error. Nothing logs a mismatch. The two sides simply drift, and once they've drifted the drift is permanent, because there is no test, no lint rule, and no runtime assertion that would ever flag "this row was written but no reader will ever return it" or "this value was computed but no component will ever render it." This is a distinct failure class from "there is a bug in the ranking math" — the ranking math, where it runs, is correct. The failure is upstream or downstream of it, at the seam.

This is not "there are bugs" — it recurs at every layer of the stack, in a different concrete form each time, which is why it reads as a pattern rather than a collection of unrelated defects:

- **At the write/filter seam:** the v2 alert-generator family (`bubble_player`, `pattern_detected`, `streak`, `surge_player`, `plateau`, `tournament_pressure`, `closing_holes`, `par_3_issues`, `recurring_weakness`, `team_trend`, `scoring_decline`) calls `upsertInsight()` (`src/app/golf/actions/insights.ts:1054`, and `:4134-4136` inside `triggerPlayerInsightsAfterRound`), which never stamps `engine_version='v3'`. The shared read-path gate `applyInsightVisibility` requires `engine_version='v3' OR signature LIKE 'v3:%'` (`src/lib/coachhelm/v3/insight-visibility.ts:34`). Nobody wired the writer to know about the filter that was added later. Result, verified live: 0 of 101 v2-engine rows pass `signature LIKE 'v3:%'` — the filter behaves exactly as designed, and an entire alert vocabulary that is actively generated today (most-recent write today, 03:45 UTC, matching the `coachhelm-roster-sweep` cron's exact schedule minute — `vercel.json:57-58`) is permanently unreachable on every surface, including the Alert Center that exists specifically to host it.

- **At the compute/reuse seam:** `short-approach-proximity-gap.ts:77` and `bunker-miss-side-amplifier.ts:117` hardcode `sample_n: 10` and `sample_n: 5` respectively, even though the exact same file tree already contains the correct pattern — `lag-distance-3putt.ts:78-80` computes `Math.min(sourceA.sample_n, sourceB.sample_n)` from real evidence already present in the same `detect()` function. The honest formula exists two files away and was not reused. The fabricated constant then propagates through three independent downstream consumers that all trust it at face value: `insight-delivery-ranking.ts:55`'s sample-damping term, `synthesis.ts:170-171`'s confidence recomputation, and `WhyPopover.tsx:189`'s user-facing "why this insight" explanation.

- **At the compute/render seam:** `getPlayerCoachHelmDashboard` fully computes a merged, visibility-filtered insight list into `dashboardData.insights` (`src/app/golf/actions/insights.ts:3030-3047`), which is fetched and passed as a prop on every load of the canonical player CoachHelm route (`src/app/golf/(dashboard)/dashboard/coachhelm/page.tsx:208-210, :452`). The receiving component, `PlayerCoachHelmHome.tsx`, declares the prop (line 84) and reads `data.focusAreas`, `data.prediction`, `data.recentRounds`, `data.playerState`, `data.playerName` — every field except `data.insights`, which does not appear once in the file or any sibling file under `src/components/golf/coachhelm/home/`. The actual cards shown come from a completely separate, independently-fetched prop pair (`topInsight`/`secondaryInsights`, wired at `coachhelm/page.tsx:212-214,459-460`). A full evidence fetch and coach-weighted ranking pass runs and is serialized to the client on every page load, for a value nothing reads.

The same seam recurs in miniature throughout the enhancement assessment: `ConfidenceCalibrator` constructed empty (fixed on this branch); the epsilon-off-by-one in `bootstrapFromDb`'s bucket boundaries (fixed on this branch); `BehaviorLearner.getLearnedPreferences()` awaited and discarded in the orchestrator; `ACK_TYPES`/`DISMISS_TYPES` in `behavior-learner.ts:63-76` not including `'feedback'`, the interaction type the rating writer actually uses; two `recordInteraction` call sites (`insights.ts:3620`, `:3726`) that record no real `insight_type` at all, collapsing every coach's learned preference into one undifferentiated `'unknown'` bucket; `metricToRoundField` (`effectiveness-writer.ts:326-354`) hardcoded to v2 metric names only, so `outcome_status` is null on 548/548 rows in prod because v3 generators write v3 `MetricId`s (`sg_ott`, `opening_hole_delta`, `practice_tournament_delta`) the function has never heard of. Every one of these is the identical shape: a value is produced correctly on one side of a seam, and the other side of the seam was never told what to look for.

A secondary, related manifestation is **duplicate live surfaces where a fix or a build lands on the wrong twin**: two components both named `InsightCard` in different directories reached via different render trees (`src/components/golf/coachhelm/insight-card/InsightCard.tsx` vs. `src/components/fairway/cards-insight/InsightCard.tsx`); `FairwayPlayerCoachHelm.tsx` and `FairwayMyDevelopment.tsx` fully built and still documented in barrel comments as "the player front door," while the actual live route renders `PlayerCoachHelmHome` and `DevelopmentDrill` instead; `HeroInsightCard.tsx`'s staggered-reveal wrapper unused because every live hero-density call site was quietly routed through a locally-defined duplicate, `HeroInsightCardInner`, that never got the animation. This is the same root disease one layer up: nothing connects "the file that documents itself as the live surface" to "the file that is actually mounted," so the two drift and only one of them is true.

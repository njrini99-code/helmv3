# Anti Slop Quality Rubric

This file defines what separates a real one-shot product plan from AI-generated bloat.

## Slop Signals

The plan or build is slop if it:

- adds many tabs but no daily workflow
- uses market names without changing product decisions
- says "AI insights" without source refs, confidence, permissions, and actions
- creates dashboards with generic cards
- mixes official stats and development metrics
- ignores messy import realities
- has no role-specific visibility
- builds direct integrations before pilots
- uses "readiness score" as fake medical authority
- treats players like staff users
- treats strength, compliance, nutrition, recruiting, and analytics as simple tabs
- has no demo story
- has no acceptance gates

## Real Product Signals

The plan is strong if every major feature answers:

1. Who uses this?
2. What decision does it improve?
3. What source data supports it?
4. What action can the user take?
5. What should the player see?
6. What should stay staff-only?
7. What happens when the data is missing or wrong?
8. What competitor owns the deep version?
9. Why is BaseballHelm still worth building?
10. What is the Phase 1 cutline?

## One Shot Build Review

Before declaring success, inspect:

- Command Center has signals, not filler cards.
- Player Today is a daily action screen, not a mini dashboard.
- Import Center has preview/rollback/provenance.
- AI cards cite source refs.
- Practice Planner can convert signals into practice blocks.
- Player Timeline is source-linked and role-safe.
- Staff Decision Room creates actions.
- Demo data proves the story.

## Copywriting Standard

Use baseball operations language:

- "limited today"
- "needs acknowledgement"
- "review import"
- "publish practice"
- "add to meeting"
- "convert to practice block"
- "player-visible"
- "staff-only"
- "source: GameChanger XML"
- "source: Rapsodo bullpen CSV"

Avoid vague SaaS language:

- "unlock insights"
- "optimize performance" without specifics
- "holistic dashboard"
- "AI-powered everything"
- "revolutionary ecosystem"
- "single pane of glass"

## Feature Acceptance Standard

A feature is acceptable only if it has:

- route or component target
- data contract
- source refs/provenance
- role permissions
- empty state
- error state
- edge cases
- test expectation
- demo data
- phase cutline

If any of those are missing, the feature is not one-shot ready.

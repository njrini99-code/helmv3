## Findings

### M02-01 Switching threads has no stale-fetch guard — an old conversation's fetch can overwrite the new one's state [observed] [severity: high]
- Evidence: `useGolfMessages` is called ONCE at the top of `FairwayMessages.tsx` with a changing argument — `useGolfMessages(selectedConversationId || '')` (`src/components/fairway/pages/messages/FairwayMessages.tsx:121`), not remounted per conversation (no `key={conversationId}` wrapper found; `MessageThreadPane` itself never calls the hook — `src/components/fairway/pages/messages/MessageThreadPane.tsx:141` comment: "Messages from the unchanged `useGolfMessages()` hook"). `fetchMessages` (`src/hooks/golf/use-golf-messages.ts:294-369`) has no `AbortController`, no request-generation counter, and no "is this still the active conversation" check before its three unconditional `setMessages`/`setError`/`setLoading` calls (`use-golf-messages.ts:342-348`). The effect that calls it is keyed only on `conversationId` (`use-golf-messages.ts:387,530`), so switching A→B tears down A's realtime channel but does **not** cancel A's already-in-flight `fetchMessages()` promise.
- Spec: plan §17.5 — "Reads carry authenticated identity, team where relevant, conversation, request generation and revision. Abort superseded work where available, but also reject late successes... An old fetch must not overwrite a new conversation." Also M-T01 ("stale failure and old receipt lookup never publish into the new conversation").
- Gap: if a user opens conversation A, then quickly opens conversation B before A's fetch resolves, and A's response arrives after B's, A's `setMessages(A's rows)` fires last and replaces B's already-rendered thread with A's messages (and vice-versa for `setError`/`setLoading`). Nothing in the hook prevents this; it is a straightforward race given the code as written, not a hypothetical needing exotic timing — any two rapid taps on the conversation rail while offline/slow triggers it.
- Proposal: thread a request-generation ref through `fetchMessages` (compare against `conversationId` captured at call time and a monotonically-incrementing counter) and no-op the three `set*` calls when the response's generation is stale; same pattern already exists elsewhere in the repo for this exact class of bug (`currentUserIdRef` here for a different race).

### M02-02 Golf messaging has two independent send paths, only one of which implements optimism/retry/idempotency [observed] [severity: high]
- Evidence: `useGolfMessages().sendMessage` (`use-golf-messages.ts:548-619`) pushes an optimistic row, wraps the server call in `withOneTransportRetry` with a collision-proof `generateClientMessageId()`, and reconciles the echo by exact id (`applyRealtimeMessageInsert`). Attachment sends go through a **separate** hook, `useMessageAttachments().sendMessageWithAttachments` (`src/hooks/golf/use-message-attachments.ts:29-145`), which never touches the `messages` array at all (no `setMessages` call anywhere in that file), generates its own id (`tempMessageId = \`temp-${Date.now()}-${Math.random()...}\``, `use-message-attachments.ts:50`) used only for the storage path, and calls `sendGolfMessageWithAttachments` directly with **no** `withOneTransportRetry` wrapper. `FairwayMessages.tsx:345` even comments "realtime replaces the optimistic stub" for the text path, with no equivalent comment or mechanism at `handleSendMessageWithAttachments` (`FairwayMessages.tsx:362-421`).
- Spec: plan §17.3 — "Carry text, quote, file references and immutable revision through every send/retry surface"; Table 16 §16 — "Sending/failure dock: ... All retry surfaces share one operation."; feature doc's own field-verified incident (2026-09-01/02 WKWebView "Load failed") is the reason the text path has a retry at all.
- Gap: (a) an attachment send has no optimistic bubble — the sender sees nothing until the realtime echo (or a refetch) puts it on screen, unlike a text send; (b) the same transport-layer failure mode that motivated `withOneTransportRetry` for text sends is not covered for attachment sends, so the exact WKWebView failure the feature doc documents can silently drop a photo/file message with no retry and no visible pending state; (c) the two id-generation schemes (`generateClientMessageId` vs the `temp-`/`Math.random` id) are inconsistent, though the attachment one is only a storage-path scope, not the message PK, so its collision risk is lower-severity, not the same defect class.
- Proposal: not in scope to design here; flagging as the concrete gap the §16.1 `SubmittedMessageOperation` contract (below) would need to close for both paths.

### M02-03 The 23505-collision "successful retry" short-circuit does not verify request equivalence [observed] [severity: high — outside M02's leased file, flagged because it's the exact contract `use-golf-messages.ts`'s own tests document]
- Evidence: `src/app/actions/messages.ts:168-170`:
  ```
  if (validatedData.client_message_id && messageError.code === '23505') {
    return { success: true };
  }
  ```
  This is reached from `sendGolfMessage` → `sendMessage` (`src/app/actions/messages.ts:603-627`, `90-252`), the exact function `useGolfMessages.sendMessage`'s retry calls (`use-golf-messages.ts:592-595`). No lookup of the existing row by id is performed to confirm its `sender_id`, `conversation_id`, or `content` match the current request before returning success.
- Spec: plan §17.3 — "On a duplicate ID, verify sender, conversation and request equivalence; do not treat every unique-constraint error as a successful retry."
- Gap: today a 23505 on this id can only really arise from the documented retry-of-self case (the comment at `use-golf-messages.ts:585-591` reasons through why a foreign-id collision can't happen via INSERT), so this is not currently exploitable given the client behavior audited — but the code itself does not enforce the invariant the comment relies on; if a future caller ever supplies a `client_message_id` value it didn't generate, or a different `content`/`conversation_id` in a genuine retry-race, the action would still report `{success:true}` for a mismatched request. This is `use-golf-messages.ts`'s own send-integrity contract (its tests explicitly document "On a duplicate ID... do not treat every unique-constraint error as a successful retry" as the standard to meet), so I'm reporting it even though the file itself sits outside the M02 lease list.
- Proposal: not in scope here; note for whichever lane owns `src/app/actions/messages.ts`.

### M02-05 §16.1 `InboxRow` vs. what `useGolfConversations` actually returns [observed] [severity: high — includes an explicit spec-anti-pattern hit]
- Evidence: `GolfConversationWithMeta` (`use-golf-messages.ts:31-42`) and its construction (`use-golf-messages.ts:1036-1102`).
- Spec: plan §16.1's proposed `InboxRow` DTO (lines 700-706 of the plan) and its own explicit warning: "Do not fabricate a complete database message row with an empty ID merely to carry an inbox preview."
- Gap, field by field:
  - `conversationId` → `id`: present.
  - `normalizedKind`/`permittedTeamScope` → only `is_group?: boolean`. The RPC `get_golf_conversations_with_details` returns a real `is_team_channel` column (confirmed in `supabase/migrations/20260621041824_harden_get_golf_conversations_rpc.sql`'s `RETURNS TABLE(...)`), but `use-golf-messages.ts`'s local `ConversationRow` interface (`use-golf-messages.ts:729-743`) never declares or reads `is_team_channel` — grepped the whole file, the only "team chat" signal it reads is the separately-fetched `is_team_chat` column from the supplemental direct query (`use-golf-messages.ts:780,820,827`), a DIFFERENT column on `golf_conversations`. So a real, distinct kind signal the backend already computes is silently dropped, and no `permittedTeamScope` (team id) is exposed on the row at all — the UI cannot show which team a group conversation belongs to from this DTO.
  - `title`: present.
  - `identityState`: absent — `other_participant?` being `undefined` conflates "not yet resolved," "lookup failed," and "this is a group with no single other party." No distinct state.
  - `avatarSummary`: DM rows get `other_participant.avatar` (single string|null); group rows get **no avatar field at all** (`use-golf-messages.ts:1039-1055` — group branch has no avatar/avatarSummary key).
  - `memberCount`: `participant_count` populated for groups; absent/undefined for DMs (never defaulted to 2).
  - `latestMessagePreview{kind,text,senderLabel,time,messageId}`: `last_message` is constructed at **both** `use-golf-messages.ts:1043-1050` and `use-golf-messages.ts:1090-1097` as `{ id: '', conversation_id: conv.id, sender_id: ..., content: ..., created_at: ..., read: false }` — a fabricated `GolfMessageRow`-shaped object with a **literal empty-string id**, which is precisely the anti-pattern the plan calls out by name. There is no `kind` (text/system/poll/etc.) on the preview, and `senderLabel` isn't resolved — only the raw `sender_id`, which the rail would have to re-resolve against the same coach/player lookup maps built for `other_participant` (and that lookup only covers non-group conversations' `otherUserIds`, `use-golf-messages.ts:982-1006`, so a group chat's last-message sender is not resolvable from this DTO at all today).
  - `viewerState{unreadCount,pinned,mute,draft,failedOperation}`: only `unread_count` present. No `pinned`, `mute`, `draft`, or `failedOperation` field exists anywhere in this hook.
  - `capabilities`: absent entirely.

### M02-06 §16.1 `ThreadPage` vs. what `useGolfMessages` returns [observed] [severity: high]
- Evidence: hook return value (`use-golf-messages.ts:677-688`): `messages, loading, error, sendMessage, editMessage, removeMessage, refetch, isOtherTyping, sendTypingStatus, currentUserId`.
- Gap, field by field:
  - `scopeKey`: implicit in the `conversationId` argument, not returned.
  - `orderedMessages` → `messages`: present, but capped at 200 with `.limit(200)` (`use-golf-messages.ts:323`) and **no `nextCursor`/`hasMore`** — there is no pagination mechanism in this hook at all. Grepped the file for `cursor`/`hasMore`/`loadMore`/`older`: none found. Any thread with more than 200 messages has no way to load earlier history through this hook. This directly matches plan §17.5's "Use deterministic keyset history and context-window reads rather than treating newest-200 as full history" — this hook does exactly the pattern the plan names and warns against.
  - `quoteSummaries`: absent (see M02-04 — `reply_to_id` isn't even selected).
  - `attachmentSummaries`: intentionally out of this hook (owned by the separate attachment path); noting the split rather than calling it a gap in isolation, but see M02-02 for the send-side consequence of that split.
  - `participantIdentities`: absent — the hook tracks only a single `otherParticipantLastReadAt` (`use-golf-messages.ts:211`), meaningful for a 1:1 DM only. For a group/team thread there is no per-participant identity map returned by this hook at all.
  - `viewerReadFrontier`: not returned — the viewer's own `last_read_at` is written (via `markGolfMessagesAsRead`) but never read back into hook state.
  - `readerFrontiers` (plural, multi-reader receipts): absent for groups. `otherParticipantLastReadAt` (singular) only works for exactly 2 participants — the realtime UPDATE handler on `golf_conversation_participants` (`use-golf-messages.ts:476-491`) updates the same single `otherParticipantLastReadAt` state regardless of which of N other participants read, so in a group thread the "read" receipt state is not per-member at all; it collapses to "the last participant-row UPDATE that arrived," which is not a defined, correct value for a group. See M-T06 below.
  - `entryUnreadBoundary` (the "New" divider): absent. Not mentioned in the feature doc's UI Contract either — appears to be a genuinely unbuilt feature rather than merely unwired state.
  - `initialLoading`/`refreshing`: a single `loading` boolean is reused by `refetch: fetchMessages` (`use-golf-messages.ts:684`), so calling `refetch()` on an already-open thread flips `loading` back to `true` the same way the initial mount does — a consumer that gates a full-screen spinner on `loading` (as opposed to `loading && messages.length === 0`) would flash the initial-load UI on every manual refresh. I did not read `MessageThreadPane.tsx` fully to confirm which gate it actually uses, so this is `risk`, not `observed`, for that specific consumer — see "What I could not determine."
  - `errorByRegion`: a single flat `error: boolean` covers only the thread-fetch failure path; send/edit/delete failures are reported via thrown `Error`s from their respective functions, not through `error`, so the "region" concept doesn't exist as state at all (it's handled by whichever caller catches the throw).

### M02-07 §16.1 `SubmittedMessageOperation` has no corresponding state anywhere [observed] [severity: med]
- Evidence: `sendMessage` returns only `true` (`use-golf-messages.ts:608`) or throws; there is no returned/retained object carrying `messageId`, `immutableRevision`, `transferState`, `commitState`, `canonicalResult`, `retryEligibility`, or `cancellationMeaning`. The optimistic row itself is pushed into `messages` and removed wholesale on any failure (`use-golf-messages.ts:599,604,611`) rather than transitioning through a tracked state.
- Spec: plan §16.1 `SubmittedMessageOperation`; Table 16 "Sending/failure dock ... All retry surfaces share one operation."
- Gap: this is consistent with the brief's "accepted behavior" note that a failed text send surfaces a toast and keeps the draft (not a persistent per-message failure chip), so I am not calling the CURRENT UX wrong — but there is no reusable operation contract a composer (M03C) could build a richer failure/retry affordance on top of without inventing its own parallel state, and per M02-02 that would need to unify two send paths, not just add fields to one.

### M02-08 No reconnect/foreground resync — realtime "connected" is treated as "caught up" [observed] [severity: high]
- Evidence: grepped `use-golf-messages.ts` for `reconnect`, `visibilitychange`, `SUBSCRIBED`, `CHANNEL_ERROR`, `resync` — the only hit is a code comment (`use-golf-messages.ts:143`) describing an ordering case, not an implementation. The channel subscription (`use-golf-messages.ts:429-512`) registers `postgres_changes`/`broadcast` handlers and calls `observeRealtimeChannel(channel, ...)` (confirmed by reading `src/lib/observability/supabase/realtime.ts` that this wraps `.subscribe()` for connect-latency/reconnect *observability*, not resync logic), but nothing in the hook reacts to a reconnect or tab-foreground event by refetching. `useGolfConversations`'s realtime effect (`use-golf-messages.ts:1128-1180`) has the same absence.
- Spec: plan §17.5 — "Join/snapshot/reconnect must cover missed-event gaps. Realtime connected does not prove the view is complete... perform authoritative scoped resync on relevant foreground/reconnect/access changes."
- Gap: Supabase's `postgres_changes` realtime does not replay events missed while a channel was disconnected. If a phone backgrounds, the network drops, or the channel enters `CHANNEL_ERROR` and later reconnects, any messages/read-receipts/typing events that occurred during the gap are never delivered and this hook has no mechanism to detect the gap and re-fetch. A user returning to an already-open thread after a network blip can be silently missing messages until they navigate away and back (which re-runs `fetchMessages` via remount/effect re-key) — the hook itself never triggers that recovery on its own.

## Findings

### M04-01 An attachment-metadata insert failure is reported to the sender as a successful send   [observed] [severity: high]
- Evidence: `src/app/golf/actions/message-attachments.ts:120-129` — when `golf_message_attachments` insert fails after the `golf_messages` row (with `has_attachments: true`) has already committed, the code logs the error and explicitly continues ("Message was sent but attachments failed - log but don't fail completely... we could try to clean up but that risks data loss"). The function falls through to notification fan-out and `return { success: true, messageId: message.id }` (line 156).
- Spec: plan §17.4 — "An attachment-metadata failure is not a complete send."
- Gap: the sender's UI (`FairwayMessages.tsx:370` checks `!result.success`) sees `success: true` and shows the message as sent. The message row exists with `has_attachments: true` but zero rows in `golf_message_attachments` — permanently, since nothing re-attempts the insert.
- Source-confirmed by the client's own downstream handling: `src/components/fairway/pages/messages/MessageThreadPane.tsx:578-596` documents the exact race this produces — "Every message reaching this effect has `has_attachments: true`, so 'no rows' is not a valid resting state" — and treats a still-empty result after one delayed auto-retry as `errored`, rendering a permanent "Couldn't load — tap to retry" chip. That comment frames the race as *transient* (commit-order timing), but the code path in M04-01 produces the *same symptom permanently* when the attachment insert itself failed (RLS, malformed row, connection drop) rather than merely not-yet-committed. The retry chip in that case will retry forever and never succeed, because there is nothing to fetch.
- Proposal: wrap the message insert + attachment insert in one transaction (an RPC/`SECURITY DEFINER` function), or on attachment-insert failure roll back by deleting the just-inserted message row and returning `success: false` so the client's existing cleanup path (`use-message-attachments.ts:105-123`) removes the orphaned storage object.

### M04-02 No cleanup of the storage object when metadata insert fails or the client never learns the outcome   [observed] [severity: med]
- Evidence: `src/hooks/golf/use-message-attachments.ts:99-123` only removes uploaded storage objects (`supabase.storage.from(STORAGE_BUCKET).remove(pathsToDelete)`) inside the `if (!messageResult.success)` branch. Given M04-01, the server action returns `success: true` even when the attachment rows never landed, so this cleanup branch never runs for that failure mode — the uploaded file stays in `golf-attachments` forever, unreferenced by any `golf_message_attachments` row.
- Evidence (second gap in the same file): if the awaited call to `sendGolfMessageWithAttachments` itself throws (transport failure — cancelled request, dropped connection) rather than resolving with `{success:false}`, execution goes to the outer `catch` at `use-message-attachments.ts:126-137`, which does **not** attempt any cleanup of the already-uploaded files, and does not attempt to reconcile whether the send actually landed server-side.
- Evidence: no repo-wide cleanup job exists for this bucket — `grep -rln "golf-attachments" src scripts` returns only `message-attachments.ts`, `attachments.ts`, `MessageThreadPane.tsx`, and `storage-buckets-tracked.test.ts`; no cron/Inngest function references it.
- Spec: plan §17.4 — "Clean up only confirmed abandoned objects" (implying some cleanup mechanism should exist for confirmed-abandoned cases); §17.3 — "A cancelled network request can leave the commit unknown. Reconcile by operation ID before... deleting staged files."
- Gap: there is no server-side reconciliation of "commit unknown" attachment sends, and no scheduled sweep for orphaned objects. Every abandoned/partially-failed upload is a permanent leak in the bucket with no retention/GC policy observed.
- What would confirm/deny further: whether `HELM_QUEUE_ENABLED`/Inngest (`src/lib/inngest/functions.ts`) contains an unrelated storage-GC job I did not have time to fully read — flagged in "what I could not verify."

### M04-03 Upload progress is synthetic, not real byte-transfer progress   [observed] [severity: med]
- Evidence: `src/lib/storage/attachments.ts:296-323` — the comment states outright: "Note: Supabase JS client doesn't support progress tracking directly. We simulate progress for UX." The implementation calls `onProgress(10)` before `supabase.storage.from(STORAGE_BUCKET).upload(...)`, then `onProgress(90)` after the (single, non-chunked) `upload()` call resolves, then `onProgress(100)` after the signed-URL call resolves. There is no intermediate byte-level callback; a 100MB video reports exactly the same three-step sequence (10 → 90 → 100) as a 10KB image.
- Spec: plan §17.4/[P-UPLOAD] — "Use real transfer callbacks. Supabase's resumable upload interface supports progress and interruption recovery; select an appropriate transport rather than emitting fixed percentages." Plan §1.1 makes this a release requirement: "an unknown send result must not look sent... Visual fidelity and data truth are independent release requirements."
- Gap: this is exactly the fixed-percentage anti-pattern the spec calls out by name. The upload uses `supabase.storage...upload()` (the simple, non-resumable upload path), not Supabase's TUS-based resumable-upload client, so there is no available interruption/resume semantics either — a network drop mid-upload has no partial-progress signal and no resume, only a hard failure back to `{ success: false }`.
- Proposal: switch to Supabase Storage's resumable (TUS) upload client, which exposes real `onProgress({ bytesUploaded, bytesTotal })` callbacks and supports resuming an interrupted transfer, rather than the current fixed three-step simulation.

### M04-04 Conversation-level mute exists as a database column but is read nowhere   [observed] [severity: med]
- Evidence: `golf_conversation_participants` carries `muted_until` and `notification_level` columns per the generated/live schema — AUTOGEN block in `memory/context/golfhelm-database.md:5179-5191` (generated from `src/lib/types/database.ts:12313-12332`, confirmed present at those line numbers).
- Evidence: `grep -rn "muted_until\|notification_level" src` returns **only** the generated type-definition file itself (`src/lib/types/database.ts:12313-12332`) — no server action, hook, or component reads or writes either column.
- Evidence: the notification fan-out (`src/lib/notifications/golf-message-fanout.ts:41-45`) selects only `user_id` from `golf_conversation_participants` when building the recipient list — it never selects `muted_until` or `notification_level`, so even if a UI existed to set them, the fan-out has no code path that would honor them.
- Spec: plan §17.6 — "Conversation mute changes actual interruption policy, not whether messages exist." Feature-doc instruction (this audit's brief): "Whether a mute control, if it exists, actually suppresses delivery. Report presence as absent if absent."
- Gap: there is no mute control in the UI (no reference to these columns anywhere in `src/components/**` either — `grep` for the column names found zero matches outside the generated types file), and no code path would suppress delivery even if one were added and the columns were populated by hand. **Reporting exactly as instructed: mute is absent as a feature; the schema plumbing for it exists and is orphaned.**
- What delivery IS gated on today, instead: the user-level (not per-conversation) `users.notification_preferences.push_messages` / `email_messages` flags, read via `gatedDelivery()` in `src/lib/coachhelm/v3/notifications/types.ts` and applied at `golf-message-fanout.ts:130-152`. This is an app-wide on/off per channel, not a per-conversation mute.

### M04-05 Message-send email notification is currently suppressed in production by the customer-email kill switch   [observed] [severity: info — policy, not defect]
- Evidence: `src/lib/notifications/golf-message-fanout.ts:130-137` calls `notifyNewMessage` (via `sendEmailNotification`) for each recipient with `email_messages` on (the default, `email_messages: true`). `notifyNewMessage` (`src/lib/notifications/index.ts:36-58`) calls `sendEmailNotification`, which (per `src/lib/notifications/email.ts:10,939,957`) routes through `gateCustomerEmail()` (`src/lib/email/outbound-gate.ts:60-85`).
- Evidence: `isCustomerEmailEnabled()` (`src/lib/email/outbound-gate.ts:32-34`) returns `true` only when `process.env.HELM_CUSTOMER_EMAIL_ENABLED === 'true'` exactly — off by default per the gate's own docstring ("No player/coach/parent-facing... customer email leaves the product while `HELM_CUSTOMER_EMAIL_ENABLED` is not exactly `'true'`") and confirmed by the repo's own recent commit history (`4674b38e1` in this session's git log: "email: player/coach notification email off behind HELM_CUSTOMER_EMAIL_ENABLED (default off)").
- Gap/plain statement per task instruction: **yes, the messaging email-notification path depends on `HELM_CUSTOMER_EMAIL_ENABLED`, and that flag defaults off.** So today, by default configuration: a new message triggers (a) the in-app bell unconditionally (not gated by the customer-email switch — `golf_calendar_notifications` insert at `golf-message-fanout.ts:163-181`), (b) push only if the recipient has explicitly opted into `push_messages` (default off), and (c) email only if `HELM_CUSTOMER_EMAIL_ENABLED=true` is set AND the recipient hasn't turned `email_messages` off. Absent that env flag, a recipient who is not actively watching the app and has not opted into push will not be notified of a new message outside the in-app bell.
- This is not asserted as a bug — it is the documented owner policy (`outbound-gate.ts:1-21`) — but it is a materially different delivery picture from what the messaging feature doc's "Known Risk Areas" implies ("Push notification coverage is not guaranteed just because in-app/email records exist") and worth surfacing plainly per this audit's explicit ask.

### M04-06 Attachments send path has no transport-failure retry, unlike the text-send path   [observed] [severity: low]
- Evidence: `src/hooks/golf/use-golf-messages.ts:6,592` — the text-send path wraps its POST in `withOneTransportRetry` (`src/lib/transient-network-error.ts`), per the feature doc's documented "accepted behavior" (retry once at 750ms on transport failure only).
- Evidence: `src/hooks/golf/use-message-attachments.ts` and its only caller `src/components/fairway/pages/messages/FairwayMessages.tsx:362-389` (`handleSendMessageWithAttachments`) call `sendMessageWithAttachments`/`sendGolfMessageWithAttachments` directly, with no `withOneTransportRetry` wrapper anywhere in either file (`grep` for the identifier in both returns nothing).
- Spec: plan §17.3 — "Carry text, quote, file references and immutable revision through every send/retry surface" (implying attachment sends share the same retry contract as text sends), and the feature doc treats `withOneTransportRetry` as the single documented retry policy for message sends without carving out an attachment exception.
- Gap: a photo/file send that hits the same "WebKit Load failed / Chromium Failed to fetch" transport error the feature doc documents for text sends gets no retry — it surfaces the toast immediately, while an otherwise-identical text send silently retries once first. This is an inconsistency between the two send paths the audit brief's accepted-behavior list does not carve out as intentional, so it is reported as a gap rather than assumed deliberate.

### M04-07 Typing-status realtime channel is a plain (non-private) broadcast, not scoped by Realtime authorization   [risk] [severity: low]
- Evidence: `src/hooks/golf/use-golf-messages.ts:429` creates `supabase.channel(\`golf-conversation:${conversationId}\`)` with no second argument — i.e., no `{ config: { private: true } }`. The same channel carries both `postgres_changes` (RLS-protected at the Postgres row level) and `broadcast` `typing` events (`use-golf-messages.ts:492-511`, `533-546`), which are NOT subject to table RLS — only Supabase's channel-level "private channel" authorization (backed by `realtime.messages` policies) would scope who can join/send/receive broadcast payloads on that topic.
- Evidence: `grep -rn "private: true" src` returns zero results anywhere in the repository — this is not a messaging-specific gap but a repo-wide absence of the private-channel pattern.
- Spec: plan §17.6/[P-REALTIME] — "Private ephemeral channels need both server authorization and explicit private client configuration."
- Gap (labeled `risk`, not `observed`, because I could not exercise this at runtime): if a client can derive or otherwise obtain a conversation's UUID (e.g., a former participant who was removed, or a leaked ID), a plain (non-private) broadcast channel of this shape is joinable by any authenticated Realtime client that knows the topic string, and typing broadcasts would not be filtered by conversation membership the way `postgres_changes` are. What would confirm this: a runtime check of the project's Realtime authorization defaults (whether "private channels required" is enforced project-wide, which would make an unauthorized `channel()` call fail to receive broadcasts) and a two-account test where a removed participant attempts to join the same topic string post-removal. I could not run this — no live Supabase project access in this audit phase (per the brief's read-only, no-runtime constraint).

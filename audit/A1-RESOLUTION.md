## 4. NEW — G-58: two production columns that no migration creates  [high] [coordinator-verified]

**This is a messages-feature defect and belongs to this audit**, unlike the baseball drift in
`A2-RESOLUTION.md` §4.

`golf_conversation_participants.muted_until` and `.notification_level` exist in production —
**confirmed by direct catalog read**, not only by `src/lib/types/database.ts:12313-12314` —
and are declared in the schema mirror `supabase/schemas/golf/10_tables.sql:482-484`, with a
`NOT NULL DEFAULT 'all'` and a `CHECK (notification_level IN ('all','mentions','muted'))`.

**No migration anywhere creates either column.** `grep -rln "muted_until\|notification_level"
supabase/migrations/` returns nothing; the only other hits are two files under
`supabase/migrations_archive/`, which are historical and not replayed. The local stack,
rebuilt from migrations, has exactly:

```
id, conversation_id, user_id, joined_at, last_read_at
```

**Consequences:**

- Any environment built from migrations — a fresh local stack, CI, a preview branch, a
  disaster-recovery rebuild — **lacks these columns**. Production is the only place they
  exist. A restore-from-migrations would silently drop the mute contract.
- Anyone implementing mute locally against the manifest's guidance hits
  `column "muted_until" does not exist` and will reasonably conclude the manifest is wrong.
- `check-supabase-drift`'s golf invariant passes, because it asserts a fixed expected-column
  list that does not include these two. It would not catch this.
- `ci.yml`'s "Declarative schema: new migrations reflected in supabase/schemas" step checks
  migrations → schemas. This is drift in the **other** direction, which nothing checks.

**Correction to `HANDOFF.md` §4, row 1.** "Mute has no UI *and no data* → `muted_until` +
`notification_level` exist; it is a wiring gap, not a schema gap" is **true of production
only**. It is a wiring gap *there* and a genuine schema gap everywhere else. Do not let the
uncorrected version send someone building against columns their dev database does not have.

**Proposal (not made here):** a forward migration that adds both columns `IF NOT EXISTS`
with the identical default and CHECK constraint, so production is a no-op and every other
environment converges. That is a migration against a shared production database and is the
owner's to approve — `db-migration-reviewer` should see it first.

## 5. G-44 — CLOSED. Signed attachment URLs do enforce membership

§A1 listed G-44 ("signed attachment URLs may not enforce membership") as informed-but-not-
settled. The production catalog settles it.

The `golf-attachments` bucket is **private** (`storage.buckets.public = false`), and its
SELECT policy scopes every object to the caller's own conversations:

```sql
golf_attachments_participant_select  SELECT
  ((bucket_id = 'golf-attachments')
   AND ((storage.foldername(name))[2] IN (SELECT user_conversation_ids(auth.uid())::text)))
```

The INSERT policy carries the identical predicate as its `WITH CHECK`. Object path segment 2
is the conversation id, tested against `user_conversation_ids(auth.uid())`.

**Why this answers the question.** A signed URL is a bearer token and does not re-check RLS
when redeemed — that is the property the finding was worried about. But minting one requires
passing the SELECT policy, so **only a participant can ever obtain a signed URL for an
attachment.** The membership gate sits at the correct place.

Two residual notes, neither a defect found:
- The guarantee depends on uploads actually writing `<something>/<conversation_id>/…`. A
  different layout does not open a hole — segment 2 simply would not match and the policy
  denies. It **fails closed**.
- Bearer exposure after minting (TTL length, URL logging/forwarding) is a code-level
  question about how long signed URLs live, not an RLS gap. Worth a look during the write
  phase; it does not reopen G-44.

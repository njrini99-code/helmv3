## 1. G-38 — the cross-tenant injection guard: no longer the audit's most urgent item

Two independent confirmations, from opposite ends:

**Production ledger.** `db-apply` dry-run for
`20260819070000_conversation_creator_cannot_inject_third_party.sql`
(run [`34096767102`](https://github.com/njrini99-code/helmv3/actions/runs/34096767102)) — the
sweep guard printed:

```
Pending on production (db push applies ALL of these, in order):
  (none)
::error::version 20260819070000 is not pending — already applied, or not a migration the ledger knows.
```

The run "fails" only because a dry-run of an already-applied migration is refused at gate 5.
That refusal *is* the answer. **Production has zero pending migrations**, and the ledger
carries this version.

**Migration content.** Replayed from scratch into the local stack, the migration produces
both objects:

```
POLICY|golf_conversation_participants|golf_participants_insert_v2|INSERT
FUNC  |golf_conversation_has_other_participant
LEDGER|20260819070000
```

So the migration is correct and production records it as applied. The migration's own
`NOT APPLIED BY THE AUTHORING SESSION` self-report described the authoring session only —
something applied it afterwards.

**Residual risk, stated honestly:** recorded-as-applied is not catalog-verified. This repo
has been bitten by exactly that (`database.md`, "Applied ≠ recorded"). But the failure mode
now requires the ledger row to exist while the DDL silently did not take, which is the rarer
direction. **G-38 drops from "possible live cross-tenant hole" to "verify opportunistically."**
`check-ledger-vs-catalog` closes it the moment `db-drift.yml` stops skipping it
(see `A2-RESOLUTION.md` §2) — and because the version *is* in the ledger, that check will
genuinely inspect it.

## 2. G-51 — confirmed. The roster presence dot cannot ever light for a teammate

§A1 predicted this exactly. Local `users` policies, from migrations:

```
POLICY|users|admin_read_all  |SELECT
POLICY|users|users_insert_own|INSERT
POLICY|users|users_select_own|SELECT
POLICY|users|users_update_own|UPDATE
```

No teammate-visibility SELECT policy exists. A non-admin viewer reads exactly their own
`users` row, so the shipped presence indicator can only ever resolve for the viewer. **G-51
is confirmed as predicted** — it is dead UI, not a rendering bug. (Policy set confirmed
against migrations; production not catalog-read. Given §4 below, do not treat "the migrations
say so" as proof of production for anything you are about to rely on.)

## 3. G-40 — the per-viewer unread fix needs no new column

`golf_conversation_participants.last_read_at` exists in **both** the migrations and
production, and `golf_messages.read` exists alongside it. The finding stands unchanged — the
shared boolean is what unread currently runs on — but the fix is a query and backfill
against an existing column, not a schema addition. That materially lowers G-40's cost.

Also confirmed present in both: `golf_messages.reply_to_id` and `edited_at`, and the
`golf_message_reactions` / `golf_message_mentions` tables. The manifest's "the database is
ahead of the UI" trap is real and now verified rather than asserted.

## 4. NEW — G-58: two production columns that no migration creates  [high] [coordinator-verified]

**This is a messages-feature defect and belongs to this audit**, unlike the baseball drift in
`A2-RESOLUTION.md` §4.

`golf_conversation_participants.muted_until` and `.notification_level` exist in production —
`src/lib/types/database.ts:12313-12314`, generated from production by `npm run db:types` —
and are declared in the schema mirror `supabase/schemas/golf/10_tables.sql:482-484`, with a
`NOT NULL DEFAULT 'all'` and a `CHECK (notification_level IN ('all','mentions','muted'))`.

**No migration anywhere creates either column.** `grep -rln "muted_until\|notification_level"
supabase/migrations/` returns nothing; the only other hits are two files under
`supabase/migrations_archive/`, which are historical and not replayed. The local stack,
rebuilt from migrations, has exactly:

```
id, conversation_id, user_id, joined_at, last_read_at
```

**Consequences:**

- Any environment built from migrations — a fresh local stack, CI, a preview branch, a
  disaster-recovery rebuild — **lacks these columns**. Production is the only place they
  exist. A restore-from-migrations would silently drop the mute contract.
- Anyone implementing mute locally against the manifest's guidance hits
  `column "muted_until" does not exist` and will reasonably conclude the manifest is wrong.
- `check-supabase-drift`'s golf invariant passes, because it asserts a fixed expected-column
  list that does not include these two. It would not catch this.
- `ci.yml`'s "Declarative schema: new migrations reflected in supabase/schemas" step checks
  migrations → schemas. This is drift in the **other** direction, which nothing checks.

**Correction to `HANDOFF.md` §4, row 1.** "Mute has no UI *and no data* → `muted_until` +
`notification_level` exist; it is a wiring gap, not a schema gap" is **true of production
only**. It is a wiring gap *there* and a genuine schema gap everywhere else. Do not let the
uncorrected version send someone building against columns their dev database does not have.

**Proposal (not made here):** a forward migration that adds both columns `IF NOT EXISTS`
with the identical default and CHECK constraint, so production is a no-op and every other
environment converges. That is a migration against a shared production database and is the
owner's to approve — `db-migration-reviewer` should see it first.

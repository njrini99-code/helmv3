## Findings

### F1 Replying and Did-not-send states do not exist in the composer   [observed] [severity: high]
- Evidence: `src/components/fairway/pages/messages/MessageComposer.tsx:1-330` — the whole file has no reply/quote prop, no reply-context render block, and no failure-banner render block. `grep -in "reply|quote"` against the file returns zero matches. The only conditional render blocks in the JSX are the attachment preview (line 229-235) and the pointer-gated hint/counter row (line 311-327).
- Spec: plan §9.2 requires six states — Resting, Typing, Replying, Attachment, Sending, Did-not-send — each with specific visual/interaction requirements; §9.3's proposed stack order is "operation-level notice → reply context → staged attachment → writing track → optional help text."
- Gap: of six required states, only three exist in this component (Resting, Typing, Attachment-staged as a bare list — no per-file progress, see F3). Sending exists but collapses visually into the disabled/empty look (see F5). Replying and Did-not-send are entirely absent — there is no quote block, no remove-reply action, and no in-composer failure banner/Retry affordance anywhere in the file.
- Proposal: not attempted here (read-only audit); a fix would add a reply-context prop/slot above the writing track and a failure-notice slot per §9.3's stack order, each independent of the other five states per §9.3's "do not represent all these dimensions with a single boolean" requirement.

### F2 Failure is the exact forbidden shortcut: toast-only, bubble removed, no in-composer banner   [observed] [severity: high]
- Evidence: on any `onSend` rejection, `FairwayMessages.tsx:346-360` (`handleSendMessage`) catches the error, calls `showToast(..., 'error')` (line 352), and returns `false` — no other state changes on the composer's side. Upstream, `use-golf-messages.ts:609-618` rolls the optimistic message OUT of the thread (`setMessages(prev => prev.filter(m => m.id !== optimisticId))`, lines 599, 604, 611) before rethrowing. `MessageComposer.tsx:199-206` only clears `message`/`pendingAttachments` `if (success)`; on failure it does nothing beyond `setSending(false)` (line 206).
- Spec: §9.2 "Did not send" row explicitly forbids "Toast-only failure … lost text" and requires "A definitively failed own send stays in place with a muted-but-readable own-message appearance and a small red outcome/retry line below" (prose above §9, "Do not dim the whole thread").
- Gap: the bubble is removed from the thread entirely (not retained muted/readable), and the only failure signal is a toast — this is the named forbidden shortcut, not merely a missing banner. The draft text/attachments are retained in the field (correct, partial credit), but the "retained own-message object" requirement (M-V30) is not met because there is no failed bubble to retain — the optimistic row disappears.

### F3 Unknown-commit outcome collapses into the same "definitive failure" toast as a confirmed rejection   [observed] [severity: high]
- Evidence: `use-golf-messages.ts:592-618` — `withOneTransportRetry` (`transient-network-error.ts:51-60`) retries exactly once on a transport-layer error, then on any remaining failure (including the case where the request may have actually reached the server and only the response was lost) the same `catch` block at line 609 fires: roll back optimistic row, log, `throw error`. `FairwayMessages.tsx:346-360` catches that and shows one generic toast ("Failed to send message" or the raw error message) regardless of cause.
- Spec: §9.5's table names 8 distinct outcomes (Sending / Sent / Read / **Checking status·Confirmation unavailable** / **Could not send** / Access revoked / Invalid content / Local persistence failed) and the prose immediately above §9 states: "An unknown commit outcome uses Checking status or Confirmation unavailable, not a red definitive failure that invites duplication."
- Gap: the implementation has exactly two client-visible outcomes — "sending" and "generic failure toast" — with no distinction between a confirmed rejection (e.g. permission/validation) and a genuinely unknown commit state (e.g. the second transport failure, where the POST may have landed). This is confirmed, not inferred: there is no code path anywhere in `handleSendMessage`/`sendMessage` that queries the operation's outcome before surfacing failure; every non-success path is treated identically.
- Note on duplication risk (accepted, not newly reported): `memory/features/team-communications.md:82-90` already documents that a manual re-tap after a failed/uncertain send carries duplicate risk and defers the real fix to "a schema-backed idempotency key … if duplicates ever become costly" — that specific risk is accepted doctrine, not a fresh finding. What §9.5 additionally requires and is *not* met is the **user-facing distinction** between "could not send" and "don't know" — that taxonomy collapse is the gap, independent of whether a fix ever adds idempotency.

### F4 `hasAttachments` can silently drop the attachments and send text only   [observed] [severity: med]
- Evidence: `MessageComposer.tsx:193-197` —
  ```
  if (hasAttachments && onSendWithAttachments) {
    success = await onSendWithAttachments(message.trim(), pendingAttachments);
  } else {
    success = await onSend(message.trim());
  }
  ```
  `onSendWithAttachments` is an optional prop (`MessageComposerProps.onSendWithAttachments?`, line 55). If it is ever `undefined` while `hasAttachments` is `true`, the `else` branch fires and sends `message` alone through `onSend`, discarding `pendingAttachments` with no error, no warning, and — on success — clearing them from state (lines 199-204) as if they had been sent.
- Spec: §9.5 — "Also fail closed if attachments exist but an attachment-capable send handler is absent: do not silently send text without the selected file."
- Gap: current code fails *open*, not closed. In the one production call site (`FairwayMessages.tsx:696-699`) `onSendWithAttachments` is always supplied, so this does not fire today — it is a latent defect in the reusable component's own contract, not (currently) an exercised bug. Reported as `observed` because the branch and its consequence are directly readable in the source, not because it has been triggered.

### F5 Sending state is visually indistinguishable from the empty/inert state   [observed] [severity: low]
- Evidence: `canSend` (`MessageComposer.tsx:219`) is `(message.trim().length > 0 || pendingAttachments.length > 0) && !sending` — `sending` forces `canSend` to `false`. The button's className ternary (lines 288-291) applies the *same* `cursor-not-allowed bg-surface-sunken text-text-tertiary` disabled treatment whether `canSend` is false because the field is empty or because a send is in flight; only the icon inside changes (bouncing dots vs. `Send`, lines 293-301).
- Spec: §9.2 Sending row requires "Arrow changes to a contained activity indicator with the same bounds" as a distinct, active-looking state (D09), not the same dimmed/inert chrome as Resting-empty.
- Gap: bounds are identical (verified — h-11 w-11 / md:h-10 w-10 fixed regardless of state, no layout jump — this part is a PASS per brief question 2), but the color/opacity treatment collapses Sending into the same muted look as "nothing to send," which is a real but low-severity fidelity gap against D09's "dimensional" sending affordance called out in §24.4.

### F6 The five-line growth is a hardcoded 120px cap, not a computed line count — and undershoots five lines even at default text size   [observed] [severity: med]
- Evidence: `MessageComposer.tsx:87-93` (auto-resize effect) clamps `scrollHeight` to a literal `120` px; the inline `style={{ minHeight: '40px', maxHeight: '120px' }}` (line 273) repeats the same literal. The textarea's own vertical padding is `py-2` (`className`, line 261 → 8px top + 8px bottom = 16px), with `border-0` (no border to subtract). Text renders at `text-base` (Tailwind default, unmodified — `tailwind.config.ts:43-44` puts the custom 9-step scale under `theme.extend`, so Tailwind's built-in `base` = 16px/24px line-height survives) on mobile, `lg:text-body` = 15px/24px line-height on desktop (`tailwind.config.ts:344`). Either way line-height is 24px. Available content height at the 120px cap is `120 - 16 = 104px`; `104 / 24 ≈ 4.3` lines.
- Spec: §9.4 — "Measure five lines from the actual line height and field padding. A fixed 120px limit is not automatically five lines under large text."
- Gap: the plan's own hypothetical ("not automatically five lines under large text") is worse than stated here — at *default* text size the 120px cap fits only ~4 lines, not 5, before scrolling kicks in; under an enlarged accessibility text size the shortfall only grows. This is a computed, not merely inferred, mismatch: `observed` line-height token values against the hardcoded pixel cap.

### F7 A successful resolve can wipe text the user typed while a send was in flight   [observed] [severity: med]
- Evidence: the `Textarea` (`MessageComposer.tsx:252-274`) has no `disabled`/`readOnly` prop bound to `sending` — the user can keep typing while `await onSend(...)`/`await onSendWithAttachments(...)` (lines 194-197) is pending. On success, `setMessage('')` (line 203) unconditionally clears whatever the *live* `message` state holds at that moment — not a snapshot of the text that was actually submitted.
- Spec: §9.3 — "When the operation settles, remove only the submitted revision. Do not wipe newer text by resolving an older request."
- Gap: because `handleSubmit` never captures the submitted string into a local const before awaiting (it re-reads `message` at line 203, the same reactive state the field is bound to), any keystrokes typed during the in-flight send are discarded on success. Pending attachments are incidentally protected from this because `AttachmentButton` is `disabled={sending}` (line 248), but no equivalent protection exists for text.

### F8 Pasted text over the limit is silently truncated, not preserved with an explanation   [observed] [severity: low]
- Evidence: `Textarea` carries a bare `maxLength={MESSAGE_MAX}` (line 259, `MESSAGE_MAX = 5000` at line 40). The server schema matches (`src/lib/validation/action-schemas.ts:75`: `content: z.string().min(1, ...).max(5000).trim()` — source-confirmed pairing), so the constant itself is correctly synced. But the browser's native `maxLength` behavior on paste is a hard, silent truncation with no user-visible explanation of what was cut.
- Spec: §9.4 — "Preserve pasted text and explain excess content rather than silently truncating a submitted snapshot."
- Gap: no paste handler intercepts long content to warn/preserve; the field just drops everything past character 5000 with no signal beyond the near-limit counter (which only appears once already at ≥90% of the limit, per `COUNTER_THRESHOLD`, line 42).

### F9 No IME composition guard on Enter-to-send   [observed] [severity: med]
- Evidence: `handleKeyDown` (`MessageComposer.tsx:209-217`) checks only `e.key === 'Enter' && !e.shiftKey`; there is no `e.nativeEvent.isComposing` check and no `keyCode === 229` fallback anywhere in the file (`grep -n "isComposing|229|compositionstart|compositionend"` against the file returns nothing).
- Spec: §9.4 — "Composition/IME confirmation never sends accidentally."
- Gap: on a fine-pointer device (`isPointerFine` true — desktop, or a tablet with a keyboard case), a user composing text in an IME (e.g. Japanese/Chinese/Korean input) who presses Enter to confirm a candidate will instead send the message, because the handler cannot distinguish an IME-confirming Enter from a send-intending Enter.
- Test-gap note: `MessageComposer.enterKey.test.tsx` (full file read) exercises fine-pointer-sends / shift-blocks / coarse-pointer-newline / coarse-pointer-button-send, and nothing else — it never simulates a composition event, so the suite is green on a contract (IME-safety) it never tests. This is the §21-flavored "gate that cannot fail" pattern this audit is asked to watch for.

### F10 Attachment "staged" state renders no real per-file progress — always shows the initial `pending` state   [observed] [severity: med]
- Evidence: `handleFilesSelected` (`MessageComposer.tsx:144-165`) seeds every new attachment with `status: 'pending'` and `uploadProgress: 0` and never updates either field again anywhere in the component (no other `setPendingAttachments` call touches `status`/`uploadProgress`). `AttachmentPreview.tsx` only renders a progress bar/percentage when `status === 'uploading'` (lines 128-154) — a state this composer never sets. The real upload progress exists one layer down: `useMessageAttachments.sendMessageWithAttachments` accepts an `onProgress` callback (`use-message-attachments.ts:19,59-61`) that `uploadAttachment` actually drives — but `FairwayMessages.tsx:365-369` (`handleSendMessageWithAttachments`) never passes an `onProgress` argument when calling `sendMessageWithAttachments`, so the callback is always `undefined` and the real progress is dropped on the floor before it ever reaches the composer's state.
- Spec: §9.2 Attachment row — "Per-file progress from actual transfer; uploaded and finalizing remain different. Preserve order and partial failure." — forbidden shortcut: "A decorative 62% matching the mockup; every file shares one fictional progress bar."
- Gap: the composer avoids the *forbidden* fictional-progress shortcut (no fake number is shown), but it also shows no real progress at all — files sit at "pending" appearance for the entire upload, then either vanish (success) or remain at "pending" (failure), never transitioning through "uploading" visually.
- Cross-lane note: the deeper mechanics here (whether a partial multi-file failure inside `Promise.all` in `use-message-attachments.ts:53-78` orphans already-uploaded files, since `uploadResults` never resolves and the existing cleanup block at lines 105-122 only runs after a *server*-side failure, not an upload-side throw) are flagged per this brief's scope note that M04 owns upload behavior — recorded here only because it explains why the composer itself can never show a real "uploaded" per-file state today.

### F11 `--keyboard-height` is subtracted once, correctly, at the screen level — composer itself does not double-count (brief question 4 answered: PASS)   [observed] [severity: n/a — confirms correct behavior]
- Evidence: `MessageComposer.tsx` contains zero references to `--keyboard-height` or `.keyboard-open` beyond one Tailwind arbitrary-variant class, `[.keyboard-open_&]:pb-4` (line 226), which only toggles the composer's own *bottom padding* (dropping the home-indicator safe-area pad while the keyboard covers it) — it does not touch height/layout via `--keyboard-height` itself. The actual height subtraction happens exactly once, at the screen container in `FairwayMessages.tsx:510-511`, using `max(0px, calc(var(--keyboard-height,0px) - ...))` against `100dvh`. `AppShell.tsx:504-507` explicitly documents *not* adding keyboard room at the shell level, deferring to the global `body.keyboard-open` rule instead. This matches the sanctioned mechanism recorded in `memory/features/team-communications.md:101-107`.
- Gap: none for the composer itself.

### F12 (risk, not composer-owned) Global `body.keyboard-open` padding is not suppressed by `data-fw-keyboard-aware`, unlike a possible expectation from its name   [risk] [severity: low]
- Evidence: `src/app/globals.css:414-416` — `body.keyboard-open { padding-bottom: var(--keyboard-height); }` is an unconditional, page-wide rule with no exception for `[data-fw-keyboard-aware]`. `CapacitorProvider.tsx:159-173` shows `data-fw-keyboard-aware` gates only the JS `scrollIntoView` centering call, not this CSS rule. `FairwayMessages.tsx:493` sets `data-fw-keyboard-aware` on the messages screen root, which *also* independently subtracts `--keyboard-height` from its own `calc(100dvh - ...)` height (lines 510-511).
- Gap (unconfirmed): whether this produces an actually-doubled gap depends on whether `<body>` scrolls independently on this route. A `dvh`-sized child's computed height is viewport-relative, not derived from the body's content-box (so body `padding-bottom` does not mechanically shrink a `100dvh` child further) — meaning this is likely benign, but I could not confirm whether `<body>` is scroll-locked (e.g. via `overflow:hidden` under an immersive/`data-fw-immersive` state) on the messages route, which is what would make the extra padding-bottom either inert or produce genuine extra dead space below the fold when the keyboard is open.
- What would confirm it: reading whatever CSS rule (if any) sets `overflow: hidden` on `<body>` when `data-fw-immersive`/mobile chat is active, or observing on a device/simulator whether extra scroll room appears below the composer when the keyboard opens on the messages screen. Recorded as `risk`, explicitly shell/shared territory (globals.css + AppShell + CapacitorProvider), not a MessageComposer.tsx defect — flagged only because brief question 4 asked about it directly.

### F14 The typing/replying focus glow and the active send button's dimensional shadow are unmapped constructions, and the focus glow's color choice conflicts with the codebase's own accessibility doctrine   [observed] [severity: med] — includes a plan/artboard disagreement
- Evidence (focus glow): `Composer.dc.html:24` (`.track-on`) is `box-shadow: inset 0 1px 0 white/0.6, 0 0 0 1px accent-500/0.30, 0 0 0 4px accent-500/0.10` — a two-layer ring built entirely from `--fw-color-accent-500`. `design-tokens.css:149-165` documents, in its own comment, that `accent-500` was *rejected* as a focus-indicator color specifically because it fails WCAG 2.2's 3:1 non-text contrast minimum, and that `--fw-color-border-focus` was deliberately bound to `accent-600` instead for exactly this reason. Current code's focus treatment (`MessageComposer.tsx:242`, `focus-within:border-accent-500 focus-within:ring-2 focus-within:ring-border-focus/30`) mixes a **solid** `border-accent-500` with a **separate** `ring-border-focus` (accent-600) — neither the artboard's double-alpha-ring construction nor a straightforward token substitution.
- Plan text: §9.1 explicitly says "The input focus edge is crisp, not a wide blurry green glow" — which is a direct, textual disagreement with what the artboard itself specifies (a two-stop, blurred-looking glow built from two box-shadow rings at 30%/10% opacity spreading out 1px/4px). **Recording this as a plan-vs-artboard disagreement per the addendum's instruction, not resolving it**: the plan's prose forbids exactly the treatment the artboard draws. Whichever is authoritative, accent-500 as the base ring color would also need to clear the same 3:1 non-text contrast bar `border-focus`/accent-600 was created to satisfy (`design-tokens.css:149-156`) — that's a second, independent reason (accessibility, not just prose-vs-artboard) to not adopt the artboard's literal color choice as-is without re-verifying contrast.
- Evidence (send-on shadow): `Composer.dc.html:26-27` — `linear-gradient(165deg, accent-600, ~accent-650)` + `inset 0 1px 0 white/0.18` + two accent-700/750-tinted drop shadows (`/0.28`, `/0.22`).

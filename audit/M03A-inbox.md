## Decision-needed items for M00 (per ADDENDUM 1 caution #2 — recorded, not resolved)

### D1 — Presence dot on pinned avatars
- Artboard citation: `Main.dc.html:44` — the first pinned avatar ("Cole"/"CB") carries a presence dot (`width: 11px; height: 11px; border-radius: 9999px; background: oklch(0.648 0.149 149.6)` = `--fw-color-accent-500`, ringed with a 2px border matching the surrounding surface color). The other four pinned avatars in the same row do not carry one. The same person's conversation row (`Main.dc.html:67-69`, "Cole Bennett") also carries the identical dot on its own avatar, while other rows (Alexis Bennett, Jordan Rivera, the group row) do not.
- Conflict: plan §24.5 explicitly says "Do not invent... Active now"-style presence; plan §5.3 (line 181) separately says "A presence dot is shown only from supported, current authorized presence... do not imply offline as a fact when state is unknown" — i.e., the plan already anticipates this exact tension and resolves it conditionally ("only from supported, current authorized presence"), not by forbidding presence outright.
- What I verified this pass: no presence/online-status field exists on `golf_coaches` or `golf_players` in the columns `use-golf-messages.ts` selects (`:160-169`, `:993-1006`), and no Supabase Realtime Presence channel is opened anywhere in `use-golf-messages.ts` (its two realtime channels, `:429` and `:1141`, are both `postgres_changes`/`broadcast` for messages and typing, not `presence`). So today there is no authorized data source this dot could bind to without new work.
- What would need to exist to back it: either (a) a Realtime Presence channel tracking each team member's connected sockets (ties online-ness to "has an open tab/app," which is what most chat presence actually means), or (b) a stored last-active timestamp with a freshness threshold. Either is a real feature addition, not a rendering fix — recording for M00 to decide whether it ships, and if so, which of the two.

### D2 — Bell badge count semantics
- Artboard citation: `Main.dc.html:28` — badge value "7" on the masthead bell, and `Empty.dc.html:26` — the same bell with no badge (implying it hides at zero, though the artboard cannot confirm that inference; it is a single static frame).
- Conflict: plan §5.1 (line 165) explicitly requires "preserve its real data semantics" and separately warns "its count is not the inbox unread-conversation count." Since no bell exists in this codebase today (F10), there is no current data semantics to preserve — this is a green-field decision, not a preservation problem.
- What would need to exist to back it: a defined notification domain distinct from per-conversation unread counts (e.g., an app-wide notifications table/feed) that this Messages-scoped lane does not own or have visibility into. Recording for M00 to decide what the "7" counts before any implementer wires a real query to it.

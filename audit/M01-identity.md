## Findings

### M01-1 Exact DM creation is a read-then-write race with no DB-level serialization [observed] [severity: high]
- Evidence: `src/app/actions/messages.ts:279-306` (`createConversation`) looks up an existing 1:1 conversation via two sequential SELECTs (`myConversations` then `sharedConversations`), and only if neither returns a match does it fall through to `INSERT` a new `golf_conversations` row (`:335-356`) and participant rows (`:418-430`).
- Evidence: `golf_conversations` (baseline `supabase/migrations/20260527000000_prod_public_baseline.sql:9358-9367`) carries no unique or exclusion constraint over `(team_id, participant-set)` or any DM-pair identity. The only unique constraint in this schema is `golf_conversation_participants_conversation_id_user_id_key UNIQUE (conversation_id, user_id)` (`:12029`), which prevents a duplicate *participant row inside one conversation*, not a duplicate *conversation* for the same pair.
- Spec: plan §17.1 — "Concurrency converges on one DM through a database-enforced identity/serialization strategy. Create conversation and memberships atomically."
- Gap: nothing in Postgres enforces "one DM per pair." Two concurrent `createConversation` calls for the same two users can both miss each other's not-yet-committed row in the lookup SELECTs and both proceed to INSERT, producing two separate DM conversations for the same pair — a duplicate the spec (and M-T04) explicitly requires to converge.
- I did not execute the race (no DB access this phase; see "What I could not verify"). The absence of any serialization mechanism is directly `observed` in the schema; the resulting duplicate-under-concurrency outcome is a `risk` I could not reproduce.
- Proposal (not applied): a partial unique index over a normalized pair-key column (e.g. `LEAST(a,b), GREATEST(a,b)` for `team_id`-scoped 1:1 rows, populated by trigger or generated column), or an advisory lock keyed on the sorted pair before the lookup-then-insert, would make this atomic. Out of scope to implement here.

### M01-2 `createGolfTeamBroadcast`'s reuse-dedup has the same race shape, lower severity [observed] [severity: low]
- Evidence: `src/app/actions/messages.ts:747-829` — dedupe-by-`(team_id, title, participant set)` is a SELECT-then-compare-then-INSERT/UPDATE sequence with no unique constraint backing it (same schema as M01-1).
- Spec: plan §17.1 (same atomicity requirement, extended to group creation by analogy).
- Gap: two coaches (or one coach double-tapping "Create") issuing the same broadcast title concurrently could each miss the other's row and create two team-chat conversations with the same title/audience. Lower severity than M01-1: broadcast creation is coach-only, not a high-frequency operation, and the existing code already treats stale/duplicate titles as a known, actively-worked issue (comment at `:738-745`).

### M01-3 Two independent code paths insert into `golf_messages`; only one has idempotency/collision handling — §17.3 "one send operation" is violated [observed] [severity: high]
- Enumeration method: `grep -rln "from('golf_messages'\|from(\"golf_messages\"" src --include='*.tsx' --include='*.ts'` (repo root) returns six files: `src/app/actions/messages.ts`, `src/app/golf/actions/message-attachments.ts`, `src/app/golf/actions/coach-notifications.ts`, `src/app/golf/actions/player-notifications.ts`, `src/lib/admin/data/activity.ts`, and a test fixture (`use-golf-messages.attachment-flag.test.ts`). I confirmed by grepping each for `.insert(` immediately after the `.from('golf_messages')` call that `coach-notifications.ts`, `player-notifications.ts` and `activity.ts` only ever `select` from the table (reading message content for notification/activity-feed previews) — none of them insert. I also grepped for `kind: 'system'` (the value `golf_messages.kind`'s CHECK constraint admits per `20260904160000_golf_messaging_structured.sql:73`, alongside `practice`/`event`/`rsvp`/`poll`/`travel`) across all of `src/` and found no golf writer setting it (only unrelated baseball `signals`/`video-classes` code uses that literal). So exactly two production code paths write `golf_messages` rows, and no code path currently writes a structured (`system`/`poll`/`rsvp`/etc.) message despite the column existing live — that gap is the same shape as M01-4's `reply_to_id` finding, for the `kind`/`payload` columns instead.
- Evidence path A (idempotent): `sendMessage()` in `src/app/actions/messages.ts:90-252` accepts an optional `client_message_id` (`:47`, `:107-111`), inserts it as the row's real `id` (`:147`), and on a primary-key collision (`23505`) from a retried send with the *same* id, treats it as an already-successful send and returns `{ success: true }` (`:168-170`). The client (`src/hooks/golf/use-golf-messages.ts:557-595`) generates the id once, reuses it across `withOneTransportRetry`'s single retry, and this is the send path `memory/features/team-communications.md` documents (`withOneTransportRetry`, 750ms, transport-failure only).
- Evidence path B (not idempotent): `sendGolfMessageWithAttachmentsImpl()` in `src/app/golf/actions/message-attachments.ts:57-164` inserts into `golf_messages` (`:89-99`) with **no `clientMessageId`/`client_message_id` parameter at all** — the row's id is always server-generated. `AttachmentUploadData`/the function signature (`:57-61`) has no id field, and the calling hook `src/hooks/golf/use-message-attachments.ts:30-140` and its caller `src/components/fairway/pages/messages/FairwayMessages.tsx:362-389` (`handleSendMessageWithAttachments`) call this **without** `withOneTransportRetry` or any other retry wrapper — confirmed by `grep` for `withOneTransportRetry` across the messages directory returning zero hits outside `use-golf-messages.ts`.
- Spec: plan §17.3 — "Generate a message UUID once. Carry text, quote, file references and immutable revision through every send/retry surface... On a duplicate ID, verify sender, conversation and request equivalence; do not treat every unique-constraint error as a successful retry." §18 — "One transaction function may be owned by M01... no duplicate competing send RPCs."
- Gap: this is exactly the two-competing-implementation shape §18 prohibits. The attachment send path cannot currently duplicate itself via automatic retry (there is none), but that cuts the other way: if the response to an attachment send is lost in transit (same WKWebView "Load failed" class documented in `memory/features/team-communications.md:82-90` for the text path), the client has **no operation ID to reconcile against** — it cannot distinguish "never arrived" from "landed but the ack was lost," and a user-initiated re-tap of Send would insert a genuine second message plus a second copy of every uploaded file, because nothing on this path is keyed by a client-generated, retry-stable id. The text-only path solved this exact problem; the attachment path does not share the fix.
- Proposal (not applied): thread the same `generateClientMessageId()` value used for the optimistic row through `sendGolfMessageWithAttachments`/`sendGolfMessageWithAttachmentsImpl`, insert it as `golf_messages.id` the same way `sendMessage` does, and apply the same `23505`-is-success handling before the attachment-metadata insert.

### M01-12 Group/team-chat unread counts use a shared, conversation-wide read flag, not each viewer's own read frontier — §17.2 is violated for group conversations in the normal (non-fallback) path [observed] [severity: high]
- Evidence — the four tables' RLS-enabled state (brief item 5, cited directly): `golf_conversation_participants` — `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` at baseline `:18998`; `golf_conversations` — `:19001`; `golf_message_attachments` — `:19227`; `golf_messages` — `:19230`. All four confirmed enabled.
- Evidence — the schema has BOTH a per-viewer column and a shared column, and only one is actually per-viewer: `golf_conversation_participants.last_read_at` (baseline `:9347-9352`) is one row per `(conversation_id, user_id)` — genuinely per-viewer. `golf_messages.read boolean DEFAULT false` (baseline `:9874-9884`) is one column on the message row itself — shared across every participant.
- Evidence — the RPC every conversation row (DM **and** group/team-chat) goes through by default computes `unread_count` from the shared column, for every conversation type: `get_golf_conversations_with_details` (`supabase/migrations/20260621041824_harden_get_golf_conversations_rpc.sql:47-53`) — `SELECT COUNT(*) FROM golf_messages m WHERE m.conversation_id = c.id AND m.read = FALSE AND m.is_deleted = FALSE AND m.sender_id != v_uid`. This runs for every row the outer query returns (`FROM golf_conversations c JOIN golf_conversation_participants cp ... WHERE cp.user_id = v_uid`, `:71-73`), i.e. every conversation the caller participates in, DM or team chat, with no `is_team_chat`/`is_group` branch anywhere in the function.
- Evidence — the write that clears it is conversation-wide, not viewer-scoped: `mark_golf_messages_read` (`supabase/migrations/20260710160000_mark_golf_messages_read_rpc.sql:44-48`) — `UPDATE golf_messages SET read = true WHERE conversation_id = p_conversation_id AND sender_id != v_uid AND read = false` — this flips the shared column for **every** other-sender message in the conversation, not just the messages the calling viewer has actually seen. In a 3+-person team chat, whichever participant opens the thread first clears the unread flag for every OTHER participant too, before they have read anything.
- Evidence — the client-side hook only patches this for a narrow fallback case, not the normal path: `src/hooks/golf/use-golf-messages.ts:718-943` (`useGolfConversations`/`fetchConversations`). The RPC's result (`conversationsData`, including every team chat's RPC-computed `unread_count`) is taken as-is (`:766`). A second, supplemental query (`:772-799`) fetches the caller's team-chat conversations directly and computes a **correct**, `last_read_at`-based per-viewer unread count for them (`:889-899`: `unreadQuery... .gt('created_at', lastReadAt)` scoped to `sender_id != userId`) — but that correct computation is only used for team chats **not already present** in the RPC's own result (`:825-833`: `!existingIds.has(conv.id)`, merged in at `:940-943`). Since the RPC's own query is a plain participant join that will normally include every team chat the caller belongs to, the "in case DB function doesn't include them" fallback (the comment at `:772`) is the exception path, not the common one — in the ordinary case a team chat's `unread_count` comes straight from the RPC's shared-column computation, not from this per-viewer fix.
- Spec: plan §17.2 — "Use each participant's read frontier rather than a shared message-wide read boolean for group truth," and M-T06 — "B reads A; C remains unread until C's own observed frontier advances."
- Gap: for a group/team-chat conversation reached through the RPC's normal path (the common case), the unread badge and count are computed from a conversation-wide boolean that any one participant's read-through clears for everyone, not from each viewer's own `last_read_at`. This is the exact defect class §17.2 and M-T06 name. The comment at `src/app/actions/messages.ts:505-508` ("group-chat unread badges are computed app-side from `last_read_at`") describes the client-side hook's *intent* and matches the fallback branch, but not the RPC-sourced common case, and the comment at `:529-534` explicitly scopes the shared-boolean write to "the 1:1 unread_count basis" — the RPC itself carries no such scoping. I did not execute a live three-user reproduction (see "What I could not verify"); this finding is `observed` from the SQL and hook logic, not from a live run.
- Note this is a distinct, and more severe, mechanism than the read-frontier note in M01's original scope summary — it is not merely "does a sender's own send advance another participant's frontier" (it does not: `sendMessage`/`sendGolfMessage` never touch `last_read_at` or `golf_messages.read` for other participants, `src/app/actions/messages.ts:142-205`), but "does one recipient's own read-through incorrectly clear another recipient's unread state" (it does, for the RPC-sourced group-chat path).
- Proposal (not applied): either (a) make `get_golf_conversations_with_details` compute unread the same `last_read_at`-based way the client-side fallback already does for every conversation, dropping the shared `golf_messages.read` column from the unread computation entirely, or (b) make `mark_golf_messages_read` a true per-viewer operation (it already advances `last_read_at` correctly at the call site in `markMessagesAsRead`, `src/app/actions/messages.ts:505-514` — the RPC's conversation-wide `UPDATE ... SET read = true` is the part that needs to stop existing for any conversation with more than 2 participants). Either fix is a schema/RPC change outside this audit's read-only scope.

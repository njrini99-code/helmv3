# Lane A08 — Invitations, authentication, account lifecycle, and native handoffs

Baseline: `3c90f9f174ac103af5fafc600aebecd98243decc`. Evidence labels used throughout: `SOURCE`, `RISK`, `PROPOSAL`, `NOT_RUN`. No device, runtime, test account, or database access was available or used. `OBSERVED`/`REPRODUCED` were never claimed.

## Top 5 actionable findings

1. **A08-001** (P1, SOURCE/RISK) — `ios/App/App/GolfBridgeViewController.swift:87-93` classifies "did the user leave the golf app" with two unanchored `url.contains("/golf/")` / `contains("/about"|"/privacy"|"/terms")` string checks — no host/origin comparison at all. A URL on a different origin that merely contains `/golf/` as a substring is treated as an in-app page (no return-to-login safety net fires); a genuine in-app URL missing that literal substring (e.g. the bare `/golf` root before its server redirect resolves) can trigger `SceneDelegate.swift:20-27`'s hardcoded full-document reload to `https://www.helmsportslabs.com/golf/login`, discarding all SPA state. Still present at this baseline. Owner: A01 (native file); A08 requests the contract.
2. **A08-003** (P1, SOURCE/RISK) — Every sign-out call site (`FairwayDashboardShell.tsx:229-248`, `FairwaySettingsGeneral.tsx:571-577`) fires `clearActiveTeam()` + `supabase.auth.signOut()` unconditionally with no check against the app's own offline round-draft store (`src/lib/offline/indexed-db.ts`) and no reuse of the "Discard unsaved changes?" `ConfirmDialog` pattern the same Settings file already implements for its own panel edits. Contradicts the plan's explicit "warn before logout when possible."
3. **A08-002** (P2, SOURCE) — `src/app/auth/callback/route.ts:196-227` discards the `error` from `.single()` reads on `golf_coaches`/`golf_players` (and the baseball equivalents), so a transient read failure is indistinguishable from "no profile" and can route an *already-onboarded* coach/player through first-run onboarding UI. Both onboarding pages self-correct on mount, so this is a flash/extra-round-trip, not data loss — but it is the same bug class the codebase explicitly fixed one file over, in `join/[code]/page.tsx`.
4. **A08-004** (P2, RISK) — `src/lib/auth/session.ts:141-167` (`getGolfSessionProfile`, the load-bearing identity gate for 40+ dashboard routes) and its own mitigating retry in `layout.tsx:101-119` both discard read errors on the coach/player lookups. Two consecutive transient failures ~300ms apart would misroute an established user to `/golf/signup` (`layout.tsx:276-283`). The retry logic is a real, well-built mitigation — this is the residual gap in it.
5. **A08-005** (P2, SOURCE) — The identical team join code produces two different outcomes depending only on entry surface: `/golf/join/[code]` auto-joins with no coach approval (`teams.ts:429-437`, `golf_join_team_with_code`), while the same code typed into Settings' "Request to Join" creates a pending request requiring coach approval (`teams.ts:908-1040`). Flagged as an open product question, not a code defect.

### A08-001 — Native shell URL classifier is unanchored substring matching (G24, still present)

- **Files/ranges:** `ios/App/App/GolfBridgeViewController.swift:81-97`, `ios/App/App/SceneDelegate.swift:17-28`.
- **Mechanism:** `GolfBridgeViewController` observes `webView.url` via KVO. `isGolfPage = url.contains("/golf/")`; `isAboutPage = url.contains("/about") || url.contains("/privacy") || url.contains("/terms")`. Neither check inspects `URL.host` or anchors the match to a path prefix — they are raw substring tests against the full absolute URL string. When both are false, `SceneDelegate`'s `onNavigateAway` closure runs `webView.load(URLRequest(url: "https://www.helmsportslabs.com/golf/login"))`, a full document navigation (not an SPA route change), after "a small delay to let the navigation settle."
- **Consequence:** (a) An off-origin URL containing `/golf/` anywhere (e.g. a redirect target embedding that literal substring in a query string or path segment) is silently accepted as if it were the app, and the native return-to-login safety net never triggers — the WKWebView has no address bar, so the user has no way to notice they have left the real app. (b) The reload itself is a blunt instrument: it is a full document load discarding all in-memory SPA state (any in-progress round, form, or navigation position), not a soft in-app redirect to `/golf/login`.
- **Verification against baseline:** Read both files in full at the pinned SHA. Confirmed present, unchanged from the described behavior. No fix commit referencing this classifier was found; this is **still present**, not previously fixed.
- **Requested fix (A01 owns the file):** anchor the classifier on `URL.host` equal to the deployed app's host and `URL.path` starting with `/golf/` (etc.), using `URLComponents`, not string containment. A08 requests this as a shared contract since the failure mode intersects session/redirect integrity, which A08 otherwise verified is well-guarded at the web layer (see "Verified passing" below).
- **Related negative tests:** T02 (stale chunk / bounded recovery), T19 (native handoff cancel/return), T24 (capability-safe behavior across binary versions).

### A08-002 — OAuth callback treats a failed profile read as "no profile"

- **Files/ranges:** `src/app/auth/callback/route.ts:161-252` (golf branch at 196-227, baseball branch at 230-252); mitigating self-check at `src/app/golf/(onboarding)/player/page.tsx:90-150` and `src/app/golf/(onboarding)/coach/page.tsx:150-210`.
- **Mechanism:** `supabase.from('golf_coaches')...single()` / `golf_players...single()` results are destructured as `{ data: golfCoach }` / `{ data: golfPlayer }` — the `error` is never read. A transient network/DB failure and a genuine "no row" both present as `data: null`, so the callback's `if (golfCoach)` / `if (golfPlayer)` guards cannot tell them apart and fall through to "No golf profile exists — redirect to golf signup" for a user who may in fact already have a completed profile.
- **Mitigation already in place:** Both `(onboarding)/player/page.tsx` and `(onboarding)/coach/page.tsx` independently re-check the profile via `.maybeSingle()` on mount and redirect to `/golf/dashboard` if `onboarding_completed` is true. So the actual user-visible consequence at this baseline is a momentary flash of the wrong first-run screen plus a wasted round trip, not stranding or data loss — this is a **P2 continuity defect**, not P0/P1.
- **Why it's worth fixing anyway:** the exact same anti-pattern was explicitly identified and fixed one file over, in `src/app/golf/join/[code]/page.tsx:38-53,100-106`, whose comments describe this precise failure mode ("a failed read left `coach` null...a coach clicking a team invite was walked through PLAYER onboarding"). The OAuth callback was evidently not covered by that fix.
- **Related negative tests:** T06 (empty vs. failed read vs. unqueried), T20 (session/membership edge cases at a notification/invite target).

### A08-003 — Sign-out has no unsynced-work warning despite a real offline round-draft store

- **Files/ranges:** `src/app/golf/(dashboard)/FairwayDashboardShell.tsx:223-248` (`useGolfSignOut`, used by both the rail footer and the More-sheet footer), `src/components/fairway/pages/settings/FairwaySettingsGeneral.tsx:571-577` (Settings' own sign-out), `src/lib/offline/indexed-db.ts:34-177` (the `golfhelm_offline` IndexedDB store, keyed by `playerId`), `src/components/fairway/pages/rounds-recover/FairwayRecoverRound.tsx:353-429` (existing recovery UI that already queries this store scoped by the current `playerId`).
- **Mechanism:** Every sign-out path calls `clearActiveTeam()` then `supabase.auth.signOut()` unconditionally, gated only by an `isSigningOut` double-tap guard. None of them consult the offline round store for a recoverable in-progress round before proceeding, and none reuse the "Discard unsaved changes?" `ConfirmDialog` leave-guard the same Settings file (`FairwaySettingsGeneral.tsx:126-275`) already built for its own dirty-panel tracking.
- **What actually happens to the data:** Traced `FairwayRecoverRound.tsx` and confirmed it filters strictly by the *current session's* `playerId` (`round.playerId !== playerId` skip at line 389), so this is not a cross-account leak risk — the local IndexedDB rows persist and remain recoverable if the *same* player signs back in on the *same* device. The user consequence is a **confidence/warning gap**, not confirmed destruction of data — labeled `RISK` accordingly (reproduction of an actual loss would need a device).
- **Why it matters:** the plan's explicit instruction is "protect privacy without silently destroying unsynced work: warn before logout when possible, then enforce the confirmed security policy." At this baseline, privacy wins unconditionally and unsynced work gets no warning at all, even though the machinery to check for it (the recovery query) and to warn about it (the ConfirmDialog pattern) both already exist elsewhere in the same codebase.
- **Related negative tests:** T04 (logout while a read/realtime callback pending), T10 (offline edits + relaunch/reconnect), T11 (storage/schema failure on local draft store).

### A08-004 — The central golf identity gate has the same discarded-error pattern, mitigated but not closed

- **Files/ranges:** `src/lib/auth/session.ts:141-167` (`getGolfSessionProfile`), `src/app/golf/(dashboard)/layout.tsx:37-133` (consumer + retry), `layout.tsx:276-283` (the fallback redirect).
- **Mechanism:** `getGolfSessionProfile()` runs `golf_coaches`/`golf_players` reads in parallel and keeps only `.data`. The dashboard layout is the primary (and by import count, near-universal — 40+ files import `getGolfSessionProfile`) consumer. It has real, well-designed protection against the *common* failure mode: when neither profile shows `onboarding_completed`, it re-queries both tables directly (bypassing `React.cache`) and, if still empty, waits 300ms and retries once more (`layout.tsx:101-119`) — explicitly built to survive "post-onboarding eventual consistency," per its own comments.
- **The residual gap:** that retry *also* only checks `.data`, never `.error`, on both the first and second attempt. So the redirect-to-onboarding branch (`layout.tsx:276-283`) is reachable by an established, fully-onboarded coach or player if the coach/player read fails (not merely returns empty) on *both* the original cached call and the 300ms-later retry — a narrower window than a naive read-error bug would suggest, but not eliminated.
- **Severity rationale:** downgraded to P2 specifically because of the demonstrated retry mitigation; flagged because this is the single highest-traffic identity gate in the golf app and the class of bug (discarded `.error`, treated as "row doesn't exist") recurs at four separate call sites across this audit (this one, A08-002's OAuth callback, and two already-fixed instances in `join/[code]/page.tsx` and `validateGolfPlayerCanJoinTeamImpl`).
- **Related negative tests:** T06, T20.

### A08-005 — Same join code, two different approval postures depending on entry surface

- **Files/ranges:** `src/app/golf/actions/teams.ts:320-353` (`validateGolfPlayerCanJoinTeamImpl` — "already on this team" is success, not failure, itself a good fix), `teams.ts:429-437` (`golf_join_team_with_code` RPC insert, no approval step), `teams.ts:551-587` (`processGolfTeamInvitationImpl`, used by the `/golf/join/[code]` deep link), `teams.ts:908-1040` (`createTeamJoinRequestImpl`, used by Settings' "Request to Join a Team"), `src/app/golf/join/[code]/page.tsx:66-148`.
- **Mechanism:** Both paths resolve the same `golf_teams.join_code` through the same `golf_team_by_join_code` SECURITY DEFINER RPC (confirmed identical by reading both call sites). The link path inserts directly into `golf_team_members` (instant, active membership). The Settings-form path inserts into `golf_team_join_requests` with `status: 'pending'`, which per `JoinTeamSection.tsx`'s own copy requires "your coach will review your request and approve you."
- **This is a product question, not a code defect** — recorded as an open question for the owner: is auto-join-via-link an intentional convenience (the coach who mints and shares the specific link is presumed to have already vetted whoever receives it), or should every join — regardless of entry surface — go through the same configurable approval gate? The current behavior is internally consistent (same RPC, same authorization check, same "one team only" rule) but the *approval semantics* diverge silently.

## Coach/player first-week maps

### Player, join-link path (existing account, correct email)
`invite link tapped` → **`/golf/join/[code]`** (`join/[code]/page.tsx:17-180`) → not authenticated → redirect to **`/golf/signup?returnTo=/golf/join/[code]`** → sign up / sign in → **`golf-sign-in-form.tsx`** extracts join code from `returnTo`, threads it through onboarding as `?joinCode=` if the player isn't onboarded yet (lines 169-196) → **`/golf/player`** onboarding (if new) → `completePlayerOnboarding` auto-joins via the stored code, or → **`/golf/join/[code]`** again (if already onboarded) → `GolfJoinTeamClient` "Confirm & Join Team" → `processGolfTeamInvitation` → **`/golf/dashboard`**. Verified: code resolved *before* any onboarding redirect (explicit fix, `join/[code]/page.tsx:66-83` comment), so a bad/expired code fails immediately with an "Invalid Invite Code" screen rather than silently after four onboarding steps.

### Player, join-link path (already a member of a DIFFERENT team)
Same route to `GolfJoinTeamClient` → tap "Confirm & Join Team" → `processGolfTeamInvitation` → `validateGolfPlayerCanJoinTeamImpl` returns `canJoin: false` with a named-team reason ("You are already on **{team}**. Golf players can only be on one team at a time.") → error renders in the client card. **Gap:** no in-flow "leave your current team" action from this screen — the player must separately navigate to Settings → Team Membership → Leave (`JoinTeamSection.tsx:130-160`) and retry the invite link. Not filed as a defect (the message is accurate and actionable), but noted as a rougher-than-necessary hand-off; would be a good P3 polish candidate (add a direct link to Settings from the error state).

### Player, join-link path (already a member of THIS team)
`validateGolfPlayerCanJoinTeamImpl` returns `alreadyOnThisTeam: true`, and the caller (`joinGolfTeamImpl:344-346`) explicitly treats this as **success** — verified fix, with a cited production incident (three new players seeing a false "already a member" failure within 67 seconds of signup). Good existing behavior.

### Player, no invite (Settings self-serve)
`/golf/dashboard/settings` → Team Membership section → enter code → `createTeamJoinRequest` → pending row in `golf_team_join_requests`, visible to the player as "Requested Xm/h/d ago" with a Cancel action (`JoinTeamSection.tsx:240-278`) → coach approves (separate coach-side flow, not traced in this lane — belongs to A04/roster territory) → player becomes an active member. Sparse/pending state is intentional and clear, not an "unavailable feature" tour.

### Coach, staff-invite path
Head coach mints a signed, non-single-use bearer token (`staff-invite.ts`) scoped to `{team, organization, role}` with a 72h TTL — **deliberately not bound to a specific email** (documented design choice, "KNOWN LIMIT — deliberately accepted": anyone the link is forwarded to can redeem it, same trade as any emailed invite link). `signupWithStaffInviteAction` (`auth.ts:801-915+`) verifies the HMAC-signed token before accepting any signup input, rejects expired/malformed/bad-signature tokens with distinct copy, and reads the role *only* from the signed payload (never from client input) so a recipient cannot escalate `coach` to `admin`. Verified as a resolved, intentional tradeoff — not filed as a new finding.

### Coach entry via a player's team-invite link (misrouting guard)
`join/[code]/page.tsx:28-64` explicitly checks for an existing coach identity before treating the visitor as a prospective player, and fails closed (throws, does not silently continue) if that coach-identity read itself errors — citing a real prior incident where a discarded read error let a coach get walked through player onboarding and acquire a stray `golf_players` row. Verified fix, present and correct at this baseline.

**Overall assessment:** the identity model in `src/lib/auth/session.ts` is clean and consistently consumed — this audit did not find a genuine id-conflation bug (auth id used where a player/coach id was required, or vice versa). The real, well-evidenced risk in this area is not conflation but **silently-discarded read errors at the boundary** (A08-002, A08-004), which produce the *same visible symptom* (misrouting to onboarding/signup) that true conflation would, so it is worth distinguishing clearly: this is a fail-open-on-error problem, not an identity-model problem.

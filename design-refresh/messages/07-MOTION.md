## Springs

## Reduce Motion

Playwright `reducedMotion: 'reduce'`, iOS Settings > Accessibility > Motion > Reduce Motion, and the page's Reduce button (`.app.reduce`) all mean the same. The page's rule, in `anim()` (lines 145 to 149): a move whose keyframes hold opacity becomes an opacity crossfade from its first to its last opacity, 120ms `linear`; a move given `rd` uses those frames instead; a move given `rd: null` does not run at all, so its end state shows at once. CSS transitions on the + icon, the mute switch, the title, the hover bar, the date pill, the hairline and the segmented thumb are set to `none` (d-extra 81 and 149). Loops stop: the skeleton pulse is off (d-extra 339) and **typing dots hold still at full opacity** (d-extra 342), which keeps the mark at 3:1 (`--a-dot`, ruling 2: light #7A766C, 3.97 on the page to 4.49 on paper; dark #827D71, 3.55 on the selected wash to 4.60 on the page, 3.62 on a bubble). In the build every RM fade runs `CH_FADE_MS` (180ms) `linear` through the shared helper (ruling 25); Messages defines no fade of its own. In framer, `chSpring(kind, reduced)` returns duration 0, so give each motion its opacity fade in the reduced branch (WAAPI `{ duration: CH_FADE_MS, easing: 'linear' }`). Direct manipulation still follows the finger under Reduce Motion (drag for times, sheet drag); only the return is instant.

## The four interrupt rules

The page's `anim(node, keyframes, spring, options)` (line 138) carries all four. Build them as below, in framer-motion where the move is a spring on a rendered element and in WAAPI (`el.animate`) on refs where the move must start from a value read off the screen.

| Rule | On the page | In the app |
|---|---|---|
| **Live-start** | `live: true`: `liveFrame()` (line 119) reads the computed `transform` and `opacity`, `cancelAll()` stops what runs, and the new move starts from those values. Velocity is not carried. | framer: retarget the same `animate` on the same node; `chSpring()` gives stiffness and damping, so the spring keeps its velocity. Never remount to restart (02-PLAN R2). WAAPI: read `getComputedStyle(el).transform` and `.opacity` *before* `cancel()`, then animate from them. |
| **Additive** | `composite: 'add'` on the list wrapper `.msgs`: two thread glides sum (send, arrival, delete, times return). | One framer motion value `y` on the message list's wrapper: on an arrival add the new row's height (`y.set(y.get() + h)`) and animate it to 0 with `chSpring('send')`; a second arrival adds again and the spring keeps going (02-PLAN 4.4). Or WAAPI with `composite: 'add'` on the wrapper. Never add a second wrapper per arrival. |
| **Carry** | `snapCarry()`/`playCarry()` (lines 158, 163): before a list re-render, every running motion on `.b, .poll, .typing, .rx [data-rx], .seen .av` is read; after it, the new node continues from that frame to rest on its own spring. | Key every row by message id so React keeps the node and the running animation. A re-render, a refetch or a realtime update never restarts or replays a row (SHARED-6). |
| **Hand-off** | A closing overlay reopened is picked up where it is: `HOLD_OUT` + `finishHoldOut()` (lift; reads the copy's transform and the scrim's opacity), `SHEET_OUT` (sheet; reads its top and opacity), `.is-closing` (attach menu; the same node turns around), `.is-leaving` (push; Back marks the page and push leaves the list showing). Never a new copy over the old one. | Keep the closing element mounted until its exit ends (no `AnimatePresence` remount for these four; an exiting node can't be re-entered). On reopen, reuse the same node and live-start toward open. For the lift, `MessageLift` keeps the settling copy and the new lift starts from its transform (02-PLAN 6.1). |

## Rules for every row

- Animate `transform` and `opacity` only. The exceptions are drawn and kept: the desktop details column (`grid-template-columns`, M-MSG-20b, the one layout animation, 04 section 8), the poll tick (`stroke-dashoffset`, M-MSG-15b), and one colour fade the page draws as a CSS transition (the switch track, 250ms, M-MSG-21c; d-extra turns off the composer's and the bar's box-shadow transitions, lines 61 and 142). Everything else that changes colour (the selected row wash, the check circle fill, reaction keys, the Muted quick action) switches in one frame.
- Blur never animates. The hold scrim's `blur(14px) saturate(120%)`, the bars' glass and the composer's glass are fixed; only their layers' opacity and transform move.
- A thread bottom is always `msgs.offsetTop + msgs.offsetHeight − scroll.clientHeight` (`maxTop`, line 593). See Scroll rules.
- Demo taps on the page run `pressOn()` (line 1362: scale .97 over 110ms, back over 280ms). That is the app's existing press controller (`lib/press.ts`) on buttons, unchanged, and not a Messages row. M-MSG-10a is the bubble's own press.
- Durations in the table give the build target first and the page solver in brackets, "496 (page 540)" (ruling 29). Frame numbers in Check are read on the design clip; the app clip reaches rest at the build target, up to 44ms sooner, with nothing visible in between. Frame numbers are ms after the trigger at 60fps; a row matches when the app frame shows the same state as the design frame within one frame (SHARED-12).
- Check: `node capture/capture.mjs --motion M-MSG-xx` records the design page (its demo button, at the `thread` route, 390 × 844, or 1280 × 800 with `--dev desk`) and the app (`/clubhouse-preview/messages?state=design&view=thread&play=<demo>`), normal and Reduce Motion, then runs that row's motion check cases. "By hand" rows have no demo: record the design page and the app on the route named, with Playwright `recordVideo` at 390 wide (or 1280 for desktop), normal and `reducedMotion: 'reduce'`.
- Don't copy the page's permanent `will-change: transform` on every `.pg` (a-head 267). Set it while a push or pop runs and remove it after.

## Never animate (this lane)

- **Count-ups.** Poll counts and percentages, reaction counts, the jump count, "3 unread", "4 of 6", "Seen by 3": text changes in one frame. Only bars (scaleX) and badges (scale) move.
- **Entrance staggers.** None on this lane: filter rows move together, bars move together, a file and its text leave together. Nothing animates on first paint, route change or state restore; a thread opens at its latest message at rest; the skeleton swaps for rows in one frame (Nick: no count-ups, no entrance staggers).
- **Re-render motion.** A realtime update, a refetch or a re-render never starts or replays a motion. Running motions carry across re-renders (Carry). Rows that arrived while away render at rest.
- **Field height.** The composer field steps a line at a time (M-MSG-06c). No height tween anywhere except the desktop details column (M-MSG-20b).
- **Blur on scroll.** Bar, composer, date pill, jump key and scrim blurs are set once. Content scrolls under the glass; no blur or shadow changes on scroll. The hold scrim's blur is present from its first frame and only its layer's opacity moves.
- **The green bar** (SHARED-1). Its height, title, switcher, bell and lip never move: not on push, not on scroll, not under a sheet. The phone bar's lip has no fade.
- **The desktop shell.** The canvas sheet's glass top bar (breadcrumbs, search ⌘K, bell, settings) and the sidebar never move on this lane; Messages motion stays inside the rail, thread and details columns.
- **Colour.** Selection washes, the check circle fill, reaction key fill, Muted fill, failed state: one frame. The only colour fade is the switch track (M-MSG-21c).

## Interrupt cases (each worth a test)

The page's motion check (`#motion-check`, `MC` line 1779, `MCASES` line 1818, `motionCheck()` line 1878) runs each case through the real engine, samples each tracked element every animation frame, and judges it with `MC.judge`. `capture.mjs motion` (or `--motion` with a row's cases) reads `window.__motionCheck`. 11g ports them to `e2e/clubhouse-messages-motion.spec.ts` on the preview fixture with the same judge (02-PLAN section 8).

State of the check: v13 passes 11 of 11 in headed Chrome 156 on the Mac (`screenshots/reference/motion-check-v13-chrome-11-of-11.png`, `SETTLED-4NOV.md` Motion check). Run it, on the page and in the build, in a headed browser at 60 Hz or better. Headless Chromium in a loaded container drops frames (25 to 40ms frames with 120 to 250ms stalls) and fails 2 or 3 cases on any version; that is the machine, not the motion, and is not a pass or a fail.

How `MC.judge` counts, per tracked element:

- **Sample:** each frame records the element's `getBoundingClientRect()` (x, y, width, height) and its effective opacity: the product of its own and every ancestor's opacity, with `visibility: hidden` or `display: none` on any of them counting as 0. A frame where the element isn't found or isn't connected is a missing frame.
- **Jump:** in one frame the box changes by more than 10px in x, y, width or height, and that frame's speed is over 3 times the faster of its two neighbouring frames (floor 0.05px/ms). A teleport, not a fast move.
- **Gap:** the element is there, then missing for a frame, then there again later in the sample. A flicker from a remount or a swap.
- **Blink:** effective opacity changes by more than 0.45 in one frame and by over 3 times its neighbours' change (floor 0.02). A visibility swap or a copy handing off to the real node shows as a blink.
- **Glide** (only in case 11, Reduce Motion): two frames in a row each moving more than 0.5px. Stepping to a new place is allowed; travelling there is not.
- **Pass:** cases 1 to 10, every tracked element has 0 jumps, 0 gaps and 0 blinks. Case 11, 0 glides and 0 gaps (jumps and blinks aren't counted there).

## Scroll rules

- **The real bottom** is `msgs.offsetTop + msgs.offsetHeight − scroll.clientHeight` (`maxTop`, line 593), never `scrollHeight − clientHeight`: a running glide's transform inflates `scrollHeight`, and scrolling to that inflated bottom gets clamped back the moment the glide ends, which shows as a jump. Use it everywhere a bottom is computed: the room glide, the jump glide, `pinBottom`, `use-thread-anchor.ts`'s callers (02-PLAN R4).
- **Desktop scroll stays Lenis** (wheel only; "I like the smooth scroll", 02-PLAN section 1). A spring scroll there (the jump glide, the make-room bottom) goes through Lenis, `scrollTo(target, { immediate: true })` once per frame, never a direct `scrollTop` write, which fights Lenis and stutters (02-PLAN R3). Phone keeps native scrolling.
- **At the bottom** for these purposes means within 60px (a re-render glides, a typing bubble animates, details pins), within 24px (a taller field or a new chip keeps the latest message in view), and within 8px (the jump count clears).
- **Jump key:** on when the reader is more than 0.9 × the scroller's height above the bottom, off when back within it (M-MSG-24). A message that arrives while the reader is more than 60px up adds to the count (M-MSG-33). The glide's target is re-read every frame; a wheel, touchstart or pointer down stops it.
- **Date pill:** only on a scroll the reader makes (a scroll the code makes is marked `quiet` and skipped); it shows the last day marker whose top has passed under the bar (bar height − 4: 116 phone, 76 desktop); it hides 1000ms after the last scroll event (M-MSG-04c).
- **Hairline:** the desktop bar's hairline shows once `scrollTop` is 2px or more (M-MSG-04b).
